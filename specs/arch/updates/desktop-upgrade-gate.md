*The desktop upgrade gate: cross-release shell entrance, the server-baked required desktop version, the Electron-mode boot barrier, the gate screen with its downloaded-update message, restart action and instructions fallback, notice-precedence rules, and gate telemetry.*

# Desktop upgrade gate

This spec governs how an installed Electron shell gets far enough to learn that it must upgrade, and how the [desktop upgrade gate](../../product/update-notifications.md#The desktop upgrade gate) then stops it at a blocking screen instead of letting an incompatible shell enter the normal interface. The screen offers a restart when the app has already downloaded its update, and otherwise tells the user how to install the latest version.

It owns the cross-release **desktop connect check** and the bounded legacy `/display` response that let installed shells reach the served gate, the server's **required desktop version** and how it is raised and delivered, the **boot barrier** that decides whether the client halts, the gate screen, the gate's precedence over the shared update notice and its ordering after the reload check, and the *desktop upgrade gate shown* event. Other desktop connect failures and their messages are code-governed. The channel-published upgrade instructions the gate may show are [update-channel.md](./update-channel.md)'s; version semantics are [arch/updates/index.md](./index.md)'s.

## The required desktop version

Each server release carries a *required desktop version*: the minimum [desktop release](../../product/versioning.md#^pv-desktop-release-version) this server is meant to be used with. It is a repository-maintained constant baked into the server build alongside its own release version, and it is **raised deliberately, by hand**, not derived from the server's release version. Desktop releases carry the version of the Television release they are built from, and most Television releases have no desktop release, so a requirement derived from the server's release version would gate every desktop user on every server upgrade, usually naming a desktop version that was never released. Routine releases leave the constant untouched, and a human raises it exactly when a shell change requires users to upgrade, the same curated judgment as a channel deploy. ^required-desktop-version

The constant is an exported value in the server package source (`packages/server/src`), reviewed like any code change; being source, it is identical in development and published builds. A server whose own release version is `0.0.0` advertises no requirement, so an unstamped development build never gates anyone. ^required-desktop-constant

**Delivery.** The `server-status` message ([version-advertisement.md#^events-version](./version-advertisement.md#^events-version)) carries `requiredDesktopVersion` (`null` when the server advertises none). It is the **first message** on every `/events` connection, the ordering the boot barrier depends on, so the gate needs no channel fetch. Keying the gate on the connected server, rather than on the channel, is what makes it fire only once that server has been upgraded ([^gate-server-driven](../../product/update-notifications.md#^gate-server-driven)). ^required-desktop-delivery

## The seam: the web client, not the shell

The gate check and gate screen live in the **server-served web client running in Electron mode**, not in the Electron shell (`packages/desktop`). ^gate-seam

The web client already holds every input the halt-or-boot decision needs: it knows it is inside the desktop app ([Electron context](#^electron-context)); it knows the shell's version where the shell declares one, through the `?desktopAppVersion=` page parameter ([client.md#^desktop-version-param](../telemetry/client.md#^desktop-version-param), which owns the parameter and its handoff from shell to page); it receives the requirement as the first message on every connection; and it owns the standard markdown pipeline the gate screen renders with.

The deeper reason is that **the shell is the component that cannot be assumed current.** Upgrade-decision logic shipped in the shell would itself go stale: an old shell with an old or buggy gate is exactly the failure the gate exists to prevent. Gate logic in the served bundle arrives fresh on every launch for as long as the shell can render the interface at all. In the shell's connect flow it would run only at connect time, need shell-side markdown rendering and version plumbing, and freeze all of it into the component that lags behind its server. The shell's identity check makes no upgrade decision. ^gate-seam-rationale

**What the gate uses from the shell.** The gate consumes: (a) what the shell sends without knowing about the gate, the `?mode=electron` parameter every shell has always sent, plus `?desktopAppVersion=` where the shell supplies it; (b) the `/events` websocket the page itself owns; (c) plain DOM rendering, with links routed through the shell's existing window-open handler and no copy affordance on the gate screen; and (d) where the shell provides them, the two update operations on the native preload bridge ([desktop updates](../desktop/updates.md#^desktop-updates-ops)), which report a downloaded update and restart the app to install it. The halt-or-boot decision uses (a) and (b) alone. The update operations only choose the gate screen's message and supply its restart action, and a shell without them gets one of the [other two messages](#^gate-instructions). They are the only shell↔bundle IPC the gate uses, and they stay stable across releases for that reason ([^desktop-updates-frozen](../desktop/updates.md#^desktop-updates-frozen)). The gate therefore works for **all** installed shells that pass the applicable [desktop connect check](#^pre-gate-handshake), including shells that predate any pre-page check: the gate code arrives in the served bundle. The breaking IPC surfaces are what the barrier fences off, never what it uses. ^gate-zero-ipc

## Desktop connect check

A *desktop connect check* is the installed Electron shell's pre-page reachability, authentication and Television identity check at `GET /desktop/connect-check`. The gate begins in the served page, after this check. The check is the one cross-release exception within the otherwise code-governed desktop connect flow: a published shell covered by one of the contracts below must reach the current bundle far enough for the gate to make its halt-or-boot decision. Other desktop connection failures and their connect-screen messages remain code-governed. ^pre-gate-handshake

Current shells send one request:

```http
GET /desktop/connect-check?desktopAppVersion=<url-encoded shell release>
Authorization: Bearer <token>   # omitted for an empty token
```

The version is informational. The server does not validate, compare, persist, emit or branch on it; the served page's `?desktopAppVersion=` and `requiredDesktopVersion` remain the gate's inputs. A token-requiring server returns `401` for a missing or invalid bearer token. An authenticated Television server returns `200` with a JSON object satisfying this minimum type:

```ts
interface DesktopConnectCheckResponse {
  product: "television";
  [additionalMember: string]: unknown;
}
```

The `product` member's name, type and value are frozen. Additional members are permitted, and the shell ignores members it does not recognize, following the update channel's tolerant-reader, additive-writer rule ([update-channel.md#^evolution-frozen-core](./update-channel.md#^evolution-frozen-core)). The shell succeeds when the status is `200` and the parsed body is a non-null, non-array object carrying that marker; every other status or body is a failed identity check. Only after success does the shell save the normalized connection and load the server page under the desktop architecture's [server page-entry contract](../desktop/connect-flow.md#^shell-page-entry); a failed check saves nothing and does not navigate. The desktop connect check never decides whether an upgrade is required. ^pre-gate-desktop

The method, path, bearer transport, informational query key, success status and fixed product marker are frozen for every shell that consumes this route. They name no product feature. A breaking identity contract uses a new route while this route and marker remain available to old shells. ^pre-gate-fixed-marker

Published desktop releases before `0.1.145` make no pre-page request: they load the server-origin root with `?mode=electron` and the token, and are governed by [Electron context](#^electron-context) and the unknown-version rule alone. Releases `0.1.145` through `0.1.206` recognize Television through authenticated `GET /display`. The bounded compatibility response, retained under [the cutoff procedure](#^pre-gate-legacy-cutoff), contains present `activeScreenID: string | null`, `activeThemeName: string | null` and `acpEnabled: boolean` members on every successful response; additional members are permitted. `activeScreenID` is output-only compatibility with an unspecified value, while theme and ACP carry their ordinary current values. ^pre-gate-legacy-display

TV-684 owns the activity threshold, representative observation window and cutoff approval for the legacy projection. Its evidence is `session_activity` where `client_app = desktop` and `desktop_app_version` is absent or `<= 0.1.206`, scoped by the event's `server_version`; missing desktop versions make this an upper bound that includes earlier shells, not an install census ([product/telemetry.md](../../product/telemetry.md)). Removal also requires the advertised desktop floor to remain above `0.1.206` while the projection still lets the affected cohort reach the gate. At the approved cutoff, product accepts that residual affected shells stop at the connect-screen identity error. The server then stops emitting `activeScreenID`, and this spec's proof retires the assertion that focused and empty `/display` states satisfy the bounded compatibility response. `activeThemeName` and `acpEnabled` remain ordinary lockstep `/display` fields. ^pre-gate-legacy-cutoff

The gate can act only after the applicable [cross-release entrance](#^pre-gate-handshake) succeeds. A server release whose served interface is incompatible with an admitted shell raises the required desktop version in the same release, under [the floor-before-breaking rule](#^ops-bump). The functional shell/page protocols behind the barrier remain free to change. ^gate-limit

## The boot barrier

The barrier governs the **server-served page**, and begins where the page begins; the shell's own [desktop connect check](#^pre-gate-handshake) precedes the page and is outside it. From page load onward, in Electron context, the web client's startup is ordered so the gate decision happens **before the client enters its functional client-server relationship**: ^boot-barrier

1. Establish the `/events` connection and pass authentication.
2. Receive the `server-status` message, the connection's first message ([version-advertisement.md#^events-version](./version-advertisement.md#^events-version)).
3. Compare the shell version against `requiredDesktopVersion` (rules below).
4. **Gated → halt boot.** No store bootstrap (no `client.display.get()`, no channels fetch), no artifact frames, and no shell IPC beyond what the gate screen itself needs ([#^gate-zero-ipc](#^gate-zero-ipc)). Render the gate screen. **Not gated → boot normally.**

The barrier protects the shell↔bundle protocols. A required-version bump exists because of breaking changes to those protocols, the artifact-content and webview IPC especially. A current bundle on an outdated shell is exactly the pairing where they may mismatch, so a gated client must never exercise them; a gate that merely covered a running client with a modal would leave every one of them live underneath. ^barrier-rationale

**Electron context** is determined by the `?mode=electron` query parameter alone. Every published desktop shell sends it, on every load path, in every shell generation, so there is no user-agent fallback. Most of the installed base does *not* send `?desktopAppVersion=`, which is why the unknown-shell-version rule ([#^gate-unknown-version](#^gate-unknown-version)) exists and describes the gate's main audience. ^electron-context

**Gate rules.** The rules are evaluated against the server the window is loaded from (in Electron context there is exactly one, the same origin scoping as [the reload contract](./version-advertisement.md#^reload-origin-rule)):

- **Gated if and only if** all of: Electron context; the message carries a non-null `requiredDesktopVersion`; and the shell version is either **unknown** (no `?desktopAppVersion=` parameter, or not a valid release-version triple) or a valid triple other than `0.0.0` numerically less than the requirement ([arch/updates/index.md#^updates-version-comparisons](./index.md#^updates-version-comparisons)). An advertised requirement that is not itself a valid release-version triple is treated as no requirement: it gates nobody. ^gate-condition
- **Unknown shell version gates.** A shell that declares no version, in a context that is unmistakably Electron, is treated as older than any requirement. Shells too old to declare a version are the gate's audience, since most of the installed base predates the `?desktopAppVersion=` parameter, and letting them through on missing data would exempt exactly the worst cases. ^gate-unknown-version
- **Everything else is not gated.** A browser client (no Electron context), a shell reporting `0.0.0` (development shells, per [arch/updates/index.md#^updates-dev-version](./index.md#^updates-dev-version)), a server advertising no requirement, and a shell at or above the requirement all boot normally. ^gate-exemptions
- **Re-evaluation.** The barrier decision repeats on every `server-status` on the connection. A halted client keeps its `/events` connection, and when a later message no longer satisfies the condition (a lowered or retracted requirement), the client reloads into a normal boot rather than un-halting in place. The normal exit is instead an upgrade and relaunch, which changes the shell version the window reports. The barrier is a **boot** decision: a client that booted normally is never halted mid-session; a raised requirement takes effect at the next reconnect or reload, each of which re-runs the boot decision. In practice that window never occurs, because a server upgrade always drops the connection, and the reconnect that delivers the new requirement re-evaluates it. ^gate-reevaluation
- **Reload before gate, while a reload is still permitted.** A bundle reload takes precedence over the gate, so the gate is normally evaluated only by a bundle that matches its server, fresh gate code included ([version-advertisement.md#^reload-gate-precedence](./version-advertisement.md#^reload-gate-precedence)). A cached initial load can arrive stale, which is why the reload runs first. When the loop guard is **exhausted**, because the one permitted reload did not clear the mismatch, the gate evaluates anyway with the current, possibly stale bundle. Both gate inputs are independent of the bundle (`requiredDesktopVersion` comes from the server on the socket, and the shell version from the page URL), so older gate code still judges correct data, and a stale-bundle gate is better than a blank state. Outside Electron context, or with no gate condition, the guard's silent behavior stands. While gated, a reconnect whose `server-status` shows a **new server version** (the server was upgraded while gated) triggers the normal loop-guarded reload, which brings the fresh bundle and its fresh gate code back to the barrier. This makes the [intended sequencing](../../product/update-notifications.md#^gate-sequencing) seamless: the agent upgrades the server while the desktop app sits gated, and the final restart, which installs the desktop update, lands on a current server with no gate. ^gate-reload-precedence

## The gate screen

While halted, the client renders the gate screen as the entire interface. It overrules any other interface state, including connection-error strings the page may record underneath (for example when the halted socket later drops): an outdated client is more likely to show errors that are irrelevant because it is out of date, so the gate winning unconditionally is by design. ^gate-screen

- What the screen renders and looks like is [ui/app/desktop-upgrade-gate/index.md](../../ui/app/desktop-upgrade-gate/index.md)'s. This spec owns the content contract: the selected instructions markdown goes through the standard markdown pipeline exactly as published, as [the toast body](./update-channel.md#^toast-render) does, including external link handling.
- **What the screen says.** The gate screen renders one of three bodies, which [the product](../../product/update-notifications.md#^gate-instructions-fallback) describes. When the shell has reported a downloaded update through `onDesktopUpdateDownloaded`, it renders the built-in *downloaded-update message* with the restart action, whatever the channel publishes, since the channel cannot know what the app has downloaded. Otherwise, when the current update state carries the channel's desktop upgrade instructions ([update-channel.md#Relay to clients](./update-channel.md#Relay to clients)), it renders them. Otherwise it renders the built-in *fallback*. The gate listens for a reported download while the screen is shown, so a download reported then changes the screen to the downloaded-update message in place. ^gate-instructions

The authoritative built-in texts are the gate surface's content: [ui/app/desktop-upgrade-gate/index.md](../../ui/app/desktop-upgrade-gate/index.md) owns the words (`content.yml`: `downloaded_update_instructions` and `fallback_instructions`) and the restart button's labels. ^gate-fallback-content
- **The restart action.** With the downloaded-update message, the screen shows the restart action, which works as the [desktop self-update notice's](./desktop-self-update-notice.md#^desktop-self-update-notice-restart) does. It is the screen's only control. ^gate-restart
- It has no dismiss affordance, and nothing interactive exists behind it, because the normal interface never started. The shell's native menu remains available, so [Disconnect from Server](../desktop/connect-flow.md#^desktop-disconnect-server) still works: a gated user can always leave the server.
- A halted client shows no update notice or bell ([product/update-notifications.md#^gate-supersedes-toast](../../product/update-notifications.md#^gate-supersedes-toast)). The suppression is an explicit interface, not a reach into the notice's internals: the shared surface subscribes to presentation state whose suppression switch the gate flips, and that is the gate's only interaction with it. The switch is one-way for a page's lifetime: every gate exit is a reload ([#^gate-reevaluation](#^gate-reevaluation)), so nothing un-suppresses in place. ^gate-precedence

## Telemetry: *desktop upgrade gate shown*

The event `desktop_upgrade_gate_shown` is a member of the closed vocabulary owned by [arch/telemetry/index.md](../telemetry/index.md) and travels as a validated telemetry client signal, whose properties [client-signals.md](../telemetry/client-signals.md) declares. Its `desktop_app_version` is the shell's version, omitted when unknown ([omission-allowed validation](../telemetry/client-signals.md#^signal-validation)), and its `required_desktop_version` is the requirement that gated it. It fires when the gate screen becomes visible for a required desktop version, once per client per required version per page load, not per render or reconnect. The gate screen sends it over the **already-open `/events` connection** that delivered the gating `server-status`, so it needs nothing from the halted boot. Sending it updates session activity on the server ([client signal forwarding](../telemetry/client-signals.md#^signal-forwarding)): the barrier blocks functional application boot but permits telemetry. ^gate-telemetry

## Operations

**Raising the required desktop version.** The constant is changed by hand, in the server package source, in the pull request that makes the shell change motivating it: a deliberate human decision, like a channel deploy. One pull request may change the server and the desktop app and raise the constant. A release that ships a change an older shell cannot survive must raise the requirement enough to gate that shell in the same release, unless an earlier release already did so. A desktop-connect-check repair that admits such a shell must not ship without that protection. ^ops-bump

1. Raise it only when a desktop shell change requires users to upgrade, because the served interface can no longer work around the old shell. Routine releases never touch it.
2. The pull request that raises it sets the release version it ships in, sets the requirement to that version, and adds `.github/PAUSE_PUBLISH`, so that merging it publishes nothing ([arch/updates/index.md](./index.md#^updates-publication-order)). The requirement is never above the release version that ships it; otherwise servers of that release would gate the desktop release built from it. Its desktop change passes its [checks on a candidate build](../../product/desktop-app.md#^desktop-checks-before-main) before it merges.
3. While publishing is paused, and once CI has passed on the commit at the tip of `main`, a maintainer builds that commit, which carries the release version and the change, and releases it in ToDesktop ([distribution.md](../desktop/distribution.md#^desktop-dist-release)). Nothing else merges to `main` between that build and the next step, so npm receives the code the desktop release was built from.
4. The next commit to `main` deletes `.github/PAUSE_PUBLISH`, and the publish workflow publishes the release under the version the pull request set.
5. After the publish, deploy the channel notice that announces the release, with its `desktop.upgradeMarkdown` written for this release ([update-channel.md#^ops-author](./update-channel.md#^ops-author)); the built-in fallback keeps the gate functional if that deploy is skipped or unavailable.

Maintainers keep this order; nothing checks that the desktop release exists before the pause file is deleted. When the order is kept, npm never offers a server release that requires a desktop release users cannot yet download. Until the publish, npm offers only earlier server releases, which the new desktop release works with ([desktop releases](../desktop/distribution.md#^desktop-dist-release)), so a server and desktop app installed for the first time work together before and after the publish. What users then see is the [intended sequencing](../../product/update-notifications.md#^gate-sequencing). ^ops-release-order

**The theming release requirement.** `REQUIRED_DESKTOP_VERSION = "1.3.1"` enforces the [product's desktop requirement](../../product/update-notifications.md#^gate-themes-release). Desktop `1.3.1` supplies the [native appearance operation](../desktop/appearance.md#^desktop-appearance-ipc) needed to keep artifact appearance consistent with the application. The [recommended desktop version](../../product/update-notifications.md#^desktop-rec-first-release) stays above this requirement, so the ordinary gate handles earlier shells. ^ops-first-gate

## Inputs to proof derivation that the spec does not otherwise show

### Directives from the designer or architect

- Under [Compositional coverage across clean seams](../testing-policy.md#Compositional coverage across clean seams), the server that answers the desktop connect check and the shell that reads it may be covered by separate contracts. Coverage of that server uses real HTTP against two servers started through production composition: one without authentication and one that requires a token. At least one gate path through the real Electron app shows exactly one successful desktop connect check before the `/events` connection begins.
- The boot barrier lives in the server-served web client, so coverage under this spec delivers `server-status` through a real `/events` websocket to the barrier in a real browser page with Electron context. It shows that a gating first message prevents page requests to `/display`, channels and artifacts, and that retracting the requirement reloads the page into a normal boot.
- Presentation-precedence coverage includes a state where the server notice would apply, one where the desktop self-update notice would apply and one where the recommendation would apply, and shows that no notice and no bell appears while the gate is active.
- The selected gate instructions are rendered through the standard markdown pipeline in a real browser, including external-link behavior. Choosing among the downloaded-update message, the channel instructions and the built-in fallback has separate coverage, which may use a stand-in for the bridge operations.
