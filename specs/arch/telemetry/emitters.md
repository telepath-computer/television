*The telemetry emitters: the server-side hook points that build events from server state at boot, CRUD, layout, pins, page presentation, and theme changes, the CLI emitter for skill installs, the forwarding point for client-signaled events, and which properties ride on which events.*

# Telemetry emitters

## What this owns

This module owns **where** telemetry events are produced and **which properties ride on each** — the wiring from server activity to the chokepoint. It composes other modules: classifications come from [derivation.md](./derivation.md), the `$session_id` from [sessions.md](./sessions.md), the GUID and suppression from [identity.md](./identity.md), and delivery from [sink.md](./sink.md). The hook points themselves live in existing server modules whose contract changes are captured in [server-telemetry-buffer.md](./server-telemetry-buffer.md) until a server spec exists.

## Behavior

**Server emitter.** Server-side hooks emit lifecycle, session, persisted-state, and forwarded client-signal events; *skill installed* is the CLI-local exception described below. Internal hook names follow channel terminology; six screen-named event/property literals remain the frozen PostHog boundary owned by [the analytics-history exception](../../product/telemetry.md#^telemetry-channel-key-exception). Persisted-state hook points:

- boot / config — `packages/server/src/server.ts`: capture `dataDirCreated`, whether the served home holds no prior serving evidence as [identity.md](./identity.md) defines it, then emit *server started* (and *installed*/*upgraded* per [identity.md](./identity.md)) with config + version.
- artifact CRUD — `server-store.ts` `createArtifact`/`updateArtifact`/`deleteArtifact`: emit the matching event with artifact classification; create/delete also carry content totals and set the content-total person properties. Delete carries `direct` when called as an artifact operation and `channel_deleted` when channel removal invokes the internal cleanup path. A metadata patch equal to the normalized stored artifact returns without an update event.
- channel CRUD and layout — `server-store.ts` `createChannel`/`updateChannel`/`removeChannel`. Create/delete carry content totals and set the content-total person properties. A changed name emits `screen_updated`; a same-value name emits nothing. Layout replacement classifies page order and each retained page's full-screen presentation independently, emitting `layout_changed` with `tab_reorder` and `tab_page_full_screen_changed` with the committed boolean as applicable. Page-size-only replacements and artifact membership side effects emit neither layout nor presentation events.
- pins, theme, and appearance — `server-store.ts` `patchDisplay`: an explicitly committed pin-list change emits *channel pins changed* with its derived operation and committed count; a selection change emits `theme_changed` with the committed theme classification, four JavaScript booleans, valid registry count, and internal selection/fallback reason; an appearance change emits `appearance_mode_changed` with the committed preference. The classifier consumes the bundled-theme installer's theme ID tuple, so the emitter carries no separate bundled-theme list. Same-value display patches emit nothing. Selection equality compares actual IDs before classification, so two distinct custom IDs still produce a switch. Both changed fields in one patch produce their own event after the whole patch commits. Consent-only changes, same-selection registry refresh, and active-package reloads emit no switch event. Pin pruning during channel deletion emits no pin-change event because the user action is channel deletion.

**CLI emitter.** `tv skills install <path>` is a local file copy; the server never sees it and may not be running. The CLI emits *skill installed* itself, through the shared chokepoint, loading the selected home's telemetry state file and minting the GUID when it is absent ([identity.md](./identity.md)), deriving the agent type (`interactive-install` for `tv skills install -i`; see [derivation.md](./derivation.md)), and attaching `installed_by_agent` when the CLI caller supplies it. It is session-less (no client id). The emit and flush are best-effort and bounded: telemetry state I/O, transport failures, and slow delivery cannot fail or hang a successful skills install, and the CLI prints successful copy output before the best-effort telemetry flush. Because the server may not be running, `skill_installed` carries the **server version** it installs against but **not** the live runtime config (bind addresses, port, etc.) — the only event for which the server-config bundle is unavailable.

**Client-signal emitter.** Client-observed events arrive as validated telemetry client signals on the `/events` socket ([client-signals.md](./client-signals.md)). The update-notification events (`client_autoreloaded`, `update_toast_shown`, `update_prompt_copy_clicked`, `desktop_upgrade_gate_shown`) carry validated version properties and have firing semantics in the updates domain: [version-advertisement.md](../updates/version-advertisement.md), [update-channel.md](../updates/update-channel.md), [desktop-upgrade-gate.md](../updates/desktop-upgrade-gate.md). `artifact_skill_prompt_copy_clicked` carries one validated fixed skill key and fires once per Copy prompt click as owned by [ui/app/skill-selector/index.md](../../ui/app/skill-selector/index.md). The event-stream hook forwards every accepted signal through the chokepoint with normal `$session_id` attribution.

**Property emission.** Properties split into per-server state (set as PostHog **person properties** via `$set`, current-value) and per-event properties (frozen on the event). Person properties answer "current state of each server" and cross-server distributions; the event copies below answer historical "what was active over a window" ([product/telemetry.md#^active-config-requirement](../../product/telemetry.md#^active-config-requirement)).

- **Server config + version** — `$set` as person properties **and** emitted on `server_started` (the config payload). The config payload includes `installed_by_agent` (the agent runtime harness name from the home's config file `installedByAgent` setting, lowercased+trimmed — the one free-string property; [product/telemetry.md#^installed-by-agent](../../product/telemetry.md#^installed-by-agent)). `server_upgraded` carries the new version and carries the old version when one was previously recorded. `session_activity` also carries the current server version. Other events do not carry the server config snapshot, keeping action-event payloads small while still preserving startup, upgrade, and activity history.
- **Pre-telemetry cohort** — `server_installed` sets person property `pre_telemetry: false`. A `server_upgraded` caused by an existing data dir with no previous telemetry version carries event property `pre_telemetry: true` and sets person property `pre_telemetry: true`. Later version-bump upgrades do not set or change the property.
- **Content totals** — total channels, total artifacts, and median & average artifacts-per-channel, computed from store state after the mutation commits — `$set` as person properties **and** emitted on the artifact/channel **add and delete** events that change them (`artifact_created`/`artifact_deleted`, `screen_created`/`screen_deleted`). No per-channel artifact count is emitted.
- **`$session_id`** is stamped on every event emitted for a client (via `sessionIdFor`, [sessions.md](./sessions.md)); session-less emits carry none.
- **Client bundle** (app/platform/browser) rides on `session_activity` ([derivation.md](./derivation.md), [client.md](./client.md)).
- **Event-specific classifications** (artifact and deletion cause, layout, pins and count, page full-screen state, fixed artifact skill, theme, agent type) ride on their own events. `skill_installed` also carries the optional `installed_by_agent` self-identifier, uses `agent_type: "interactive-install"` for interactive target selection, and never carries destination paths or external-installer arguments.

### Theme and appearance snapshots

The server telemetry runtime reads one current snapshot from committed store state at emission time, using [property derivation](./derivation.md#^theme-settings-derivation). Every server-produced event carries its six settings as person properties through `$set`, alongside any other person properties belonging to that event. This initializes settings on boot and keeps the next emitted event accurate after consent changes, registry refresh, or telemetry re-enablement, without a cache, a new event, or a background timer. The CLI-local `skill_installed` emitter has no live store and does not attach this snapshot. Suppression and the one-final-opt-out-event rule continue to apply. ^theme-settings-publication

Every `session_activity` also carries the complete six settings as ordinary event properties beside the existing version and client bundle, preserving state at the time of activity. Other events retain their own event-property shapes: `theme_changed` has theme state, the four JavaScript booleans, registry count and reason; `appearance_mode_changed` has appearance mode. The runtime uses the same current settings for an event's settings fields and its person properties. False values and `none` are sent explicitly so person properties cannot retain a previous theme's enabled flags. ^theme-settings-history

Boot emission reads state after theme validation and fallback. It emits the existing lifecycle events with current settings, without reconstructing a switch before telemetry initialization. A running server's invalid-theme fallback on registry refresh emits `theme_changed` with reason `fallback`; direct selection uses `selection`, including selecting None. Reasons come from the mutation path and are not client-supplied analytics fields. ^theme-settings-transitions

**Pre-first-boot GUID:** a skill install can occur before any server has booted, so no GUID exists yet — the CLI **mints** the GUID (sharing the server's minting path) rather than dropping the event, since minting an absent GUID is a one-time creation with no concurrent server. See [identity.md](./identity.md).

## Testing

Server telemetry is proven with production state mutations that run through a real `ServerStore`, `Server`, and telemetry runtime. The sink's [real PostHog integration](./sink.md#Real PostHog integration test surface) proves delivery from the telemetry chokepoint to PostHog. The CLI emitter contract is proven under this spec. The successful `tv skills install` call into the emitter is proven under the CLI architecture's [bundled skills boundary](../cli/index.md#Bundled skills boundary).

Under the testing policy's [compositional coverage rule](../testing-policy.md#Compositional coverage across clean seams), this suite proves each handoff once. The range of classification behavior is proven under [derivation.md](./derivation.md), session behavior under [sessions.md](./sessions.md), and identity behavior under [identity.md](./identity.md).
