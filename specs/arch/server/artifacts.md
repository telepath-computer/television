*The artifact registry on the server: the artifact record and its two kinds, which channel holds an artifact, and how the server watches a path artifact's files and tells clients they changed.*

# Artifact registry

An artifact is a record that points at content: a file or folder on the server's machine, or a web address. The server keeps the records, places each artifact on a channel, serves the files of the ones that point at local paths, and watches those files so that an open artifact follows its source. This document defines the record and the watching. What a person can rely on from an artifact is [product/artifacts.md](../../product/artifacts.md), and serving its files is [the artifact proxy](./artifact-proxy.md).

## The record

```ts
type Artifact =
  | { id: string; kind: "path"; title: string; path: string }
  | { id: string; kind: "url"; title: string; url: string };
```

The server stores each artifact's *artifact record* as one file ([storage](./storage.md#^srv-records)), together with the two fields [resources](../resources/index.md#^rs-artifact-record) own. The same shape travels to clients wherever an artifact does. ^srv-artifact-record

- **The record is only a pointer.** The server never copies, moves, changes or deletes the file, folder or address an artifact points at, when the artifact is created, repointed or deleted ([product CLI](../../product/cli.md#Artifact commands)). The one exception is the Markdown editor, which saves a person's edits to a Markdown artifact's file.
- **`id`** is generated by the server and never supplied by a caller ([artifact ID](../../product/artifacts.md#^af-artifact-id)). It is a ULID, 26 characters of Crockford's base32, and is never reused. The only artifacts with other IDs are onboarding artifacts that [earlier releases installed](../onboarding/installer.md#^artifact-ids) under fixed ones.
- **`kind` and `id` never change.** An update may change the title, the path of a path artifact, or the address of a URL artifact, and nothing else.
- **`title`** is stored exactly as given ([name](../../product/artifacts.md#^af-name)).
- **`path`** is absolute. Which paths an artifact can be created from, and the form the path is stored in, are the [product CLI's](../../product/cli.md#Path artifact creation); a path is checked again whenever the artifact's content is requested ([real location](../../product/artifacts.md#^af-real-location)).
- **`url`** is an `http:` or `https:` address. One whose path has the form of a Television artifact address, `/artifact/<id>/…` with an ID of the generated form, on any host, is a *remote artifact*, which the product calls a [shared artifact](../../product/artifacts.md#Shared artifacts); any other is an external page. The shape of the address decides, never its host. ^srv-remote-artifact

## Which channel holds an artifact

An artifact is created on a channel and stays on exactly one. The record does not say which: a channel's [layout](../layout/index.md#^ly-model) names the artifacts on its pages, and that is the only place membership is stored. The server works out each artifact's channel from the layouts when it loads them and keeps that in memory. Storing membership once means a layout and a record cannot disagree about it. ^srv-artifact-channel

Creating an artifact adds a page for it, deleting it removes it from its page, and moving it changes two layouts; [layout](../layout/index.md#Layout updates) owns all three. Deleting a channel deletes the records of the artifacts on it ([channels](../../product/channels.md#^ch-delete-semantics)).

An artifact can be left on no channel, by [a move that did not finish](../layout/index.md#^ly-move). Its record, its address, its store and its share link keep working; no channel shows it.

## Watching content

The server watches the files of every path artifact, so that a client showing the artifact can reload it when its source changes ([folder updates](../../product/artifacts.md#^af-folder-live-update)). What it watches follows from the stored path: a file path watches that file, and a folder path watches the whole tree under the folder, at any depth and with no filter on names or extensions. Creating, editing, renaming or deleting any file under the folder counts, whether or not the loaded document uses it. URL artifacts are not watched. ^rn-local-content-change

A change is announced on the [event stream](./http.md#The event stream) as:

```ts
{ type: "artifact-content-changed"; artifactID: string }
```

The event says only that something changed. Changes that arrive close together are announced once. What a client does with the event is [reload and navigation's](../artifact-frame/reload-navigation.md#Local path-content updates).

One watcher module serves both path artifacts and the [active theme package](../themes/index.md#^themes-active-package-watch), so both recover from the same situations in the same way: ^rn-shared-content-watcher

- **A folder is watched with one recursive watch at its root**, not one watch per directory, so a large tree costs no more to watch than a small one.
- **A watched file or folder that disappears is treated as a change, and is picked up again when it returns.** Editors and build tools often replace a file or a whole folder instead of writing into it. The watcher reports the loss, checks for the path until it exists again, then watches it again and reports that too.
- **A watcher that fails while its target still exists is closed and the failure is logged.** That artifact or theme stops updating live until its watcher is started again, by a change of its path or selection or by a restart; nothing else is affected.

The module reports only that content changed, went missing, came back or failed. Each of its two users decides what that means and announces its own event, `artifact-content-changed` for an artifact and `theme-changed` for the theme.

## Testing guidance

Watcher coverage runs the production watcher over real temporary files and folders, in both its file and its folder form, because the behavior that matters is the operating system's: what a rename, a replaced folder or a deleted root actually delivers. Coverage of each user, artifacts here and themes in [theme architecture](../themes/index.md), then shows that it uses this module and turns its reports into its own event.
