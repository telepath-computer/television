*Local artifact content on the server: the artifact proxy that serves a path artifact's files at its address, under the artifact's own ID or a share ID, and the content watcher that tells clients when an artifact's or the active theme's files change.*

# Local artifact content

A path artifact points at a file or folder on the server's machine. The server serves that content at the artifact's address, to any browser that holds the address, and watches it so that the artifact's document reloads when its source changes. This spec owns the artifact proxy's addresses and answers, and the content watcher. Neighbouring specs own the rest of an artifact document's delivery: which files a folder serves and the check of where they really are ([product/artifacts.md](../../product/artifacts.md#^af-real-location)), the headers that isolate the document ([isolation](../artifact-frame/isolation.md)), caching ([proxy caching](../artifact-frame/proxy-caching.md)), what is injected into an HTML document ([the artifact bridge](../artifact-frame/artifact-bridge.md)), and how a client reloads ([reload and navigation](../artifact-frame/reload-navigation.md)).

## The artifact proxy

The *artifact proxy* serves a path artifact's content under `/artifact/<id>/`, where `<id>` is the artifact's own ID or its share link's ID ([resolving an ID](../resources/index.md#^rs-resolve-id)). It requires no token: the ID is the capability ([product/artifacts.md](../../product/artifacts.md#^af-artifact-id)). It answers `GET` and `HEAD` only, and any other method with `405` and `Allow: GET, HEAD`. An ID that reaches no artifact, or reaches a URL artifact, is answered with a plain `404`. ^srv-artifact-proxy

Under the artifact's own ID:

- **A folder artifact** serves the files below its address that [product/artifacts.md](../../product/artifacts.md#^af-folder-files) allows, with the folder's `index.html` or `index.htm` at the address itself. A request for the folder, or for a folder inside it, without the trailing slash is redirected to the same path with one.
- **A single-file artifact** is served at `/artifact/<id>/<file-name>`, under its file's own name, so that relative references in the document resolve as they do beside the file. `/artifact/<id>` and `/artifact/<id>/` redirect there, and every other path under the ID is a missing file. A Markdown file is served rendered as an HTML document; the rendering is part of the code-governed [frame core](../artifact-frame/index.md#^frame-core-carve-out).

Redirects are `301`. When the artifact's entry, its file or its folder's index, is missing or its real location fails the [check](../../product/artifacts.md#^af-real-location), the proxy answers `404` with the built missing-artifact document, which the frame shows as its [error page](../../ui/app/artifact-frame/index.md); any other missing or refused file gets a plain `404`. ^srv-proxy-entries

Under a share ID, the proxy serves `/artifact/<share-id>/…` as it serves the artifact's own address, except that every redirect it sends, every error document and every response header is built from the ID and the path in the request, never from the artifact's own ID or from the names of its files and folders on disk, which can contain that ID. A single-file artifact is therefore served at `/artifact/<share-id>/` itself; `/artifact/<share-id>` redirects to `/artifact/<share-id>/`, and every other path under the share ID, the file's name included, answers as a missing file. This holds for the redirects and errors of the library that streams the files, and while the files change during a request: a single file that has become a folder is answered as missing. An error response carries its status and fixed text for it, never the server's own text for the failure, such as a file's path, which contains the artifact's ID when its files lie in a folder named for it. A share ID that reaches nothing, such as a revoked one, is served as an ID that names no artifact. ^rs-share-serving

Every proxy response carries `X-Content-Type-Options: nosniff`, so a browser never runs a file as a type other than the one it is served as, and `Referrer-Policy: no-referrer`, so the artifact's address, which carries its ID, does not leave with the document's requests to other sites. The [sandbox header](../artifact-frame/isolation.md#^iso-sandbox-header), the [cross-origin headers](../artifact-frame/isolation.md#^iso-routes) and the [cache headers](../artifact-frame/proxy-caching.md) are their specs'. ^srv-proxy-headers

## Content watching

The server watches the content of every path artifact and of the active theme, and announces changes on [the event stream](./http.md#^srv-events). What is watched follows the artifact's stored path: a file artifact's file, and a folder artifact's whole tree, with no filter by name, extension or depth, so that creating, editing, renaming or deleting any file below the folder is a change ([product/artifacts.md](../../product/artifacts.md#^af-folder-live-update)). URL artifacts are not watched. The active theme's package is watched as a folder ([theme architecture](../themes/index.md#^themes-active-package-watch)). ^rn-local-content-change

One watcher module serves path artifacts and the active theme alike. It watches a file through the folder that holds it, matching the file's name, so that an editor that saves by replacing the file is still seen. When a watched file or folder disappears, the watcher reports a change, checks for the same path until it returns, then watches it again and reports another change. An error from a watch whose path is still present goes to the watcher's owner, which logs it and closes that watch. The module itself announces nothing to clients. ^rn-shared-content-watcher

Each owner turns what it hears into one debounced event: a path artifact's changes into `{ type: "artifact-content-changed", artifactID }`, and the active theme's into `theme-changed` for the selected theme ([theme architecture](../themes/index.md#^themes-active-package-watch)). A change heard from a watch that has since been replaced, for an artifact whose path has changed or that has been deleted, or for a theme no longer selected, produces no event. Changing an artifact's path starts watching the new target and announces a content change. ^srv-content-events

## Testing

The production watcher is proven in file and folder modes over real temporary trees, including a path that disappears and returns and a watch that fails, and a change to a nested file that is not the folder's index produces `artifact-content-changed` for the folder's artifact. [Product artifacts](../../product/artifacts.md#^af-folder-live-update) owns the end-to-end acceptance of a folder artifact reloading through a running server, the real event stream and real browser and Electron clients, and [theme architecture](../themes/index.md#Testing) owns the active theme's events; this spec needs no duplicate end-to-end cases.
