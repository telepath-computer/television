*Artifact template guidance: using copies, saving artifact snapshots, and maintaining templates through the bundled television skill.*

# Artifact template guidance

The `television` skill introduces artifact templates and carries a separate document for using and authoring them. This spec owns that guidance and its source-to-bundle placement. [Product behavior](../../product/templates.md) and the [folder contract](./index.md) own the facts it teaches; [making skills](../making-skills.md) owns general bundle and installation mechanics.

## Skill introduction

The primary `SKILL.md`, built from `packages/skills/skills/television/src/skill-intro.md`, names `tv templates list`, `tv templates show <id>`, `tv create-artifact --template`, and `tv templates path`. It tells agents to check the list when a person asks for an artifact, including a “macro” or “stock artifact,” and use `show` before writing data for the chosen template. It explains that folder templates create copies and points to `templates.md` for using, creating, changing, or fixing templates, including adding an artifact to the toolbox. It retains guidance to use [display-option flags](../../product/cli.md#^cli-create-display) when the request calls for particular display settings. ^artifact-template-skill-intro

## Template document

The skill build copies `packages/skills/skills/television/src/templates.md` into the bundle beside `SKILL.md`, `theming.md`, and `resources.md`. It teaches the selected-home convention, the required manifest fields, optional display options, folder and URL templates, optional `data.json` and manifest `dataSchema`, and local icons. It uses `list` to choose from names, descriptions and optional URLs, then `show <id>` to inspect the installed folder path, version and optional `dataSchema` before preparing caller data. It teaches agents to read starting data from `data.json` in the folder `show` reports, since [neither record includes it](./index.md#discovery). Both commands always scan again, so listing immediately after an edit checks the edited files. The app instead keeps a watched cache for instant Toolbox opening. It explains that caller data, including explicit `null`, replaces `data.json` entirely, with no merging; otherwise creation uses `data.json` when present, or leaves the store unwritten. Starting data is validated and written within the server creation request. The root `manifest.json` and `data.json` stay with the template; page and supporting files are copied into each artifact. It also teaches agents how to inspect content left by a [failed creation](./index.md#^artifact-template-copy). ^artifact-template-authoring-doc

The introduction, template document, and CLI capabilities distinguish changing one artifact from changing a template. Agents edit the copied page files directly to change one artifact. Editing the page files or `data.json` in an installed template changes only artifacts created afterwards.

To “add an artifact to the toolbox,” the template document teaches agents to take a snapshot: copy the page and supporting files into a new folder under the templates folder, use the folder name as the template ID, and write `manifest.json`. Read the current artifact store value and save that value as `data.json`, including `null`; omit the file when the store has no value. A single-file HTML artifact becomes a folder with `index.html`. A URL artifact becomes a URL template using its URL, with no `data.json` or `dataSchema`. The original artifact is left as it is.

The template document teaches that pages render defaults for empty or partial stores without writing them on load, and schema defaults do not supply starting content. For a folder template without `data.json`, the document teaches that it must be usable from an unwritten store: a template people fill in lets them add content from the page, writing only when they act; a template whose content comes from an agent shows that nothing is there yet and suggests asking the agent. A `README.md` gives context about the data and page files, available both in the installed template folder and in copies. The document points to `resources.md` for store operations rather than restating them. URL templates have no store and reject caller data, `data.json`, and `dataSchema`.

Authors declare local SVG or PNG files using [manifest icons](./index.md#icon-delivery). For a URL template, the agent fetches the best site icon once: prefer SVG or a large PNG declared through `<link rel="icon">`, `apple-touch-icon`, or the site web app manifest; otherwise fetch `/favicon.ico` and convert it to PNG. Save the result in the template folder and list it in `icons`. Neither the app nor the server fetches favicons. Toolbox shows icons and names; the required description remains useful to agents. It explains the supplied and default icon presentation owned by [Toolbox](../../ui/app/toolbox.mdx#icons).

The document explains [bundled installation](./bundled-installation.md): valid installed versions at or above the minimum survive later boots; invalid or older folders are backed up and replaced at the same path. For page authoring and template-folder naming, it refers to the Artifact workflow and HTML artifact style sections of `SKILL.md`.
