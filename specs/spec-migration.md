*The state and rules of Television's in-progress move to spec-driven development; itself transitional, retired once the migration completes.*

# Spec Migration

## What this is

Television adopts spec-driven development progressively. This document identifies the requirements under spec authority and the boundaries where code remains authoritative. It is transitional and retires once that migration is complete.

## How specs and code coexist

Specs govern the requirements they state. Code governs behavior outside those requirements. A spec that reaches one part of a module does not adopt the entire module. Package documentation provides implementation orientation and defers to the applicable specs and authoritative code.

## The redesign boundary

The redesigned application is spec-governed only at the product, UI, and architecture contracts listed below. Code beneath those contracts remains code-authoritative when no owning spec has migrated it; the listed frame-core, connection-lifecycle, navigation-recording, and desktop connect-check failure-message carve-outs are deliberate examples, not missing placeholder specs. This keeps the redesign from claiming untouched server, shared-client, transport, rendering, and service internals merely because a new contract reaches them.

A redesign contract may impose one requirement on an otherwise unmigrated module. That requirement lives in a clearly marked **buffer** in the nearest owning spec and is authoritative there; surrounding module behavior does not migrate with it. Layout migration, channel-state display migration, onboarding server/store integration, telemetry server integration, startup bind failure, and the ACP agent home context use this pattern. A later architecture spec absorbs the buffer and its assertion relationships without changing the requirement merely to relocate it.

**Existing product boundary.** The redesign removes client-side multi-server aggregation. One client connects to one server, the channel sidebar lists that server's channels, and state needs no server-origin grouping or disambiguation ([product/channels.md#^ch-single-server](product/channels.md#^ch-single-server), [arch/channel-state/index.md](arch/channel-state/index.md)). Multi-server implementation removal is conformance work against this settled boundary, not an open product choice. ^migration-redesign-boundary

## Under code authority

Behavior outside the requirements listed above remains code-authoritative. The [spec index](index.md) locates the owning specs; this map records their boundaries.

## How an area migrates

New work is spec-first ([spec-workflow.md](spec-workflow.md)). An area becomes spec-driven by intentionally choosing and specifying its requirements and adding its owners to this map. Adoption is incremental: it normally accompanies substantial work in an area or an explicitly scheduled migration. Existing code can inform that work; it does not automatically become a requirement.

Migration is two-sided about tests. An area migrates with proofs for its product, architecture, and UI specs. Under spec authority, "migrated" implies "under the testing policy" ([arch/testing-policy.md](arch/testing-policy.md)): greenfield promises receive the policy's full proof discipline, while behavior already well covered by pre-policy tests is cited in proofs as **inherited tests** ([arch/testing-policy.md#^inherited-tests](arch/testing-policy.md#^inherited-tests)) at the bar those tests were written to. Outside spec authority, tests remain code authority and are changed minimally and strategically, exactly like the code they cover.
