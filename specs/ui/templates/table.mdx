*UI spec: the bundled Table template page, an editable grid that a person and an agent can fill together.*

# Table template

The Table template makes an artifact that shows and edits text in rows and columns. Each story on this page is one state of the page, and the template page must pass a [UI conformance](../../spec-ui.md#conformance) check against every one. The prose states the behaviour the stories cannot show.

The [store contract](../../arch/templates/table.md#^bundled-artifact-template-table-store) owns the data, order, and paths each change writes. The [resource SDK](../../arch/resources/sdk.md#^sdk-access) owns how the page learns its access level.

<Artifact><Canvas of={Stories.WithData} /></Artifact>

## A new table

A new Table draws four blank columns and four blank rows, with no header row. These cells are an editing surface, not stored data: opening the Table makes no write.

Typing in a drawn cell creates that row and column. It also creates each drawn column to the left and each drawn row above, so the cell keeps the position where the person entered it. Drawn rows and columns after that cell stay unstored.

## Rows, columns and cells

Rows and columns follow their stored order. Cells contain plain text. An absent cell is blank. Text stays on one line and ends in an ellipsis when it is wider than its cell. The grid scrolls in either direction when it is larger than the artifact; the header and the reference strips stay with the visible grid while it scrolls.

There is no search or page-only sorting. The position a person sees is always stored order, so inserting beside a selection has one unambiguous stored position.

When the header row is on, its cells show the stored column names. When it is off, the names stay stored but the row is absent. An unnamed column has a blank header cell.

## Selecting cells, rows and columns

Clicking a cell selects it. The cell gets a quiet accent outline and fill. Column letters and row numbers appear by position in two continuous, rounded strips outside the table. The strips use the page surface, a muted border, and dividers between items. They are hidden while nothing is selected.

For a selected cell, only its row number and column letter receive a quiet emphasis. Clicking a letter selects that whole column; clicking a number selects that whole row. A whole-row or whole-column selection uses the accent colour on its strip item and a pale accent across the selected cells. Shift-clicking another item in the same strip extends the selection from its anchor.

When a cell is selected and not being edited, the arrow keys move the selection by one cell. Escape clears the selection and hides the strips. A cell, row number, or column letter that has keyboard focus shows the foundation focus ring. The grid, cells, header fields, and strip controls expose their roles, selection, positions, and names to assistive technology.

## Editing cells and headers

Typing while a cell is selected replaces its contents and starts editing in place. Double-clicking it, pressing Return, or pressing F2 starts editing with the existing text. The editor is the cell itself with the foundation focus outline; arrow keys and the usual text-editing keys then work in the text.

Return commits the text and selects the cell below. Tab commits and selects the cell to the right. Holding Shift reverses either direction. Clicking another cell commits before selecting it. Escape cancels the edit and restores the stored text.

<Artifact><Canvas of={Stories.EditingCell} /></Artifact>

Header cells use the same selection and editing rules. Committing an empty body cell removes its stored cell value. Committing an empty header removes the column name.

## Clearing contents

Delete or Backspace clears the selected cell, the cells in selected rows, or the cells in selected columns. It never removes a row or column. When a header cell is selected, it clears that column name.

## Adding, inserting, and deleting structure

A plus sign at the end of each visible reference strip adds a row or column at the end. Right-clicking a row number or column letter selects it and opens a canonical `<tv-menu>` below that strip item.

The row menu contains “Insert row above”, “Insert row below”, “Delete row” or “Delete rows”, and “Show header row” or “Hide header row”. The column menu has the corresponding “Insert column left”, “Insert column right”, and column deletion actions, followed by the same header action. Destructive actions use the canonical danger treatment.

<Artifact><Canvas of={Stories.OpenMenu} /></Artifact>

With a row or column selection, Cmd-Shift-= on macOS or Ctrl-Shift-= elsewhere inserts before the selection. Cmd-minus or Ctrl-minus deletes the selected rows or columns. Inserting gives each new entry an order between its neighbours, so the other entries do not move in the store. Deleting a column does not remove values left under that column key in rows.

Showing or hiding the header changes only the `showHeader` setting. It does not add, remove, or rename a column.

## Changes from elsewhere

The page follows the whole store live. Changes outside the cell or header currently being edited appear at once, without disturbing the selection.

While a person is editing one field, an incoming change to that same field does not replace the text or move the caret. Committing writes the local text, so the last write applied to that path wins. Cancelling shows the latest stored value. A row or column removed elsewhere disappears; if it held the active editor, editing ends and the nearest remaining cell is selected.

## Read-only and access loss

When the page can only read its store, as through a read-only share, the table can still be selected and navigated. Cells and headers cannot enter editing, Delete and the structural shortcuts do nothing, the plus signs are absent, and right-clicking a strip item does not open an action menu. The page switches between editable and read-only as access changes.

<Artifact><Canvas of={Stories.ReadOnly} /></Artifact>

When all access is lost, as after a share link is revoked, the page keeps the last table it received and becomes read-only. An active editor closes and shows the last confirmed value.

## Saving and disconnection

Each change saves when it is committed. Normal saving shows no message. While the page cannot reach its server, it keeps the last table it received, becomes read-only, and shows “Reconnecting…” in muted text in a strip ruled off along the bottom. It becomes editable and catches up with stored changes after reconnecting.

If a save is refused, the affected path returns to its stored value and “Couldn't save that change.” appears in the same strip for a few seconds. “Reconnecting…” takes precedence. The strip is a status region, so a screen reader hears each message.

## Data the page cannot read

Agents can write Table data directly, so it can break the [store contract](../../arch/templates/table.md#^bundled-artifact-template-table-store). The page never rewrites data it cannot read.

When the whole value breaks the contract, the store has no value, or the server reports that saved data is unavailable, an error page replaces the table: centred in the page, a warning icon in a ruled circle, “This table can't be shown”, and below it in muted text, “Its saved data isn't in the form this page reads. Ask your agent to check it.” Nothing on it can be edited. The error page is an alert, so a screen reader hears it when it replaces the table.

The error page follows the data live. Once an agent fixes the data, the table returns.
