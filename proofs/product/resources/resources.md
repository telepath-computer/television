*How the resource layer's user-facing promises are proven: built-CLI and real-browser walks of an artifact's own store, share links across two servers, a share viewer who never sees the artifact's ID, the share commands, the common commands through a store's life and recovering a deleted artifact's data, with created stores and bindings proven where the flag can be turned on and their breadth carried by the resource architecture proofs.*

# Resources — proof

Proves [specs/product/resources/resources.md](../../../specs/product/resources/resources.md).

## Coverage model

Every assertion below is an acceptance walk at the outermost boundary: the built `tv` CLI as spawned processes over temporary [Television homes](../../../specs/product/cli.md#^cli-home), the server those processes start, and, for page behavior, a real browser loading the Television app, or a share link, and the SDK exactly as that server serves them. No Television mechanism is mocked on these paths. The built CLI is the shipped build, so every walk runs with [the bindings flag](../../../specs/product/resources/resources.md#^rs-flag) off.

The spine has nine walks. The page walk proves that an artifact's page finds and uses its own store, from a plain-HTTP address that is not `localhost`, and the HTTPS-front walk that pages reached through a front that terminates TLS do so too. The sharing walk is the spec's two-server directive: a producer and a viewer run as separate built servers with authentication on, the browser holds only the viewer's credentials, and the producer's enforcement of a share link's level is proven from inside the shared page, including against a page that bypasses the SDK. The exposure walk opens a share link in a browser that holds no token and records everything it receives. The share-command walk drives `tv share-artifact` and `tv unshare-artifact` through a link's life and their refusals. The common-command walk takes an own store through its description, usage, events and destruction. The recovery walk deletes an artifact and copies its store's data into a new artifact's store. The flag-off walk proves that the shipped build offers and serves no created store and no binding, and the help walk that no help it prints lists their commands.

Both browser walks honor the plain-HTTP rule by giving each server a host name that the browser resolves to the loopback address, so pages run outside a secure context. The sharing walk runs in Chromium and Firefox, as the spec's testing directive requires. Of the other walks, only the page walk is in the repository's Firefox selection, because it is the shortest path through the served SDK and the secure-context rules differ between the two browsers.

Created stores and bindings exist only with the flag on, which no shipped build can reach, so no acceptance walk can prove them. They are proven where a test can turn the flag on, through [the resource architecture proof's hook](../../arch/resources/index.md#Test hooks): creating stores, binding and unbinding, their refusals and the tokenless bind warning cross from the CLI's command actions to a really-running server with the flag on in [the CLI seam](../../arch/resources/index.md#^rs-arch-t-cli-seam), and live bindings, another artifact's own store bound to an artifact, the page's level on a bound store and the page's events with the flag on are [the page connection's contracts](../../arch/resources/index.md#The page connection). The hook changes the flag's value and nothing else; that the shipped build has it off is what the flag-off walk proves. That a store created with the flag on stays an ordinary store with the flag off, its bindings kept but unread, and that they take effect again once the flag is on, is [the architecture's contract for data left by the flag](../../arch/resources/index.md#^rs-arch-t-flag-off-stored).

Breadth lives in the architecture proofs and composes through clean handoffs: description, usage and resource-ID validation, the first write's order, loading, share-ID resolution and share changes, every command's output shape and refusal, event delivery and the page's subset, deletion through every path, requests from other origins and the page connection's rules in [the resource architecture proof](../../arch/resources/index.md); the SDK's functions, the page's access level, handles and connection in [the SDK proof](../../arch/resources/sdk.md). [The connection](../../../specs/product/resources/resources.md#^rs-connection), its status and its failing at once while the page is disconnected, needs a network a test can cut, so it is proven in a real browser against a running server by [the SDK proof's status](../../arch/resources/sdk.md#^sdk-t-connection-status) and [reconnection](../../arch/resources/sdk.md#^sdk-t-reconnect) assertions and [the JSON store's disconnected assertion](../../arch/resources/json-store.md#^js-arch-t-disconnected), each through the SDK proof's network proxy. The JSON store's content behavior, its commands and the `unavailable` status are walked in [the JSON store product proof](./json-store.md).

Not tested: [the model's limits](../../../specs/product/resources/resources.md#^rs-limits) describe exposures, not behavior to build, including what a page on another site can read from the event stream on a tokenless server. That a client holding only an artifact's ID can use its store is exercised anyway, by [the artifact-route contract](../../arch/resources/index.md#^rs-arch-t-artifact-routes)'s client, which is not a browser. That each artifact's document runs apart from the app and from other artifacts, sandboxed in a browser and in a partition of its own in the desktop app, is walked by [artifact isolation's escalation walks](../../arch/artifact-frame/isolation.md#^iso-t-escalation-browser), [in the desktop app](../../arch/artifact-frame/isolation.md#^iso-t-escalation-electron) too, and the storage shared artifacts from one producer share there by [its storage-visibility matrix](../../arch/artifact-frame/isolation.md#^iso-t-desktop-storage). The sharing and exposure walks keep the producer's token out of the browser, because [the promise to share viewers](../../../specs/product/resources/resources.md#^rs-share-hides-id) concerns a viewer who holds only the link. That a share link's own content keeps its links relative is the author's responsibility, which the exposure walk's fixture honors. `wrong-type` cannot arise while `json` is the only type; the SDK proof notes it.

## Test hooks

- **HTTPS front.** A test front listens at a mapped host name, terminates TLS with a certificate generated for the run, and forwards each connection's bytes unchanged to the built server's plain-HTTP port, as a front such as `tailscale serve` does. The browser context is told to accept that certificate (`ignoreHTTPSErrors`). The front stands in for software outside Television and replaces no Television mechanism.
- **Browser host-name mapping.** Browser walks launch the browser with its resolver mapping test host names to `127.0.0.1` (Chromium's `--host-resolver-rules`, Firefox's `network.dns.localDomains`), so a server bound to loopback is reached at a plain-HTTP origin that is not `localhost` or a loopback address, where browsers withhold secure-context features. Production browsers resolve names through ordinary DNS; the mapping changes no Television mechanism.

## Assertions

### Acceptance criteria

Shared declaration: each server is the built CLI's `tv --home <home> serve` over a temporary home whose config file sets port `0`, following [the test-runner recipe](../../../specs/arch/test-runner/test-runner.md#Test infrastructure addresses); every command is a spawned built `tv` process given that home and port. Authentication is on unless an assertion says otherwise. HTML artifacts are authored fixture files registered through `tv create-path-artifact`, and the viewer adds shared artifacts through `tv create-url-artifact`; stores are written only through pages and `tv resource json` commands, and share links are made only through `tv share-artifact`. Browser walks use the host-name mapping hook above and the testing policy's default CSS-motion override, which forfeits only motion that no assertion here claims. No other mock or test hook is used.

- **Acceptance — a page uses its artifact's store.** In a real browser, the Television app is loaded from the server at a mapped plain-HTTP host name, and shows an artifact whose source imports `/sdk/v1/resources.js` and calls `getStore()`, with no artifact ID or token in the source. Before anything writes to the store, `tv resource json get --artifact <id>` prints `{"exists":false}` and the artifact's record has no store; the page's `getAccess` resolves `read-write`, its `onAccessChanged` callback hears `read-write`, and its `onValue` listener on the whole value hears no value. The page writes, the listener hears the write, and `tv resource json get --artifact <id>` then shows it; the listener, registered before the first write, was called for no other reason. A `tv resource json set --artifact <id>` from the shell reaches the page's listener without a reload, and the page's `onResourcesChanged` callback receives `changed` with the path written, and no resource ID or artifact ID. A handle from `getStore(resourceID)`, given the store's own resource ID as the record shows it, fails its first operation with `not-enabled` while the artifact's store keeps working. The walk runs in Chromium and in Firefox. This proves [an artifact's store](../../../specs/product/resources/resources.md#^rs-artifact-store), [the SDK's use of the page's own address](../../../specs/product/resources/resources.md#^rs-sdk-own-address), [handles](../../../specs/product/resources/resources.md#^rs-sdk-handles), the artifact's own ID carrying `read-write` under [levels](../../../specs/product/resources/resources.md#^rs-id-levels), the page's half of [events](../../../specs/product/resources/resources.md#^rs-events) and [plain HTTP](../../../specs/product/resources/resources.md#^rs-plain-http) — *(policy-grade test: `test/node/resource-page-acceptance.test.ts` "uses its artifact's store before and after the first write, hears shell changes, and finds stores by resource ID not enabled", in Chromium and Firefox)*. ^rs-ac-page-spine
- **Acceptance — pages behind an HTTPS front.** In Chromium, the Television app is loaded at [the test front's](#Test hooks) `https:` address, and shows an artifact whose source imports `/sdk/v1/resources.js` and calls `getStore()`. The artifact's frame is a secure context at an address on the front's origin, although its document's own origin is opaque, and the SDK opens its page connection at `wss://` on the front's host. The page's `getAccess` resolves `read-write`; its write reaches `tv resource json get --artifact <id>`; and a `tv resource json set --artifact <id>` from the shell reaches its listener without a reload. The artifact's share link at `read`, opened at the front's address, connects at `wss://` too, and its page's `getAccess` resolves `read`, its listener hears the store's value, and its write is refused with `read-only`, leaving the store unchanged. This proves [HTTPS fronts](../../../specs/product/resources/resources.md#^rs-https-front) — *(policy-grade test: `test/node/resource-https-front-acceptance.test.ts` "uses its artifact's store and a share link's level through a front that terminates TLS")*. ^rs-ac-https-front
- **Acceptance — sharing and permissions across two servers.** A producer and a viewer run as separate built servers on different mapped host names. On the producer, artifact A is an authored HTML file whose page shows its store and its access level, and whose store holds a value written through `tv resource json set --artifact`. `tv share-artifact --id A --access read` on the producer prints A's share link, and the viewer adds that link as a shared artifact through its own built CLI. The browser opens the viewer's app holding only the viewer's token. From inside the shared page, which the app frames from the producer's origin, the walk shows that the producer's server enforces the link's level:
  - the page shows the store's value, and `getAccess` resolves `read`;
  - a write through the SDK is rejected with `read-only` and never shown, and the same write sent over the page's own WebSocket with the shared code's message framing, bypassing the SDK, is refused with `read-only`; the producer's store is unchanged;
  - a `tv resource json set --artifact A` on the producer reaches the page's open listener live;
  - `tv share-artifact --id A --access read-write` on the producer, while the page stays open, makes its `onAccessChanged` callback hear `read-write`, and its next write succeeds, appears in the producer's `tv resource json get --artifact A`, and is still there after the shared page reloads; the link the second command printed equals the first;
  - the page, sandboxed by the viewer's frame and the producer's header, can use no browser storage, and its request to the producer's administrative routes is refused;
  - a page on the viewer's origin that knows the share link opens the producer's page connection for the share ID, which is its authority, at the link's level, while its request to the producer's administrative routes, of the kind browsers send without a CORS preflight and carrying no token, is refused and changes nothing;
  - `tv unshare-artifact --id A` on the producer closes the page's connection, after which the page's `onAccessChanged` callback hears that it has no access, the page's next operation on its store fails with `no-store`, and a fresh load of the share link's address is answered `404`, with nothing of the artifact.

  The walk runs in Chromium and in Firefox. This proves [share links](../../../specs/product/resources/resources.md#^rs-share), [the share ID](../../../specs/product/resources/resources.md#^rs-share-id), the share ID's level under [levels](../../../specs/product/resources/resources.md#^rs-id-levels), [share changes taking effect for open pages](../../../specs/product/resources/resources.md#^rs-share-changes), [server-enforced read access](../../../specs/product/resources/resources.md#^rs-read-enforced), [shared artifacts](../../../specs/product/resources/resources.md#^rs-shared-artifact) and [other origins](../../../specs/product/resources/resources.md#^rs-other-origins) — *(policy-grade test: `test/node/resource-sharing-acceptance.test.ts` "enforces a share link's level in a shared page, including against a page that bypasses the SDK, as the level changes and the link is revoked", in Chromium and Firefox)*. ^rs-ac-sharing
- **Acceptance — a share viewer never sees the artifact's ID.** In a real browser context that holds no token, the walk opens the share link of a shared folder artifact stored in a folder named for its ID, at `read`, first without its trailing slash, and the share link of a single-file HTML artifact stored in a file named for its ID. It records the address of every page, every request and response with its headers and status, every redirect, every WebSocket message in both directions, every SDK result and event the page receives, and every console message and page error. The fixture's page reads its store, reads `getAccess`, registers `onAccessChanged`, `onValue` and `onResourcesChanged`, attempts a write, and loads a missing file and a subfolder by relative links; meanwhile the shell writes to the store with `tv resource json set --artifact`, sets the store's description and usage to text containing the artifact's ID with `tv resource describe`, and changes the link's level to `read-write`, after which the page writes. The walk then asserts that the artifact's own ID appears nowhere in the recording, including in the redirect to the trailing slash, the redirect to the subfolder's index, the single-file artifact's address and responses, the missing-file response, the opening state, the `changed` event and the access change. This proves [the artifact ID never reaching a share viewer](../../../specs/product/resources/resources.md#^rs-share-hides-id) — *(policy-grade test: `test/node/resource-share-exposure.test.ts` "a share viewer receives nothing that carries the artifact's ID")*. ^rs-ac-share-hides-id
- **Acceptance — the share commands through a link's life.** On a server whose config file adds a second listening address, `tv share-artifact --id <id>`, without `--access`, exits `0` and prints one line for each connect link `tv links` prints, each that link's origin followed by `/artifact/<share-id>/`, with the same share ID in every line, which is neither the artifact's ID nor contained in it; `tv get-artifact` shows the link in the artifact's record at `read`. Running it again without `--access`, and with `--access read`, prints the same lines; with `--access read-write` it prints the same lines too, and the record shows the new level. Then `tv share-artifact --id <id>` without `--access` exits nonzero, saying that the link is `read-write` and naming `--access read-write` and `--access read`, and the record still shows `read-write`. `tv unshare-artifact --id <id>` prints `Artifact <id> is no longer shared.`, and the record has no link; running it again exits nonzero, saying the artifact has no share link. Sharing again prints a different share ID. Refusals: `share-artifact` with a level that is neither `read` nor `read-write` is a directive error; both commands with an ID that names no artifact exit nonzero; `share-artifact` for a URL artifact exits nonzero, saying that only artifacts this server serves from its own files can be shared; for a Markdown file artifact, `share-artifact --access read-write` exits nonzero, saying that read-write sharing is not supported for it, and creates no link, while `share-artifact` without `--access` then creates a `read` link to it; and on a server whose config file sets `"auth": false`, `share-artifact` exits nonzero, saying that sharing needs the token, while `unshare-artifact` revokes a link made before the server was restarted without its token. Deleting a shared artifact with `tv delete-artifact` stops its link's address serving it. This proves [the share commands](../../../specs/product/resources/resources.md#^rs-share-cli), [which artifacts can be shared](../../../specs/product/resources/resources.md#^rs-shareable), [tokenless servers refusing links](../../../specs/product/resources/resources.md#^rs-share-tokenless) and the command half of [share changes](../../../specs/product/resources/resources.md#^rs-share-changes) — *(policy-grade test: `test/node/resource-acceptance.test.ts` "share an artifact, change the link's level, revoke it, and refuse what cannot be shared", which needs a second loopback address and is skipped, saying so in its name, where none can be bound)*. ^rs-ac-share-cli
- **Acceptance — the common commands through a store's life.** An artifact's store is written through `tv resource json set --artifact <id>`, with `tv resource events` running. `tv resource list` prints the store with the resource ID the artifact's record shows, type `json`, the fixed own-store description, an empty usage, `available`, a creation time and the artifact as its owner; `tv resource list --artifact <id>` prints it with `read-write`; `tv resource info <resource-id>` prints it with one binding, the owner's at `read-write`. `tv resource describe <resource-id> "Tasks for the launch"` prints its line, then `describe --usage` with a usage of several lines, and then both at once, each printing its line, and `info` shows them; `describe` without either is a directive error, and with an empty description exits nonzero, changing nothing. `tv resource destroy <resource-id>` exits nonzero, naming the artifact with `read-write` and mentioning `--force`, and leaves the store; `destroy --force` prints `Resource <resource-id> destroyed; removed bindings for <id>.`, the artifact's record no longer has a store, `get --artifact <id>` prints `{"exists":false}`, and `info <resource-id>` fails with `Resource not found: <resource-id>`. The next `set --artifact <id>` creates a store under a different resource ID. `events` printed `changed`, `updated` and `destroyed` lines in order, each naming the resource ID and the `changed` and `destroyed` lines the artifact. A second artifact is deleted after its store is written, and destroying that store needs no `--force`. This proves [the common commands](../../../specs/product/resources/resources.md#^rs-cli), [an own store](../../../specs/product/resources/resources.md#^rs-own-store) with its fixed description and implicit binding, [description and usage](../../../specs/product/resources/resources.md#^rs-usage), [lifetime](../../../specs/product/resources/resources.md#^rs-lifetime), [destroying a bound resource](../../../specs/product/resources/resources.md#^rs-destroy-bound) and the agents' half of [events](../../../specs/product/resources/resources.md#^rs-events) — *(policy-grade test: `test/node/resource-acceptance.test.ts` "list, describe, watch the events of and destroy an artifact's own store")*. ^rs-ac-common-commands
- **Acceptance — recovering a deleted artifact's data.** An artifact's store is written through `tv resource json set --artifact <id>`, and `tv delete-artifact` deletes the artifact. `tv resource list` still prints its store, with the deleted artifact as its owner: `tv resource json get --resource <resource-id>` prints the stored value, and `--artifact <id>` now fails with `Artifact not found: <id>`. The walk registers the same file as a new artifact and runs `tv resource json set --artifact <new-id> --file <path>` with the value read; the new artifact's store then holds it, and the old store is unchanged. This proves [deleting an artifact and recovering its data](../../../specs/product/resources/resources.md#^rs-artifact-deleted) — *(policy-grade test: `test/node/resource-acceptance.test.ts` "keep a deleted artifact's store, find it with list and copy its data into a new artifact's store")*. ^rs-ac-recovery
- **Acceptance — the shipped build offers no created store and no binding.** Through the built CLI, `tv resource bind <resource-id> <id> --access read`, `tv resource unbind <resource-id> <id>` and `tv resource json create --description x` each exit as directive errors, creating nothing. Requests to the server's administrative routes, with the token, that create a store and that bind an artifact are each refused with `not-enabled`, creating nothing under `<home>/resources/` or `<home>/state/`. This proves [the flag off](../../../specs/product/resources/resources.md#^rs-flag-off) in the shipped build — *(policy-grade test: `test/node/resource-acceptance.test.ts` "offer and serve no created store and no binding while the flag is off")*. ^rs-ac-flag-off
- **Acceptance — the shipped build's help lists no created store or binding command.** Through the built CLI, top-level help (`tv --help`, `tv help`), the help of `tv resource` (`tv resource --help`, `tv help resource`, `tv resource help`) and the help of `tv resource json` (`tv resource json --help`, `tv resource help json`, `tv resource json help`) each exit `0` and list the commands the flag leaves: `resource`, `share-artifact` and `unshare-artifact` among the top level's, exactly `list`, `info`, `describe`, `destroy`, `events`, `json` and `help` under `tv resource`, and exactly `get`, `set`, `update`, `push`, `remove`, `watch` and `help` under `tv resource json`. None of these, nor the help printed for `tv resource bind --help`, `tv resource unbind --help`, `tv resource json create --help`, `tv resource help bind`, `tv resource help unbind`, `tv resource json help create` and `tv help resource bind`, lists `bind`, `unbind` or `create` as a command, or names `bind`, `unbind` or `json create` anywhere in its text. This proves the help output of [the flag off](../../../specs/product/resources/resources.md#^rs-flag-off) in the shipped build — *(policy-grade test: `test/node/resource-acceptance.test.ts` "list no created-store or binding command in any help while the flag is off")*. ^rs-ac-flag-off-help
