*How the JSON store's user-facing promises are proven: a page and an agent sharing an artifact's store through the served SDK and the built CLI, a page seeing its own writes, the `tv resource json` commands, and unreadable stored data, with breadth carried by the JSON store architecture proof.*

# JSON store — proof

Proves [specs/product/resources/json-store.md](../../../specs/product/resources/json-store.md).

## Coverage model

The assertions below are acceptance walks at the outermost boundary: the built `tv` CLI as spawned processes over temporary [Television homes](../../../specs/product/cli.md#^cli-home), the server those processes start, and a real browser loading the Television app and the SDK as that server serves them, from a plain-HTTP host name that is not `localhost`. No Television mechanism is mocked on these paths.

Four walks make up the spine. In the page walk, a page and an agent share an artifact's store through the store's functions and the commands, and the data survives a server restart. The local-write walk shows a page its own write at once, clears its saving state on confirmation, and rolls back a write the server refuses. The command walk covers every `tv resource json` command available in the shipped build, its output and its principal refusals. The storage walk shows unreadable stored data reported as unavailable, left byte-for-byte unchanged, and isolated from other stores.

Breadth composes from [the JSON store architecture proof](../../arch/resources/json-store.md) through clean handoffs. The shared module's path, value, array, equality and ordering rules are contract-tested once and reused by the server, the SDK and the CLI, so the walks sample them rather than enumerate them. Server-side write application, server-filled values, limits, transactions, subscriptions and durability failures are contracts over a real filesystem and real connections. The SDK's local-write model, child events, transactions and reconnection run in a real browser against a running server, as that spec's testing directive requires, including a connection lost while writes are unconfirmed and reads and writes made while the page is disconnected. Those browser tests construct the server in process rather than through the built CLI; the walks here cross the built-CLI boundary once for each principal path.

Access levels and the sharing walk, including writes through `read` access refused when the SDK is bypassed, are proven by [the resources product proof](./resources.md). The read and write classification of every operation is [the architecture's access contract](../../arch/resources/json-store.md#^js-arch-t-access). `create` exists only with [the bindings flag](../../../specs/product/resources/resources.md#^rs-flag) on, which the shipped build cannot reach, so it is proven with the flag on by [the CLI seam](../../arch/resources/json-store.md#^js-arch-t-cli-seam) and [contract](../../arch/resources/json-store.md#^js-arch-t-cli-contract).

## Test hooks

Browser walks use [the resources proof's host-name mapping](./resources.md#Test hooks); no other hook is used.

## Assertions

### Acceptance criteria

Shared declaration: servers are the built CLI's `tv --home <home> serve` over temporary homes whose config file sets port `0`, with authentication on; every command is a spawned built `tv` process given that home and port. HTML artifacts are authored fixture files registered through `tv create-path-artifact`, and each uses its own store. Browser walks load the Television app from the server at a mapped host name and use the testing policy's default CSS-motion override, which forfeits only motion that no assertion here claims. No other mock or test hook is used.

- **Acceptance — a page and an agent share a store.** An authored artifact shown in the app uses its store, which `tv resource json set --artifact <id> '{"items":{}}'` has given a starting value. The page's `onValue` on `items` delivers `{}` first. Two `push` calls return references with keys at once, before confirmation, and `onChildAdded` delivers both children in creation order. An `update` of two paths applies both. A `runTransaction` on a counter commits and resolves with `committed` true. A `set` whose value nests `serverTimestamp()` and `increment(2)` stores a number of milliseconds near the server's clock and the incremented number. `set(ref, null)` stores `null`, which `tv resource json get` reports as `{"exists":true,"value":null}`, and `remove` deletes a path, which `get` then reports as `{"exists":false}`. An array written whole reads back as an array. Each change the page makes appears in `tv resource json get`, and a `tv resource json set` from the shell reaches the page's `onValue` without a reload. After the server is stopped and started again over the same home, `get` returns the same value. This proves [the API](../../../specs/product/resources/json-store.md#^js-api), [plain JSON](../../../specs/product/resources/json-store.md#^js-plain-json), [arrays](../../../specs/product/resources/json-store.md#^js-arrays), [server values](../../../specs/product/resources/json-store.md#^js-server-values), [transactions](../../../specs/product/resources/json-store.md#^js-transactions), [`onValue`](../../../specs/product/resources/json-store.md#^js-on-value), [child events](../../../specs/product/resources/json-store.md#^js-child-events) and the persistence in [write order](../../../specs/product/resources/json-store.md#^js-write-order) — *(policy-grade test: `test/node/resource-page-acceptance.test.ts` "uses the store's functions on plain JSON, sees shell changes live, and keeps the data across a restart")*. ^js-ac-page-spine
- **Acceptance — a page sees its own writes.** On a page opened through the artifact's share link at `read-write`, a `set` is delivered to the page's `onValue` listener at once with `metadata.hasPendingWrites` true, and the listener then receives a snapshot with `hasPendingWrites` false and the same value once the write is confirmed. After `tv share-artifact --access read` changes the link's level while the page stays open and the page's `onAccessChanged` callback has heard `read`, the page's next `set` rejects with code `read-only` without its listener ever receiving the value, and `tv resource json get --artifact` shows no change. This proves [local writes](../../../specs/product/resources/json-store.md#^js-local-writes), [the pending flag](../../../specs/product/resources/json-store.md#^js-pending-flag) and the page-side half of [writes through `read` access](../../../specs/product/resources/json-store.md#^js-read-local). The other half, a write the server refuses after the page showed it, needs the write to reach the server before the page hears of the change; [the architecture's browser assertion](../../arch/resources/json-store.md#^js-arch-t-refused-after-shown) arranges that deterministically — *(policy-grade test: `test/node/resource-page-acceptance.test.ts` "shows a write at once as pending, clears pending on confirmation, and refuses a write through read access without showing it")*. ^js-ac-local-writes
- **Acceptance — the `tv resource json` commands.** Each command runs as a spawned built process and exits `0` with the spec's output. On an artifact whose store has never been written, `get --artifact <id>` prints `{"exists":false}`, and a `watch --artifact <id>` started then prints that line first. `set --artifact <id>` with a single value argument prints `JSON store of artifact <id> updated.`, which the running `watch` follows with the new value; `get` prints `{"exists":true,"value":…}` for the whole value, for a path and for `/`, and `{"exists":false}` for a missing path; `set` with a path and with a value read through `--file <path>` and through `--file -` from standard input, `update` and `remove` change what `get` returns; `push` prints `{"key":"<new-key>"}` and its value is found under that key. The same store reached with `--resource`, its resource ID taken from `tv get-artifact`, answers `get` with the same value and prints `JSON store <resource-id> updated.` for `set`. `watch` prints a line with the new value after each change another command makes once its previous line has appeared; after a burst of writes from other commands its last line equals what `get` then returns; and it exits `0` on `SIGINT`. Refusals: value text that is not JSON is a directive error that changes nothing; a value argument together with `--file` is refused; a command given neither `--artifact` nor `--resource`, or both, and one given an option it does not define, such as `--name` or `--resource-id`, are directive errors that change nothing; `--artifact` with an ID that names no artifact fails with `Artifact not found: <id>`; `--artifact` naming a URL artifact fails, saying that only artifacts this server serves from its own files have a store, and naming no kind of file; `--resource` with an ID that names no store fails with `Resource not found: <id>`. A store holding a string of 1,000,000 characters, within the size limit, is read whole: `get` with its standard output a pipe exits `0` only after printing all of it. This proves [the commands](../../../specs/product/resources/json-store.md#^js-cli), [their store options](../../../specs/product/resources/json-store.md#^js-cli-store), [`watch` converging on the stored value](../../../specs/product/resources/json-store.md#^js-watch) and [paths](../../../specs/product/resources/json-store.md#^js-paths) at the shell — *(policy-grade tests: `test/node/resource-acceptance.test.ts` "read, write and watch an artifact's store by artifact and resource ID, and refuse bad values, wrong options and missing stores", and "print a value near the size limit whole through piped standard output")*. ^js-ac-cli
- **Acceptance — unreadable stored data.** Two artifacts' stores are written through the built CLI and the server is stopped. One store's `content.json` is overwritten with bytes that are not valid JSON, and the server is started again over the same home. `tv resource json get` and `set` with `--artifact` on that store fail with a message saying it is unavailable, while `get` and `set` on the other store succeed. The unreadable file's bytes are unchanged after those commands and after another restart. This proves [storage](../../../specs/product/resources/json-store.md#^js-storage) and [status](../../../specs/product/resources/resources.md#^rs-status) — *(policy-grade test: `test/node/resource-acceptance.test.ts` "report an artifact's store whose stored data cannot be read as unavailable, leave its file alone, and keep the other working")*. ^js-ac-unavailable

Coverage relationship: [writes rolled back when the connection is lost, and writes and reads failing while the page is disconnected](../../../specs/product/resources/json-store.md#^js-disconnect), [reconnection](../../../specs/product/resources/json-store.md#^js-reconnect), and [a write whose save the server cannot confirm](../../../specs/product/resources/json-store.md#^js-uncertain-write), which leaves the store available with the value its file holds, are proven in [the JSON store architecture proof](../../arch/resources/json-store.md#Local writes in a real browser) and its [durability contract](../../arch/resources/json-store.md#^js-arch-t-uncertain); that such a value can be lost in a crash before the next successful save is a cost the spec states, not behavior to prove. When `watch` reads is [the architecture's `watch` contract](../../arch/resources/json-store.md#^js-arch-t-watch); that it may skip values held only between two reads is a limit the spec states, not behavior to prove; the order of a connected page's writes under [write order](../../../specs/product/resources/json-store.md#^js-write-order) is [the page connection's write-order contract](../../arch/resources/index.md#^rs-arch-t-sequence), with the SDK sending writes in the order the page made them, which [the local view](../../arch/resources/json-store.md#^js-arch-t-local-view)'s generated programs check against what the server stores; that no write is sent twice, so none is applied twice, is proven by [its lost-connection assertion](../../arch/resources/json-store.md#^js-arch-t-lost-connection), in which a write the server applied before the loss rolls back, is not sent again, and reaches the page's listener when the connection returns. A rolled-back write that the server applies after the page has reconnected reaches the page's listeners as another client's change does, which [the page walk](#^js-ac-page-spine) shows with a change from the shell; that the server may apply it after the page's later writes is a limit the specs state, not a behavior to prove. An exception thrown by a page's callback is [the SDK's isolation contract](../../arch/resources/sdk.md#^sdk-t-callback-isolation).
