# Artifact templates — proof

Proves [specs/product/templates.md](../../specs/product/templates.md).

## Coverage model

Acceptance walks use a built `tv` process, a running authenticated server in a temporary home, real files and stores, and a real browser where live pages matter.
Authored folder templates import the served resource SDK; URL-template fixtures point to a local HTTP page. Setup creates channels/artifacts through production commands or HTTP.
The copied-artifact walk proves independent page files and stores, starting data and later template edits. CLI acceptance also proves ordinary deletion. A URL walk proves the separate URL outcome without a store.
Refusal and partial-failure walks prove the principal unsuccessful outcomes at the same command boundary.
[Template architecture](../arch/templates/index.md) carries schema, icon, scan, cache-ordering, placement, display and failure-step breadth at cheaper boundaries.
[CLI architecture](../arch/cli/index.md) carries argv and flat list/show projection; [product CLI](./cli.md) carries process input and focus-failure output.
[Toolbox](../ui/app/toolbox.md) carries interaction, appearance and UI failure behavior; the creation journeys here prove its real server outcome.
[Reload/navigation](../arch/artifact-frame/reload-navigation.md) carries shared watcher mechanics, and [bundled installation](../arch/templates/bundled-installation.md) carries minimum-version recovery.
The [Checklist](../ui/templates/checklist.md#^checklist-ui-ac-new) and [Sticky note](../ui/templates/sticky-note.md#^sticky-note-ui-ac-new) creation walks extend the Toolbox journey through each shipped seed, starting display, first edit and saved result. The [Weather creation walk](../ui/templates/weather.md#^weather-ui-ac-new) covers its empty seed, transparent 340-by-340 reference-pixel display, configuration write, page-owned Open-Meteo fetch and saved cache. Together these shared walks accept [the bundled-template promise](../../specs/product/templates.md#^artifact-template-bundled) without another product-level browser suite; authored page behavior remains the author’s responsibility.
No mechanism is mocked in these walks except the standing CSS-motion override, which forfeits CSS motion only to the owning UI proofs.

## Test hooks

No production test hook is needed. Temporary homes, template files, caller data and a local URL target are fixtures.

## Discovery and creation

- **Acceptance** (spawned built CLI → real server/filesystem): under [discovery](../../specs/product/templates.md#finding-and-using-an-artifact-template) and [CLI access](../../specs/product/templates.md#access-from-the-app-and-cli), list immediately reflects added/repaired/edited folders and invalid-folder errors; show resolves the exact ID and returns the current full folder or URL record including its installed path and optional schema. The list contains only summaries and errors; show contains no app metadata. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “rescans authored templates and refuses an invalid or removed folder” and “shows freshly edited exact template records and refuses invalid, absent or unreadable lookups”)* ^templates-ac-discovery
- **Acceptance** (built CLI and real browser → server, copied folders and SDK; authored page and starting/caller data): under [copied results](../../specs/product/templates.md#^artifact-template-result) and [starting data](../../specs/product/templates.md#starting-data-and-schemas), two creations return distinct ordinary IDs and independent folders without origin fields; titles use the manifest name or caller title. Root manifest/data files stay in the template, supporting files are copied, and stores use template data or caller replacement. Later page/data edits affect only subsequent creations, and removing the template leaves existing artifacts usable. Editing one copied page or store affects only that artifact. *(policy-grade test: `packages/web/test/e2e/templates-real-stack.test.ts`, “copied CLI artifacts use starting data and remain independent of template edits and removal”)* ^templates-ac-cli-create
- **Acceptance** (built CLI → real server/filesystem): under [copied results](../../specs/product/templates.md#^artifact-template-result), retitling preserves the copied path. Deleting the created artifact removes its record while retaining the local folder and store. *(policy-grade test: `test/node/cli-acceptance.test.ts`, “creates an independent template copy with starting data and ordinary artifact lifecycle”)* ^templates-ac-copy-lifecycle
- **Acceptance** (spawned built CLI → real server; local HTTP target fixture): under [URL templates](../../specs/product/templates.md#finding-and-using-an-artifact-template), creation returns an ordinary URL artifact at the trimmed manifest address, with the chosen title, no store and no origin field. A later manifest address edit does not repoint it. URL page display follows [ordinary artifact coverage](./artifacts.md), not a separate external-site compatibility matrix. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “creates ordinary URL templates and refuses URL data before creation”)* ^templates-ac-url-create
- **Acceptance** (real browser → Toolbox → authenticated server): under [Toolbox creation](../../specs/product/templates.md#^artifact-template-popover), activating a folder item creates a copied page immediately after the selected tab in the focused channel and focuses it; the page loads with template starting data, or an unwritten store when no `data.json` exists. In an empty channel it becomes the only page. A URL item creates and focuses an ordinary URL artifact. Observe unmodified requests: `source: "ui"`, selected-tab placement, no `data` or `display`. *(policy-grade tests: `packages/web/test/e2e/toolbox-acceptance.test.ts`, “click and Return create copied artifacts with starting data after selected tab or in empty channel (^toolbox-ac-activation, ^templates-ac-ui-create)” and “Toolbox creates and focuses an ordinary URL artifact without a store”)* ^templates-ac-ui-create

## Display values

The following pairs extend the CLI and browser journeys above rather than adding a full journey for each display field.

- **Acceptance** (built CLI → real server): under [display precedence](../../specs/product/templates.md#^artifact-template-display-options), command width and explicit false full-screen override only those manifest values; manifest height and other values remain. Later manifest edits leave the saved display settings unchanged. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “lets a template creation option override only its own display value”)* ^templates-ac-display-cli
- **Acceptance** (same CLI journey): under [transparency precedence](../../specs/product/templates.md#^artifact-template-display-options), `--no-transparent` overrides manifest true, get-artifact omits the false field, and an ordinary later transparency update survives a manifest edit. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “lets a template creation option override only its own display value”)* ^templates-ac-transparent-cli
- **Acceptance** (real browser → Toolbox → server): under [Toolbox display defaults](../../specs/product/templates.md#^artifact-template-display-options), a partial manifest determines width/full-screen while omitted height uses the shared default; the request omits display. *(policy-grade tests: `packages/web/test/e2e/toolbox-acceptance.test.ts`, “Toolbox uses manifest display and shared defaults without sending display”)* ^templates-ac-display-ui
- **Acceptance** (same browser journey): under [transparency defaults](../../specs/product/templates.md#^artifact-template-display-options), manifest true creates a transparent frame with its title bar hidden at rest and true in metadata. Fade mechanics remain with [the frame proof](../ui/app/artifact-frame/transparency.md#^af-ui-ac-transparent-hover). *(policy-grade tests: `packages/web/test/e2e/toolbox-acceptance.test.ts`, “Toolbox creates a focused transparent frame from manifest defaults without sending display”)* ^templates-ac-transparent-ui

## Refusal and recovery

- **Acceptance** (spawned built CLI → real server, invalid folder and valid channel fixtures): under [discovery refusal](../../specs/product/templates.md#finding-and-using-an-artifact-template), invalid template creation reports its scan error without an artifact; removing that folder makes the same ID report not found. *(policy-grade test: `test/node/cli-acceptance.test.ts`, “rescans authored templates and refuses an invalid or removed folder”, refusal checks only)* ^templates-ac-cli-refusal
- **Acceptance** (built CLI → real server; schema-bearing folder and URL-template fixtures): under [starting data](../../specs/product/templates.md#starting-data-and-schemas), schema-invalid caller data is refused before creation with a field/reason and `tv templates show <id>` guidance; URL-template data is refused before creation. Supplying valid data, including null where allowed, succeeds and is durably readable; no caller or template data leaves the store unwritten despite required fields or schema defaults. Later ordinary store writes are not restricted by the template schema. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “validates caller data before creation and keeps unwritten, null and later writes distinct” and “creates ordinary URL templates and refuses URL data before creation”)* ^templates-ac-data-refusal
- **Acceptance** (built CLI → real server; caller-supplied data and post-boot file at the resource-directory path as a real obstruction): under [creation failure](../../specs/product/templates.md#^artifact-template-data), first-write failure after registration exits 1 without success lines and identifies the copied target, generated ID and unconfirmed store step. Earlier record/content remains inspectable. [Architecture](../arch/templates/index.md#^templates-t-failure) covers other failing steps. *(policy-grade tests: `test/node/cli-acceptance.test.ts`, “reports an unconfirmed starting-data write and preserves the copy”)* ^templates-ac-cli-post-copy-failure
