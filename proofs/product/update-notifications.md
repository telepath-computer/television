*How Television's update promises are proven: real browser and Electron journeys for the server-update notice, auto-reload, the desktop self-update notice, the desktop recommendation and the gate, and the desktop product's update check on a candidate build for the desktop app's own updates.*

# Update notifications — proof

Proves [specs/product/update-notifications.md](../../specs/product/update-notifications.md).

## Coverage model

Real browser and Electron journeys against a running server cover the server-update notice, auto-reload, the desktop self-update notice, the desktop recommendation and the blocking gate. The complete update sequence is composed from three real paths, as the spec's Testing section directs: the notice, a reload after a real server restart, and the gate followed by a real app relaunch. No test installs a server upgrade.

The desktop self-update notice and its restart are proven in the real Electron app with the update runtime in its simulation mode, as the spec's Testing section directs. In that mode the runtime reports a downloaded update a few seconds after launch, with no network or ToDesktop build. The notice presents with the reported version, and pressing **Restart to update** reaches the main process. In test mode the main process records the restart instead of calling the runtime ([desktop updates](../arch/desktop/updates.md#Test hooks)). A gated app whose runtime reports a download shows the downloaded-update message and sends the same request.

What only the built app does is proven by the desktop product's [update check](./desktop-app.md#^desktop-ac-updates), which opens a candidate build on a real Mac with the runtime's simulated update: the notice presents the downloaded version, and **Restart to update** quits the app and opens it again. Downloading and installing a real release are the runtime's, which ToDesktop's smoke tests exercise before a build is released ([releases](../../specs/arch/desktop/distribution.md#^desktop-dist-release)). No Television check observes a real release downloading, the check the app makes when it starts, the install when the user quits without restarting, which is the runtime's unchanged default, or the case where a Mac app opened again before that installation finishes runs the earlier release. In the Electron gate journeys, a relaunch that reports a version meeting the requirement stands in for an installed update and passes the gate.

The Electron journeys control the shell's reported version through `TV_TEST_DESKTOP_APP_VERSION`, a declared mock of `app.getVersion()` whose real path the gate proof crosses unhooked. The production floor runs with no requirement override: a shell reporting `0.1.216` is gated. That floor gates every npm-installed shell, so the two recommendation walks set the declared `TV_TEST_REQUIRED_DESKTOP_VERSION` hook to `1.3.1`, under which a shell reporting `1.3.2`, a release of the npm package, passes the gate and receives the recommendation; that the production floor leaves the recommendation no client is the gate proof's floor contract. Version-comparison breadth remains in the [gate proof](../arch/updates/desktop-upgrade-gate.md#^updates-t-themes-desktop-floor). These tests install no npm package and do not establish that old binaries render the current interface.

Some promises order no test ([spec purposes](../../specs/arch/testing-policy.md#^spec-purposes)). Maintainers release the desktop app before they publish a release that raises the requirement, and the channel announces the release after that. Nothing checks that order ([release order](../../specs/arch/updates/desktop-upgrade-gate.md#^ops-release-order)), so no test observes that such a server is never installable before its desktop release. The publish workflow behavior the order relies on is covered by the [publish-workflow contract](../arch/updates/index.md#^updates-t-publish-order). That the app finds nothing to download between desktop releases, and that apps installed from npm never update themselves, follow from what Television releases and are not code a test can exercise. Channel fixtures and version hooks are declared below; channel publication is a separate release operation.

## Assertions

### Acceptance criteria

These are the behaviors a conformant implementation must exhibit, covered by tests that cite the anchored criteria where useful. They walk the spine end to end; the breadth behind them (validation permutations, failure injection) is owned by the arch specs under [arch/updates/index.md](../../specs/arch/updates/index.md), as are the sanctioned test hooks these criteria presuppose.

The update suite was authored with these criteria under the testing policy. Plain citations are policy-grade cited. The cross-release entrance contracts owned by [desktop upgrade architecture](../../specs/arch/updates/desktop-upgrade-gate.md#^pre-gate-handshake) compose with the real-Electron gate criteria.

The exact release version in update details is an authoring contract for Television's channel content, which the product renders verbatim. A browser acceptance fixture gives the channel document and authored markdown the same version and proves that the real channel-to-toast path preserves it; the [channel deployment runbook](../../specs/arch/updates/runbook-channel-deploy.md) governs the content chosen for each external deployment.

Shape declaration for every criterion below ([per the declaration schema](../../specs/arch/testing-policy.md#^declaration-schema)): each is an **acceptance test**, except [#^ac-desktop-self-update](#^ac-desktop-self-update), which cites the desktop product's update check. Boundaries: a really-running Television server driven over real HTTP and websockets; a real browser for browser behavior; the real Electron app (the `e2e:desktop` surface) for Electron behavior. Fixtures and hooks: a test-authored channel document served over real HTTP and reached via `TV_UPDATE_CHANNEL_URL` (with `TV_UPDATE_CHANNEL_POLL_INTERVAL_MS` for mid-run state changes); version stamps controlled via the `TV_TEST_*` hooks ([arch/updates/index.md#^updates-test-hooks](../arch/updates/index.md#^updates-test-hooks)); the developer marker via the spawned server's home directory — [#^ac-toast-dev-host](#^ac-toast-dev-host) sets `TV_UPDATE_CHANNEL_URL` like every criterion (the override is how tests reach controlled channel content, not part of what that walk proves; the no-override gating proof is [update-channel.md#^t-marked-host-polls](../arch/updates/update-channel.md#^t-marked-host-polls)). Mocks are minimized to none on every path, setup included. The browser walks use the testing policy's standing motion-disablement carve-out and forfeit motion, which no criterion here promises; the Electron walks likewise make no motion claim. Two additional declared exceptions are the test sink on [#^ac-telemetry](#^ac-telemetry) below and the desktop-version criteria's shell version, controlled via `TV_TEST_DESKTOP_APP_VERSION` — a declared mock of `app.getVersion()`, whose real path is proven unhooked by [desktop-upgrade-gate.md#^t-shell-version-param](../arch/updates/desktop-upgrade-gate.md#^t-shell-version-param). Individual criteria state only what differs. ^ac-declaration

The full update journey — a channel deploy, the toast, the user's agent upgrading the server, the reload, the gate, and the desktop app's own update — is deliberately proven as **three composed real spines** (toast, reload, gate) rather than one mega-test: their shared seam, a server restarting at a new version, is itself tested (^ac-reload-heals), so composition covers the journey without a test that shells out to npm. The desktop app's own update, from a gated app to one that passes the gate, is [#^ac-desktop-self-update](#^ac-desktop-self-update). A mocked end-to-end "full journey" test is a non-goal. The composed **browser** walk runs in both server auth modes — authless, and authed with a real bearer token from the store carried in the page connect URL and authenticating the socket for real, the token surviving the auto-reload; the update mechanisms sit outside the auth boundary today, and the authed walk is the standing defense for the day one of them stops being — *covered by both auth-mode rows in `packages/web/test/e2e/update-journey.spec.ts`, the restart-at-version cases cited above, and `packages/desktop/test/e2e/update-journey.spec.ts` “gate with channel instructions → upgrade-and-relaunch → normal boot with the toast”*. ^ac-composition

**Auto-reload**

- A connected client whose interface was built from an older release than the running server reloads itself when its connection (re)establishes, and after the reload runs the server's current interface — with no user-visible notice beyond the reload itself — *covered by `test/node/update-reload.e2e.test.ts` “heals a stale client: reconnect after a restart-at-B reloads into the B interface”*. ^ac-reload-heals
- A reload fetches the server's current interface even if the previous interface was cached: the interface entry document is always revalidated against the server — *covered by `test/node/update-reload.e2e.test.ts` “revalidates a cache-primed entry document: the reload fetches the current interface”*. ^ac-reload-fresh
- If the version mismatch persists after one reload, the client makes no further reload attempts and shows no UI for that server release in that tab session; a subsequent new server release triggers a fresh single attempt — *covered by `test/node/update-reload-guard.e2e.test.ts` “guards the loop: a persisting mismatch reloads exactly once, silently; a NEW release retries once”*. ^ac-reload-guard
- A client running a development build (no release version stamped) never auto-reloads, regardless of the server's version — *covered by `test/node/update-reload-guard.e2e.test.ts` “a development (0.0.0) bundle never auto-reloads, whatever the server version”*. ^ac-reload-dev

**Update toast and bell**

- With the channel advertising a version newer than the server's, every connected client (browser and desktop alike) shows the toast with the notice's markdown rendered as the interface renders markdown; links open externally — *covered by `packages/web/test/e2e/update-notification.01.spec.ts` “^ac-toast-shows: a newer channel version shows the rendered notice in a connected client” and the external-link path in `packages/desktop/test/e2e/update-notification.spec.ts`*. ^ac-toast-shows
- A channel fixture with release version `1.5.0` and authored markdown naming **Television 1.5.0** reaches a real browser through a really-running server and renders that exact version unchanged. The fixture and temporary server data are authored inputs; no mechanism is replaced. This path is shared with [product versioning](./versioning.md) — *covered by `packages/web/test/e2e/update-notification.01.spec.ts` “^ac-toast-shows: a newer channel version shows the rendered notice in a connected client”*. ^ac-toast-release-label
- With the channel advertising a version not newer than the server's (one representative walk: equal), a browser shows no toast and no bell; the equal-vs-older breadth is owned by [update-channel.md#^t-relay](../arch/updates/update-channel.md#^t-relay), while an independently qualifying desktop recommendation is [#^ac-desktop-rec](#^ac-desktop-rec)'s — *covered by `packages/web/test/e2e/update-notification.01.spec.ts` “^ac-toast-not-newer: an equal channel version shows no notice and no bell”*. ^ac-toast-not-newer
- A notice with a prompt shows the composed copy button with the surface's own label ([ui/app/update-notification/index.md#^un-copy-button](../../specs/ui/app/update-notification/index.md#^un-copy-button) — the channel's `promptButtonLabel` is not consumed); clicking it places the exact prompt text on the clipboard. A notice without a prompt shows no button — *covered by `packages/web/test/e2e/update-notification.01.spec.ts` “^ac-toast-copy: the copy button carries the surface's own label and places the prompt on the clipboard”; modern and plain-HTTP fallback breadth is [ui/app/copy-button/index.md#^cb-ac-clipboard](../ui/app/copy-button/index.md#^cb-ac-clipboard)*. ^ac-toast-copy
- Dismissing the toast hides it, and it does not auto-show again for that channel version across reloads and browser or desktop restarts; a strictly newer channel version shows a fresh toast — *covered by `packages/web/test/e2e/update-notification.01.spec.ts` “^ac-toast-dismiss: dismissal survives reload and profile reopen; a newer notice pops fresh” and `packages/desktop/test/e2e/update-notification.spec.ts` “^ac-toast-desktop: notice, external link, persistent dismissal, bell re-open, and clipboard copy in the real Electron app”*. ^ac-toast-dismiss
- While the channel advertises a version newer than the server's, the bell icon is visible in every connected client — including after the toast is dismissed — and offers no dismiss affordance; once no update applies (for example the server is upgraded to the announced release), the bell is gone — *covered by `packages/web/test/e2e/update-notification.02.spec.ts` “^ac-bell-visible: the bell shows while an update applies — dismissed included — and leaves when none does”*. ^ac-bell-visible
- Clicking the bell presents the toast again — including after a dismiss-forever — with its full content and working copy button — *covered by `packages/web/test/e2e/update-notification.02.spec.ts` “^ac-bell-refires: after dismiss-forever the bell re-presents the full notice with a working copy button”*. ^ac-bell-refires
- In the real Electron app, the essential toast mechanics hold as in the browser: the toast shows for a newer channel version, external links use the system handler, dismissal survives a profile restart, the bell re-opens the notice, and the copy button places the prompt on the clipboard. One combined walk on the `e2e:desktop` boundary suffices; the per-behavior breadth lives in the browser criteria above — *covered by `packages/desktop/test/e2e/update-notification.spec.ts` “^ac-toast-desktop: notice, external link, persistent dismissal, bell re-open, and clipboard copy in the real Electron app”*. ^ac-toast-desktop
- With the channel failing (one representative walk: unreachable), clients show no server-update toast, channel bell, or error; a previously fetched valid notice continues to apply. A qualifying desktop recommendation remains independent of that failure. The failure-mode breadth (timeout, non-200, malformed, invalid shape) is owned by [update-channel.md#^t-poll-failures](../arch/updates/update-channel.md#^t-poll-failures) — *covered by `packages/web/test/e2e/update-notification.02.spec.ts` “^ac-toast-silent-failure: the channel going unreachable is invisible — the last notice continues to apply”*. ^ac-toast-silent-failure
- On a server host with `~/.tv-developer` present, clients show the toast for a newer channel version exactly as on an unmarked host — the marker does not affect update notifications ([#^toast-dev-host](../../specs/product/update-notifications.md#^toast-dev-host)). This walk proves the marked-host product surface; polling without the URL override is [update-channel.md#^t-marked-host-polls](../arch/updates/update-channel.md#^t-marked-host-polls) — *covered by `packages/web/test/e2e/update-notification.02.spec.ts` “^ac-toast-dev-host: with ~/.tv-developer on the server host, the toast shows exactly as on an unmarked host”*. ^ac-toast-dev-host

**Desktop self-update notice**

- The real Electron app, launched with the update runtime's simulation flag and connected to a really-running server whose channel makes no server notice apply, presents the desktop self-update notice and the bell a few seconds after launch. The notice has its authored heading, the simulated version, which is the running app's version followed by `-simulated`, and **Restart to update** after Later. Reloading the page after the report presents the notice again, so a page loaded after the download learns of it. Pressing the restart button leaves the notice open with the button restarting, and the main process's restart log records exactly one request, for that version. Differences from [the declaration](#^ac-declaration): the simulation flag is the runtime's own; the restart log is the declared test-mode seam, which stands in for the runtime's restart ([desktop updates](../arch/desktop/updates.md#Test hooks)); and the shell version keeps the harness default — *covered by `packages/desktop/test/e2e/update-notification.spec.ts` “^ac-desktop-self-update-notice: the runtime's downloaded update presents the notice before and after a reload, and Restart to update reaches the main process”*. ^ac-desktop-self-update-notice

**Desktop upgrade recommendation**

Both recommendation criteria connect to a server whose required desktop version is staged at `1.3.1` through the declared `TV_TEST_REQUIRED_DESKTOP_VERSION` hook, because the production floor of `1.5.0` gates every app installed from npm, and the shell reports `1.3.2`, a release of the npm package, through the declared shell-version hook. They prove that the [current recommendation](../../specs/product/update-notifications.md#^desktop-rec-first-release) reaches an app installed from npm that passes the gate; that the production floor leaves it no client is the gate proof's floor contract.

- The real Electron app, connected with no applying server notice, reaches the normal interface and automatically presents the authored recommendation through the update notice. The rendered body contains its heading, the statement that this copy was installed with npm and receives no more updates, and the [installation steps](../../specs/product/update-notifications.md#^desktop-rec-markdown). Clicking its download link hands the authored download address to the desktop app's external-link handling. The notice shows [no copy button](../../specs/product/update-notifications.md#^desktop-rec-copy-prompt): Later is its only action. Dismissing the recommendation leaves the bell, prevents automatic presentation across a profile restart, and the bell re-presents it — *covered by `packages/desktop/test/e2e/update-notification.spec.ts` “^ac-desktop-rec: an npm-installed shell gets the recommendation with its download link, persistent dismissal and bell re-open”*. ^ac-desktop-rec
- In the real Electron app, when the same recommendation-eligible shell connects while a newer channel release makes a server-update toast apply, only the server toast appears. Dismissing it leaves the bell representing that toast, and clicking the bell re-presents the server body and copy-prompt control without revealing the desktop recommendation. This proves [the shared order](../../specs/product/update-notifications.md#^notice-precedence) for the recommendation — *covered by `packages/desktop/test/e2e/update-notification.spec.ts` “^ac-desktop-rec-precedence: a dismissed server notice keeps the bell and never reveals the recommendation”*. ^ac-desktop-rec-precedence

**Desktop app updates**

- **Acceptance — the desktop app's own update.** The [desktop app's updates](../../specs/product/update-notifications.md#^desktop-self-update) are accepted by the desktop product's [update check](./desktop-app.md#^desktop-ac-updates), which opens a candidate build on a real Mac with the runtime's simulated update. The app presents the desktop self-update notice with the simulated version, and pressing **Restart to update** quits the app and opens it again. Downloading a real release within ten minutes and installing it are the runtime's, left to ToDesktop's smoke tests before a release. The release that introduces the notice, 1.4.2, orders no test; review checks it. The notice and the restart request are also covered continuously by [#^ac-desktop-self-update-notice](#^ac-desktop-self-update-notice). The gated app's part of [the upgrade sequence](../../specs/product/update-notifications.md#^gate-sequencing) is composed. The update runtime starts in the main process before any page loads ([its start contract](../arch/desktop/updates.md#^desktop-updates-t-start)), and the gate is web content, so a gated app keeps checking for updates. [#^ac-gate-downloaded-update](#^ac-gate-downloaded-update) shows a gated app offering the restart once its download is reported. The Electron gate journeys show that a relaunch reporting a version that meets the requirement passes the gate. A run recorded by the pull request that moved the desktop app to ToDesktop observed a gated app download a release, install it on quit and pass the gate. ^ac-desktop-self-update

**Desktop upgrade gate**

- [Television 1.5's required desktop upgrade](../../specs/product/update-notifications.md#^gate-themes-release) is exercised in the real Electron app against a running server using the production required constant, with `TV_TEST_REQUIRED_DESKTOP_VERSION` absent. The server version uses the declared release-version hook; only the older shell version is supplied through `TV_TEST_DESKTOP_APP_VERSION`. A shell reporting `0.1.216` reaches only the blocking gate and built-in instructions, with no functional renderer request, recommendation or bell. Quit that app, then relaunch with the shell-version hook unset: the actual candidate shell reaches the normal interface without a gate. Whether that shell also receives the recommendation depends on the candidate's version and is not part of this criterion. This composes with [isolation's desktop escalation walk](../arch/artifact-frame/isolation.md#^iso-t-escalation-electron) for what the compatible shell keeps from artifact code. No desktop update is installed; the relaunch stands in for it — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-themes-desktop-required: the production floor gates an older shell and an unhooked compatible relaunch boots”*. ^ac-themes-desktop-required
- The real current Electron app, reporting a shell release older than its connected server's required desktop release through the declared version hook, stops at the sole blocking gate presentation with upgrade instructions rendered, and the normal application boot never starts. Server request observation begins before Electron launch: the complete record contains one permitted main-process `GET /desktop/connect-check` before `/events`, then no renderer-issued `/display`, channel, or artifact request; the desktop main process's own `GET /artifacts`, which [its partition reaper](../../specs/arch/desktop/artifact-partitions.md#^dp-reaper) sends whenever the server's page loads and which the boot barrier does not govern, is recorded apart and is the only other request the main process sends — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-gate-blocks + ^ac-gate-fallback: an older shell halts at the gate with the built-in instructions; no boot”*. ^ac-gate-blocks
- A desktop app that does not meet the gating condition (one representative walk: shell exactly at the requirement) reaches the permanent application shell with no gate; the exemption breadth (above the requirement, no requirement advertised, dev versions, browser) is owned by [desktop-upgrade-gate.md#^t-gate-decision](../arch/updates/desktop-upgrade-gate.md#^t-gate-decision) — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-gate-not-gated: a shell exactly at the requirement boots normally with no gate”*. ^ac-gate-not-gated
- The gate remains the sole application presentation across a top-level reload and an authenticated `/events` reconnect while the shell remains outdated, with no functional renderer request at any point; after a relaunch that reports a version meeting the requirement, standing in for an installed desktop update, the permanent application shell replaces it — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-gate-persists: the gate holds across reload and reconnect; upgrading and relaunching clears it”*. ^ac-gate-persists
- A gated desktop app shows no server-update toast, desktop self-update notice, desktop recommendation, or bell — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-gate-supersedes-toast: a gated app shows channel gate instructions but no server toast and no bell”, “^ac-gate-supersedes-toast: a recommendation-eligible gated app shows no recommendation and no bell” and the downloaded-update case cited at [#^ac-gate-downloaded-update](#^ac-gate-downloaded-update)*. ^ac-gate-supersedes-toast
- A browser client is never gated — *covered by `packages/web/test/e2e/gate-boot-barrier.spec.ts` “a browser client is never gated, whatever requirement the server advertises”*. ^ac-gate-desktop-only
- A gated desktop app with no channel available at all and no downloaded update still functions, rendering the built-in fallback (the gate surface's copy, [ui/app/desktop-upgrade-gate/index.md](../../specs/ui/app/desktop-upgrade-gate/index.md)), which gives the user the desktop app's download link and tells them to install the latest version — the spine walk for gate-without-channel; the instructions-selection breadth is [desktop-upgrade-gate.md#^t-gate-instructions](../arch/updates/desktop-upgrade-gate.md#^t-gate-instructions) — *covered by the combined block/fallback case cited at [#^ac-gate-blocks](#^ac-gate-blocks)*. ^ac-gate-fallback

- The real Electron app, reporting a shell release older than its connected server's required desktop release through the declared version hooks, and launched with the update runtime's simulation flag, stops at the gate. Once the runtime reports its download, the gate shows the authored downloaded-update message with **Restart to update**, and no server notice, desktop self-update notice, recommendation or bell appears. Pressing the button leaves it restarting, and the main process's restart log records exactly one request, for the simulated version. Differences from [the declaration](#^ac-declaration) are those of [#^ac-desktop-self-update-notice](#^ac-desktop-self-update-notice) — *covered by `packages/desktop/test/e2e/upgrade-gate.spec.ts` “^ac-gate-downloaded-update: a gated app whose runtime reports a download offers Restart to update, which reaches the main process”*. ^ac-gate-downloaded-update

Coverage relationship: an installed desktop shell must recognize the current server before any served-bundle acceptance path can apply. The architecture's [pre-page contracts and proofs](../../specs/arch/updates/desktop-upgrade-gate.md#^pre-gate-handshake) compose with the real-Electron block/fallback spine above, without a second full gate journey or an end-to-end test against a previously published package.
