# Sticky note template (UI) — proof

Proves [specs/ui/templates/sticky-note.mdx](../../../specs/ui/templates/sticky-note.mdx).

## Coverage model

Browser acceptance opens a Sticky note created through the real template path in a temporary serving home. The copied page runs in the production artifact sandbox and loads the served resource SDK on a plain-HTTP host other than `localhost`, using the shared template real-stack harness. Store changes cross real HTTP or WebSocket connections; administrative reads confirm saves. Fixtures are the bundled seed and authored note values written through production commands or APIs.

Pointer, keyboard, clipboard, selection, focus and scrolling run in a real browser. No case substitutes the DOM or SDK. Behavior tests use the standard CSS-motion override and forfeit motion. Conformance keeps CSS motion real and adds no stylesheet; conform settles animations for capture. Fault cases control the shared forwarding proxy or real saved files as declared below, without inventing store replies. Accessibility evidence covers roles, names, read-only state and live-region update order, not spoken output from every screen reader.

[Sticky note architecture](../../arch/templates/sticky-note.md) owns package contents, validation variations, exact save timing, write scope, confirmation ownership and reconnect decisions. These acceptance tests prove the user paths through those contracts with real timers and services. [Resource SDK](../../arch/resources/sdk.md) and [JSON store](../../arch/resources/json-store.md) proofs own transport, rollback and durability; these cases establish the response of the page.

One conformance file compares every exported [Sticky note story](../../../storybook/spec/templates/sticky-note/sticky-note.stories.ts), including unembedded exports, with the copied page served by a running Television server. Storybook is built from the same worktree. Comparisons use real Chromium, the complete `.sticky-note-page` root outside the app shell, matching viewport, theme and appearance, and completed story `play` setup. Both pages wait for their bundled Caveat font. Conformance proves appearance; the behavioral assertions prove the prose. The assertions below cite the behavior tests and story comparisons.

## Test hooks

The server receives the real built `sdkDir` allowed by [SDK packaging](../../../specs/arch/resources/sdk.md#^sdk-packaging); production resolves the same bundle from the installed package.

The shared forwarding proxy may delay initial resource messages, hold a page write or its confirmation, close a connection, and refuse reconnection until released. Production delivers normally. Passing messages are unchanged; real subscription, authorization, writes, rollback and reconnection still run. These controls establish particular timings, not all network schedules.

For a refused save, selective WebSocket buffering holds the access notification while forwarding the later real write rejection, then releases the notification. The server normally sends access first. This is a message-order mock, forfeiting ordinary access ordering to [access acceptance](#^sticky-note-ui-ac-access); it replaces neither authorization nor rollback. Reuse the proxy whose preservation and cleanup are checked by `packages/server/test/network-proxy.test.ts`, as in the [Checklist proof](./checklist.md#test-hooks).

Browser observation may record SDK events and DOM mutations without replacing handlers or changing rendered content. Clipboard fixtures are placed on the real clipboard and pasted with native input. Damaged-file cases stop the server before changing its real saved file and restart it through the existing server harness.

## Entry, editing, and keyboard

Unless stated otherwise, each acceptance uses the real browser/server/store boundary and fixtures above, with no mocks beyond the standard CSS-motion override.

- **Acceptance — new note and saving.** Under [A new note](../../../specs/ui/templates/sticky-note.mdx#a-new-note) and [Typing](../../../specs/ui/templates/sticky-note.mdx#typing), open the real Toolbox, observe that the Sticky note tile draws its supplied icon, and choose it. The artifact has an empty `text` seed, a 360-by-360 page using the shared full-screen default, and a transparent frame. Opening neither focuses nor selects the text box named `Note`, and writes nothing. Reach it with Tab and separately by clicking; type and observe the hint disappear. Pause while focus remains in the field and confirm the saved value through the API and reload. Make another edit and leave the field before the pause expires: saving starts on blur. Clear the text: the hint returns and the saved string is empty. Normal saving shows no message. [The architecture timing contract](../../arch/templates/sticky-note.md#^templates-sticky-note-t-saving) covers exact 400 ms boundaries; this real-time walk proves both triggers are wired, without adding an unstated timing tolerance. It also carries [independent asset delivery](../../arch/templates/sticky-note.md#^templates-sticky-note-t-delivery). *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “new Sticky note from Toolbox persists its seed, display, edits and independent assets”)*. ^sticky-note-ui-ac-new
- **Acceptance — native text editing.** Under [Typing](../../../specs/ui/templates/sticky-note.mdx#typing), Return and Shift-Return insert line breaks. Paste clipboard text containing spaces and blank lines at a real caret; the complete saved string preserves them as plain text. A clipboard fixture carrying both HTML and plain text inserts the plain-text representation. Select and copy part of the field, then undo a native text edit, observing the field and clipboard through browser facilities. Spellcheck is disabled. Extra root fields survive all saves under [write scope](../../arch/templates/sticky-note.md#^templates-sticky-note-t-write-scope). *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “real editing preserves line breaks, spaces, copying and native undo”)*. ^sticky-note-ui-ac-editing

## Live data and access

- **Acceptance — agent changes and two writers.** Under [Changes from elsewhere](../../../specs/ui/templates/sticky-note.mdx#changes-from-elsewhere), use spawned `tv resource json set --artifact <id> /text` commands to replace and clear text, then another real viewer to edit. Updates appear without reopening. While the first viewer has unsent typing, deliver a remote value: local text, caret/selection and scroll position remain unchanged. After the local pause or blur sends its save, subsequent SDK values appear unless newer typing is unsent. Deliver an unchanged value and check that selection stays put. Control the order of two real saves and read back the last stored complete string; both viewers settle on it, without merging text or replaying an earlier suppressed value. The [older-confirmation seam](../../arch/templates/sticky-note.md#^templates-sticky-note-t-confirmation) proves that an acknowledgement cannot erase newer typing. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “agent commands and two viewers preserve active typing and follow the latest stored write”)*. ^sticky-note-ui-ac-live
- **Acceptance — read-only and changed access.** Under [Read-only](../../../specs/ui/templates/sticky-note.mdx#read-only), open real populated and empty shares with `read` access. `Note` is exposed as a read-only text box; empty text has no typing hint, native selection and copying work, and input makes no writes. Agent edits update the page. Upgrade the same link through the server and save an edit; downgrade it while unsent typing exists: the draft is discarded, the latest saved text appears, and further input, blur and delay expiry start no save. Restore `read-write` access on the same link through the server and confirm editing returns without replaying the discarded draft; save a fresh edit. Finally revoke the link: the latest saved text remains visible and read-only. This follows the [share-link lifecycle](../../../specs/product/resources/resources.md#^rs-share); restoration is exercised before revocation. No access state is injected. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “real share access changes discard drafts and retain the latest saved read-only text”)*. ^sticky-note-ui-ac-access

## Loading, disconnection, and failed saves

- **Acceptance — first load.** Under [Opening a note](../../../specs/ui/templates/sticky-note.mdx#opening-a-note), hold the initial resource messages after loading the actual document and SDK. The `Loading` state has no editable text or loading message. Sever the resource connection and refuse reconnection: the page shows `Reconnecting…` through a status region and remains unavailable for editing. Restore the real connection; valid data and established write access permit typing without reopening. Observe the status region being established before its text is updated, as in Checklist. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “first load waits for readable data and access and announces disconnection before recovering”)*. ^sticky-note-ui-ac-loading
- **Acceptance — offline draft and reconnect.** Under [Saving](../../../specs/ui/templates/sticky-note.mdx#saving), sever an established editable connection and refuse new connections. `Reconnecting…` appears in the status region and typing still changes the note. Several edits retain the latest text without making disconnected write calls. Another real client changes the store. Restore connectivity: the retained text stays visible through the fresh read and is saved after the access/read checks and pause or blur condition described in [architecture](../../arch/templates/sticky-note.md#^templates-sticky-note-t-reconnect). Include a save in flight when the connection closes, so real SDK rollback cannot erase the retained draft. With no draft, reconnect displays the latest remote text. Repeat a disconnect on a read-only share: it stays read-only and input starts no writes. No normal-save message appears on recovery. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “offline typing survives rollback and saves after reconnect checks”; “read-only disconnection stays read-only and reconnect without a draft shows current text”)*. ^sticky-note-ui-ac-offline
- **Acceptance — reload and close lose unsaved text.** Under [Saving](../../../specs/ui/templates/sticky-note.mdx#saving), disconnect a previously editable note and type a draft wholly while offline, so none of it has been sent. Reload before reconnection, then reconnect: only the last stored text appears and no draft is saved. Repeat by closing the page and opening the same artifact in a new page. This proves the in-memory lifetime without assuming the outcome of a write sent before disconnection. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “reloading or closing an offline note loses its unsent draft”)*. ^sticky-note-ui-ac-draft-lifetime
- **Acceptance — refused save and status priority.** Under [Saving](../../../specs/ui/templates/sticky-note.mdx#saving), hold a real save from a read-write share and its access notification, downgrade access through the server, and release the write for real rejection. Type a newer unsent edit before rejection arrives. The note drops both drafts and displays the SDK rollback value, even while focused, with `Couldn't save that change.` in the established status region. Observe the message disappearing after a few seconds without fixing an unspecified exact duration. In another pass, disconnect while the failure message is visible: `Reconnecting…` takes precedence. Release access messages and restore access/connectivity; a fresh edit saves, with no replay of rejected typing. Selective buffering forfeits ordinary message order as declared above. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “a genuinely refused save discards newer typing and announces rollback with reconnect priority”)*. ^sticky-note-ui-ac-save-failure

## Unreadable data and recovery

- **Acceptance — invalid or missing value.** Under [Data the page cannot read](../../../specs/ui/templates/sticky-note.mdx#data-the-page-cannot-read), replace the root with an invalid value through the real API while a local edit is waiting to save. An alert replaces the text box with `This note can't be shown` and the guidance shown by `Unreadable`; the unsent edit is discarded. Input, blur and the pending delay cannot write or repair the bad value. Repair through the API: the note reappears without reopening and fresh typing saves, while the discarded edit never returns. Repeat with a missing root and on initial load. Disconnect while the alert is visible to reach `UnreadableDisconnected`, then restore connectivity and repair. Observe an exposed alert and its content; conformance owns its appearance. [Validation contracts](../../arch/templates/sticky-note.md#^templates-sticky-note-t-validity) cover the remaining type variations. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “unreadable data discards pending typing and recovers without reopening”)*. ^sticky-note-ui-ac-invalid
- **Acceptance — saved data unavailable.** Under [Data the page cannot read](../../../specs/ui/templates/sticky-note.mdx#data-the-page-cannot-read) and [resource recovery](../../../specs/arch/resources/index.md#^rs-storage), stop the server, damage the actual store file with invalid JSON, and restart on the same home. The open note receives a real unavailable error, shows the same noneditable alert and leaves the damaged bytes untouched. Keep the page open, stop the server, repair the file and restart: the note reconnects and recovers without reload. No storage operation or error response is fabricated. *(policy-grade tests: `packages/web/test/e2e/template-sticky-note-real-stack.test.ts`, “damaged saved bytes show the alert and recover after repair and restart”)*. ^sticky-note-ui-ac-unavailable
