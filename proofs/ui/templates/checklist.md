# Checklist template (UI) — proof

Proves [specs/ui/templates/checklist.mdx](../../../specs/ui/templates/checklist.mdx).

## Coverage model

Browser acceptance opens a Checklist made by the real template-creation path in a temporary serving home. The copied page runs in the production artifact sandbox and loads the served resource SDK on a plain-HTTP host other than `localhost`. Store changes cross real HTTP or WebSocket connections into the real store; administrative reads confirm saves. Fixtures are the bundled seed and authored checklist values, written through production commands or APIs.

Real pointer, keyboard, selection, clipboard, focus, and scrolling behavior matter here, so no case uses a mocked DOM or a replacement SDK. Behavior tests use the standard CSS-motion override and forfeit motion. Conformance uses real CSS motion with no injected stylesheet; conform settles animations when capturing the pages. Fault cases control a forwarding proxy or real saved files as declared below; none fabricates a store reply. The tests observe state transitions rather than sleeping. Accessibility observations cover exposed roles, names, focus, and live-region update order, without claiming spoken output from every screen reader.

[The Checklist architecture proof](../../arch/templates/checklist.md) owns validity and ordering variations, write scope, and renumbering transactions. This proof walks the user paths that consume those contracts. [Resource SDK coverage](../../arch/resources/sdk.md) and [JSON store coverage](../../arch/resources/json-store.md) own connection, rollback, and storage mechanisms; the cases here prove the page responds to them.

[Conformance](../../../specs/spec-ui.md#conformance) compares every exported [Checklist story](../../../storybook/spec/templates/checklist/checklist.stories.ts) with production in the same state, including their args, globals, viewport parameters, and deterministic focus/selection `play` setup. This includes exports not embedded in the MDX page. Conformance runs in real Chromium against the Storybook built from this worktree and the copied artifact page served by a running Television server through the forwarding proxy declared under Test hooks. It compares `.checklist-page`, outside the app shell, at the viewport and light or dark appearance declared by the story. No markup or styles are added to production. Conformance establishes what each state renders; browser assertions establish behavior.

The assertions below name the shipped model contracts and real-browser tests. The stories remain design authority; the tests supply implementation evidence.

## Test hooks

The server receives its real built `sdkDir`, as allowed by [SDK packaging](../../../specs/arch/resources/sdk.md#^sdk-packaging); production resolves the same bundle from the installed package.

A forwarding proxy may delay the first resource response, hold a page write, close the page connection, and refuse new connections until released. Production has no such hold. Messages that pass are unchanged: the SDK and server still perform subscription, authorization, writes, rollback, and reconnect. This controls fault timing and does not prove behavior under every network schedule.

The refused-save case additionally requires selective WebSocket message buffering: hold the access notification while forwarding the later write rejection on the same connection, then release the notification. The server normally sends the notification first; the forwarding proxy’s per-connection server-message predicate holds only the notification. `packages/server/test/network-proxy.test.ts` checks frame preservation, release and disconnect cleanup. It preserves message contents, authorization, and rollback, but forfeits production message order; [access-change acceptance](#^checklist-ui-ac-access) covers normal delivery.

Platform contract cases supply the platform classification to the production shortcut decision; the browser seam uses actual host detection. This forfeits non-host operating-system input delivery, as required by [platform coverage policy](../../../specs/arch/testing-policy.md#^platform-breadth).

## Entry, editing, and keyboard

Unless an assertion says otherwise, each acceptance below uses the browser/server/store boundary and fixtures described above, with no mocks beyond the CSS-motion override.

- **Acceptance — new checklist.** Under [A new checklist](../../../specs/ui/templates/checklist.mdx#a-new-checklist), choose the installed Checklist in the real Toolbox, whose tile shows the Checklist's own icon. The new artifact opens with title `Checklist`, no items, and focus in the add field. Its persisted seed and page display values are the ones checked by [the package contract](../../arch/templates/checklist.md#^templates-checklist-t-package); the created page is 640 by 800 reference pixels and uses the shared full-screen default. Type an item and press Return: it is stored not done at the end, the add field clears and retains focus, and a reload shows the saved item. Return on empty or whitespace-only add input writes nothing. Proves [Adding an item](../../../specs/ui/templates/checklist.mdx#adding-an-item) as well. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “new Checklist from the Toolbox persists its seed, display, additions and independent assets”)* ^checklist-ui-ac-new
- **Acceptance — title and entry into the list.** Under [The title](../../../specs/ui/templates/checklist.mdx#the-title), clicking the title places a caret; typed changes reach `title` before blur. Clearing it leaves an empty stored string and shows the `Untitled` placeholder, not a stored replacement title. A real multiline paste joins lines with spaces. Return and Shift-Return each add an empty first item and focus it without inserting a newline into the title; leaving that item empty removes it. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “title saves before blur, preserves empty title, joins pasted lines and enters the list”; “Return focuses the optimistic row before an ordinary or transaction acknowledgement”)* ^checklist-ui-ac-title
- **Acceptance — item editing and completion.** Under [Items](../../../specs/ui/templates/checklist.mdx#items), clicking a box toggles its stored done state without moving the row; clicking text permits editing and saves before blur, preserving spaces. Editing a done item retains its done state. Return and Shift-Return create an empty item immediately below and move the caret into it without adding a text newline; leaving an empty or whitespace-only item removes it. Agent-authored line breaks display as spaces without a write merely from rendering. The page offers a flat list, no nesting action and no clear-done action. Within an active field, native browser undo undoes a text edit. Conformance covers done styling and the caret-only editing treatment. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “items save complete objects, retain whitespace and order, insert rows and keep native undo”; “Return focuses the optimistic row before an ordinary or transaction acknowledgement”)* ^checklist-ui-ac-items
- **Acceptance — navigation and empty Backspace.** Under [Items](../../../specs/ui/templates/checklist.mdx#items), use short and wrapped item fixtures. Backspace in an empty item with a predecessor removes it and puts the caret at the predecessor end; with no predecessor, including a sole empty item, it neither removes nor moves focus. Up on the first visual line moves to the preceding item or title; Down on the last visual line moves to the next item or add field. On interior visual lines, the browser keeps navigation within the field. Observe real selection and focus, not dispatched synthetic key events. *(policy-grade tests: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “real keys navigate visual lines, handle empty Backspace and toggle without moving the caret” and “pointer positions on either side of a soft wrap preserve visual-line navigation”)* ^checklist-ui-ac-navigation
- **Contract — completion shortcut.** Under [Items](../../../specs/ui/templates/checklist.mdx#items), production shortcut handling selects Cmd-Return on macOS and Ctrl-Return elsewhere. Authored platform and key-event values exercise both branches; the supplied platform forfeits native input and detection to the following seam. *(policy-grade test: `packages/server/test/checklist-model.test.ts`, “Checklist completion shortcut”)* ^checklist-ui-t-shortcut
- **Seam — completion shortcut delivery.** On the actual browser host, press the appropriate shortcut while editing a real stored item. Under [Items](../../../specs/ui/templates/checklist.mdx#items), host detection and keyboard input reach the production handler and SDK: done toggles, the item stays in place, and the selection/caret stays where it was. No platform mock is used here; coverage does not claim a run on another OS. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “real keys navigate visual lines, handle empty Backspace and toggle without moving the caret”)* ^checklist-ui-t-shortcut-delivery
- **Acceptance — multiline paste.** Under [Items](../../../specs/ui/templates/checklist.mdx#items), paste clipboard text with several lines and blank lines into the add field: nonblank lines append in order, one item each. Paste into the middle of an existing item: the first nonblank line is inserted at the caret, preserving surrounding text, later nonblank lines become successive items below, and the caret ends at the last inserted item. Read back the real store to check text and order. The clipboard is populated with fixture text and pasted through the browser, not a substituted clipboard handler. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “real clipboard paste appends lines and inserts at an item caret in order”)* ^checklist-ui-ac-paste
- **Acceptance — removal and accessible controls.** Under [Items](../../../specs/ui/templates/checklist.mdx#items), the items are exposed as a list. Hover and editing expose the remove button. Tab reaches each checkbox and remove button, named after its item as the prose states, including `Empty item`; the title is a text box named `Title`, every item text box is named `Item N` for its current one-based position, and the add field is named `Add an item`. Assert the item names again after removal changes the positions. Space toggles the focused checkbox and persists it. Removing a middle row focuses the next text, removing the final row focuses the preceding text, and removing the sole row focuses the add field. There is no page action to restore a removed row. Conformance covers focus-ring appearance; real keyboard focus and activation are asserted here. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “accessible checkbox and remove controls work by keyboard and preserve removal focus”)* ^checklist-ui-ac-remove

## Live data and access

- **Acceptance — agent changes and two writers.** Under [Changes from elsewhere](../../../specs/ui/templates/checklist.mdx#changes-from-elsewhere), use a second real viewer and spawned `tv resource json` commands to change the title, push items with orders, replace complete items, and remove keys. The first page updates without reloading; other rows and the title update while an item editor remains active. A remote write to that active item does not replace the text on screen. With controlled sequential writes from both viewers, the last confirmed write is stored; leaving the editor shows that stored value. This also exercises the command forms taught by [the README](../../arch/templates/checklist.md#^templates-checklist-t-readme). *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “spawned agent commands and two viewers update live while preserving active text until blur”)* ^checklist-ui-ac-live
- **Acceptance — removal during editing.** Under [Changes from elsewhere](../../../specs/ui/templates/checklist.mdx#changes-from-elsewhere), remove the active item through the real administrative API. It remains in the editor. Continuing to type, and separately leaving it with nonempty text, restores the complete object at the same key with its order and done state. Leaving it empty keeps it removed. Other items remain unchanged. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “remote removal restores active nonempty drafts on typing or blur and leaves empty drafts removed”)* ^checklist-ui-ac-remote-remove
- **Acceptance — read-only and access changes.** Under [Read-only](../../../specs/ui/templates/checklist.mdx#read-only), open a real read-only share link with populated and empty data: title/items are text, boxes cannot toggle, add and remove controls are absent, and the empty view says `No items`. Agent writes still update it. Change that same link to read-write through the server: editing becomes available and a save succeeds; change it back while an editor is active: further input starts no writes. Revoke the link: after the SDK reports null access, the page retains its last view read-only. This crosses real `getAccess`/`onAccessChanged` delivery, with no injected access state. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “real share access upgrades, downgrades and revocation retain a read-only view”)* ^checklist-ui-ac-access

## Loading, disconnection, and failed saves

- **Acceptance — first load.** Under [Opening a checklist](../../../specs/ui/templates/checklist.mdx#opening-a-checklist) and [Saving](../../../specs/ui/templates/checklist.mdx#saving), hold the initial resource response at the forwarding proxy after the actual document and SDK load. Before data arrives, there is no title, list, add field, or loading text. Close the connection before releasing data and refuse reconnections: the otherwise blank page shows `Reconnecting…` in the bottom strip with `role="status"`. Observe that the status region is in place before the page inserts the message. Restore the real connection: the current checklist appears without a page reload. The proxy changes timing/reachability only, with no fake snapshot. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “first load stays blank, announces disconnection only after mounting its status and recovers”)* ^checklist-ui-ac-loading
- **Acceptance — disconnection and recovery.** Under [Saving](../../../specs/ui/templates/checklist.mdx#saving), sever an established page connection and refuse new ones through the proxy. The checklist stays visible and becomes read-only with `Reconnecting…`. Input while disconnected changes no stored data. Another real client edits the store; restore connectivity and observe current data, removal of the strip, and resumed editing without reload. Repeat the disconnect over the error page to cover the `UnreadableDisconnected` pose; it retains the error and shows the same strip. The loading case above covers the other underlying page state. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “disconnect retains valid or unreadable views and reconnect restores current editable data”)* ^checklist-ui-ac-reconnect
- **Acceptance — refused save.** Under [Saving](../../../specs/ui/templates/checklist.mdx#saving), open a read-write share and hold a page write plus the later access notification using the selective WebSocket control declared above. Downgrade the link through the real server before releasing the write, so real authorization refuses a change the page already showed. The affected value rolls back to the stored value, including when its text editor still has focus, and the bottom strip with `role="status"` says `Couldn't save that change.` then disappears after a few seconds. Observe that the status region is in place before the message is inserted, and observe disappearance without pinning an unstated exact duration. Release the access notification and restore write access through the server; a later edit saves. The proxy forfeits production message order and uncontrolled timing, not authorization or rollback. The same strip is available over a blank or error page; [the stories](../../../storybook/spec/templates/checklist/checklist.stories.ts) and stylesheet govern that shared placement. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “a genuinely refused save rolls back the focused editor and dismisses its mounted status”; “a refused title save does not retain an unrelated item named undefined”)* ^checklist-ui-ac-save-failure

## Unreadable data and recovery

- **Acceptance — invalid or missing value.** Under [Data the page cannot read](../../../specs/ui/templates/checklist.mdx#data-the-page-cannot-read), open a checklist with valid data, then write a value containing one malformed item through the real administrative API. The whole checklist is replaced by an alert containing the warning icon, `This checklist can't be shown`, and the specified guidance text; no title or surviving good row remains editable. The malformed value stays unchanged. Repair it through the API and observe the checklist return live. Remove the root value and repeat recovery; an initial load with invalid or missing data reaches the same error, without seeding or repairing it. [Validity contracts](../../arch/templates/checklist.md#^templates-checklist-t-validity) cover the other malformed inputs; [the write-guard seam](../../arch/templates/checklist.md#^templates-checklist-t-invalid-guard) covers pending input. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “malformed and missing values replace the whole checklist with an alert without repair”)* ^checklist-ui-ac-invalid
- **Acceptance — saved data unavailable.** Under [Data the page cannot read](../../../specs/ui/templates/checklist.mdx#data-the-page-cannot-read), stop the server, replace the store content file with invalid JSON bytes, and start the server on that home. The copied page receives a real `unavailable` error and shows the same noneditable alert, leaving the damaged bytes untouched. Keep the page open, stop the server, repair the file with a valid checklist, and restart: the page reconnects and recovers without reload. This follows [resource recovery rules](../../../specs/arch/resources/index.md#^rs-storage); it does not expect the server to watch files edited behind its back. No storage or error response is mocked. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “real damaged saved bytes show unavailable and recover after repair and server restart”)* ^checklist-ui-ac-unavailable
