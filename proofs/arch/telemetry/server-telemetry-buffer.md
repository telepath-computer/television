# Server telemetry integration (buffer) — proof

Proves [specs/arch/telemetry/server-telemetry-buffer.md](../../../specs/arch/telemetry/server-telemetry-buffer.md).

## Coverage model

The module proofs named below cover the imposed handoffs; direct server obligations use real HTTP, websocket, filesystem, and auth. The [store theme/appearance contract](../../../specs/arch/telemetry/server-telemetry-buffer.md#^store-theme-telemetry) is covered by the emitter's [committed-action seam](./emitters.md#^t-theme-settings-actions). The [bootstrap settings reader](../../../specs/arch/telemetry/server-telemetry-buffer.md#^bootstrap-theme-telemetry) is covered by its [boot/activity/control snapshot seams](./emitters.md#^t-theme-settings-refresh). Those assertions use a recording sink and forfeit only delivery to the live PostHog proof; they do not replace the store reader. No duplicate test is ordered here for those handoffs. Remaining direct obligations and their fixtures are declared below, following this spec's compositional testing directive.

## Assertions

### Test assertions

Most imposed handoffs are proved by the telemetry module that consumes them: event-stream activity by [client.md#^t-activity-fires](./client.md#^t-activity-fires) and [the emitter session seam](./emitters.md#^t-session-stamp); generic client signals by [client-signals.md#^t-signal-forwarding](./client-signals.md#^t-signal-forwarding); store hooks by [emitters.md#^t-emit-hooks](./emitters.md#^t-emit-hooks); lifecycle bootstrap by [identity.md#^t-boot-derivation](./identity.md#^t-boot-derivation) and [product/telemetry.md#^ac-persist-auth-install](../../product/telemetry.md#^ac-persist-auth-install); and control/status behavior by [identity.md#^t-optout-event](./identity.md#^t-optout-event) and [identity.md#^tel-t-unavailable](./identity.md#^tel-t-unavailable). The server-module obligations stated directly here use a real `ServerStore` or listening authenticated `Server` over a temporary home. Authored persisted marker files are fixtures; there are no server, filesystem, route, or auth mocks.

- **Seam** (real metadata-bearing `/events` websocket → session runtime): a correct fixed activity signal reaches session capture, while a mismatched client id, an extra payload field, or a socket without client metadata produces no event or session — *(covered by inherited tests: the three activity cases in `packages/server/test/telemetry-event-stream.test.ts`, with the no-metadata case minimally table-driven to add mismatched-id and extra-field messages)*. ^tel-t-activity-validation
- **Contract** (served-evidence classifier at `ServerStore` construction): empty storage, token plus empty storage directories, and telemetry state alone remain fresh; display state, either onboarding state path, populated current or legacy channel metadata, artifact metadata, theme content, and agent-authored artifact content are existing served data; constructing the store twice changes fresh to existing — *(covered by inherited tests: `packages/server/test/server-store-bootstrap.test.ts` “reports whether this bootstrap created the Television data directory structure”, all seven standing “served-evidence dataDirCreated classification” cases, and “does not count a telemetry-only state file as an existing Television data directory”, with that matrix minimally extended for the legacy-channel, theme-content, and agent-artifact directories)*. ^tel-t-data-dir-created
- **Contract** (the same served-evidence classifier at `ServerStore` construction, over a real temporary home; no mocks): a home holding only `config.json`, and a home holding `config.json` with a token and empty storage directories, remain fresh: a serving store constructed over either home captures `dataDirCreated: true` — *(policy-grade test: `packages/server/test/server-store-bootstrap.test.ts` "classifies a home holding only its config file, or the config file with a token and empty directories, as fresh")*. ^tel-t-config-not-evidence
- **Acceptance** (outer boundary: unauthenticated real HTTP requests against a token-requiring running server): `GET /telemetry`, `POST /telemetry/enable`, and `POST /telemetry/disable` are rejected by the standard auth policy without changing telemetry state or emitting an opt-out event — *(covered by `packages/server/test/telemetry-control.test.ts` “rejects unauthenticated telemetry controls without changing state, the runtime gate, or emitted events”)*. ^tel-t-route-auth
