*How the desktop upgrade gate is proven: connect-check contracts over real HTTP, decision and selection contracts with the production thresholds, gate-screen contracts with a stand-in for the update operations, a real-browser boot barrier, and the product's real-Electron gate walks, with maintainer release order left untested.*

# Desktop upgrade gate — proof

Proves [specs/arch/updates/desktop-upgrade-gate.md](../../../specs/arch/updates/desktop-upgrade-gate.md).

## Coverage model

Contract tests cover version comparison, source selection, development exemptions, message selection and notice precedence. The halt-or-boot decision takes only the page parameters and the server's status as inputs, so no bridge operation can change it. The gate screen's use of the update operations is covered with a stand-in bridge, as the spec's Testing section allows: which of the three messages it shows, its switch to the downloaded-update message while shown, and its restart action. The release-floor contract imports the production required and recommended constants and exercises the real status builder and gate and recommendation decisions with authored inputs; it does not replace those decisions. With the floor at `1.5.0` and the recommendation at `1.4.0`, it shows that every earlier shell gates, apps installed from npm and earlier downloaded apps alike, and that shells at `1.5.0` or later pass with no recommendation. Real websocket/browser coverage proves the boot barrier, while [product acceptance](../../product/update-notifications.md#^ac-themes-desktop-required) exercises the current floor through Electron and a server with no required-version override. The shell-version hook lets one installed test shell represent an older version and forfeits actual old-binary execution to the separate connect contracts and previously recorded compatibility analysis. The unhooked shell-version seam and compatible relaunch cover the real version source.

A requirement is the release its pull request ships in, and the desktop release built from that release meets it, as does any later desktop release ([bumping the requirement](../../../specs/arch/updates/desktop-upgrade-gate.md#^ops-bump)). The decision contract's case for a shell above the requirement proves that a later release passes. The rest of the operations order no test ([spec purposes](../../../specs/arch/testing-policy.md#^spec-purposes)): maintainers keep the [release order](../../../specs/arch/updates/desktop-upgrade-gate.md#^ops-release-order), pausing npm publishing until the desktop release is out, and nothing checks that order. The publish workflow behavior it relies on, the pause file and publishing the version the pull request set, is covered by the [publish-workflow contract](./index.md#^updates-t-publish-order). What the order means for running apps composes from proven parts. The product's gate walks, which run in Electron on Linux, show that a shell below the requirement stays gated across reloads and reconnects. A gated app leaves the gate through its own update, whose gated part [the product's self-update acceptance](../../product/update-notifications.md#^ac-desktop-self-update) composes. The update runtime starts in the main process before any page loads ([its start contract](../desktop/updates.md#^desktop-updates-t-start)), and the gate is web content, so a gated app keeps checking for updates. [Gated downloaded-update acceptance](../../product/update-notifications.md#^ac-gate-downloaded-update) shows a gated real Electron app whose runtime reports a download changing to the downloaded-update message and sending its restart. The Electron gate journeys show that a relaunch reporting a version that meets the requirement passes the gate. A run recorded by the pull request that moved the desktop app to ToDesktop observed both from a gated app.

The native menu remains usable while the served gate halts the app. [Desktop product acceptance](../../product/desktop-app.md#^desktop-ac-gate-disconnect) proves [Disconnect from Server on the gate](../../../specs/arch/updates/desktop-upgrade-gate.md#^gate-screen); connection architecture owns its deletion and cancellation breadth. The [app proof](../../ui/app/index.md#^ap-ac-gate-uncovered) proves that a later auth rejection cannot replace a displayed gate. These compose with the existing boot-barrier and gate-lifetime evidence rather than repeating version permutations.

## Test hooks


Per [the domain's test-hook posture](./index.md#^updates-test-hooks). The gate acceptance criteria need both sides of the comparison under test control:

- **`TV_TEST_REQUIRED_DESKTOP_VERSION`** (server) — overrides the required desktop version the server advertises. Same inertness mechanism as `TV_TEST_VERSION` ([version-advertisement.md#^hook-server-version](./version-advertisement.md#^hook-server-version)): consulted only when `__TV_VERSION__` is undefined, so it exists only in from-source runs and is structurally absent from release builds. ^hook-required-version
- **`TV_TEST_DESKTOP_APP_VERSION`** (shell) — when the shell runs with `TV_TEST_MODE=true` (the desktop e2e harness's existing test gate, already used to stub external-URL opens in `packages/desktop/src/index.ts`), it reports this value instead of `app.getVersion()`. The main process resolves the shell version once per connect attempt and uses that value for both the connect-check query and the remote page's `desktopAppVersion` parameter. The [`e2e:desktop` harness](../../../specs/arch/desktop/e2e-harness.md#^desktop-e2e-launch-contract) launches Electron via Playwright with a controlled environment, so setting both version variables is one `launchDesktop` option. Inert in normal use because it requires the compound gate — `TV_TEST_MODE` plus the variable — matching the shell's existing test-seam precedent. Under the testing policy's [Mocking policy](../../../specs/arch/testing-policy.md#Mocking policy), this replacement is a mock; [Testing](../../../specs/arch/updates/desktop-upgrade-gate.md#Testing) requires a separate real Electron crossing of `app.getVersion()` with the hook unset. ^hook-shell-version

## Assertions

### Test assertions

- **Contract** (server producer side of the `/desktop/connect-check` HTTP seam; a real HTTP client talks to normally composed authless and token-requiring servers; authored query values cover present, absent, and malformed informational versions; no mocks or test hooks): authless and valid-bearer requests receive `200` with a JSON object containing `product: "television"`, missing/invalid credentials receive `401`, and query content never changes the result; additional response members are permitted — *covered by both cases under `packages/server/test/desktop-connect-check.test.ts` “GET /desktop/connect-check”*. ^updates-t-preflight-server-contract
- **Contract** (desktop reader side of the same HTTP seam; a recording HTTP peer returns authored statuses and bodies — a declared mock forfeiting real server authentication and emission to the sibling producer contract): the shell sends exactly one `GET /desktop/connect-check` with its informational version and optional bearer token, accepts `200` with the product marker alone or with unknown members, rejects non-`200`, non-JSON, non-object bodies including `null` and arrays, and missing/wrong-marker responses, and never requests `/display` — *covered by all cases under `packages/desktop/test/connect-preflight.test.ts` “preflightConnection desktop connect check”*. ^updates-t-connect-check-reader-contract
- **Contract** (main-process connection boundary; `fetch`, Electron window and storage are recording peers, forfeiting real HTTP/IPC/disk/navigation to [desktop connection acceptance](../../product/desktop-app.md#^desktop-ac-connect-link)): under [the desktop connect check](../../../specs/arch/updates/desktop-upgrade-gate.md#^pre-gate-desktop), before success the shell neither saves the submitted link nor loads the remote page; marker success permits saving its normalized origin/token and, after the setup success presentation, loading the root with Electron mode, token when present, and the same resolved version used by the check. Failure saves nothing and makes no remote navigation. A server requiring a newer app still passes a successful identity check; its served page decides the gate. The local renderer's completion/cancellation ordering belongs to [product connection acceptance](../../product/desktop-app.md#^desktop-ac-connect-link) and [disconnect](../desktop/connect-flow.md#^desktop-t-disconnect). *(covered by `packages/desktop/test/connect-flow.test.ts` “starts without a record in setup and saves a checked link before the Connected handoff” and “keeps rejected setup links inline and a tokenless retry carries no previous token”; supplemented by inherited tests: `packages/desktop/test/main.test.ts` “connect IPC accepts additive connect-check JSON, saves normalized fields, and loads the versioned remote URL” and “connect IPC does not save submitted fields or loadURL when the connect check fails”)* ^updates-t-preflight-desktop-contract
- **Contract** (legacy `/display` producer side; a real HTTP client with a valid bearer token talks to a normally composed server, then the verbatim predicate from published `0.1.206` revision `244b0b833` is applied as an authored fixture; no mocks or test hooks): focused and empty display states both satisfy the [bounded compatibility response](../../../specs/arch/updates/desktop-upgrade-gate.md#^pre-gate-legacy-display) — *covered by `packages/server/test/desktop-connect-check.test.ts` “published 0.1.206 /display identity predicate” → “accepts focused and empty display states”; retire this assertion under [the cutoff procedure](../../../specs/arch/updates/desktop-upgrade-gate.md#^pre-gate-legacy-cutoff)*. ^updates-t-legacy-connect-check-contract
