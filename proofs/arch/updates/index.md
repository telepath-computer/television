# Updates architecture — proof

Proves [specs/arch/updates/index.md](../../../specs/arch/updates/index.md).

## Coverage model

Pure contracts prove what counts as a release version, the two comparisons, and how a server resolves its version from the build stamp. Repository contracts read the manifests and the committed publish workflow directly: every workspace, including the private desktop workspace, carries the root version; the workflow publishes nothing while `.github/PAUSE_PUBLISH` is present or its commit is no longer the tip of `main`; it publishes the manifests' version when npm does not have it and otherwise raises the patch number; and it versions every workspace, builds, then publishes the CLI package. The workflow's two `npm version` commands are also run for real on a temporary fixture monorepo, which proves what each does to the manifests. That the workflow chooses the right one is read from the workflow text, and only a real publish runs the choice against the npm registry.

The npm publishing eligibility, queue settings and action pins are checked as the YAML contract sent to GitHub, without mocking or reimplementing its expression evaluator. These tests do not exercise GitHub authorization or scheduling, or publish to npm. GitHub first evaluates the publishing configuration on a publish workflow run after merge; a maintainer checks that run. SHA syntax tests do not establish that an action commit exists in its upstream repository.

What users receive is accepted elsewhere: [product versioning](../../product/versioning.md#^versioning-ac-release-identity) compares the packed CLI package with the desktop upload directory built from the same commit, [version advertisement](./version-advertisement.md#^t-web-stamp) proves the web stamp, and [product CLI](../../product/cli.md#^cli-ac-help-version) proves the packaged `tv --version`.

The [publication order](../../../specs/arch/updates/index.md#^updates-publication-order) orders no test ([spec purposes](../../../specs/arch/testing-policy.md#^spec-purposes)). A desktop release usually follows a publish when a maintainer decides to make one. For a release that raises the required desktop version, maintainers pause publishing until the desktop release that meets it is out, and deploy the channel notice after the publish; the gate's operations say that nothing checks that order ([release order](../../../specs/arch/updates/desktop-upgrade-gate.md#^ops-release-order)). The workflow behavior the order relies on, the pause file and publishing a version npm does not have yet, is covered by the contract below.

## Test hooks


Most of this domain's acceptance criteria can only run end-to-end against versions and channel content the test controls, so each module spec includes a **Test hooks** section defining the sanctioned control knobs — spec authority, so implementers extend these rather than inventing ad-hoc ones. Two naming families with different postures: `TV_UPDATE_CHANNEL_*` variables are **operational** overrides, honored in every build (they also serve staging and dry-run channel deploys); `TV_TEST_*` variables are **test-only** and each states its inertness mechanism — ignored in release builds via the build-time version define, or gated behind the desktop shell's existing `TV_TEST_MODE` flag. A hook that would change release behavior without one of those guards does not belong in this family. ^updates-test-hooks

## Assertions

### Test assertions

The update suites were authored with these specs under the testing policy. Plain citations below are policy-grade cited; inherited evidence is labeled separately.

- **Contract** (pure version helpers over authored strings and build-stamp inputs; no mocks or test hooks): release versions accept only plain numeric triples, newer-than compares numeric components, reload staleness is string inequality with the `0.0.0` exemption, and the server resolver reads the build stamp before the guarded source-test hook — *covered by the `isReleaseVersion`, `isNewerVersion`, `isStaleBundle`, and `resolveUpdateReleaseVersion` groups in `packages/server/src/updates/version.test.ts`*. ^updates-t-version-model
- **Contract** (repository manifests read directly; no mocks or test hooks): every workspace package, including the private desktop workspace, carries the root release version — *(covered by inherited test: `test/repo/package-version-sync.test.ts` “every workspace package.json version matches the root”)*. ^updates-t-package-lockstep
- **Contract** (committed publish workflow read directly; no mocks or test hooks): the gate fetches the tip of `main`, compares it with the checked-out commit, and sets its publish output to false when they differ; every later step requires the true output. The workflow skips every publishing step while `.github/PAUSE_PUBLISH` exists at the triggering commit or on `main`; the version step sets every workspace to the CLI manifest's version, then raises the patch number of the root and every workspace for as long as npm already has that version; all workspace versioning finishes before the release build; and the build finishes before the workflow's one `npm publish`, which publishes the CLI package — *(covered by tests: `test/repo/package-version-sync.test.ts` “publishes only the CLI package, under a version npm does not yet have, after versioning and building” and “skips every publishing step for a paused or stale commit”)*. ^updates-t-publish-order
- **Contract** (the publish workflow's two `npm version` commands run for real on a temporary fixture monorepo; no mocks or test hooks): the patch command raises the root and every workspace one patch together, and the sync command brings every workspace to a version already set in the root — *covered by `test/repo/package-version-sync.test.ts` “auto-bump branch bumps root and every workspace together” and “explicit-bump branch syncs workspaces up to an already-bumped root”*. ^updates-t-version-commands

- **Contract** (committed publish YAML parsed directly; no mocks or hooks): the publishing job requires the official repository, successful CI, a push event, a head repository equal to `github.repository`, and branch `main`, using exactly those comparisons joined by `&&` with no extra terms at job level before any step. Eligible jobs share a queue retaining waiting jobs without cancelling active jobs; the concurrency key separates ineligible event/head-repository/branch/conclusion combinations from the eligible queue. External action references use full commit SHAs. This proves [npm publishing eligibility](../../../specs/arch/updates/index.md#^updates-publish-eligibility) at the configuration boundary; the [pause, stale-commit and build-order contract](#^updates-t-publish-order) remains in force. GitHub's evaluation, hosted token isolation and scheduling are external platform behavior, not simulated here — *(covered by tests: `test/repo/public-workflow-boundaries.test.ts` “requires a successful upstream main push before the publishing job starts”, “retains eligible publishing jobs in a non-cancelling queue separate from ineligible runs”, and “pins external actions in publish to full commit SHAs”)*. ^updates-t-publish-eligibility

Coverage relationship: [product versioning](../../product/versioning.md#^versioning-ac-release-identity) owns the real CLI/server tarball and the desktop upload directory built from the same commit, and verifies their release identities together. Together with the manifest and workflow contracts above, these prove the release pipeline gives the server and served bundle one finalized release version without reclassifying CLI cases.
