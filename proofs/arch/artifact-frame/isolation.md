*How artifact isolation is proven: escalation walks in which hostile artifact code, sandboxed in Chromium and Firefox and unsandboxed in its partition in the real Electron app, fails to obtain the token, act with the app's authority or reach the main process; a desktop walk showing artifacts' storage apart from the window's and from each other's; walks showing artifacts still load what they need; and the header, route, frame-attribute, header-rewriting and permission rules as contracts with real-browser and real-Electron crossings.*

# Artifact isolation — proof

Proves [specs/arch/artifact-frame/isolation.md](../../../specs/arch/artifact-frame/isolation.md).

## Coverage model

The spec's testing directive is honored by the escalation walks, [#^iso-t-escalation-browser](#^iso-t-escalation-browser) in Chromium and Firefox and [#^iso-t-escalation-electron](#^iso-t-escalation-electron) in the real Electron app. Each runs against a server that requires the token, with the token held where the app keeps it, and shows an authored hostile artifact whose own code tries each way to the token or to the app's authority: browser storage, the app's page through a frame it creates or a window it opens, a copy of itself opened as a popup, service workers, the token routes over HTTP and WebSocket, and, in a browser, its parent and navigation of the whole tab. In a browser the artifact runs sandboxed, so storage throws and the token routes' answers are unreadable. In the desktop app it runs unsandboxed in its artifact partition, as the directive requires: storage works but is its partition's, the app's page it frames holds no token there, and the token routes answer it readably, with `401`. The desktop walk also looks for Electron and the preload's internals. Each walk asserts that every attempt fails to reach the token or the app's authority and that the token, the server's state and the app are unchanged. The directive's storage-visibility matrix is [#^iso-t-desktop-storage](#^iso-t-desktop-storage): one walk in which probes in the window's page and in artifacts of every kind each write markers to `localStorage`, IndexedDB and a cookie, find exactly the markers the matrix allows and no token but the window's, and find the same again after the app restarts. That the main process ignores IPC from a webview, whatever its channel, is proven in the real Electron app by [the desktop root's IPC-sender seam](../desktop/index.md#^desktop-t-ipc-senders-seam), because artifact code behind the preload's context isolation cannot send IPC at all, so only code standing in for a compromised renderer can try. The preload's context isolation and the application-link relay through the app's page are [the bridge proof's](./artifact-bridge.md#^ab-ac-application-link-electron-seam).

The working walk, [#^iso-t-artifacts-load](#^iso-t-artifacts-load), shows in the same three runtimes that an artifact still loads its module script, font, data, the canonical bundle, its store and the missing-file page, which crosses the cross-origin rules on the routes artifacts load from a sandboxed page in the browsers and the same routes from an unsandboxed page in the desktop app. Shared artifacts cross the proxy's `ETag` exposure in [the bridge's shared-artifact acceptances](./artifact-bridge.md#^ab-ac-content-poll), and the SDK route is crossed by [the SDK proof's](../resources/sdk.md) browser tests on artifact pages, which the server sandboxes.

The header and the route rules are contracts over real HTTP against a running server. The frame attributes are a host contract under jsdom, whose mocked frame forfeits the browser's own handling to two Chromium seams: one follows a reused frame across documents with and without a sandbox, and one reads the features the browser grants. The desktop app's header rewriting is a contract on the production response-header function with authored responses, crossed in the real Electron app by [#^iso-t-desktop-header-seam](#^iso-t-desktop-header-seam), which reads a document's origin, through a reload that revalidates, and the referrers its requests carry. The desktop permission handlers are a main-process contract with Electron's sessions mocked, crossed in the real Electron app. Which session each webview uses, that every partition's session is set up before its first webview, and the fallback partition, which keeps the header, are [the desktop artifact partitions proof's](../desktop/artifact-partitions.md).

The [known limitations](../../../specs/arch/artifact-frame/isolation.md#^iso-limitations) are accepted costs, not behavior to build, and order no tests of their own. The browser escalation walk observes storage throwing, the desktop permission seam observes pointer lock refused, [the browser application-link walk](../../product/artifact-navigation.md#^ac-application-links-browser) answers Chromium's prompt on each application link clicked in an HTML artifact and sees a `javascript:` link there do nothing, the storage matrix observes URL artifacts on one producer's origin sharing storage, and the `television` skill's map guidance is checked in the built skill. Shared artifacts from older producers, an updated desktop app on an older server and the website data left in other sessions are cross-version cases the bridge spec calls non-goals; the fallback partition those servers' interfaces get is the partitions proof's seam. What a page can reach on a server without a token belongs to tokenless mode and [TV-379](https://linear.app/telepath-computer/issue/TV-379).

## Test hooks

Besides the host-name mapping below, Electron walks use [the e2e harness's fixture hook](../../../specs/arch/desktop/e2e-harness.md#^desktop-e2e-fixture-hook), which only selects the app URL, or the saved connection the e2e helper writes before launch, and the [external-open record](../desktop/index.md#Test hooks) of `TV_TEST_MODE`. Where an Electron walk runs code in a webview's page through Electron's `executeJavaScript`, that code plays the artifact's own code and replaces no production mechanism.

- **Host-name mapping.** The storage-matrix walk launches Electron with Chromium's `--host-resolver-rules` mapping `*.test` to `127.0.0.1`, so pages served from loopback have hosts of their own: a browser keeps cookies by host, ignoring the port, and the walk needs each origin on its own host. Production resolves names through ordinary DNS; the mapping changes no Television mechanism.

## Assertions

### Escalation

Shared declaration for the two escalation walks: the outer boundary is a real browser, or the real Electron app, showing the app served by a really-running server that requires the token, where the app holds the token as it does after connecting. The hostile artifact is an authored HTML folder artifact registered through the production API. Its code runs its attempts on load and again from a real click, and records each outcome where the test reads it; the test requires the attempts made from the click to hold user activation, and does not check activation on load, where Firefox sometimes reports it before anything has been clicked; Playwright reads the artifact's records from its frame or webview, and reads a popup's from the popup. The default CSS-motion override is the only mock, and it forfeits only motion no assertion claims.

- **Acceptance — hostile code in the browser** (Chromium and Firefox): from inside the artifact's frame, using `localStorage`, `sessionStorage`, `document.cookie` or IndexedDB throws `SecurityError`; reading the parent's document, storage or address throws; a frame the artifact creates for the app's page `/` and a window it opens for `/` cannot be read by it; a popup it opens for its own address runs its code again, still sandboxed by the header, and there too every use of storage throws; registering a service worker fails; `fetch` and `XMLHttpRequest` calls to each token route in [the route table](../../../specs/arch/artifact-frame/isolation.md#^iso-routes) give the artifact no readable response, with and without a guessed `Authorization` header; a `text/plain` `POST` that creates a channel, of the kind browsers send without a CORS preflight, is refused and creates nothing; WebSockets to `/events` and `/acp` deliver no message; and assigning `top.location` changes nothing. Afterwards the app's stored token is unchanged, the server's channels and artifacts are as before, and the app's own requests still succeed. This proves the [sandbox header](../../../specs/arch/artifact-frame/isolation.md#^iso-sandbox-header), the [iframe sandbox](../../../specs/arch/artifact-frame/isolation.md#^iso-iframe-sandbox) and the token routes of [the cross-origin rules](../../../specs/arch/artifact-frame/isolation.md#^iso-routes) against hostile code, and the [product promise](../../../specs/product/artifacts.md#^af-sandbox) in a browser — *(policy-grade test: `packages/web/test/e2e/artifact-isolation.test.ts` "artifact storage and authority stay isolated in the browser", in Chromium and Firefox, with a random shell-storage sentinel)*. ^iso-t-escalation-browser
- **Acceptance — hostile code in the desktop app** (the real Electron app connected through the saved connection to the server, with the token in the window's storage and a random sentinel beside it; the hostile artifact runs unsandboxed in its artifact partition): from inside the artifact's webview, the document's origin is the server's; `localStorage`, `sessionStorage`, `document.cookie` and IndexedDB work, and `localStorage` holds neither the app's stored token nor the sentinel; a frame the artifact creates for the app's page `/` loads on the same origin and can be read, and its `localStorage` holds neither the token nor the sentinel; `require`, `process`, `module`, `Buffer` and Electron's `ipcRenderer` are not defined; the only global the native preload supplies is its content bridge, whose messages reach only the app's page, and whose application-link request records no external open without user activation or for a web, `file:` or `javascript:` value; `window.open` for the app's page or the artifact's own address opens no Electron window; registering a service worker from the artifact's folder succeeds, and the window's page then has no service worker registration; `fetch` and `XMLHttpRequest` calls to each token route in [the route table](../../../specs/arch/artifact-frame/isolation.md#^iso-routes), with and without a guessed `Authorization` header, are answered `401`, readably, since they are same-origin; the `text/plain` `POST` that would create a channel is answered `401` and creates nothing; and WebSockets to `/events` and `/acp` deliver no message and close with `4401`. Afterwards the app is still connected to the same server, with its stored token, the sentinel and its saved connection unchanged, the window's storage holds nothing the artifact wrote, the server's channels and artifacts are as before, no update restart or appearance change happened, and the app's own requests still succeed after a reload. This proves [the sessions](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-sessions) and the desktop paragraph of [the cross-origin rules](../../../specs/arch/artifact-frame/isolation.md#^iso-routes) against hostile code, and the [product promise](../../../specs/product/artifacts.md#^af-sandbox) in the desktop app; that IPC sent from a webview's own renderer is ignored is [the IPC-sender seam](../desktop/index.md#^desktop-t-ipc-senders-seam) — *(policy-grade test: `packages/desktop/test/e2e/artifact-isolation.test.ts` "artifact storage and authority stay isolated in the desktop app", with a random shell-storage sentinel)*. ^iso-t-escalation-electron
- **Acceptance — the storage-visibility matrix** (the real Electron app connected through the saved connection to a really-running server that requires the token, at `127.0.0.1`, launched with the [host-name mapping](#Test hooks); fixtures created through the production API on separate tab pages of one channel, and fixture pages served by a local HTTP server; the walk runs each probe in its page as the artifact's code would, and the window's probe in the window's page; no mocks). The probes are:
  - **W**, the window's page;
  - **L1** and **L2**, two authored HTML folder artifacts on the server, in partitions of their own;
  - **S1** and **S2**, two URL artifacts at the server's own addresses of L1 and L2, so on the window's origin in the URL-artifact partition;
  - **T1** and **T2**, two external page artifacts on `site-a.test`, and **T3**, one on `site-b.test`;
  - **P**, a shared artifact whose producer is a second running server, added at `producer.test`.

  Every probe first writes a marker of its own: a `localStorage` entry, an IndexedDB database, and a persistent, host-only cookie with `Path=/` and a `Max-Age`, each named for the probe. Then every probe reports which probes' markers it finds, separately in `localStorage`, in IndexedDB and in its cookies, and whether the server's token appears in any `localStorage` value or cookie it can read. In each of the three kinds of storage, the findings are exactly:

  | Probe | Finds the markers of |
  | --- | --- |
  | W | W |
  | L1 | L1 |
  | L2 | L2 |
  | S1, S2 | S1 and S2 |
  | T1, T2 | T1 and T2 |
  | T3 | T3 |
  | P | P |

  and only W finds the token. The app then quits and is launched again with the same `userData` directory; once every webview has loaded, every probe reports again without writing, and the findings are the same. This proves [the sessions](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-sessions), including the URL-artifact partition's separation by origin and its cookies by host, under the spec's storage-visibility directive; the persistence of every partition, the URL-artifact partition included, that [the sessions table](../../../specs/arch/desktop/artifact-partitions.md#^dp-sessions) gives by naming them `persist:`; that a shared artifact from another host runs unsandboxed under [the header rewriting](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-header), since its storage would otherwise throw; and the shared storage that [limitation 17](../../../specs/arch/artifact-frame/isolation.md#^iso-limitations) accepts — *(policy-grade test: `packages/desktop/test/e2e/artifact-isolation.test.ts` "storage visibility in the desktop app matches the matrix across the window and every kind of artifact, before and after a restart")*. ^iso-t-desktop-storage

### Artifacts keep working

- **Acceptance — what an artifact loads** (outer boundaries: Chromium, Firefox and the real Electron app, each showing the app served by a really-running server; the fixture is an authored HTML folder artifact registered through the production API whose page imports a module script and loads a font from its own folder, fetches a JSON file beside it, links the canonical stylesheet and components script, and reads and writes its store through `/sdk/v1/resources.js`; the walk then removes the folder's `index.html`; the Electron fixture hook only selects the app URL; the default CSS-motion override is the only mock): the page's origin is opaque in the browsers and the server's in the desktop app, where it runs unsandboxed in its artifact partition; the module script runs, the font is applied, the JSON is read, the canonical bundle styles the page, and the store's value round-trips; once `index.html` is gone, the same frame or webview, reloaded as the app reloads a changed artifact, shows the missing-file page with its styles and the artifact's title and path. This proves the routes artifact documents load, under [the cross-origin rules](../../../specs/arch/artifact-frame/isolation.md#^iso-routes), from a sandboxed page in the browsers and an unsandboxed one in the desktop app — *(policy-grade tests: `packages/web/test/e2e/artifact-isolation.test.ts` "a sandboxed artifact loads its own files, the canonical bundle, its store and the missing-file page", in Chromium and Firefox; and `packages/desktop/test/e2e/artifact-isolation.test.ts` "an artifact loads its own files, the canonical bundle, its store and the missing-file page in its partition")*. ^iso-t-artifacts-load

### The header and the routes

- **Contract — the sandbox header** (a really-running in-process server over temporary artifact and theme folders, driven by a real HTTP client; no mocks): every response from the artifact proxy and the active-theme route carries exactly the [sandbox header](../../../specs/arch/artifact-frame/isolation.md#^iso-sandbox-header), with no `allow-same-origin` and no top-navigation token: under an artifact's ID and its share ID, for an HTML page with the bridge injected, a Markdown file rendered by the proxy, an image, a PDF, a JSON and an SVG file, the redirect to a folder's trailing slash, a missing file, a refused method, a request body the server cannot parse, `HEAD`, and a `304` revalidation, and for an artifact ID the server cannot decode; and on the theme route for the active package's stylesheet, a script entry, an HTML file, the null theme's empty stylesheet, a missing path, a refused method and a request body the server cannot parse — *(policy-grade tests: `packages/server/test/sandbox-header.test.ts` "is on every artifact proxy response, under the artifact's ID and its share ID" and "is on every active-theme route response")*. ^iso-t-header
- **Contract — cross-origin rules by route** (the same server, with the token required; requests carry `Origin: null`, as a sandboxed artifact's do, and another site's origin; no mocks): the artifact proxy answers with `Access-Control-Allow-Origin: *` and `Access-Control-Expose-Headers: ETag`; `/canonical/v<n>/…`, `/theme/…`, `/sdk/v1/…` and `/views/artifact-missing/…` answer with `Access-Control-Allow-Origin: *`; none of these responses allows credentials. Each token route in [the route table](../../../specs/arch/artifact-frame/isolation.md#^iso-routes), with and without the token, and its `OPTIONS` preflight, answers with no CORS header, and the preflight grants nothing; `/health`, the app's page and the other `/views/…` answer with none. WebSocket upgrades to `/events` and `/acp` carrying the token and either `Origin` are accepted. This proves [the cross-origin rules](../../../specs/arch/artifact-frame/isolation.md#^iso-routes); the resource routes are [the resource architecture's origin contract](../resources/index.md#^rs-arch-t-origin) — *(policy-grade tests: `packages/server/test/cross-origin-routes.test.ts`, the cases under “cross-origin rules by route (^iso-t-routes)”)*. ^iso-t-routes

### The frame attributes

- **Contract — the `sandbox` and `allow` attributes** (the production artifact-frame view under jsdom with authored artifact records and a fake application service; the iframe's loading is mocked, forfeiting the browser's own handling to [#^iso-t-reused-frame](#^iso-t-reused-frame) and [#^iso-t-features](#^iso-t-features)): at the moment each `src` is assigned, the frame has the `sandbox` attribute with exactly the header's tokens for a proxied document, a proxied Markdown file and a shared artifact, and no `sandbox` attribute for the Markdown editor, the placeholder for an external page, the artifact-missing page the app shows, and an external page under browser demo mode, including when one iframe element moves from each kind of document to another; and every artifact iframe carries exactly the [allow list](../../../specs/arch/artifact-frame/isolation.md#^iso-iframe-allow). Theme frames are [theme delivery's](../themes/delivery.md#Sandboxed frames). This proves [the iframe sandbox](../../../specs/arch/artifact-frame/isolation.md#^iso-iframe-sandbox) table and ordering, and [the allow list](../../../specs/arch/artifact-frame/isolation.md#^iso-iframe-allow), at the host — *(policy-grade tests: `packages/web/test/artifact-view.test.ts` "sandboxes proxied and shared documents, and nothing else, as one iframe element moves between them", "sandboxes a proxied Markdown file and not the placeholder for an external page when Back and Forward assign them" and "shows the missing-artifact page the app renders in no frame, and frames the recovered editor unsandboxed")*. ^iso-t-attributes
- **Seam — a reused frame across documents** (the app's artifact-frame view → the browser's sandboxing of the frame's next document, crossed in Chromium against a really-running server; an authored folder artifact with a link to an external fixture page served on another origin, and a shared artifact whose producer is a fixture HTTP server that sends no sandbox header; no mocks): the artifact's page has an opaque origin; after its link to the external page, the placeholder in the same frame has the app's origin; after Back, the artifact's page has an opaque origin again; and the shared artifact's page has an opaque origin although its response carried no header — *(policy-grade test: `packages/web/test/e2e/artifact-isolation.test.ts` "one artifact frame sandboxes the artifact's pages and a shared artifact's, and not the placeholder between them")*. ^iso-t-reused-frame
- **Seam — features the browser grants** (the frame's `allow` attribute → the browser's Permissions Policy, crossed in Chromium against a really-running server; an authored HTML artifact; no mocks): inside the sandboxed artifact, the browser reports the Permissions Policy features `clipboard-write`, `fullscreen`, `autoplay`, `picture-in-picture`, `web-share` and `encrypted-media` as allowed, apart from one it does not implement, as Chromium on Linux does not implement `web-share`, and `geolocation`, `camera`, `microphone`, `clipboard-read` and `midi` as not allowed; a real click on a control that requests fullscreen enters fullscreen — *(policy-grade test: `packages/web/test/e2e/artifact-isolation.test.ts` "a sandboxed artifact is granted the six browser features and no others, and enters fullscreen from a click")*. ^iso-t-features

### The desktop header rewriting

- **Contract — rewriting the artifact proxy's headers** (the production response-header function the main process installs on artifact and URL-artifact partitions, over authored response details; no mocks): for a response to a request whose path is `/artifact/<id>` or below it, on any host and under an artifact ID or share ID, that carries `X-TV-Version` under any capitalization of its name, a `Content-Security-Policy` header whose whole value is a `sandbox` directive, with the sandbox header's tokens, with other tokens, with none, or in other capitalization and spacing, is removed, while a `Content-Security-Policy` that holds other directives, alone or beside `sandbox`, is kept unchanged; when a response carries several policies, each is judged alone, so a sandbox-only policy is removed and the others are kept; `Referrer-Policy` is `strict-origin-when-cross-origin` afterwards, whether the response carried `no-referrer`, another policy or none; every other header keeps its name and values. A response without `X-TV-Version`, and a response to `/artifactx/…`, `/theme/…`, `/views/…`, `/` or a path that merely contains `/artifact/` below its first segment, is returned unchanged. This proves the rule of [the header rewriting](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-header) — *(policy-grade tests: `packages/desktop/test/artifact-partitions.test.ts` "rewrites only the artifact proxy's sandbox header and referrer policy" and "leaves responses that are not the artifact proxy's unchanged")*. ^iso-t-desktop-header
- **Contract — where the rewriting is installed** (the production main-process module; Electron's sessions are declared mocks recording what is installed on each; the mocks forfeit a real session to [#^iso-t-desktop-header-seam](#^iso-t-desktop-header-seam) and [the partitions proof's fallback seam](../desktop/artifact-partitions.md#^dp-t-fallback-seam)): the main process installs the header function on every artifact partition's session and on the URL-artifact partition's, and on neither the window's session nor the fallback partition's. This proves where [the header rewriting](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-header) applies — *(policy-grade test: `packages/desktop/test/main.test.ts` "rewrites headers in artifact and URL-artifact partitions only")*. ^iso-t-desktop-header-sessions
- **Seam — an unsandboxed document and its referrers** (the real Electron app connected through the saved connection to a really-running server; an authored HTML folder artifact whose page loads an image from, and fetches, a local fixture HTTP server on another origin that records each request's `Referer`, and fetches a file of its own folder, whose request headers the test observes through Electron's `onSendHeaders` on the artifact's session, an observer that replaces nothing; no mocks): in the artifact's webview the document's origin is the server's, also after the webview reloads and the server answers the revalidation with `304`, which Electron reports as the cached document; the request to the other origin carries the server's origin followed by `/` as its `Referer`, with no path, and the same-origin request carries the document's full address. This proves that [the header rewriting](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-header) reaches the document in a real webview, through the HTTP cache — *(policy-grade test: `packages/desktop/test/e2e/artifact-isolation.test.ts` "an artifact runs unsandboxed in its partition and sends other sites only its server's origin as referrer")*. ^iso-t-desktop-header-seam

### The desktop permission handlers

- **Contract — permission handlers** (the production main-process module; Electron's sessions, the permission callbacks and the web contents are declared mocks, the web contents posing as a webview's or as the window's; the mocks forfeit Electron's real permission requests to [#^iso-t-permissions-seam](#^iso-t-permissions-seam)): the main process sets both a permission request handler and a permission check handler on the window's session and on each partition session it sets up, artifact, URL-artifact and fallback; on each, for a webview's web contents, both grant `clipboard-sanitized-write`, `fullscreen` and `mediaKeySystem` and refuse every other permission Electron defines, `pointerLock` among them, the same for every webview whatever its URL; for the window's web contents, the window's session's handlers grant. This proves [the desktop permissions](../../../specs/arch/artifact-frame/isolation.md#^iso-desktop-permissions) — *(policy-grade test: `packages/desktop/test/main.test.ts` "grants a webview only clipboard writing, fullscreen and media keys in every session, and grants the window everything")*. ^iso-t-permissions
- **Seam — permissions in a real webview** (the real Electron app connected to a really-running server; an authored HTML artifact, unsandboxed in its artifact partition; the fixture hook only selects the app URL, and Chromium's fake capture device gives the microphone request a device; no mocks): from a real click inside the artifact's webview, writing to the clipboard succeeds and fullscreen is entered, while requests for notifications, geolocation, the microphone and pointer lock are refused, and the window's own page is still granted a permission it requests. With the document unsandboxed, the microphone request reaches the handlers, which refuse it — *(policy-grade test: `packages/desktop/test/e2e/artifact-isolation.test.ts` "a webview's artifact writes to the clipboard and enters fullscreen from a click, and is refused notifications, geolocation, the microphone and pointer lock")*. ^iso-t-permissions-seam

### Map guidance

- **Seam** (production `television` skill source → the real manifest-driven skills build → shipped `television/SKILL.md`; no mocks): the skill's guidance on HTML artifacts says that third-party mapping services may not work in artifacts because the sandbox strips the referrer and other information they expect, and recommends Leaflet with Esri's World Street Map or World Imagery tiles. Independent guidance review, as in [resource guidance](../resources/guidance.md#Coverage model), judges the wording. This proves the skill guidance that item 9 of [the known limitations](../../../specs/arch/artifact-frame/isolation.md#^iso-limitations) describes — *(policy-grade test: `test/repo/resource-guidance.test.ts` "says that mapping services may not work in artifacts because the sandbox strips what they expect, and recommends Leaflet with Esri's tiles"; and guidance review)*. ^iso-t-map-guidance

Coverage relationship: the Markdown editor, the error pages and the placeholder run unsandboxed and trusted; that the Markdown editor treats a file's script as text is [the bridge's Markdown seam](./artifact-bridge.md#^ab-ac-markdown-bridge-seam). That a theme package's HTML file opened as a page runs sandboxed follows from [#^iso-t-header](#^iso-t-header) on the theme route and the browser's own enforcement, which the escalation walks cross for the artifact proxy; it orders no walk of its own.
