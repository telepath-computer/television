*How the resource SDK is proven: its build contents and serving over real HTTP, and its behavior as the server serves it, in a real browser on a plain-HTTP origin that is not `localhost`, against a running server.*

# Resource SDK — proof

Proves [specs/arch/resources/sdk.md](../../../specs/arch/resources/sdk.md).

## Coverage model

The SDK's testing directive governs every browser test here: each loads `/sdk/v1/resources.js` exactly as a running server serves it, in a real browser, from a page whose plain-HTTP origin is not `localhost`, so the secure-context restriction is in force. The origin comes from the browser host-name mapping hook; each test page also checks that `window.isSecureContext` is false before it starts, so a harness that drifted onto a secure origin fails rather than passing quietly. No test runs the SDK in Node or a mocked DOM.

Browser tests are contracts on the SDK's public interface, the boundary artifact code calls. The test plays the artifact code from an authored HTML artifact; behind the interface everything is real, including a really-running in-process server over temporary storage, its page connection and the network. Share links, and bindings with the flag on, are changed through the server's administrative routes.

One harness piece stands in for something outside Television and replaces no Television mechanism: a test-controlled TCP proxy acts as the network, so a test can cut or hold connections. Reconnection timing uses Playwright's page clock, a mock of the page's timers that forfeits only real elapsed time.

The build and serving contracts use the real server build and real HTTP. The CLI's copy of the SDK into its package and the resolver that passes it to the server are [the CLI architecture proof](../cli/index.md#^cli-build-sdk-copy)'s. The built-CLI walks in [the resources product proof](../../product/resources/resources.md#^rs-ac-page-spine) load the SDK the packaged CLI serves, in Chromium and Firefox.

Local writes, transactions, child events, and what a lost connection does to the JSON store's writes, reads and listeners belong to [the JSON store architecture proof](./json-store.md), whose browser tests use this proof's harness. `wrong-type` cannot be reached while `json` is the only type, so no handle test orders it.

## Test hooks

- **Browser host-name mapping.** As declared in [the resources product proof](../../product/resources/resources.md#Test hooks): the browser resolves test host names to the loopback server.
- **Bindings on.** As declared in [the resource architecture proof](./index.md#Test hooks): the in-process server is constructed with the bindings flag on where an assertion says so.
- **Network proxy.** A test-controlled TCP proxy between the browser and the server forwards traffic unchanged and lets a test sever open connections, refuse new ones, or hold traffic in either direction, or only the page's write messages, until released. It stands in for a network and replaces no Television mechanism; production pages connect through whatever network lies between them and the server.

## Assertions

### Build and serving

- **Contract** (the real server package build; esbuild's metafile is read as the record of what the bundler emitted; no mocks): the build produces `packages/server/dist/sdk/v1/resources.js` as one ES module, with the SDK's notices file beside it and nothing else in the SDK directory, and every input the metafile lists for the module is first-party source under `packages/shared/src/`, with nothing from `node_modules`, the CLI package, or the shared client's administrative methods. What the notices declare is [the licensing proof's](../../product/licensing.md#^licensing-ac-adapted-code). This proves [the build](../../../specs/arch/resources/sdk.md#^sdk-build) — *(policy-grade test: `packages/server/test/e2e/resource-sdk-build.spec.ts` "the SDK build")*. ^sdk-t-build
- **Contract** (a really-running in-process server with authentication on, given the built SDK directory as `sdkDir`, and Node's `fetch`; no mocks): `GET` and `HEAD` for `/sdk/v1/resources.js` without a token answer `200` with `Content-Type: text/javascript; charset=utf-8`, an `ETag` and `Cache-Control: no-cache`; the body equals the built file's bytes, and requests carrying different artifact paths in `Referer` receive identical bytes; a request carrying the `ETag` in `If-None-Match` is answered `304`. `GET` and `HEAD` for `/sdk/v1/THIRD-PARTY-NOTICES.txt` without a token answer `200` with `Content-Type: text/plain; charset=utf-8`, an `ETag` and `Cache-Control: no-cache`, and the body equals the built notices file's bytes. A server constructed without `sdkDir` answers `404` for both paths while its resource routes keep working. This proves [serving](../../../specs/arch/resources/sdk.md#^sdk-serving) and [packaging's optional option](../../../specs/arch/resources/sdk.md#^sdk-packaging) — *(policy-grade test: `packages/server/test/e2e/resource-sdk-build.spec.ts` "serving the SDK")*. ^sdk-t-serving

### Behavior in the browser

Shared declaration for the assertions below: shape contract on the SDK's public interface; a real browser loads the served module from a page on a mapped plain-HTTP host name; a really-running in-process server over temporary storage serves the page and the SDK; authored HTML artifacts are fixtures, and share links and bindings are changed through the administrative routes. Hooks and mocks are only those an assertion names.

- **Finding the artifact.** Pages served at `/artifact/<id>/`, at `/artifact/<id>/index.html`, in a subfolder of a folder artifact, and at the artifact's share link each read and write their own artifact's store, at the level their address carries. On a page served by the same server at a path of another form, every function the module exports fails with `not-artifact-page`: a function that returns a promise rejects with it, and any other throws it. On these plain-HTTP pages the page connection opens over `ws:` at the page's own host. This proves [finding the artifact](../../../specs/arch/resources/sdk.md#^sdk-artifact-id) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "finding the artifact")*. ^sdk-t-artifact-id
- **The layer's functions.** `getAccess` resolves with `read-write` on a page under the artifact's own ID and with the link's level under its share ID, and rejects with `no-store` on a page of an artifact that has no store. An `onAccessChanged` callback hears the level once the connection's opening state has arrived, then hears each change the link's level goes through, and nothing after its `Unsubscribe`. On a page of an artifact that has no store, it hears `null` once the opening state has arrived; when the page was opened through a share link, a change of the link's level calls it no more, and `getAccess` still rejects with `no-store`. On a page opened through a share link, a callback that is the page's only use of the SDK hears `null` once the link is revoked and the SDK has reconnected, and `getAccess` then rejects with `no-store`. An `onResourcesChanged` callback receives `changed` for the artifact's store, without a resource ID, until its `Unsubscribe` is called and none after. With the flag off, `listResources` and `getResourceInfo` reject with `not-enabled`. With the bindings hook, `listResources` resolves with every store the artifact can use, ordered by resource ID: its own store once it has been written, at the page's level, and each store it is bound to, another artifact's own store included, at the page's level on it; each entry has exactly its resource ID, type and level, also for a store whose description and usage were set and for an unavailable store. `getResourceInfo` resolves with any one of them, the artifact's own store included, and rejects with `not-bound` for a resource ID the artifact cannot use; and `onResourcesChanged` receives the bound stores' events. Every rejection is an `Error` with a string `code` and a message, and the module exports no error class. This proves [the layer's functions](../../../specs/arch/resources/sdk.md#The layer's functions), [the page's access level](../../../specs/arch/resources/sdk.md#^sdk-access) and [errors](../../../specs/arch/resources/sdk.md#^sdk-errors) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "the layer's functions")*. ^sdk-t-layer
- **Handles.** `getStore()` and `getStore(resourceID)` return handles without sending anything over the network, observed through the network proxy; `getStore()`'s handle has a `resourceID` of `null`. On a page of an artifact that has no store, the first operation on `getStore()`'s handle fails with `no-store`. On a page opened through a share link, revoking the link makes the handle's next operation fail with `no-store` once the SDK has reconnected, and each of its active listeners receives the error through its error callback and is removed. When the artifact's own store is destroyed through the administrative routes, the handle's `onValue` listener hears no value and stays, and its next write succeeds. With the flag off, the first operation on a handle from `getStore(resourceID)` fails with `not-enabled`, and a listener on the handle from `getStore("")` receives that error, never the value of the artifact's own store, at whose path a listener on `getStore()`'s handle is already registered. With the bindings hook, a handle from `getStore(resourceID)` given the artifact's own store's resource ID reads and writes the store that `getStore()`'s handle does, at the page's level; the first operation on a handle for a store the artifact is not bound to fails with `not-bound`; when the binding is removed, the handle's next operation fails with `not-bound`, and each of its active listeners receives the error through its error callback and receives nothing after the artifact is bound again; after rebinding, the same handle's operations and new listeners work. This proves [handles](../../../specs/arch/resources/sdk.md#^sdk-handles) and [handles for bound stores](../../../specs/arch/resources/sdk.md#^sdk-bound-handles) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "handles")*. ^sdk-t-handles
- **Connection lifecycle.** Loading the module opens no connection; the first operation, subscription, or `onResourcesChanged`, `onAccessChanged` or `onConnectionStatusChanged` registration opens one, and further stores share it. The connection closes once no listener, callback, unconfirmed write or outstanding request remains, and the next operation opens a new one. This proves [the connection client](../../../specs/arch/resources/sdk.md#^sdk-connection) and [one page connection at a time](../../../specs/arch/resources/index.md#^rs-page-connection) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "connection lifecycle")*. ^sdk-t-connection
- **Connection status.** Observed through `getConnectionStatus` and an `onConnectionStatusChanged` callback, with the network proxy controlling the network: the status is `idle` after the module loads, and calling `getConnectionStatus` then opens no connection, as the proxy shows. It is `connecting` once the page first subscribes, and stays so while the proxy holds the server's opening state; it becomes `connected` when the opening state is released. Severing the connection makes it `disconnected`, and the callback hears that before the page's listener hears an unconfirmed write roll back and before that write's promise rejects. With the proxy refusing connections it stays `disconnected` through the reconnection attempts, and becomes `connected` when the proxy accepts again and the opening state arrives. A first connection that the proxy ends before its opening state takes the status from `connecting` to `disconnected`. When the page's last listener is unsubscribed and nothing else needs the connection, the status becomes `idle`. A callback hears the status as it stands soon after its registration, then each change in order, and nothing after its `Unsubscribe`; a page whose only use of the SDK is a status callback keeps its connection open. This proves [the connection status](../../../specs/arch/resources/sdk.md#^sdk-connection-status), the order of a loss in [reconnection](../../../specs/arch/resources/sdk.md#^sdk-reconnect), and the status half of [the product's connection promise](../../../specs/product/resources/resources.md#^rs-connection) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "connection status")*. ^sdk-t-connection-status
- **Reconnection.** With the network proxy refusing connections after a cut and Playwright's page clock driving time, the SDK's successive connection attempts follow exponential backoff starting at 250 milliseconds, with jitter, and the interval stops growing at 30 seconds. Once the proxy accepts again, the SDK resubscribes every active subscription and sends no request it made before or during the loss, as the proxy shows. While the page is disconnected, `getAccess` rejects at once with `disconnected`; an `onResourcesChanged` callback and an `onAccessChanged` callback registered before the loss, and ones registered during it, receive the page's events and level changes after the reconnection. A `getAccess` made while the proxy holds the first connection's opening state waits for it and resolves once it is released; when the proxy instead ends that connection before its opening state, the waiting `getAccess` rejects with `disconnected`. With the bindings hook, `listResources` and `getResourceInfo` likewise reject at once while the page is disconnected, and so does a `listResources` outstanding when the connection is lost. This proves the backoff, resubscription, waiting and failing rules of [reconnection](../../../specs/arch/resources/sdk.md#^sdk-reconnect) and [the connection status](../../../specs/arch/resources/sdk.md#^sdk-connection-status) for the layer's functions; what a loss does to the JSON store's writes, reads and listeners is the JSON store proof's — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "reconnection")*. ^sdk-t-reconnect
- **Callback isolation.** An `onValue` callback and an `onResourcesChanged` callback that throw are each reported as an uncaught error in the page, while the other callbacks registered for the same change still run and later changes are still delivered over the same connection. This proves [callback isolation](../../../specs/arch/resources/sdk.md#^sdk-callback-isolation) — *(policy-grade test: `packages/server/test/e2e/resource-sdk.spec.ts` "callback isolation")*. ^sdk-t-callback-isolation

Coverage relationship: [plain HTTP](../../../specs/arch/resources/sdk.md#^sdk-plain-http) is the condition every browser test above runs under, guarded by its `isSecureContext` check, and the [product page walk](../../product/resources/resources.md#^rs-ac-page-spine) repeats it with the built CLI in Chromium and Firefox. The page connection's scheme under [the connection](../../../specs/arch/resources/sdk.md#^sdk-connection) is therefore `ws:` in every browser test above, and `wss:` on `https:` pages in [the product's HTTPS-front walk](../../product/resources/resources.md#^rs-ac-https-front). Rejecting a write through known `read` access before it is shown is [the JSON store's local-write contract](./json-store.md#^js-arch-t-local-view).
