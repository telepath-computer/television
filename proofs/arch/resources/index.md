# Resource architecture — proof

Proves [specs/arch/resources/index.md](../../../specs/arch/resources/index.md).

## Coverage model

The product spine is walked by [the resources product proof](../../product/resources/resources.md): built CLI processes, two real servers and real browsers, including the sharing walk that proves the producer enforces a share link's level against a page that bypasses the SDK, and the exposure walk that records everything a share viewer's browser receives. This proof carries the layer's breadth at its own boundaries, mostly as contract tests on the server side.

Server contracts construct the real `Server` and `ServerStore` in process over temporary storage on the real filesystem, and drive them through real HTTP and WebSocket clients. A client that plays the SDK uses the shared code's message framing, which is the production framing, so the SDK is absent rather than mocked; [the SDK proof](./sdk.md) proves the other side of that seam, and the product walks cross it for real. Storage, loading and startup recovery use a real filesystem, as this spec's testing directive requires, with authored files for the damaged and leftover states a crash or a hand edit could leave.

Three things cannot be reached honestly through real state, and each has a declared hook below. The order of file writes and flushes is not revealed by a real filesystem, and a disk that fails, or a read it refuses, cannot be staged on one: a test running as root reads past file permissions. A colliding ID practically never arises from a random generator. And the bindings flag is a constant that the shipped build cannot turn on, so behavior that exists only with the flag on is proven on servers and CLI environments a test constructs with it on, as the spec's testing directive requires; the flag-off refusals are proven both here and, in the shipped build, by [the product's flag-off walk](../../product/resources/resources.md#^rs-ac-flag-off). Each hook's mock forfeits only what its assertions name.

Requests from other origins are proven with real requests to a running server, as the testing directive requires: requests of the kind browsers send without a CORS preflight on both route families, and WebSocket upgrades on the artifact routes, whose page connection is the layer's one WebSocket, each with another site's `Origin`, with `Origin: null`, as a sandboxed artifact page sends, and with the `https:` origin of a page behind a front that terminates TLS. A page on another site that holds a share link is walked in [the sharing acceptance](../../product/resources/resources.md#^rs-ac-sharing), and pages behind such a front in [the HTTPS-front walk](../../product/resources/resources.md#^rs-ac-https-front).

The share and `tv resource` commands are covered by in-process CLI contracts with a fake client, which forfeit HTTP to a seam crossing the CLI to a real server, and by the built-process walks in the product proof. JSON store routes, write application, the content file and subscriptions are [the JSON store architecture proof](./json-store.md)'s.

Not ordered: a resource stored under two types cannot arise while `json` is the only implemented type, because the server reads only that type's directory; the [type contract](../../../specs/arch/resources/index.md#^rs-type-contract) and [wire boundary](../../../specs/arch/resources/index.md#^rs-wire-boundary) describe structure, proven through the JSON store's behavior rather than by tests of their own. That the flag is the constant `RESOURCE_BINDINGS_ENABLED`, `false`, and that production passes no other value, is [the flag](../../../specs/arch/resources/index.md#^rs-flag-constant)'s structure, proven in the shipped build by the product's flag-off walk.

## Test hooks

- **Storage operations.** The resource layer's file writer and reads, and the artifact record writer, take their filesystem operations from one injected adapter. A test may supply an adapter that records each temporary-file write, file flush, rename, directory creation, directory flush and deletion in order, and may make chosen operations fail, the layer's reads of files and directories and its checks of whether a path exists included. A failing operation may first change the file it acts on, so that a read of that file finds it not valid. Production uses Node's filesystem operations.
- **Bindings on.** A test may construct `Server` with `resourceBindings: true`, and a CLI environment with `resourceBindings: true`. Production passes neither, so the shipped build has the flag off. The hook changes the flag's value and nothing else, so it forfeits nothing on the flag-on path; that the shipped value is off is the product's flag-off walk.
- **A file replaced during a request.** A test may wrap Node's `fs.statSync`, which the artifact proxy's own check of a single file uses, so that the real check runs and then the test replaces that file on disk with a folder, before the library that streams files looks at the path again. The wrap changes the real filesystem and nothing the server computes; it forfeits only the race's natural timing, which no test can produce on demand.
- **ID generator.** The server's generator of artifact IDs, share IDs and resource IDs is injected. A test may supply one that returns chosen IDs before falling back to the production generator, so that a newly generated ID can equal an existing one. Production uses `ulid`. The mock forfeits only the randomness of the IDs, which no test can judge.

### Bootstrap and artifact deletion

- **Contract** (a really-running in-process server over temporary storage, driven through real HTTP; with the recording storage-operations adapter, and with the bindings hook where named; one case makes the bindings file's rename fail, which forfeits only a disk that really fails): deleting a shared artifact through the artifact delete route, and deleting a channel that holds one, each delete its record with a flush of its directory, stop its share ID resolving, close the page connections opened under its ID and under its share ID, and leave its store, whose manifest still names it and which is reached by its resource ID. With the flag on, each deletion also removes every binding of that artifact, emits `unbound` for each on the `/events` stream, and leaves the stores, their content and other artifacts' bindings to its own store unchanged; when the bindings file cannot be saved, the deletion still succeeds, and the artifact's bindings still end at once with `unbound` for each. This proves [artifact deletion](../../../specs/arch/resources/index.md#^rs-artifact-delete) — *(policy-grade test: `packages/server/test/resources/events.test.ts` "artifact deletion")*. ^rs-arch-t-artifact-delete

Coverage relationship: loading the layer at [bootstrap step 2](../../../specs/arch/resources/index.md#^rs-bootstrap), before the onboarding installer runs, is crossed by [the installer's declared-store contract](../onboarding/installer.md#^t-onboarding-stores), whose installs write artifacts' stores during that same boot. A binding left behind by a crash between deleting an artifact and removing its bindings is the dangling-binding case of [#^rs-arch-t-startup](#^rs-arch-t-startup).

### Route families and requests from other origins

These contracts run against a really-running in-process server. HTTP requests use Node's `fetch`; WebSocket clients use the shared message framing. No mechanism is mocked; the bindings hook is used where named.

- **Contract — artifact routes.** A page connection at `/artifact-resources/<id>/v1/connection` under an artifact's ID reaches that artifact's store at `read-write`, and one under its share ID at the link's level; neither reaches another artifact's store, including when the connection request carries the server's valid token as a header or query parameter. A path whose ID reaches no artifact connects, and every operation on the artifact's store is refused with `no-store`. No message on a connection carries an artifact ID or a share ID, so a connection under a share ID never receives the artifact's ID. That holds when requests fail: under a `read-write` share link, a write refused because each step of the store's first write in turn fails or has an uncertain outcome (the record's pointer, the store's directory, its manifest and its content), or because a later save of its content does, and every operation while the store's files cannot be read, is refused with `unavailable` whose message says whether the outcome is unknown and carries no artifact ID, share ID or path under the server's home; once the link is revoked, neither the share ID nor any ID the page received reaches the store. With the flag on, a connection reaches exactly the stores its artifact is bound to, its own included, by resource ID, at the lower of its ID's level and the binding's; operations on any other resource ID are refused with `not-bound`; and no message carries another artifact's ID or bindings, including a store's information when it is another artifact's own store or other artifacts are bound to it. With the flag on, after the descriptions and usages of the artifact's own store and of a store bound to it are set to text containing the artifact's ID, a connection under its share ID receives no message carrying that text or that ID: its opening state, its `listResources` and `getResourceInfo` answers, which give each store's resource ID, type and the page's level and nothing else, and its events, among which is no `updated`. Under the same share link, a write to a store bound to the artifact whose save fails or has an uncertain outcome, and every operation on that store, `listResources` and `getResourceInfo` while the bindings file cannot be read, are refused with `unavailable` in messages that carry neither ID nor any path under the server's home, while the artifact's own store keeps working. A tokenless server enforces the same levels. This proves [the artifact routes](../../../specs/arch/resources/index.md#^rs-artifact-routes) and the levels of [resolving an ID](../../../specs/arch/resources/index.md#^rs-resolve-id) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "the artifact routes")*. ^rs-arch-t-artifact-routes
- **Contract — administrative routes.** With authentication on, a request under `/api/resources/v1/` without the bearer token, or with a wrong one, is refused with `401`, and with the token it succeeds, for a JSON store operation and a share change alike. On a tokenless server the same requests succeed without a token, apart from creating a share link. An artifact ID or a share ID presented in place of the token grants nothing. This proves [the administrative routes](../../../specs/arch/resources/index.md#^rs-admin-routes) — *(policy-grade test: `packages/server/test/resources/admin-routes.test.ts` "administrative route authorization")*. ^rs-arch-t-admin-routes
- **Contract — requests from other origins.** On both route families, requests with an `Origin` naming another site, with `Origin: null`, as sandboxed artifact pages send, and with an `Origin` naming the request's own host under `https:`, as pages behind a front that terminates TLS send, are served as requests without `Origin` are. On the administrative routes, a `POST` of the kind browsers send without a CORS preflight (a `text/plain` body) with any of these `Origin`s succeeds with the token; without it, a server that requires the token refuses it with `401` and it changes nothing, and a tokenless server applies it. On the artifact routes, a WebSocket upgrade with any of these `Origin`s opens under an artifact ID at `read-write` and under a share ID at the link's level, where a write under a `read` link is refused with `read-only` and changes nothing; a plain request with any of them is answered with `426`, the page connection being a WebSocket. No response on these routes, including to an `OPTIONS` request, carries a CORS header. No resource route changes state on `GET` or `HEAD`: each state-changing route answers those methods without effect. This proves [requests from other origins](../../../specs/arch/resources/index.md#^rs-any-origin) — *(policy-grade tests: `packages/server/test/resources/admin-routes.test.ts` "requests from other origins on the administrative routes" and `packages/server/test/resources/page-connection.test.ts` "requests from other origins on the artifact routes")*. ^rs-arch-t-origin

### The page connection

These contracts drive page connections with a client that plays the SDK through the shared message framing against a really-running in-process server, using `increment` writes where applying a write twice would show. The storage-operations hook and the bindings hook are used only where named.

- **Contract — the opening state, and connections that stand alone.** The first message on a connection under an artifact's ID carries `read-write`, under a share ID the link's level, and under an ID that reaches no artifact with a store no level; with the flag on it carries the resource ID of the artifact's own store once its first write has created it, and none before then or with the flag off, when the store's first write sends the connection no access, and the artifact's explicit bindings with each store's resource ID, type and the page's level on it, and none for its own store; and it carries the server's time, and nothing that identifies the artifact, the page or an earlier connection. A write sent on a new connection with the sequence number of a write applied on an earlier one is applied again, so the server keeps no record of a page's writes between its connections. This proves the opening state of [the page connection](../../../specs/arch/resources/index.md#The page connection) and its [connections that stand alone](../../../specs/arch/resources/index.md#^rs-page-connection) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "the opening state, and connections that stand alone")*. ^rs-arch-t-opening-state
- **Contract — write order.** Writes on one connection to its artifact's own store and, with the flag on, a bound store are applied in the order sent, and each is answered by its sequence number. Sequence numbers may skip values. This proves [write order](../../../specs/arch/resources/index.md#^rs-write-sequence) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "write order")*. ^rs-arch-t-sequence
- **Contract — checks at application time.** A write through a share ID at `read` is refused with `read-only` and leaves the store and its events unchanged. Changing the link's level between two writes applies the second at the new level. When the artifact's own store is destroyed, the connection's subscriptions to its own store hear no value and stay, and its next write is applied to a new store. A change of the level of a share link to an artifact that has no store sends the connection its access with no level. Changing the artifact's path through the artifacts route from an HTML file to a Markdown file, and back, closes nothing: the connections opened under its ID and its share ID keep their subscriptions and levels, and read the store's value. With the flag off, an operation on a store by resource ID is refused with `not-enabled`. With the flag on: under a share ID at `read`, a write to a store bound `read-write` is refused with `read-only`; rebinding an open connection's artifact from `read-write` to `read` between two writes refuses the second, and unbinding it refuses the next operation with `not-bound`; unbinding ends the connection's subscriptions to that store with `not-bound` and sends `unbound`; destroying the store ends them and sends `destroyed`; a change of the share link's level sends the connection its access, carrying the new level and each explicit binding at the page's new level on it, and then `bound` for each binding whose level for the page changed; the first write of the artifact's own store and its destroy each send the access again, with the store's resource ID and then without it; under the storage-operations hook, a first write refused after its artifact's pointer was saved, whether the pointer's save left its outcome unknown or a later step failed, sends the access with the store's resource ID all the same, and one refused because the pointer was not saved sends none; and when the artifact is deleted while its bindings file cannot be saved, under the storage-operations hook, its subscriptions end with `not-bound`, it receives `unbound`, and no later value or event for that store reaches it. This proves the checks and changes of access of [the page connection](../../../specs/arch/resources/index.md#The page connection) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "checks at application time")*. ^rs-arch-t-checks
- **Contract — notifications before acknowledgement.** On a connection subscribed to the path it writes, the subscription update caused by a write arrives before that write's acknowledgement. This proves [notifications before acknowledgement](../../../specs/arch/resources/index.md#^rs-notify-before-ack) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "notifications before acknowledgement")*. ^rs-arch-t-notify-before-ack

### Events and errors

- **Contract — events.** Against a really-running in-process server with an `/events` client that has received the stream's first message: with the flag off, each write to an artifact's own store emits `changed` with the store's resource ID, the artifact's ID and the paths the write touched; a write by resource ID to a deleted artifact's store names the deleted artifact; changing a description or usage emits `updated` with the store's summary; destroying a store emits `destroyed` with its resource ID and its owner's ID; and nothing else is emitted. With the flag on, creating, binding, rebinding, unbinding, writing to and destroying a created store each emit the matching `ResourceEvent` with the spec's shape, in order, a write's `changed` and the `destroyed` carrying the store's resource ID and no artifact ID, each as `{ type: "resource-event", event }` among the stream's other messages. Destroying a bound store emits `destroyed` and no `unbound`. A client that reads the store's files on receiving an event finds the change already there; for `destroyed`, that is the destroy's first step, an own store's owner's record without `store`. This proves [resource events](../../../specs/arch/resources/index.md#^rs-arch-events), the flag-off rule that [`created`, `bound` and `unbound` are never emitted](../../../specs/arch/resources/index.md#The bindings flag), and the delivery of [the `/events` stream](../../../specs/arch/resources/index.md#^rs-events-stream) — *(policy-grade test: `packages/server/test/resources/events.test.ts` "resource events")*. ^rs-arch-t-events
- **Contract — the stream's token.** On a server that requires the token, an `/events` connection without a token, or with a wrong one, is closed with 4401, and one with the token receives `server-status` as its first message, before any event. On a tokenless server a connection without a token receives it too. This proves the token and first message of [the `/events` stream](../../../specs/arch/resources/index.md#^rs-events-stream) — *(policy-grade tests: `packages/server/test/events.test.ts` "/events websocket stream", in its cases "rejects websocket clients without a valid token using 4401", "rejects websocket clients with an invalid token string" and "sends exactly one server-status message on connect and replays no domain events", and, for the tokenless server, "sends server-status first to a client without a token on a tokenless server")*. ^rs-arch-t-events-token
- **Contract — a page's events.** A page connection for artifact X receives `changed` for X's own store, with the paths and no resource ID or artifact ID, and nothing for another artifact's store, whether under X's ID or its share ID. With the flag on, it receives `destroyed` and `changed` only for the stores X is bound to explicitly, each by resource ID, another artifact's own store included, with no artifact ID; `bound` and `unbound` only for X's own bindings and without an artifact ID; and no `updated` or `created`, so changing a bound store's description or usage sends X nothing; binding and unbinding another artifact Y to a store X uses sends X nothing. This proves the page's subset of [resource events](../../../specs/arch/resources/index.md#^rs-arch-events) and the events of [the page connection](../../../specs/arch/resources/index.md#The page connection) — *(policy-grade test: `packages/server/test/resources/page-connection.test.ts` "a page's events")*. ^rs-arch-t-page-events
- **Contract — administrative refusals.** Each refusal answers with a non-2xx status and `{ error, code }`. With the flag off: `not-enabled` for creating a store, binding and unbinding; `no-artifact` for an artifact store operation, a share change or `list --artifact` naming no artifact; `no-store` for an artifact that has no store; `not-found` for a store operation, `info`, `describe` or `destroy` with a resource ID that names no store, and with a value that is not a resource ID; `invalid-description` for an empty description, one of 1,025 bytes and one with a line break; `invalid-usage`; `still-bound` for destroying an own store whose owner exists without force, with `bindings` listing the owner's binding; `not-shareable`, `not-shared` and `tokenless` for share changes; and `unavailable` for an operation on an unavailable store. With the flag on: `invalid-description` for creating a store without a description; `no-artifact` for binding an ID that names no artifact; `not-bound` for unbinding an artifact that is not bound; `owner-binding` for binding or unbinding an own store's owner; and `still-bound` for destroying a bound store without force, with `bindings` listing each binding, an owner's included. A forced destroy returns the removed bindings. This proves the administrative refusals of [errors](../../../specs/arch/resources/index.md#Errors) and of [the flag off](../../../specs/arch/resources/index.md#The bindings flag) — *(policy-grade test: `packages/server/test/resources/admin-routes.test.ts` "administrative refusals")*. ^rs-arch-t-refusals

Coverage relationship: the web client's indifference to `resource-event` messages on `/events` is the general [unknown-message contract](../updates/version-advertisement.md#^t-unknown-message), which proves that any unrecognized message type is ignored without affecting later messages. This proof orders no resource-specific client test. The stream's lack of an origin check, and what a page on another site can read from it on a tokenless server, is an exposure the spec states as accepted, not behavior to build; no test pins it.

### CLI integration

- **Contract** (authored argv entering the real in-process `runCLI` dispatcher, ending at a fake `TelevisionClient` peer and injected output writers; authored return values are fixtures, and the fake forfeits HTTP, WebSocket and server processing to [#^rs-arch-t-cli-seam](#^rs-arch-t-cli-seam); with the bindings hook where named): `share-artifact --id <id> --access <level>` calls `resources.share` with the artifact ID and level and nothing else, and prints each origin of the reply followed by its path, `<origin>/artifact/<share-id>/`, one per line in the reply's order, as OSC-8 hyperlinks exactly when the output reports a terminal; without `--access` it calls `resources.share` with the artifact ID alone, and with a level that is neither `read` nor `read-write` it is a directive error that makes no call. `unshare-artifact --id <id>` calls `resources.unshare` and prints the product's line. `list`, `info`, `describe`, `destroy` and `events` each make the one call their name matches, with the resource ID passed as `resourceID` and `--artifact` as `artifactID`; `describe` passes a description, a `--usage` text of several lines, or both, and with neither is a directive error that makes no call; `list` and `info` print compact one-line JSON; `describe` and `destroy` print the product's confirmation lines, `describe`'s naming the description, the usage or both, and the forced-destroy line naming each removed binding; `events` prints each event as one compact JSON line, exits `0` on `SIGINT` and on `SIGTERM`, and fails like an unreachable server when its connection ends. With the flag off, `bind`, `unbind` and `json create` are unknown-command directive errors that make no call, and no help lists them: the help of `resource`, by `--help`, `help resource` and `resource help`, lists exactly `list`, `info`, `describe`, `destroy`, `events`, `json` and `help`; the help of `resource json`, by `--help`, `resource help json` and `resource json help`, lists exactly the six JSON verbs and `help`; and top-level help, by `--help` and `help`, names neither binding command. With the flag on, `bind` and `unbind` pass the resource ID, the artifact ID and, for `bind`, the level, and print the product's lines; `bind` writes the tokenless warning to stderr exactly when the result's `authRequired` is false, and without `--access` is a directive error that makes no call. An HTTP status error from the client is printed as other HTTP status errors are. This proves [the share commands' integration](../../../specs/arch/resources/index.md#^rs-share-cli-integration) and [CLI integration](../../../specs/arch/resources/index.md#^rs-cli-integration) — *(policy-grade tests: `packages/cli/test/resource-commands.test.ts` "the share commands", "the common commands", "the commands the flag leaves out" and, with the flag on, "binding")*. ^rs-arch-t-cli-contract
- **Seam** (the CLI command action → a really-running in-process server, through the shared client's real HTTP and WebSocket transports; commands receive the server's home and port; injected output writers replace process streams but no mechanism on the handoff; the bindings hook turns the flag on in both the CLI environment and the server where named): `share-artifact` reaches the administrative routes and prints a link whose address the server then serves as the artifact, and `unshare-artifact` revokes it. Without `--access`, `share-artifact` creates a `read` link; after `--access read-write`, it fails with the server's refusal, which names `--access`, and the link stays `read-write`. With the flag on, created stores and bindings go through their life: with `events` running, the walk creates two stores with `json create`, one with a usage of several lines, each printing its resource ID; binds artifact A to the first at `read-write` and to artifact B's own store at `read`; runs `list --artifact`, `info`, `describe` with a description, with `--usage` and with both, `unbind`, and `destroy` without and with `--force`; each reaches the administrative routes and prints the product's output, ordered as the spec orders it, each store with its resource ID and its usage as last set; `destroy` while artifacts are bound fails, names each with its access level, mentions `--force`, and leaves the store, and `destroy --force` prints the confirmation line naming the removed bindings; after A is deleted, `info` on B's own store shows A's binding gone; `bind` and `unbind` of B to its own store are refused, saying that an artifact is always bound to its own store. `events` prints one compact JSON line for each change in order (`created`, `bound`, `updated`, `unbound`, `changed`, `destroyed`), the `changed` line naming the path the walk wrote, and nothing for an artifact created while it runs. Refusals cross too: `info` for a resource ID that names no store fails with `Resource not found: <resource-id>`, `json create` without `--description` is a directive error, and with an empty description creates nothing. On a tokenless server, `bind` succeeds with its confirmation line and writes exactly the product's warning to stderr, and with authentication on it writes nothing to stderr. `events` fails like an unreachable server when the server ends its connection and where nothing listens, and with a token the server rejects it fails with the same unauthorized message as `list`, though the stream reports the rejection by closing with 4401 rather than with an HTTP status. This proves the transport half of [the share commands' integration](../../../specs/arch/resources/index.md#^rs-share-cli-integration) and [CLI integration](../../../specs/arch/resources/index.md#^rs-cli-integration), and, with the flag on, [creating stores and bindings](../../../specs/product/resources/resources.md#^rs-binding), [usage](../../../specs/product/resources/resources.md#^rs-usage), [destroying a bound resource](../../../specs/product/resources/resources.md#^rs-destroy-bound), [the bind warning](../../../specs/product/resources/resources.md#^rs-cli-bind), the commands' half of [tokenless mode](../../../specs/product/resources/resources.md#^rs-tokenless) and agents' [events](../../../specs/product/resources/resources.md#^rs-events) — *(policy-grade tests: `test/node/resource-cli-integration.test.ts` "the share commands against a running server" and "created stores and bindings against a running server", whose walk turns the flag on)*. ^rs-arch-t-cli-seam
