*How the JSON store's architecture is proven: the shared module's path, value and write rules as contracts, the content file, the server's write application, durability failures, transactions and subscriptions against a running server, the SDK's local-write model and reconnection in a real browser, and the `tv resource json` CLI integration.*

# JSON store architecture — proof

Proves [specs/arch/resources/json-store.md](../../../specs/arch/resources/json-store.md).

## Coverage model

Breadth is proven in three places, each at the cheapest boundary that does not misrepresent it. The product spine is walked in [the JSON store product proof](../../product/resources/json-store.md), whose built-CLI and browser walks sample the rules below rather than enumerate them.

The shared module's rules for paths, values, applying a write, equality, child order, limits and push keys are pure contract tests in Node with authored inputs and no mocks. The server, the SDK and the CLI all import that one module, so these contracts compose into every caller through a single handoff, and the server and browser tests below cross it for real.

Server behavior is proven by contracts against a really-running in-process server over temporary storage on the real filesystem, driven by administrative HTTP and by clients that play the SDK through the shared message framing. Durability failures, which a real filesystem cannot produce on demand, use [the resource architecture's storage-operations hook](./index.md#Test hooks); its mock forfeits real disk failure, which no automated test can stage.

The SDK's behavior is proven in a real browser loading the module as the server serves it, from a plain-HTTP origin that is not `localhost`, under [the SDK proof's harness](./sdk.md#Test hooks). This spec's testing directive is honored in the section [Local writes in a real browser](#Local writes in a real browser): a write the server refuses after the page showed it, a connection lost while the page has unconfirmed `increment` writes, one of which the server applied before the loss, and writes and reads made while the page is disconnected. Those tests stand in for a network with the SDK proof's network proxy; the server and its storage are otherwise real.

The CLI verbs are covered by an in-process contract with a fake client, which forfeits transport to a seam with a real server; how `watch` follows a value through the event stream is a contract of the shared client against a scripted server; and by [the product command walk](../../product/resources/json-store.md#^js-ac-cli) through the built CLI.

## Assertions

### The shared module

These are contracts on the shared module's exported functions with authored inputs and no hooks. The push-key contract sets the system time with Vitest's fake clock, which forfeits only the passage of real time; no other mock is used.

- **Paths, equality and order.** Parsing splits on `/` and drops empty segments, so `""`, `"/"` and `"a//b/"` address the root and `a/b`. A segment over 768 UTF-8 bytes is refused with `invalid-path`, and so is a path of 33 segments. `0` and `12` are indices and `01` is not; an index addresses an array element when the parent is an array and a member otherwise, and reading through an array with a non-index or an index past its end finds no value. Equality ignores object key order. Children order index keys first, numerically, then other keys by UTF-16 code units. This proves [paths](../../../specs/arch/resources/json-store.md#^js-arch-paths), the segment limit of [limits](../../../specs/arch/resources/json-store.md#^js-arch-limits), and the equality and child order of [applying a write](../../../specs/arch/resources/json-store.md#^js-arch-apply) — *(policy-grade tests: `packages/shared/test/resources/json-paths.test.ts` "JSON store paths" and "JSON store equality and child order")*. ^js-arch-t-paths
- **Values.** `null`, booleans, finite numbers, strings, arrays and plain objects are accepted. `undefined`, `NaN`, `Infinity`, a function, a `Date`, a `Map` and a class instance are refused with `invalid-value`, as is an object key that is empty, contains `/` or exceeds 768 bytes. A server-value placeholder may stand anywhere in a written value, and a delete placeholder only as an `update` entry; elsewhere it is refused with `invalid-value`. A plain object with the key `.sv` is stored as written. This proves [values](../../../specs/arch/resources/json-store.md#^js-arch-values) — *(policy-grade test: `packages/shared/test/resources/json-values.test.ts` "JSON store written values")*. ^js-arch-t-values
- **Applying a write.** Setting below a missing parent, or below a string, number, boolean or `null`, creates objects along the path. Setting an existing array element works; setting an index at or past the array's length, a non-index key below an array (as `push` below an array would), or a path below a missing element is refused with `invalid-path`. Deleting an array element is refused with `invalid-path`; deleting a path with no value changes nothing and creates no parents. An `update` applies all its entries or none, and one whose keys address the same path once parsed, such as `a` and `a/`, or one within another, such as `a` and `a/b`, is refused with `invalid-path`, changing nothing. This proves [applying a write](../../../specs/arch/resources/json-store.md#^js-arch-apply) — *(policy-grade tests: `packages/shared/test/resources/json-apply.test.ts` "applying a set", "applying a delete" and "applying an update")*. ^js-arch-t-apply
- **Limits.** A value whose compact JSON is exactly 1,048,576 bytes is accepted and one byte more is refused with `too-large`, whether the excess comes from the written value or the rest of the store. A value at depth 32, 32 keys below the store's root, is accepted, and a write that would put a value at depth 33 is refused with `invalid-path` and changes nothing, in three cases: a scalar written at a 33-segment path, a value written at the root whose deepest member lies 33 keys below it, and a value whose deepest member lies 3 keys below it written at a 30-segment path. A write's message of exactly 16,777,216 UTF-8 bytes, including multibyte characters, passes the sender's measure, and one byte more is refused with `too-large`. This proves [limits](../../../specs/arch/resources/json-store.md#^js-arch-limits) and the measure of [the message limit](../../../specs/arch/resources/json-store.md#^js-arch-write-limit) — *(policy-grade tests: `packages/shared/test/resources/json-limits.test.ts` "the size limit", "the depth limit" and "the message limit")*. ^js-arch-t-limits
- **Push keys.** Keys are 20 characters from the spec's alphabet. Keys generated at increasing clock times sort in that order, and their first 8 characters encode the time. Many keys generated within one millisecond are distinct and sort in generation order. This proves [push keys](../../../specs/arch/resources/json-store.md#^js-arch-push-keys) — *(policy-grade test: `packages/shared/test/resources/push-keys.test.ts` "push keys")*. ^js-arch-t-push-keys

### The server

These contracts run against a really-running in-process server over temporary storage on the real filesystem. Writes are sent through administrative HTTP or by a client that plays the SDK through the shared framing. Hooks are used only where named.

- **The content file.** After writes to an artifact's store, its `content.json` holds the value as compact JSON, `null`, `{}` and `[]` included, and removing the whole value deletes the file and leaves the manifest, so the store reads as having no value across a restart while one holding `null` reads as `null`. A `content.json` replaced by the same value pretty-printed reads back as that value. One that is not valid JSON, and one whose value breaks a limit, make the store unavailable when it loads, and each is left byte-identical. This proves [the content file](../../../specs/arch/resources/json-store.md#^js-arch-content-file) — *(policy-grade test: `packages/server/test/resources/startup.test.ts` "a JSON store's content file")*. ^js-arch-t-content-file
- **Write application.** Writes from several clients to one store, sent concurrently, are each applied whole, one at a time: every intermediate value the store reports equals the result of applying some prefix of them in one order. `serverTimestamp()` is filled with a server time between the request's sending and its acknowledgement; `increment(n)`, including nested in an object, is filled with the number before the write plus `n`, or `n` where no number was. This proves [applying writes](../../../specs/arch/resources/json-store.md#^js-arch-apply-writes) — *(policy-grade test: `packages/server/test/resources/json-store-server.test.ts` "applying writes on the server")*. ^js-arch-t-apply-writes
- **Changed paths.** Against a really-running in-process server, each write emits one `changed` whose `paths` list what it touched: a `set` and a `remove` their path; a `push` its path with the new key; an `update` with entries at nested paths each entry's full path below the update's path, in the order of its entries; a transaction's write its path; and a write at the whole value the empty string. A path given with extra slashes is listed by its segments joined with single slashes. This proves [changed paths](../../../specs/arch/resources/json-store.md#^js-arch-changed-paths) — *(policy-grade test: `packages/server/test/resources/json-store-server.test.ts` "the paths a changed event lists")*. ^js-arch-t-changed-paths
- **Durability failures.** With the storage-operations hook failing a step before the rename, the write is refused, the file and the value reads return are unchanged, and the store stays available. With the hook failing the directory flush after the rename, or after the deletion of `content.json` that removes the whole value, the write is refused with `unavailable` and a message saying that its outcome is unknown, and the store takes the write's result, or no value, as its value: a subscriber hears it as a change, on the page connection carrying the write's sequence number and before the refusal; `changed` is emitted with the write's paths; `get` returns it; no `updated` is emitted; and the store stays available, so a following write succeeds. When the failing flush first leaves the file not valid, or reading it back then fails, the value before the write stands, the write is refused the same way, nothing is heard or emitted, and the next successful write saves a file built on that value. This proves the failure rule of [applying writes](../../../specs/arch/resources/json-store.md#^js-arch-apply-writes) and [an uncertain write](../../../specs/arch/resources/json-store.md#^js-arch-uncertain) — *(policy-grade test: `packages/server/test/resources/json-store-server.test.ts` "durability failures")*. ^js-arch-t-uncertain
- **The message limit.** A `set` whose message is exactly 16,777,216 bytes, almost all of it `increment` placeholders whose result fits the size limit, is applied through the page connection and through the administrative route. One byte more closes the page connection with 1009 and is refused by the administrative route with `too-large`, and neither changes the store. This proves the server's side of [the message limit](../../../specs/arch/resources/json-store.md#^js-arch-write-limit) — *(policy-grade test: `packages/server/test/resources/json-store-server.test.ts` "the message limit")*. ^js-arch-t-write-limit
- **Read order and sequence numbers.** A page's `get` and subscription sent on a connection directly after its write reflect that write, and every value sent on the connection carries the highest sequence number of that connection's writes it includes. On a new connection, values count only the new connection's writes. This proves [read order](../../../specs/arch/resources/json-store.md#^js-arch-read-order) — *(policy-grade test: `packages/server/test/resources/json-store-page.test.ts` "read order and sequence numbers")*. ^js-arch-t-read-order
- **Compare-and-set.** A transaction write is applied only when the value at its path equals the value it carries, including the case where both are absent; otherwise it is refused and the reply carries the current value. This proves the server's compare-and-set step of [transactions](../../../specs/arch/resources/json-store.md#^js-arch-transactions) — *(policy-grade test: `packages/server/test/resources/json-store-page.test.ts` "compare-and-set")*. ^js-arch-t-cas
- **Subscriptions.** On registration a subscriber receives the current value or its absence, and then a value after each applied write that changes the value or existence at its path. A write elsewhere in the store, and a write that leaves the path's value equal, send it nothing. This proves [subscriptions](../../../specs/arch/resources/json-store.md#^js-arch-subscriptions) — *(policy-grade test: `packages/server/test/resources/json-store-page.test.ts` "page subscriptions")*. ^js-arch-t-subscriptions
- **Access classification.** Through a share ID at `read`, `get` and subscriptions succeed, while `set`, `update`, `push` with a value, `remove` and a transaction's compare-and-set are each refused with `read-only` and change nothing. This proves the read and write classification the [type contract](../../../specs/arch/resources/index.md#^rs-type-contract) requires, as [the product's access rule](../../../specs/product/resources/json-store.md#^js-access) states it — *(policy-grade test: `packages/server/test/resources/json-store-page.test.ts` "access classification")*. ^js-arch-t-access

### Local writes in a real browser

Shared declaration: shape contract on the SDK's public interface; a real browser loads the served module from a mapped plain-HTTP host name, and a really-running in-process server serves the page, through the network proxy where named; authored HTML artifacts using their own stores, opened through their own IDs or through share links, are fixtures, with a created store bound to one where named, and other clients write through administrative HTTP. The network proxy and the bindings hook are used only where named.

- **The SDK's functions.** `ref` and `child` throw `invalid-path` for a path breaking the path rules, as does `push`, with or without a value, when its key would make a path of more than 32 segments, showing and sending nothing; references expose `key`, `parent`, `root` and `path` as specified, and `getStore()` returns the artifact's store, whose `resourceID` is `null`. A snapshot's `exists`, `val`, `child`, `forEach` (stopping when the callback returns true), `size` and `metadata` behave as specified. `push` returns a reference with its key synchronously, which resolves with the new child's reference when the write is confirmed and rejects when it is refused; `push` without a value resolves at once and sends nothing, observed through the network proxy. Awaiting `push` gives a reference with the returned reference's key and path, which is not itself a promise and reads the written value, and so does a confirmation chained through `catch` or `finally`. The reference has `catch` and `finally`, so chaining `catch` onto `push` works: `catch` hears a refusal by the server, after the page showed the write, and not a confirmation, and `finally`, chained after `catch` or straight onto `push`, runs once the write settles either way, its own promise settling as the write did. `set(ref, null)` stores `null`, and `deleteValue()` in `update` deletes its path. `set` with `NaN` or `undefined` rejects with `invalid-value` and changes nothing in the store. This proves [the SDK functions](../../../specs/arch/resources/json-store.md#^js-arch-sdk) and their [error codes](../../../specs/arch/resources/json-store.md#^js-arch-errors) — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "the SDK's functions")*. ^js-arch-t-sdk
- **The local view.** With the network proxy holding the server's replies: a write is shown at once; the page sees its confirmed value with queued writes applied in order; `hasPendingWrites` is true for snapshots at the write's path, above it and below it, and false elsewhere; estimated server values appear, a timestamp near the server's time and an increment of the number the page sees, and are replaced by the server's values on release. On release, each location's `onValue` listeners receive a snapshot with `hasPendingWrites` false, including where the value did not change, and no other listener is called for that change alone. A change from another client arriving under a queued write is shown with the write reapplied on top. With the bindings hook, on a page listening at its artifact's own store through both `getStore()` and its resource ID, a write through either address is shown at once at both with `hasPendingWrites` true, both hear it confirmed with `hasPendingWrites` false, a transaction through the resource ID, at a path where only `getStore()` listens, starts without fetching from the value that a write through `getStore()` shows, and resolves with a snapshot whose `hasPendingWrites` is true while a later write through `getStore()` is unconfirmed, and a write that a lost connection rolls back is rolled back at both. When the store is destroyed while a write through its resource ID is unconfirmed, the `getStore()` listener stops showing the write once the page hears its access without that resource ID, and still does not show it once the server refuses the write with `not-bound`. Child events are computed from successive values: added, removed and changed children in child order, `onChildAdded` for every child of the first value, and none for a value that is not an object. When a callback writes, every listener hears the change being delivered before the change the write makes: a list kept from `onChildAdded` and `onChildRemoved`, whose `onChildAdded` callback removes one child as it hears another added, ends equal to the store, whether the children arrive in the listener's first delivery or from the page's own write; and when one `onValue` callback writes, a second `onValue` listener at the same location hears the values in the order the page showed them. When one callback writes several times, every listener hears each change in turn: both `onValue` listeners hear every value the writes produce, a listener the callback adds after its writes first hears the value the page shows then, and a child that the writes add and then remove is heard added and then removed. A change reaches every watched path before a callback's write changes the store again: when a callback at one path writes twice, a listener at the store's root hears each state in turn. A listener starts from the value where it was added: added where the value is known and followed at once by a write, it hears that value and then the change, so an `onChildRemoved` listener hears the removal of a child that was present when it was added. A snapshot's value and `hasPendingWrites` stand as they did at the change that called the listener: when another client's change adds two children and the `onChildAdded` callback for the first writes to the second, the second child's `onChildAdded` snapshot and the location's `onValue` snapshot carry the other client's values with `hasPendingWrites` false, and the write is heard afterwards as a change of its own, pending and then confirmed. Across seeded generated programs, in which listeners of every kind sit at overlapping paths in two stores sharing the page's one connection, its artifact's own store and, with the bindings hook, a created store bound to the artifact at `read-write`, and their callbacks write with `set`, `update`, `remove`, `increment`, `push` and transactions, add and remove listeners and throw, each listener hears, in order, exactly the states the page showed from the one it was added in (or, added where no value was known, from the first the server sent), and the server stores the last; the expected states are replayed from the page's recorded writes with the shared write rules, which [their own contracts](#^js-arch-t-apply) prove. After a page opened through a share link learns that its access is `read`, a write rejects with `read-only` before any listener is called, and, with the bindings hook, so does a write to a store bound to the artifact once the page learns that its level on it is `read`, from the opening state under a share link at `read` or from a `bound` event, and a write to the artifact's own store by its resource ID, whether the page received that resource ID in the opening state or when another client's first write created the store. With the bindings hook, under a share link changed to `read`, a write made in the `onAccessChanged` callback that hears the change is refused this way for the artifact's own store by either address and for a store bound at `read-write`; changed back to `read-write`, a write that callback makes to the bound store is shown and applied; and on a page of an artifact that has no store, bound to two stores at `read-write`, a write made in the `onResourcesChanged` callback that hears the first become `read` is refused this way for the second. In each case the network proxy sees no write sent. Once the connection that reported the level has closed, whether because nothing was outstanding or because it was lost, and the link's level has become `read-write`, a write is shown and applied. A `set` of `increment` placeholders whose message would exceed the message limit rejects with `too-large` before any listener is called, and the network proxy sees nothing sent. A write that a listener makes as it hears the page's own write is sent after that write, and both are applied. Changing an object after passing it to `set`, `update` or `push`, or after returning it from a transaction's function, changes neither what the page sees nor what is stored. An `update` of an array's existing elements whose result is within the size limit, though the same keys would exceed it in an object, is shown at once and applied. This proves [local writes](../../../specs/arch/resources/json-store.md#^js-arch-local-writes) and the SDK's side of [the message limit](../../../specs/arch/resources/json-store.md#^js-arch-write-limit) — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "the local view")*. ^js-arch-t-local-view
- **A write the server refuses after the page showed it.** On a page opened through a share link at `read-write`, with the network proxy holding traffic in both directions, the page writes, its listener shows the write, and the link's level is changed to `read` through the administrative route. On release, the server refuses the write with `read-only`, the listener receives the previous value, the write's promise rejects with `read-only`, and the store is unchanged. This proves the refused-write rule of [local writes](../../../specs/arch/resources/json-store.md#^js-arch-local-writes) for access changed while the page is open — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "a write the server refuses after the page showed it")*. ^js-arch-t-refused-after-shown
- **A lost connection with unconfirmed writes.** The network proxy holds the server's replies to a page's `increment` write, which the server applies, then holds the page's next `increment` write, which the server never receives, and severs the connection. At once, without the page clock, both writes roll back: the page's listener hears the value without them, both promises reject with `disconnected`, and `getConnectionStatus` already returns `disconnected` when they do; a write the listener makes as it hears the rollback rejects with `disconnected` too. Another client changes the store twice while the page is disconnected. When the proxy accepts again, neither write is sent again, as the proxy shows; the listener hears the current value once, which includes the applied increment and the other client's last change but not its first; and the store shows the first increment applied exactly once and the second not at all. This proves the rollback at a loss of [local writes](../../../specs/arch/resources/json-store.md#^js-arch-local-writes), the loss and resubscription of [reconnection](../../../specs/arch/resources/sdk.md#^sdk-reconnect), and the listener rule after a reconnection — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "a lost connection with unconfirmed writes")*. ^js-arch-t-lost-connection
- **Reads and writes while disconnected.** With the network proxy refusing connections after a cut: `get` rejects at once with `disconnected`; `set`, `update`, `remove`, `runTransaction` and `push` with a value each reject at once with `disconnected`, `push` still returning its reference with its key, and the transaction's function is never called; no listener is called for any of them. A `get` outstanding when the connection is lost, its reply held by the proxy, rejects with `disconnected`. An `onValue` listener registered before the loss, and one registered during it at a path no listener holds, stay registered: when the proxy accepts again, none of the refused writes is sent and the store is unchanged by them, both listeners hear the store's current value, which another client changed during the loss, and both hear later changes. A write made after the reconnection is shown and applied. This proves the disconnected rules of [reconnection](../../../specs/arch/resources/sdk.md#^sdk-reconnect) for the JSON store's functions, the disconnected refusal of [local writes](../../../specs/arch/resources/json-store.md#^js-arch-local-writes) and [transactions](../../../specs/arch/resources/json-store.md#^js-arch-transactions), and the store's half of [the product's connection promise](../../../specs/product/resources/resources.md#^rs-connection) — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "reads and writes while disconnected")*. ^js-arch-t-disconnected
- **Waiting for a first connection.** While the network proxy holds the server's opening state on the page's first connection, a `set` and a `get` made then neither fail nor send anything. When the opening state is released, the write is sent and applied, the `get` is answered with the write's value as pending, and an `onValue` listener registered with them first hears that value as pending, then confirmed. When the proxy instead ends a first connection before its opening state, a `set` and a `get` made while it was connecting reject with `disconnected`, and the write rolls back: it is never sent, and the listener's first value after the reconnection does not include it. This proves the waiting rule of [the connection status](../../../specs/arch/resources/sdk.md#^sdk-connection-status) for the JSON store's functions and the rollback of [local writes](../../../specs/arch/resources/json-store.md#^js-arch-local-writes) for a connection that closes before its opening state — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "waiting for a first connection")*. ^js-arch-t-first-connection
- **Transactions.** The function receives the value the page sees, fetched first when no listener holds it. Returning `undefined` aborts with `committed` false and sends nothing. When another client changes the value between the function's call and its write, arranged by the function itself on its first call, the function is called again with the current value and the transaction commits once. A function whose value is changed before every attempt rejects with `max-retries` after 25 calls. Each attempt is shown as an unconfirmed write, replaced by the next, and rolled back after an abort or failure; a committed transaction resolves with a snapshot of the value after it. This proves the SDK's side of [transactions](../../../specs/arch/resources/json-store.md#^js-arch-transactions) — *(policy-grade test: `packages/server/test/e2e/resource-json-store-sdk.spec.ts` "transactions")*. ^js-arch-t-transactions

### CLI integration

- **Contract** (authored argv entering the real in-process `runCLI` dispatcher, ending at a fake `JsonStoreClient` and injected output writers with an injected standard input; authored return values are fixtures, and the fake forfeits HTTP, WebSocket and server processing to [#^js-arch-t-cli-seam](#^js-arch-t-cli-seam); with the bindings hook where named): each verb but `create` passes `--artifact` or `--resource` as the store address `artifactID` or `resourceID`, and neither or both is a directive error that makes no call, as is an option the commands do not define, such as `--name` or `--resource-id`; `set`, `update` and `remove` print the product's confirmation line naming the store as it was addressed; a value comes from its argument, from `--file <path>` read from a temporary file, or from `--file -` read from standard input, and giving both is refused; text that does not parse as JSON is a directive error and makes no call; `set` and `update` with one argument after the store take it as the value for the whole value; a path of `/` and an omitted optional path both pass the root; with the flag on, `create` passes `--description` and `--usage`, a usage of several lines included, and a value to the client and prints the resource ID it returns as `{"resourceID":"<resource-id>"}`, and without `--description` it is a directive error that makes no call; `push` generates its key with the shared module, passes it to the client and prints it; `get` and `watch` print the exists-or-not shape; `watch` exits `0` on `SIGINT` and `SIGTERM` and fails like an unreachable server when its connection ends. This proves [the commands](../../../specs/arch/resources/json-store.md#^js-arch-cli) — *(policy-grade test: `packages/cli/test/resource-commands.test.ts` "the JSON store commands")*. ^js-arch-t-cli-contract
- **Contract — `watch`** (the shared client's `watch` over its real HTTP and WebSocket transports, against a scripted test server that plays the `/events` stream and the JSON store's `get` route, records each `get` it answers, and holds each answer until the test releases it; the script forfeits the real server's emission and timing, which [the seam below](#^js-arch-t-cli-seam) crosses): `watch` sends no `get` before the stream's first message, then passes the first `get`'s result. `watch` recognizes its store by the address it was given: by the event's `artifactID` for `--artifact` and its `resourceID` for `--resource`, so a `watch` by artifact ID started before the store's first write follows that write's event, whose resource ID it never knew. A `changed` event for another store, or for its store whose paths neither equal the watched path, contain it nor lie within it, causes no `get`; one listing an equal, a containing or a contained path causes one. While a `get` is held, three more such events cause exactly one more `get`, sent only after the held one is answered. A result equal to the last one passed, including an object with its keys in another order, passes nothing. A `destroyed` event naming the resource ID it was given ends a `watch` by `--resource` with `not-found`, and one naming the artifact it was given makes a `watch` by `--artifact` read again and print that the store has no value; a `get` refused with `not-found` ends it with that refusal, and the stream's other messages and other stores' events change nothing. - **Seam** (the CLI command action → a really-running in-process server through the shared client's real HTTP and WebSocket transports; injected output writers replace process streams but no mechanism on the handoff; the bindings hook turns the flag on in both the CLI environment and the server where named): `get`, `set`, `update`, `push`, `remove` and `watch` reach the server's JSON store routes for an artifact's store by `--artifact` and by `--resource`, `watch` through the `/events` stream as well, and each change appears in the next `get`; with the flag on, `create` makes a store that the same verbs reach by `--resource`. A running `watch` prints a line with the new value after a change at its path and none for a write elsewhere in the store, and after a burst of writes at its path ends, its last line equals what `get` returns. A value given on the command line with a `.sv` key is stored as written, since command-line values are plain JSON. JSON text whose number is too large to be finite, such as `1e400`, parses to an infinity; `set`, `update` and `push` given one, and with the flag on `create`, at the top of the value or nested in it, fail with the `invalid-value` refusal and change nothing, rather than storing the `null` that serializing it would send. A `set` whose request body would exceed the message limit fails with the `too-large` refusal even when the command is given an address where nothing listens, since the shared client refuses it before sending. `watch` with a token the server rejects fails with the same unauthorized message as `get`, though the stream reports the rejection by closing with 4401 rather than with an HTTP status; where nothing listens it fails like an unreachable server. This proves the transport half of [the commands](../../../specs/arch/resources/json-store.md#^js-arch-cli), the shared client's side of [the message limit](../../../specs/arch/resources/json-store.md#^js-arch-write-limit) and, for command-line values, [values](../../../specs/arch/resources/json-store.md#^js-arch-values) — *(policy-grade tests: `test/node/resource-cli-integration.test.ts` "the JSON store commands against a running server", among them "events and watch fail like an unreachable server where nothing listens")*. ^js-arch-t-cli-seam
