# Blaxel Test Shards — proof

Proves [specs/arch/test-runner/blaxel-testshards.md](../../../specs/arch/test-runner/blaxel-testshards.md).

## Coverage model

The host marker’s provider-selection behavior and one-file local limit are covered by [the runner marker proof](test-runner.md#^t-blaxel-host-marker) and [local admission proof](test-runner.md#^t-runner-file-admission). The setup sentence directs callers to those rules rather than defining a second marker mechanism. The runner’s [live remote handoff](test-runner.md#^t-runner-remote-handoff) adds native-entrypoint and retry-policy evidence on the real planned and targeted paths; this proof retains ownership of Blaxel transport, leasing, and setup. The corporate credential location is setup information checked by human review, not a new token-source mechanism. The existing token-source assertions remain unchanged; no test reads the vault or asserts its item name.

Coordinator lease ordering and pool decisions are checked cheaply as contracts that substitute the worker's operations; they claim no worker or transport coverage. Under the [worker-code rule](../../../specs/arch/test-runner/blaxel-testshards.md#^blaxel-worker-code-live), the code that manages workers (leasing, the owner audit, stopping processes, temporary cleanup, checkout and dependency setup) runs only in the live acceptances below. Worker behavior those acceptances do not reach has no automated test: legacy, incomplete and unreadable lease records, deletion reservations, including reserving a worker whose expired lease's processes could not be stopped, audit mode, an unreadable owner audit, races for the short guard, unexpected mount boundaries and directory identity changes during cleanup, dependency reinstallation after a declaration change, and the stale-owner diagnostic's execution.

The live acceptances below enter through the canonical CLI on a dedicated pool: normal retrieval, refusal while another coordinator holds the worker, recovery after coordinator death, and pool creation/deletion. They share a small committed fixture selection and fresh workers rather than repeating a full suite for every failure permutation. Both planned and targeted execution paths are crossed. Resource retention composes with [reporting's diagnostics assertions](reporting.md#Resource diagnostics); helper teardown belongs to [the testing-policy proof](../testing-policy.md#Worker-owned builds).

The spec's [testing guidance](../../../specs/arch/test-runner/blaxel-testshards.md#testing-guidance) require real API/transport, fresh provisioning, and observed Node/Chromium temporary paths. Private workers and bounded disposable processes supply those observations; no deliberately exhausted host or shared-pool contamination is needed. The live driver and its native fixtures live in `experiment:blaxel-harness` and `experiment:blaxel-harness-fixtures`, excluded from `all` and ordinary CI by their experiment kind. Mocks below forfeit those crossings to the named live assertions. The live driver shares these observations within one fresh private pool; focused coordinator contracts carry uncommon coordinator failure permutations without repeating paid-service runs.

`test/repo/blaxel-stale-owner-audit.test.ts` checks the diagnostic's construction and the coordinator's ordering without running the diagnostic. `test/repo/test-runner-provider.test.ts` exercises shell activation ordering with an authored nvm replacement in a shell isolated from host startup files. That contract check does not install nvm or establish real worker activation.

Repository selection composes several pieces across clean seams. A contract test proves URL conversion. A seam test runs real Git against a temporary checkout's `origin` to prove selection, and a process-boundary test runs the real coordinator to prove that an unusable selection stops it before dispatch. The coordinator's use of the selector and the generated script is a source assertion. The live runs that the spec's [testing guidance](../../../specs/arch/test-runner/blaxel-testshards.md#testing-guidance) orders for a repository-selection change carry the GitHub transport, token, and real worker handoff: they run from checkouts of two repositories on the same pool, including workers whose checkout last served the other repository. When the two runs' commits have identical dependency declarations, those workers' logs must show no clone and a `deps` cache hit, which is the live evidence that switching repositories keeps installed dependencies. Within one repository, the live retrieval acceptance observes a dependency-cache miss on fresh workers and a hit on the next run.

Pool discovery also has a contract test that runs the shared discovery helper used by the pool manager and coordinator with the installed Blaxel SDK against a loopback HTTP server returning authored paginated sandbox responses. The SDK builds requests and handles pages through its native-fetch path over loopback HTTP. This proves page traversal, label filtering and deployed-only filtering; production HTTP/2 transport, real authentication and service compatibility are covered by live evidence: a read-only multi-page listing and the required live Blaxel run.

## Test hooks

`readBlaxelGithubToken` accepts `cwd` (the directory containing `.blaxel-gh-token`) and `env` (the environment source), so tests can control token precedence without changing process-wide state. The coordinator uses the process defaults.

`acquireShardLeases` accepts `acquire` (one lease attempt), `transferShardInputs` accepts `write` (one sandbox-file upload), and `finishInterruptedRun` accepts `preserveReport` (the initial interrupted report write), `releaseLeases` (remote process and lease cleanup), and `finalizeReport` (the final interrupted report write). Tests may supply recording or failing callbacks to isolate scheduling, ordering, and failure handling. Under the testing policy's [mocking policy](../../../specs/arch/testing-policy.md#Mocking policy), these replacements earn no coverage of the Blaxel API, sandbox file upload, or remote cleanup.

`resolveBlaxelRepositoryUrl` accepts `cwd`, the checkout whose `origin` it reads; the coordinator uses the process working directory. The generated `deps` script writes its hit-or-miss outcome to `TV_TEST_DEPS_CACHE_STATUS_FILE`, which the worker reports in the shard's setup phases.

The SDK reads `BL_API_URL`, `BL_API_KEY`, and `BL_WORKSPACE`; the discovery contract test supplies a loopback API and fixture credentials in an isolated working directory and home, with an explicit child environment that preserves the test owner token and disables SDK telemetry and HTTP/2. Production uses the configured Blaxel API and credentials.

A coordinator milestone hook, enabled only by `TV_TEST_RUNNER_SELFTEST`, can wait on a fixture-controlled rendezvous immediately before report download while renewal continues; ordinary runs do not wait. It changes scheduling, not lease state, process results, or report bytes. Live recovery uses the existing `--lock-ttl-seconds` override to shorten the abandonment wait, not a fake clock or altered retry budget.

`retainAttemptEvidence` accepts the lease’s SDK filesystem and a coordinator download directory. The prepared-but-undispatched contract substitutes an authored worker results tree for the SDK reads and a no-op worker teardown; local writes remain real. The worker's own inventory and teardown are carried by the live acceptances. Production reads the worker results tree through the installed SDK.

Pool-management contract tests may supply recording/failing SDK operations; ordinary pool commands use the installed SDK. These substitutions forfeit provider behavior to the live pool acceptance below.

### Lease, recovery, and scratch

- **Seam — stale-owner lockout.** In the live harness, on one fresh private worker before any fixture run, the driver issues the production lease commands through the SDK with the coordinator's own shell wrapper: it acquires a lease with a short recovery interval, prepares it and registers a dispatch whose entry request it holds back. Once the worker's lease deadline has passed, that old identity's renewal is refused, and a process carrying an unrelated owner token holds the worker: a new acquisition is refused and the old record is kept. After that process is stopped, the new acquisition recovers the old lease with a confirmed-cleanup receipt. The held-back entry request then fails with the lease-lost refusal and never runs its script, which would create a sentinel file; the old identity's renewal and release are refused and leave the new record. The new owner tears down and releases. Refusals are observed as the lease command's exit `42` and stated reason. The fixtures are the authored lease inputs, the entry script and the token-bearing `sleep`; no mechanism is mocked. This proves [registration, renewal and release](../../../specs/arch/test-runner/blaxel-testshards.md#leases) and [recovery's hold on unknown owners](../../../specs/arch/test-runner/blaxel-testshards.md#abandoned-runs) on a real worker; the default 1200-second recovery interval is the source check in the provider coverage above. (policy-grade test: `test/runner-fixtures/blaxel-harness/driver/harness.test.ts` “qualifies exclusive retrieval, active and quiet recovery, temporary placement, and pool lifecycle”) ^blaxel-t-stale-owner-lockout

- **Contract — coordinator ordering and failures.** The coordinator's lease lifecycle uses recording/failing transport, download, and cleanup callbacks. Under [release](../../../specs/arch/test-runner/blaxel-testshards.md#leases), renewal spans acquisition, execution, cleanup, and retrieval. A successful shell exit still requires descendant confirmation; unknown dispatch or failed cleanup cannot release. Successful retrieval and identity validation precede release; a download retry neither reruns tests nor resets worker results. An unused lease waits for pending writes and retains produced evidence. On interruption, the authoritative interrupted report precedes cleanup/retrieval and cannot become an ordinary completion report; cleanup still runs after a report-write error. A coordinator that loses ownership stops issuing mutations and reports infrastructure failure. These callbacks forfeit API, signals, and downloads to the live retrieval/recovery assertions; existing signal-report fixtures supply breadth without another native suite. (policy-grade tests: `test/repo/blaxel-lease-contracts.test.ts` “retrieval retries after teardown without rerunning work; uncertainty never releases”, “renewal continues while retrieval waits and stops on ownership loss”, and “preparation evidence is downloaded before an undispatched attempt releases”; `test/repo/test-runner-provider.test.ts` interrupted-report and explicit TTL-forwarding cases) ^blaxel-t-lease-order

### Pool mutation

- **Contract — publication and deletion ordering.** The pool manager uses authored sandbox states and recording/failing SDK operations. Under [Pool](../../../specs/arch/test-runner/blaxel-testshards.md#pool) and [Deleting workers](../../../specs/arch/test-runner/blaxel-testshards.md#deleting-workers), it publishes eligibility only after successful provisioning/verification, refuses to refill partial pools, refuses deletion of valid leases, and unpublishes before deleting an idle or expired worker. A failed deletion stays unavailable and visible. Command failure on a previously eligible worker holds/reports it, while a fresh worker never published may be deleted without a lease. SDK substitutions forfeit actual metadata changes and deletion to the live pool acceptance. (policy-grade tests: `test/repo/blaxel-lease-contracts.test.ts` “pool eligibility follows verification, and deletion reserves then unpublishes” and “failed deletion of never-published workers remains retryable without their runtime”) ^blaxel-t-pool-order

- **Acceptance — fresh pool and safe deletion.** Through canonical pool commands and the real API, create the dedicated pool used by the live assertions, observe workers become eligible only after runtime/architecture verification, and run the fixtures on them. Attempt deletion while the retrieval gate holds valid leases: the command reports refusals and exits nonzero, and the original run still completes. After release, delete the pool and confirm its workers are absent; a new coordinator cannot dispatch there. This proves the [pool mutation](../../../specs/arch/test-runner/blaxel-testshards.md#deleting-workers) and [setup](../../../specs/arch/test-runner/blaxel-testshards.md#setup) spine through actual Blaxel label changes and deletion. These observations share the retrieval scenario rather than provisioning another pool.
