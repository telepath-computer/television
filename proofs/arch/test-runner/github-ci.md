# GitHub Actions CI — proof

Proves [specs/arch/test-runner/github-ci.md](../../../specs/arch/test-runner/github-ci.md).

## Coverage model

Coverage declarations are carried inside the migrated assertion blocks below. PR concurrency is a parsed-YAML contract: it verifies the configuration sent to GitHub without simulating the service’s scheduler or cancellation behavior.

## Test hooks


`setup-workspace`'s `cache-namespace` input and `setup-shard-readiness`'s `cache-namespace` input place cache entries from a validation run ([#Testing](../../../specs/arch/test-runner/github-ci.md#Testing)) under scratch prefixes. `setup-shard-readiness`'s `cache-key-suffix` input forces an exact-key miss without requiring a source or dependency change. The production workflow passes none of these inputs and therefore uses the `nm` workspace namespace, the `shard-readiness-v2` readiness namespace, and no suffix.

`checkManifestCoversRegistry` accepts the registry and manifest to compare. `runRecipes` accepts `root` (the workspace where recipes run) and `manifest` (the recipes to run). `packUntrackedFiles` accepts `root` (the Git workspace to enumerate) and `archivePath` (the archive to write); the helper CLI exposes the same workspace substitution as `--root`. Production uses the repository root and the committed registry and manifest.

## Assertions

### Test assertions

Shapes per [testing-policy.md](../../../specs/arch/testing-policy.md). Workflow-file contract assertions live in `test/repo/test-runner-guardrails.test.ts` and `test/repo/public-workflow-boundaries.test.ts`; worker contract assertions in the shard-runner's coverage.

**Contract — the committed workflow encodes this spec** (the YAML is the producer-side artifact under test):

- **Contract** (committed CI YAML parsed directly; no mocks or hooks): workflow concurrency is scoped by workflow, event and PR number, using a unique run ID for non-PR events; cancellation is enabled only for PR events. This proves the declared [superseded PR policy](../../../specs/arch/test-runner/github-ci.md#^gha-pr-concurrency), preserving independent push/manual runs and different PRs. Hosted cancellation is GitHub behavior, not a mocked acceptance path — *(covered by test: `test/repo/public-workflow-boundaries.test.ts` “cancels only superseded runs of the same PR while keeping other CI runs independent”)*. ^gha-t-pr-concurrency
- The pull-request and push triggers both target `main` and `integration/**`, so nested integration branch names are included. — *(covered by test: `test/repo/test-runner-guardrails.test.ts` “CI validates pushes and pull requests for main and nested integration branches”)*. ^gha-ci-branch-targets
- Both setup composites read `node-version-file: .nvmrc`, expose no independent Node-version input or default, and select Node before resolving cache identity. Every CI job that executes a repository command has exactly one direct or composite selector; the three direct sites precede the attestation decision, shard-plan agreement validator, and attestation writer respectively. `setup-playwright` carries no selector and every call follows an owning setup composite.
- The ordinary dependency cache step uses an exact key with no `restore-keys`; the key string carries the OS, CPU-architecture, Node major resolved from the selected runtime, and execution-image identity components; and its `hashFiles` list includes `package-lock.json`, the prepare-chain input trees, and `packages/skills/package.json`; the cached path list includes `node_modules`, `packages/skillbench/dist`, and `packages/skillbench/dist`.
- `setup-shard-readiness` selects Node before resolving its key, derives the key's Node-major label from that runtime, requires non-empty `ImageOS` and `ImageVersion`, carries the full input hash, uses the `shard-readiness-v2` payload namespace, and restores one archive containing the ordinary cached paths plus `~/.cache/ms-playwright`, with no fallback key. The build's `npm ci`, browser preparation, and save are miss-only. A shard miss cannot fail at restore: it emits a warning, self-seeds dependencies plus Chromium and Firefox without saving the combined cache, and records a cache-miss fallback phase.
- The build and every e2e shard execute real Chromium and Firefox launch probes. `e2e:desktop` keeps the `setup-playwright` composite action; an e2e shard invokes it only while self-seeding a miss. No job declares a container (containerization deferred; see Browser environment).
- Every job that reaches the runner's owner-lifecycle paths (the e2e shard jobs, `unit`, and `e2e:desktop`) asserts-or-installs the inspection tool set (`ss`, readable `/proc`).
- The build job runs the `test.prebuilt.mjs` recipes and uploads the artifact under the manifest-derived name (`prebuilt.mjs artifact-name` — no hardcoded duplicate) with `retention-days: 1`; the e2e shard jobs download and extract it with stored permissions and set `TEST_SHARD_SKIP_PRECOMMANDS=1`; the `e2e:desktop` job does neither (fan-out scope above); the join job checks out the repository. **The workflow contains no hand-maintained output list**, and no second artifact carries source to a consumer.
- **Contract.** The packed set equals exactly the untracked files and symlinks git reports for a workspace, minus those under `node_modules`, `.git`, and `.test-runs` — compared against git's own listing, with no expected-path list in the test. Fixtures: a real git repository built by the packer's own recipe runner, seeded with the shapes that distinguish this contract — an executable file, a symlink, a zero-byte file, an empty directory, an output no ignore rule covers, generated files under both root and nested `node_modules`, and test scratch under `.test-runs`. The real repository's build is not packed in this test; two full product builds to prove a packer property would cost more than the property is worth, and live CI exercises that path on every run. That is what makes a shard with skipped pre-commands able to run the surfaces that would have followed a `preCommand` build: the licensing gate and its inventories, tarball and desktop assertions, asset-copy checks, and development-layout lookups all read files the build wrote, and every such file ships. A second assertion covers [the one rule](../../../specs/arch/test-runner/github-ci.md#^gha-prebuilt-tracked-rule): after the recipes no tracked file differs from the commit, and a fixture recipe that leaves one modified fails the build job. ^gha-prebuilt-cli-outputs
- The manifest's `artifactName` is the literal `"prebuilt-dists"` (typed literal, asserted).
- The shard worker suppresses `preCommand` under both knob forms while leaving the surface command unchanged, proven by executing a minimal plan file through the real worker process.
- The join (`e2e-required`) depends on the build job and the e2e matrix. Its job-level condition combines `always()` with the shared draft guard: drafts report neutral/skipped without entering the join script, while every non-draft run executes the strict path. That path passes only when build and e2e both report success and fails for missing, skipped, cancelled, or failed dependencies. It checks out the repository and runs its validator from that checkout; no artifact carries source to it. It also depends on the `vibe-mode` job, which checks out the repository, selects Node once, and runs the vibe-mode check; a vibe-mode result other than success fails the join before the attested-skip path and the build and e2e checks, and the job takes no attestation dependency.
- The registry/manifest consistency check holds: every `preCommand`-declaring surface is covered by exactly one manifest recipe (this replaces the former prose-only "manifest covers every surface" line with the mechanical check the manifest shape enables).

- `packages/web/playwright.config.ts` pins CI workers to 2.

**Contract — worker and validator behavior** (each side proven in isolation):

- The shard worker with `--skip-pre-commands` (or the env form) executes zero `preCommand`s while running the surfaces themselves unchanged through the same `--plan <path>` input used in CI.
- The `e2e-ci` suite equals all e2e surfaces except `tag:electron`; the workflow retains the dedicated `e2e:desktop` job.
- Every direct shard computes a complete VM-timing plan, uploads a complete 30-day run artifact, and the required join rejects plan, provider, tree, total, index, assignment, or collection disagreement.
- Direct test jobs preserve VM schedule, checkout, dependency and browser cache outcome, readiness, plan, compute, report, and publication timing in their run events and summary; the post-artifact agreement join uploads its own machine-readable phase and Actions step summary.
- Direct local test jobs resolve their artifact from `--run-dir-output`, validate that exact path under the workspace `.test-runs/` root, and never require the root to contain only one directory.
- A missing artifact or a failed extraction fails the consuming job; no path is inspected and no rebuild fallback exists.

**Acceptance — live CI as the outermost boundary:** static YAML checks cannot prove that a live job restores an equivalent tree or that artifact fan-out delivers working builds. When required by the spec’s [Testing](../../../specs/arch/test-runner/github-ci.md#Testing) section, live evidence must include a fully green run of an isolated copy of the complete `ci.yml` job graph, triggered only from its implementation branch. Its jobs must show (a) an image-bound combined-cache **hit** with `npm ci` and browser preparation skipped, every shard's launch check green, and the full suite green; (b) `preCommand`s skipped while surfaces consume the artifact; and (c) the join validating exact plan agreement from its own checkout. A focused isolated run must force a shard-key miss and prove that the warning, local dependency/browser setup, cache-miss fallback metric, both browser launches, tests, and join remain green. An induced build failure must prove that the join cannot report a false pass. Because `ci.yml` triggers only on pushes to `main` or branches under `integration/` and pull requests targeting those branches, an isolated validation copy must use one of those trigger paths to provide this evidence before promotion. Required-check context wiring under the production names remains for the operator to verify on the first production run. A miss-path run is required to produce the cache entry used by the hit-path run. Every subsequent CI run exercises the promoted paths.

**Boundary gaps — stated honestly per [testing-policy.md](../../../specs/arch/testing-policy.md):** key construction enforces that changing a prepare input causes a cache miss. This was verified by changing those inputs in an isolated cache run, but no committed test simulates the Actions cache service.
