# Artifact records — proof

Proves [specs/arch/artifacts/index.md](../../../specs/arch/artifacts/index.md).

## Coverage model

Model contracts check the path and URL record variants with transparency true or absent.
Existing store and route tests cover target normalization, ordinary metadata updates, and records without optional resource fields.
Real HTTP walks create and update both artifact kinds, read the saved JSON, and observe the records delivered over WebSocket.
These walks prove that enabled transparency reaches storage and clients as true, while an update supplying false removes the field.
Creation with false or an omitted value stores no field, covered for path and URL sources by layout and for templates by template resolution.
A boot seam loads authored records with the field absent or true, including records predating the field; the frame contract proves the corresponding opaque or transparent state.
Invalid updates are rejected through the real HTTP route before any field changes.
Temporary homes, HTML files, request bodies, and stored records are fixtures; no production mechanism is mocked.

[Layout](../layout/index.md) covers creation display validation and placement; [templates](../templates/index.md) covers manifest resolution and its separate creation route.
[Resource architecture](../resources/index.md#^rs-arch-t-artifact-record) retains the existing store/share tests, and its writer contracts cover durable saves and uncertain outcomes.
The transparency walk checks preservation of those fields without repeating the resource protocol or simulating a disk failure.
[Product artifacts](../../product/artifacts.md#^af-ac-transparent) owns visible browser and desktop outcomes and retention after a move and restart.
[CLI](../../product/cli.md#^cli-ac-transparent) owns the command and printed-metadata boundary.
No new registry behavior is adopted beyond the contracts named by the spec.

## Test hooks

No production test hook is needed. Stored-record fixtures are written before the real server boots; ordinary creation and updates use production requests.

## Record and target contracts

- **Contract** (authored records → production artifact schema and constructor; no mocks or hooks): under [the record shape](../../../specs/arch/artifacts/index.md#^ar-record), path and URL records retain their ID, kind, title, and corresponding pointer; both HTTP and HTTPS URLs are accepted. Construction emits the flat record without a version field. *(covered by inherited tests: `packages/artifact/test/unit/model.test.ts`, “accepts path artifacts”, “accepts http(s) URL artifacts”, and “constructs path and URL artifacts”)* ^ar-t-record-shape
- **Contract** (authored create/repoint inputs → real `ServerStore` with temporary files, HTTP absent; no mocks or hooks): under [create and update target rules](../../../specs/arch/artifacts/index.md#create-and-update-inputs), paths and URLs are trimmed, directory pointers retain a trailing separator, file pointers do not, and the normalized pointer is saved. Invalid path targets and non-HTTP(S) URLs are refused. *(covered by inherited tests: `packages/server/test/server-store-artifacts.test.ts`, “creates path artifacts with trimmed targets and appends them to the owning channel”, “creates URL artifacts with trimmed http(s) URLs”, “normalizes directory paths to a trailing separator regardless of input form”, “strips a trailing separator supplied on a file path”, “normalizes directory paths on update”, “rejects a directory without a root index in either input form”, “rejects unsupported file extensions whether or not a trailing separator was supplied”, and “rejects invalid create inputs with InvalidRequestError”; `packages/server/test/server-store-url-artifacts.test.ts`, “rejects non-http(s) URL schemes”)* ^ar-t-targets
- **Seam** (artifact HTTP routes → real store and filesystem through HTTP; temporary path files and HTTP(S) URL strings, no mocks or hooks): under [create and update inputs](../../../specs/arch/artifacts/index.md#create-and-update-inputs), a create reaches the store and its returned record is available by ID; title and path updates preserve the other record fields and reach disk. A URL repoint reaches the stored URL artifact through the shared client. *(covered by inherited tests: `packages/server/test/endpoints.test.ts`, “POST /artifacts creates a trimmed path artifact and round-trips the stored shape” and “PATCH /artifacts/:id updates title and path fields”; `test/node/cli-integration.test.ts`, “server and CLI round-trip through status, title update, get, and delete”)* ^ar-t-input-seam
- **Contract** (authored path and URL records → production record schema; no mocks or hooks): under [the stored transparency rule](../../../specs/arch/artifacts/index.md#^ar-transparent), records with `transparent` absent or true validate and retain that shape; a string, number, or null is not a valid value. Path records may also carry their valid `store` and `share` fields. False is a valid creation or update input, whose conversion to field absence is proven at the write boundaries below, not a stored-record fixture. The [frame consumer](../../ui/app/artifact-frame/transparency/index.md#^af-ui-ac-transparent-state) proves that true enables transparency and absence is opaque. *(policy-grade tests: `packages/artifact/test/unit/model.test.ts`, “retains true or absent transparency on path and URL records and rejects nonbooleans”)* ^ar-t-transparent-model

The existing [resource-field assertion](../resources/index.md#^rs-arch-t-artifact-record) proves the `store` and `share` portion of [the record contract](../../../specs/arch/artifacts/index.md#^ar-record), including loading a record without them. ID generation and preservation are [product ID coverage](../../product/artifacts.md#^af-ac-artifact-id); title presentation is [product title coverage](../../product/artifacts.md#^af-ac-title). These are reused obligations, not additional tests.

## Transparency and update boundaries

- **Acceptance** (real authenticated HTTP client → running server, real filesystem and WebSocket client; temporary home, valid path files and HTTP(S) URL targets; no mocks or hooks): under [record transport](../../../specs/arch/artifacts/index.md#^ar-record) and [transparency writes](../../../specs/arch/artifacts/index.md#^ar-transparent), create one artifact of each kind with `display.transparent: true`. The saved file at `state/artifacts/<id>.json`, create response, individual/list/channel API records, and created event agree on a top-level `transparent: true`, the matching ID, and the kind-specific pointer, with no stored `display` object or version field. Updating only `transparent` to false removes the field from the saved record, update response, reads, and updated event; updating only to true restores it. A title or corresponding pointer update that omits transparency preserves it and keeps ID and kind fixed. On the path artifact, establish a store and share link through resource operations, then toggle transparency and change the title: both resource fields remain intact. A subsequent share-level change preserves transparency. *(policy-grade tests: `packages/server/test/artifact-transparency.test.ts`, “round-trips %s transparency through records, HTTP, events, and restart” (path and URL cases))* ^ar-t-transparent-roundtrip
- **Seam** (stored JSON records → real server boot loader, observed through authenticated HTTP; authored path and URL records with `transparent` absent or true, including records predating the field; no mocks or hooks): under [record loading](../../../specs/arch/artifacts/index.md#^ar-record) and [compatibility with records without the field](../../../specs/arch/artifacts/index.md#^ar-transparent), each record loads with its original identity and pointer. API results retain true when stored and omit the field when absent. The [frame contract](../../ui/app/artifact-frame/transparency/index.md#^af-ui-ac-transparent-state) interprets those records as transparent and opaque respectively. *(policy-grade tests: `packages/server/test/artifact-transparency.test.ts`, “loads authored path and URL records with true or absent transparency”)* ^ar-t-transparent-load
- **Acceptance** (real authenticated HTTP client → running server and temporary filesystem; path and URL artifacts established through creation requests, malformed JSON field values as fixtures; no mocks or hooks): under [patch validation](../../../specs/arch/artifacts/index.md#create-and-update-inputs), an empty patch, wrong types for title/path/url/transparent, both pointers together, and a pointer for the other artifact kind are rejected before any record change. Pair an invalid field with a valid title or transparency change to detect partial application; served records and disk bytes remain unchanged. A patch cannot change ID or kind or manage `store` or `share`. The assertion does not choose whether unknown fields are ignored or rejected; it checks that those protected fields remain unchanged. *(policy-grade tests: `packages/server/test/artifact-transparency.test.ts`, “rejects invalid whole %s patches without changing records or protected fields” (path and URL cases))* ^ar-t-patch-validation

Creation with omitted or false transparency and invalid creation values is covered by [layout creation](../layout/index.md#^ly-ac-create-transparent) and [layout refusal](../layout/index.md#^ly-ac-create-transparent-invalid). Template creation uses [template resolution](../templates/index.md#^templates-t-transparent-resolution). Record durability remains the [resource writer](../resources/index.md#^rs-arch-t-write-order) and [uncertain-save contract](../resources/index.md#^rs-arch-t-uncertain-save); those assertions already cover every artifact-record rewrite.
