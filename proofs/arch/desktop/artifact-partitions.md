*How desktop artifact partitions are proven: naming, attachment, the record and the reaper as contracts, crossed in the real Electron app connected to a running server, including a stand-in for an interface without partition support and a reaping across a restart.*

# Desktop artifact partitions — proof

Proves [specs/arch/desktop/artifact-partitions.md](../../../specs/arch/desktop/artifact-partitions.md).

## Coverage model

The spec's testing directive is honored by three real-Electron tests in which Electron's sessions and the filesystem are real. [#^dp-t-sessions-seam](#^dp-t-sessions-seam) connects the app to a running server through the saved connection and shows the served interface's artifacts of every kind, reading which session each webview uses, where Electron keeps it, and what the record holds. [#^dp-t-fallback-seam](#^dp-t-fallback-seam) loads, through the e2e harness's fixture hook, an authored page that stands in for a served interface without partition support: it creates webviews with no partition and with a name the main process does not know, which the production interface never does. [#^dp-t-reaper-acceptance](#^dp-t-reaper-acceptance) deletes an artifact through the production API and crosses a restart of the app, so the reaper's removal of a partition Electron had opened is observed on disk.

The breadth is contracts. Naming is a pure contract with no mocks. The main process's handling of an attaching webview is a contract with Electron's attach event, sessions and window declared as mocks; the real attachment is the seams'. The record is a contract over a temporary directory on the real filesystem. The reaper is a contract with a fake `fetch` and a fake clock over a temporary directory, which forfeits the real server and real time: the server crossing is the acceptance walk's, and the hourly cadence, which no test waits for, is proven only on the fake clock. The served interface's side, the flag and the `partition` attribute, is a preload contract and a host contract under jsdom, whose mocked webview forfeits Electron's attachment to the sessions seam. The cross-release answer of `GET /artifacts` is a server contract over real HTTP.

What isolation requires of each partition's session, the header rewriting and the permission handlers, is [artifact isolation's proof](../artifact-frame/isolation.md); this proof shows that the main process sets each session up before its first webview, and the isolation seams show what that setup does. The product promise that the desktop app deletes a deleted artifact's own browser storage ([product/artifacts.md#^af-delete-semantics](../../../specs/product/artifacts.md#^af-delete-semantics)) is the acceptance walk here.

## Test hooks

This proof declares no hooks of its own. [#^dp-t-fallback-seam](#^dp-t-fallback-seam) uses [the e2e harness's fixture hook](../../../specs/arch/desktop/e2e-harness.md#^desktop-e2e-fixture-hook) to load its authored page in place of a served interface; the other real-Electron tests use the saved connection, which the e2e helper writes into a temporary `userData` directory before launch as an earlier connection would have.

## Assertions

### Names and attachment

- **Contract — partition names** (the production naming function over authored origins and IDs; no mocks): `tv-artifact:<id>` with an origin gives `persist:artifact-` followed by the first 32 lowercase hexadecimal digits of the SHA-256 digest of `<origin>\n<id>`, checked against digests the test computes independently, for a ULID and for IDs holding spaces, slashes, colons, uppercase and non-ASCII characters; the same ID under two origins, and two IDs differing only in case under one origin, give different names; `tv-url-artifact` gives `persist:url-artifacts` under every origin; no partition gives `persist:webview-fallback`; `tv-artifact:` with an empty ID, `tv-artifact` without its colon, `tv-url-artifacts`, `persist:url-artifacts` and an arbitrary name are refused. This proves the names in [the sessions table](../../../specs/arch/desktop/artifact-partitions.md#^dp-sessions) and the classification in [attachment](../../../specs/arch/desktop/artifact-partitions.md#^dp-attach) — *(policy-grade test: `packages/desktop/test/artifact-partitions.test.ts` "names each partition from the requested partition and the page's origin")*. ^dp-t-names
- **Contract — attaching a webview** (the production main-process module; Electron's `will-attach-webview` event and its web preferences, `session.fromPartition`, the sessions it returns and the window's web contents are declared mocks, the window posing as showing the server's page or the local `file:` page; the mocks forfeit a real attachment to [#^dp-t-sessions-seam](#^dp-t-sessions-seam) and [#^dp-t-fallback-seam](#^dp-t-fallback-seam)): for `tv-artifact:<id>` while the window shows an HTTP(S) page, `tv-url-artifact` and no partition, the handler sets `webPreferences.partition` to the name [#^dp-t-names](#^dp-t-names) gives, keyed by the window's page origin, and before returning sets up that partition's session, once however many webviews later use it; it records the artifact partition and nothing for the other two; it leaves the bridge preload and context isolation in place ([artifact-bridge.md#^ab-ac-preload-attachment](../artifact-frame/artifact-bridge.md#^ab-ac-preload-attachment)); it refuses, by preventing the event's default and setting up no session, every refused name and `tv-artifact:<id>` while the window shows the local page; and it never sets up the window's session as a partition's. This proves [attachment](../../../specs/arch/desktop/artifact-partitions.md#^dp-attach) at the main process — *(policy-grade test: `packages/desktop/test/main.test.ts` "places each attaching webview in its partition, sets up the partition's session first, and refuses unknown partitions")*. ^dp-t-attach
- **Contract — the bridge flag** (the production window preload; Electron's `contextBridge` and `ipcRenderer` are declared mocks, as in the preload's other contracts): the native preload bridge carries `artifactPartitions` with the value `1`, on the server's page and on the local page alike. This proves [the flag](../../../specs/arch/desktop/artifact-partitions.md#^dp-bridge-flag) at the preload — *(policy-grade test: `packages/desktop/test/connect-preload.test.ts` "tells the served interface that artifact webviews go in partitions")*. ^dp-t-bridge-flag
- **Contract — the interface's partition names** (the production artifact-frame view under jsdom in Electron mode, with authored artifact records, a fake application service and an authored native preload bridge; the webview's loading is mocked, forfeiting Electron's attachment to [#^dp-t-sessions-seam](#^dp-t-sessions-seam)): with the bridge carrying `artifactPartitions: 1`, every webview the view creates has its `partition` attribute before its `src` is first assigned: `tv-artifact:<id>` for an HTML file, a folder and a Markdown file artifact, with the ID unchanged, and `tv-url-artifact` for an external page artifact and a shared artifact; the same webview element keeps its partition as its document moves to another of the artifact's pages, to an external page and back; when the artifact's record changes kind, from path to URL and back, the view replaces the webview with a new element carrying the other partition before its `src` is assigned. With the bridge absent, carrying no `artifactPartitions`, or carrying another value, no webview gets a `partition` attribute. This proves [the interface's names](../../../specs/arch/desktop/artifact-partitions.md#^dp-interface-names) and its reading of [the flag](../../../specs/arch/desktop/artifact-partitions.md#^dp-bridge-flag) — *(policy-grade tests: `packages/web/test/artifact-view.test.ts` "names each artifact webview's partition before its first navigation, and replaces the webview when its partition changes" and "names no partition unless the native bridge carries the flag")*. ^dp-t-interface-names
- **Seam — partitions in real webviews** (the real Electron app connected through the saved connection to a really-running server that requires the token, showing its served interface; fixtures created through the production API on separate tab pages of one channel: an HTML folder artifact, a Markdown file artifact, an external page artifact whose page a local fixture HTTP server serves on another origin, and a shared artifact whose producer is a second running server; no mocks): each artifact's webview carries the `partition` attribute its kind needs; the folder and Markdown artifacts' webviews use sessions whose storage path is `<userData>/Partitions/artifact-<key>`, with `<key>` computed by the test from the server's origin and each artifact's ID; both URL artifacts' webviews use the one session whose storage path is `<userData>/Partitions/url-artifacts`; no webview's session is the window's; `artifact-partitions.json` holds, under the server's origin, exactly the two artifact partitions with their artifacts' IDs, and nothing for the URL artifacts; following a link in the folder artifact's page to the external fixture page leaves that webview in the folder artifact's partition. After the app quits and is launched again with the same `userData` directory, a value the folder artifact's page wrote to `localStorage` is there again. This proves [the sessions](../../../specs/arch/desktop/artifact-partitions.md#^dp-sessions), the interface's names, [attachment](../../../specs/arch/desktop/artifact-partitions.md#^dp-attach) and [the record](../../../specs/arch/desktop/artifact-partitions.md#^dp-record) in the real app — *(policy-grade test: `packages/desktop/test/e2e/artifact-partitions.test.ts` "places each artifact's webview in its partition and records the server's artifact partitions")*. ^dp-t-sessions-seam
- **Seam — the fallback partition** (the real Electron app; the fixture hook loads an authored page, served by a local fixture HTTP server, that stands in for a served interface without partition support, with a `localStorage` sentinel in the window's storage; a really-running server serves an authored HTML artifact whose page reports its origin and its use of storage; no mocks): a webview the page creates with no `partition` attribute for the artifact's address uses the session whose storage path is `<userData>/Partitions/webview-fallback`, not the window's; its document's origin is `"null"` and touching `localStorage` throws `SecurityError`, because the fallback partition keeps the sandbox header; a second webview the page creates with no partition, for another fixture page on the window page's own origin, uses the same session, and what that page writes to its `localStorage` is not in the window's, while the window's sentinel is unchanged and invisible to it; a webview created with the partition `persist:arbitrary` is refused, so no web contents for it ever exist and no `Partitions/arbitrary` directory is created. This proves the fallback row of [the sessions](../../../specs/arch/desktop/artifact-partitions.md#^dp-sessions) and the refusal in [attachment](../../../specs/arch/desktop/artifact-partitions.md#^dp-attach) in the real app; that the fallback partition's permission handlers refuse what the others do is [isolation's permission contract](../artifact-frame/isolation.md#^iso-t-permissions) — *(policy-grade test: `packages/desktop/test/e2e/artifact-partitions.test.ts` "puts webviews named with no partition in the fallback partition, still sandboxed, and refuses unknown partitions")*. ^dp-t-fallback-seam

### The record

- **Contract — the partition record** (the production record functions over a temporary `userData` directory on the real filesystem; one case gives them a recording filesystem peer instead, which forfeits real disk operations to the rest of this contract and to [#^dp-t-sessions-seam](#^dp-t-sessions-seam)): recording a partition writes the complete record to a temporary sibling of `artifact-partitions.json` and then renames that sibling over it, in that order, as the recording peer's operations show; with no record, a first artifact partition writes `{ "version": 1, "servers": { "<origin>": { "<name>": "<id>" } } }`, the name without `persist:`, and leaves no temporary file beside it; further partitions for the same and another origin are added beside it; recording a partition already present leaves the file's bytes and modification time unchanged; a record that is not JSON, has another `version`, or holds a server or entry of the wrong shape is read as empty, and the next recorded partition replaces it with a valid record of that one entry; a record that cannot be read is read as empty. This proves [the record](../../../specs/arch/desktop/artifact-partitions.md#^dp-record) — *(policy-grade test: `packages/desktop/test/artifact-partitions.test.ts` "records each server's artifact partitions atomically and reads a malformed record as empty")*. ^dp-t-record

### The reaper

- **Contract — when the reaper runs** (the production reaper; a fake clock, a fake `fetch` answering the artifact list, and a temporary `userData` directory; the fake clock forfeits real time, and the fake `fetch` the real server, to [#^dp-t-reaper-acceptance](#^dp-t-reaper-acceptance)): with a saved connection, a reaping starts when the window finishes loading the connection's server page and again every hour while that page stays loaded, measured from each load; none starts while the window shows the local page, after the window loads a page of another origin, after Disconnect from Server or after the window closes, and none starts without a saved connection, as under the fixture hook; a load or hour that falls while a reaping's request is in flight starts no second reaping. Its request is `GET <origin>/artifacts`, with `Authorization: Bearer <token>` when the connection has a token and no `Authorization` header when it has none. This proves when [the reaper](../../../specs/arch/desktop/artifact-partitions.md#^dp-reaper) runs and what it asks — *(policy-grade tests: `packages/desktop/test/artifact-partitions.test.ts` "reaps when the server's page loads and hourly while it stays loaded, one reaping at a time" and "stopping aborts a reaping in flight, which then changes nothing", and `packages/desktop/test/main.test.ts` "starts and stops the reaper from the window's page events")*. ^dp-t-reaper-schedule
- **Contract — what the reaper deletes** (the same reaper, fake `fetch` and temporary directory, with authored partition directories under `Partitions/` and an authored record holding entries for the connected origin and another origin; the reaper's record of partitions opened since the start is set by the test through the production function the attach handler calls; one case replaces the directory removal with one that fails, forfeiting only a filesystem that really refuses): for each entry of the connected origin whose ID the answer lacks, the partition's directory and then its entry are removed, and an entry whose directory is already missing is removed too; entries whose IDs the answer lists, entries of the other origin, entries for partitions opened since the start, and the `url-artifacts` and `webview-fallback` directories are left as they were; an entry recorded while the request is in flight stays although the answer lacks its ID; a partition recorded before the request, not yet opened when it is sent, and opened by a webview while it is in flight stays, with its directory and entry, although the answer lacks its ID, because the opened check is made when the reaper deletes, not when it asks; a failed removal leaves its entry; and an answer other than `200`, a body that is not JSON, an `artifacts` that is missing or not an array, an element without a string `id`, and a request that fails each leave every directory and the record unchanged. This proves the deletion rules of [the reaper](../../../specs/arch/desktop/artifact-partitions.md#^dp-reaper) — *(policy-grade tests: `packages/desktop/test/artifact-partitions.test.ts` "deletes only the partitions of artifacts the server no longer lists, and only those not opened since the start", "keeps the entry of a partition whose directory cannot be removed" and "changes nothing unless the server lists its artifacts")*. ^dp-t-reaper-deletes
- **Acceptance — reaping across a restart** (the real Electron app connected through the saved connection to a really-running server that requires the token; two authored HTML folder artifacts, A and B, created through the production API on separate tab pages of one channel, whose pages each write a value to `localStorage`; before each reaping the walk observes, it writes into the record an entry, with a directory, for a partition of an artifact the server never had, which no webview opens, so that entry's disappearance shows the reaping has run; no mocks or test hooks): once both webviews have loaded, the record lists both partitions; A is deleted through the production API; reloading the served interface runs a reaping that leaves A's partition directory and entry in place, because Electron opened it in this run; the app quits and is launched again with the same `userData` directory; once the served interface has loaded, A's directory and entry are gone, and B's partition, its entry and the value its page wrote remain. This proves [the reaper](../../../specs/arch/desktop/artifact-partitions.md#^dp-reaper) against the real server and filesystem, and the desktop app's deletion of a deleted artifact's own storage under [product/artifacts.md#^af-delete-semantics](../../../specs/product/artifacts.md#^af-delete-semantics) — *(policy-grade test: `packages/desktop/test/e2e/artifact-partitions.test.ts` "deletes a deleted artifact's partition at the first reaping after a restart and keeps the others")*. ^dp-t-reaper-acceptance

### The artifact list

- **Contract — `GET /artifacts` as the reaper reads it** (a really-running in-process server that requires the token, over temporary storage, driven through real HTTP with `Authorization: Bearer <token>`; no mocks): with 250 artifacts across three channels, path and URL artifacts both, the answer is one `200` JSON body whose `artifacts` array holds an object with each artifact's ID as a string `id`, every artifact once and nothing else; after one artifact is deleted, the answer lacks exactly that ID. This proves [the cross-release answer](../../../specs/arch/desktop/artifact-partitions.md#^dp-artifacts-route) — *(policy-grade test: `packages/server/test/endpoints.test.ts` "lists every artifact in one answer for the desktop reaper (^dp-t-artifacts-route)")*. ^dp-t-artifacts-route
