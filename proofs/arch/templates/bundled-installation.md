# Bundled artifact template installation — proof

Proves [specs/arch/templates/bundled-installation.md](../../../specs/arch/templates/bundled-installation.md).

## Coverage model

Build evidence reads the real bundled source and package output. Validation failures use temporary source trees passed to the production validation command through its source-directory argument. Boot cases construct a serving store over temporary homes with authored installed folders and state files; they use the real validator and filesystem. A token-only construction shows that serving is the installation boundary. Socket entries in fixture folders obstruct backup or replacement copies through the real filesystem. A recording adapter delegates state writes to Node filesystem operations so the test can observe the temporary write and rename; a directory placed at the temporary path makes one write fail through the real filesystem.

The scanner and installed-folder validity live in [template architecture](./index.md). [The CLI architecture proof](../cli/index.md) proves that the built package path reaches the serving store. [Checklist](./checklist.md), [Calendar](./calendar.md), [Sticky note](./sticky-note.md), and [Markdown](./markdown.md) architecture proofs cover their packages and starting values; their linked UI proofs or existing UI authority own page behavior. We do not test routine source-version increases as a new behavior: the minimum-version rule below covers whether an installed copy stays. The four-ID inventory permits a real failure on one package while the others install. An installer-contract fixture supplies a bundled-ID list to prove removal from that set; it does not change the shipped inventory, which remains covered by the real build. Replacement and retry cases exercise the Checklist folder. Cases that record Calendar as handled and absent leave it uninstalled while Sticky note and Markdown can still install independently.

## Test hooks

The bundled-template validation command accepts an optional source-directory argument for temporary fixture trees; the server build supplies the real `packages/server/assets/templates` directory. The argument changes only the input tree and forfeits no validation behavior.

The bundled-state writer accepts a filesystem-operations adapter for temporary-file write and rename. Production uses Node filesystem operations. A test adapter records the paths and delegates to those same operations; it may create a directory at the chosen temporary path just before delegating the write. This changes only the timing of that real filesystem obstruction and forfeits no filesystem behavior. Temporary source trees, installed folders, and state files are fixtures.

A warning recorder replaces `console.warn` in failure contracts; it forfeits process-stream formatting, which this proof does not claim. A contract may supply an authored bundled-ID/minimum list to the installation loop; production uses the shipped inventory. This planned affordance forfeits inventory wiring to the real build and boot seams, not installer behavior.

Replacement-order tests may observe filesystem/state operations while delegating them to Node, and obstruct the temporary state path just before a write. They may inject a stop after destination removal to pose an interruption; this mock forfeits operating-system process termination, while the subsequent boot and all saved files remain real. It does not prove power-loss durability.

## Assertions

- **Contract** (temporary source trees → production bundled-template validation command; source-directory argument as declared above, no mocks): Under [the bundled package rule](../../../specs/arch/templates/bundled-installation.md#bundled-packages), an absent or extra folder, an invalid folder, and a manifest below its minimum version fail validation with a useful diagnostic. Exercise missing, invalid and below-minimum cases for each bundled ID; the exact valid three-template inventory passes. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, “accepts exactly the bundled templates at or above their minimum versions”)*. ^templates-install-t-validate
- **Seam** (real source tree → production server build → packaged tree; no mocks): Under [the bundled package rule](../../../specs/arch/templates/bundled-installation.md#bundled-packages), the build runs bundled-template validation on all four real source folders and copies the complete tree, including Sticky note font and notices, with matching relative paths and bytes into `packages/server/dist/templates/` and onward into the CLI package. *(policy-grade test: `test/node/cli-assets.test.ts`, “ships the complete bundled template tree byte-for-byte through both builds”)*. ^templates-install-t-build
- **Contract** (state file → serving installer and recorded state-file operations delegated to the real filesystem): Under [the state contract](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-state), valid version-1 state keeps unique exact IDs in English-locale order. The operation record shows a write to a temporary file in the state directory followed by a rename from that file onto `bundled-templates.json`; a hard link to the former state retains its old bytes. Missing state means unhandled IDs; malformed, unsorted, duplicate, or unreadable state (the last posed as a directory at the state-file path) warns and leaves both template handling and state untouched for that boot, with no write or rename call. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, cases tagged `^templates-install-t-state`)* ^templates-install-t-state
- **Seam** (serving boot → installed folder and state file, real filesystem): Under [the specified behavior](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-replacement), an unhandled absent ID installs; a handled absent ID remains absent; a valid existing folder at or above the minimum remains byte-for-byte intact and becomes handled; an invalid or below-minimum occupant is replaced only after a hidden timestamped backup succeeds. A token-only construction installs nothing. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, cases tagged `^templates-install-t-boot`)* ^templates-install-t-boot
- **Seam** (failed/interrupted replacement → real serving boot over the filesystem; prior installed folder, hidden backup and saved-state fixtures): under [replacement recovery](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-backup), an absent destination with its ID durably removed is reinstalled on the next boot and recorded as handled. A backup failure leaves the destination intact; a state-removal write failure also leaves it intact. Observe backup completion before durable state removal, destination removal afterward, and handled recording only after complete replacement. The declared stop/failure controls forfeit actual crash/disk-failure generation, not recovery. No assertion requires a complete destination during interruption. When Checklist is initially unhandled or durably marked unhandled before a failed replacement, successful Markdown and Sticky note installation adds their IDs while preserving any handled `calendar` entry; retry records all four IDs in sorted order and preserves the valid Sticky note folder. A backup failure before durable state removal preserves any existing handled Checklist entry. *(policy-grade tests: `packages/server/test/bundled-template-installation.test.ts`, cases tagged `^templates-install-t-retry`)* ^templates-install-t-retry
- **Seam** (state-write failure → next serving boot, real filesystem): Under [the state and retry rules](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-state), start with valid state that has not handled `checklist`. After boot installs the complete folder, the delegated write meets a directory created at its chosen temporary-file path and fails. The warning leaves the prior state file byte-identical and the complete Checklist folder at its destination. With the obstruction removed, the next boot keeps that valid folder and records `checklist` through the observed temporary write and rename. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, cases tagged `^templates-install-t-state-retry`)* ^templates-install-t-state-retry

- **Contract** (installation loop at the shipped-inventory boundary; bundled inventory plus an authored fixture ID, real directories/state and a socket obstructing one backup, warning recorder): under [failure containment and bundle removal](../../../specs/arch/templates/bundled-installation.md#serving-boot), one failed ID warns while the remaining IDs are handled; dropping an ID from the supplied list leaves its installed folder and contents available to the ordinary scanner. The inventory mock forfeits real membership to the build seam. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, case tagged `^templates-install-t-containment`)* ^templates-install-t-containment
- **Seam** (bundled replacement → existing copied artifact records, pages and stores over real boot/filesystem; artifacts and stores established through production operations before making the installed template invalid/below minimum, no mocks): under [same-path replacement](../../../specs/arch/templates/bundled-installation.md#serving-boot), replacement retains the installed template path and every created artifact record, copied page and store byte while preserving prior template content in its hidden backup. A valid edited folder at/above minimum survives even with a newer bundled source. Deleting a handled template leaves it absent on reboot while created artifact pages, records and stores remain intact. *(policy-grade tests: `packages/server/test/bundled-template-installation.test.ts`, “preserves copied pages, records and stores through %s replacement and handled deletion”)* ^templates-install-t-copied-artifacts

- **Seam** (serving boot → independent installed folders and handled-ID state, real filesystem): Under [replacement](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-replacement) and [failure isolation](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-backup), a home that already records a handled Checklist deletion installs the unhandled Calendar, Sticky note and Markdown and leaves Checklist absent. A fresh home installs all four. Keeping valid edited Calendar, Sticky note and Markdown copies and backing up or replacing below-minimum copies follow the shared rule. A real socket obstruction making Checklist backup fail still permits Calendar, Sticky note and Markdown installation and records only successful handling; clearing it permits retry on the next boot without overwriting the valid Sticky note. State remains uniquely sorted. This extends the existing filesystem fixture pattern without mocking the installer. *(policy-grade test: `packages/server/test/bundled-template-installation.test.ts`, “handles all four templates independently across prior state, preservation, replacement and a failed backup”)*. ^templates-install-t-independent-ids
