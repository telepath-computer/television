# Bundled artifact template installation — proof

Proves [specs/arch/templates/bundled-installation.md](../../../specs/arch/templates/bundled-installation.md).

## Coverage model

Build evidence reads the real bundled source and package output. Validation failures use temporary source trees passed to the production validation command through its source-directory argument. Boot cases construct a serving store over temporary homes with authored installed folders and state files; they use the real validator and filesystem. A token-only construction shows that serving is the installation boundary. Socket entries in fixture folders obstruct backup or replacement copies through the real filesystem. A recording adapter delegates state writes to Node filesystem operations so the test can observe the temporary write and rename; a directory placed at the temporary path makes one write fail through the real filesystem.

The scanner and installed-folder validity live in [template architecture](./index.md). [The CLI architecture proof](../cli/index.md) proves that the built package path reaches the serving store. [Checklist](./checklist.md) and [Sticky note](./sticky-note.md) architecture proofs cover their packages and starting values; their linked UI proofs own page behavior. We do not test routine source-version increases as a new behavior: the minimum-version rule below covers whether an installed copy stays. The two-ID inventory permits a real failure on one package while the other installs. A former bundled folder continues to appear through the ordinary scanner, which has no bundle membership filter; no current package removal is posed here.

Installation contracts use the actual bundled packages and temporary copies for validation failures, backups, replacement, and state-write retries. Existing Checklist lifecycle tests remain evidence for the shared mechanism. Two-package validation, complete build copying, backup/replacement failure state expectations and independent handling below are pending extensions; they do not turn the existing Checklist-only checks into evidence for Sticky note.

## Test hooks

The bundled-template validation command accepts an optional source-directory argument for temporary fixture trees; the server build supplies the real `packages/server/assets/templates` directory. The argument changes only the input tree and forfeits no validation behavior.

The bundled-state writer accepts a filesystem-operations adapter for temporary-file write and rename. Production uses Node filesystem operations. A test adapter records the paths and delegates to those same operations; it may create a directory at the chosen temporary path just before delegating the write. This changes only the timing of that real filesystem obstruction and forfeits no filesystem behavior. Temporary source trees, installed folders, and state files are fixtures.

- **Contract** (state file → serving installer and recorded state-file operations delegated to the real filesystem): Under [the state contract](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-state), valid version-1 state keeps unique exact IDs in English-locale order. - **Seam** (serving boot → installed folder and state file, real filesystem): Under [the specified behavior](../../../specs/arch/templates/bundled-installation.md#^bundled-artifact-template-replacement), an unhandled absent ID installs; a handled absent ID remains absent; a valid existing folder at or above the minimum remains byte-for-byte intact and becomes handled; an invalid or below-minimum occupant is replaced only after a hidden timestamped backup succeeds. Each boot warns and leaves a complete prior folder or complete replacement at the failed destination. A real socket obstruction making Checklist backup fail still permits Sticky note installation and records only successful handling; clearing it permits retry on the next boot without overwriting the valid Sticky note. State remains uniquely sorted.
