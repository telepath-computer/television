# Checklist artifact template — proof

Proves [specs/arch/templates/checklist.md](../../../specs/arch/templates/checklist.md).

## Coverage model

Package contracts read the actual bundled files. Store contracts exercise the same validation, ordering, and transaction-update logic the copied page uses, with authored values and no replacement SDK. They cover input variations without requiring a browser for every value.

Browser seams use a copied Checklist artifact, the served resource SDK, a running server, and its real JSON store. They observe outgoing operations and read persisted results through the administrative API. A forwarding network proxy can hold a transaction attempt while another client writes; it changes delivery timing without replacing comparison, retry, or persistence. It does not establish behavior under arbitrary network schedules.

The [Checklist UI proof](../../ui/templates/checklist/index.md) owns editing, focus, concurrent viewers, access changes, failures, and recovery. Its [conformance assertion](../../ui/templates/checklist/index.md#^checklist-ui-ac-conformance) owns rendered appearance; the delivery seam below proves that the copied page actually loads its packaged stylesheet. Thumbnail appearance and README meaning also require review; file checks cannot prove that a screenshot depicts the intended state or that prose teaches an agent correctly.

[Template architecture](./index.md) owns general copying and seed creation; [bundled installation](./bundled-installation.md) owns build membership and boot replacement. [The JSON store proof](../resources/json-store.md) owns push-key generation, last-write-wins, transaction retry, and durability. The assertions here establish that Checklist uses those mechanisms with the specified scope.

## Test hooks

The package and pure contracts need no replacement production dependency; direct calls exercise the validation and ordering logic used by the shipped page.

Browser cases use the served SDK path and forwarding proxy declared in the [Checklist UI proof](../../ui/templates/checklist/index.md#test-hooks). A proxy may record operations and hold a compare-and-set request until an administrative write completes; production delivers it immediately. No request or reply is fabricated.

## Store contracts

- **Contract** (authored values → production Checklist validator, transport absent; no mocks): Under [validity](../../../specs/arch/templates/checklist.md#^bundled-artifact-template-checklist-store), accept the seed, arbitrary store-valid item keys, finite negative and fractional orders, empty strings, and extra fields at the root and in items. Reject absent values, null or array roots, missing or wrongly typed title/items, and any item missing or mistyping `order`, `text`, or `done`, including nonfinite orders supplied directly to the validator. One bad item rejects the whole value. Extra fields do not affect the decision or mutate input. JSON transport itself cannot carry nonfinite numbers; its rejection belongs to the JSON store proof. [The error-page acceptance](../../ui/templates/checklist/index.md#^checklist-ui-ac-invalid) crosses valid and invalid results into the real page. *(policy-grade test: `packages/server/test/checklist-model.test.ts`, “Checklist whole-value validation”)* ^templates-checklist-t-validity
- **Contract** (authored item maps and insertion positions → production ordering logic; no mocks): Under [ordering](../../../specs/arch/templates/checklist.md#store), sort by ascending numeric order, then JSON-store key order, including numeric keys such as `2` and `10` before non-index keys, and non-index keys in UTF-16 order. Adding to an empty list uses 0; top and end use minimum minus one and maximum plus one; insertion between neighbours uses their midpoint. Equal neighbours, adjacent representable numbers, and extreme orders for which adding or subtracting one cannot move strictly beyond a neighbour select renumbering. Done state never changes ordering. *(policy-grade test: `packages/server/test/checklist-model.test.ts`, “Checklist ordering and insertion”)* ^templates-checklist-t-order
- **Contract** (authored current maps → production renumbering callback; no mocked store, transaction transport absent): Under [renumbering](../../../specs/arch/templates/checklist.md#store), each callback invocation sorts its current input, inserts the new item in the requested position, and assigns consecutive orders from 0, preserving all other fields of existing items. Invoke it again with another writer having changed text, done state, order, extra fields, membership, or removed the predecessor: it derives from that current input, preserving those changes and appending when the predecessor has gone. Missing or invalid `items` aborts without a proposed write. This proves callback behavior, not retries; [the real transaction seam](#^templates-checklist-t-transaction) supplies that crossing. *(policy-grade test: `packages/server/test/checklist-model.test.ts`, “Checklist renumbering callback”)* ^templates-checklist-t-renumber

## Store crossings

These seams drive actual input on the copied page and read the real store. Authored fixtures include extra root and item fields, tied orders, and exhausted numeric gaps. Only the standard CSS-motion override replaces behavior; it forfeits motion. Proxy holds, where named, control network timing without replacing SDK or server logic.

- **Seam** (page edit handlers → resource SDK → real store operations): Under [write scope](../../../specs/arch/templates/checklist.md#store), observe that title editing writes only `title`; text and checkbox saves set the complete `{ order, text, done }` object only at `items/<key>`, dropping extra fields from that item while preserving the root and other items. Ordinary additions use `push` under `items`, with a complete object and a generated key; deletion removes only its key. Read the stored result as well as observing operation paths. The [UI entry and editing tests](../../ui/templates/checklist/index.md#^checklist-ui-ac-title) may carry these observations rather than duplicate their interactions. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “new Checklist from the popover persists its seed, display, additions and independent assets”; “title saves before blur, preserves empty title, joins pasted lines and enters the list”; “items save complete objects, retain whitespace and order, insert rows and keep native undo”; “accessible checkbox and remove controls work by keyboard and preserve removal focus”)* ^templates-checklist-t-write-scope
- **Seam** (page insertion → SDK transaction at `items` → real compare-and-set retry and persisted result): Under [renumbering concurrency](../../../specs/arch/templates/checklist.md#store), trigger insertion between tied or numerically adjacent orders and observe a transaction on `items`, using a key generated by `push`, that adds exactly one item and renumbers the map. Hold its first compare-and-set request, change the map through the real administrative API, then release it. A real conflict causes a retry that retains the concurrent changes, including extra item fields; a second case removes the predecessor and places the new item at the end. Subscribers see the committed map with insertion and renumbering together, and root fields remain intact. The contract above supplies the remaining numeric variations. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “renumbering retries from concurrent data with all extra fields”; “renumbering retries from concurrent data after predecessor deletion”; “Return focuses the optimistic row before an ordinary or transaction acknowledgement”)* ^templates-checklist-t-transaction
- **Seam** (in-flight page renumbering → real concurrent invalidation → aborted transaction): Under [the transaction abort rule](../../../specs/arch/templates/checklist.md#store), hold an attempt, then remove `items` or replace it with an invalid map through the administrative API. On conflict, the retry proposes no write: the page adds no item, and the external value remains unchanged. [Invalid-data UI coverage](../../ui/templates/checklist/index.md#^checklist-ui-ac-invalid) owns the error page. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “renumbering aborts when concurrent items become missing”; “renumbering aborts when concurrent items become invalid”)* ^templates-checklist-t-transaction-invalid
- **Seam** (whole-value subscription → page write guards → real store): Under [no writes after invalid data](../../../specs/arch/templates/checklist.md#store), invalidate the root through another client while the page has an active editor and unsent input. After the invalid value is delivered, subsequent input, blur, and any deferred save start no write; the invalid value remains untouched. A separate ordering case holds an ordinary write already sent before invalidation: releasing it follows the store last-write-wins rule, with no claim that the page cancels it. After a valid value arrives, fresh user input can save again. *(policy-grade test: `packages/web/test/e2e/template-checklist-real-stack.test.ts`, “invalid subscriptions guard unsent input and blur while an already-sent write remains last-write-wins”)* ^templates-checklist-t-invalid-guard
