# Weather artifact template — proof

Proves [specs/arch/templates/weather.md](../../../specs/arch/templates/weather.md).

## Coverage model

Package contracts read the real bundled manifest, seed, page files, icon and README. The generic [template proof](./index.md) owns creation-time schema enforcement, copying, display-option precedence and independent stores. [Bundled installation](./bundled-installation.md) owns build membership and boot replacement. The assertions here establish the Weather values supplied to those shared paths.

Pure contracts exercise the configuration and saved-forecast parser, request builder, Open-Meteo response normalizer, request eligibility, forecast selection, display windows, rounding and elapsed age used by the copied page. Success fixtures are captured Open-Meteo responses with their CORS header. Edited copies vary one relevant response field for mapping and failure breadth. Those are fixtures, not replaced page code; the contracts do not claim HTTP, browser CORS, store or rendered-page coverage.

Default browser tests run the copied page in Television's real sandbox against a running server, resource SDK and JSON store. They intercept every `https://api.open-meteo.com/**` request and script its captured response, delay or failure. That interception mocks the provider and public network, forfeiting the live endpoint, current provider response, provider timing and availability. The browser still makes the production fetch and applies real CORS checks to the captured `Access-Control-Allow-Origin` header. An unexpected provider method, URL, query or disposition fails the test, and every other external request is blocked.

One opt-in browser test, excluded from CI and default verification, crosses the real browser-provider seam from Television's opaque-origin sandbox. It proves the live endpoint, current browser CORS path and response acceptance at the time it runs, and can refresh the committed fixtures. It does not prove the provider's terms or limits, future compatibility or availability, or the desktop `Origin` and `Referer` path. The release gate remains human sign-off, not a test result.

The [Weather UI proof](../../ui/templates/weather.md) owns visible labels, responsive composition, placeholder states, access and recovery, attribution and conformance. It shares the primary creation/fetch/save walk with this proof. The first-party condition drawings and Toolbox icon need no third-party notice. The warning and spinner copied from the foundation use Phosphor artwork; [licensing coverage](../licensing.md#^licensing-t-weather-icons) owns the asset record and generated package notice.

## Test hooks

No production test hook is required. Contract tests call the same production parsing, request, normalization and selection modules the page imports.

Playwright may control the browser clock. Production uses the browser clock. Clock control forfeits real elapsed scheduling, not the page's timer callback, request decisions or time-zone calculations.

Browser tests intercept the provider at the network boundary as declared above. They use temporary Television homes, real stores and authored configuration or saved-cache fixtures. The opt-in live test removes that interception for the exact provider request only.

## Store and display contracts

- **Contract** (authored roots → production manifest-schema validator and Weather parser; transport and DOM absent, no mocks): Under [the store schema](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-store) and [page checks](../../../specs/arch/templates/weather.md#store), classify an absent value and `{}` as empty and accept configured Celsius and Fahrenheit locations with extra fields. Reject other incomplete or wrongly typed configuration, empty place names and out-of-range coordinates as unreadable. Accept an omitted `forecast` or any root-schema value in that field, then separately accept only forecasts with matching coordinates and units, recognized conditions and IANA zone, complete current values, valid dates and offset-bearing instants, at most 24 hourly entries, and daily highs at least their lows. An invalid or incompatible saved forecast is ignored without making valid configuration unreadable; a valid saved forecast is compatible across a place-only change. Inputs remain unchanged. [Creation-schema coverage](./index.md#^templates-t-preflight) proves that the manifest schema gates starting and caller data; [UI invalid-data acceptance](../../ui/templates/weather.md#^weather-ui-ac-invalid) crosses page classification into the copied artifact. *(test to be written)* ^templates-weather-t-validity
- **Contract** (compatible forecast, current instant and IANA zone → production display-window derivation; authored cache fixtures, no mocks): Under [the hourly window](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-hourly-window) and [daily window](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-daily-window), parse timestamps as instants regardless of written offset. Stably sort, keep the first duplicate instant or date, discard hours through the current local clock hour and dates before the current local date, then retain the first 23 future hours and first seven remaining dates. Empty arrays remain valid. Run with `TZ=UTC`. For `Asia/Kolkata` at 1:30 AM, drop both 1:00 AM and a 1:45 AM instant that is later than now but inside the same local hour, and retain 2:00 AM. Give duplicate instants different offsets and fractional seconds, and make text order differ from instant order. For the `America/New_York` fallback, retain the second 1 AM while the current instant is in the first 1 AM, using distinct `-04:00` and `-05:00` instants. Cover dates east and west of UTC. Construct expected dates as calendar fields, never by parsing `YYYY-MM-DD` as a UTC instant. Browser-zone independence belongs to [UI time-zone acceptance](../../ui/templates/weather.md#^weather-ui-ac-time-zones). *(test to be written)* ^templates-weather-t-windows
- **Contract** (compatible forecast and current instant → production current-value derivation; authored fixtures, no mocks): Under [current high/low and elapsed age](../../../specs/arch/templates/weather.md#store) and [UI current conditions](../../../specs/ui/templates/weather.mdx#current-conditions), choose high and low only from the first retained daily entry for the current date at `timeZone`, and omit them when absent. Derive age from `updatedAt` in completed minutes, hours and days, treating less than a minute and future skew as now. Bind 59 seconds, 60 seconds, 90 seconds, 59 minutes 59 seconds, 60 minutes, 23 hours 59 minutes and 24 hours. Positive and negative half-degree values in current, hourly, daily-low and daily-high positions round away from zero; zero never carries a minus sign; stored values do not change. UI acceptance owns the English labels and placement. *(test to be written)* ^templates-weather-t-current-values

## Provider request and response

- **Contract** (configured location → production request builder; authored configurations, no mocks): Under [the request form](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-request), build a GET to exactly `https://api.open-meteo.com/v1/forecast` with the configured coordinates, requested current/hourly/daily field lists, matching `temperature_unit`, `timeformat=unixtime`, `timezone=auto` and `forecast_days=7`. Place names and saved forecasts never enter the URL. Exercise both unit values, negative and fractional coordinates, and exact query membership independent of parameter order. *(test to be written)* ^templates-weather-t-request
- **Contract** (captured Open-Meteo JSON → production response normalizer; captured success fixtures and edited copies, HTTP absent at the test edge, no mechanism mocks): Under [response success and WMO mapping](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-wmo), accept only a successful JSON-shaped response with integer `utc_offset_seconds`, complete valid current data and the expected temperature-unit strings. Map every documented WMO code to the specified condition and summary, including slight hail for 96, heavy thunderstorm for 97 and heavy hail for 99; map `is_day` 0 and 1 without inference. For hourly and daily arrays, drop only entries with a missing, null, non-finite, invalid or unmapped requested value, and drop a daily high below its low; extra values beyond `time` are ignored. Apply the hourly-window ordering, duplicate and eligibility rules at receipt and retain at most 24 entries. Empty normalized lists can still succeed while incomplete current data, bad units, bad metadata, invalid JSON and unknown current codes fail. Stamp `updatedAt` with the supplied receipt instant and requested coordinates and units. A normalized success passes the same forecast checks as saved data. *(test to be written)* ^templates-weather-t-response
- **Contract** (captured UNIX-time responses → production normalizer and forecast windows; browser process in `TZ=UTC`, no mocks): Under [Open-Meteo time conversion](../../../specs/arch/templates/weather.md#forecast-request-and-mapping), hourly epoch seconds become instants and use the returned IANA zone only for local display. For the captured New York response spanning the 1 November 2026 fallback, apply its fixed `utc_offset_seconds` to each daily epoch before taking the date: the seven results remain 27 October through 2 November even though converting the last timestamp through `America/New_York` directly would produce 1 November. At `2026-11-01T02:30:00Z`, the New York current date is 31 October and the retained dates cross the offset change through 2 November. Repeat with an `Asia/Kolkata` response and its half-hour offset at `2026-10-27T20:00:00Z`, when the Kolkata current date is 28 October. Expected dates are literal fields calculated from the documented offset rule, not from `new Date('YYYY-MM-DD')` or the process zone. Feed the normalized results into the production windows and assert the retained dates and hours. *(test to be written)* ^templates-weather-t-provider-time-zones

## Request lifecycle, saving and access

- **Contract** (request state, current configuration and clock instant → production request-check decision; authored states, HTTP/store/DOM absent at the test edge, no mocks): Under [the request check](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-request-check), request only when configuration exists, no attempt for its coordinates and units is running, no failed attempt for them began in the preceding 15 minutes, and no compatible saved or in-memory forecast has a non-future `updatedAt` in that period. A success contributes only forecast freshness. A failure at 14 minutes suppresses a retry and one at 15 minutes permits it. A future-dated forecast is not fresh. Changing only the place reuses a fresh forecast. Exercise Celsius success → Fahrenheit success → Celsius and `{}` → same configuration: each return requests immediately because no compatible forecast or relevant running/failed attempt remains. An unavailable store produces no request. A store value without configuration also clears the running attempt, failed-attempt record and in-memory forecast as specified. *(test to be written)* ^templates-weather-t-request-check
- **Acceptance** (real Chromium Page Visibility and clock → copied page → intercepted provider; real server, SDK and store; captured provider fixtures; provider mock and standard CSS-motion override): Under [the request check](../../../specs/arch/templates/weather.md#^bundled-artifact-template-weather-request-check), a visible document checks about every minute and receives a new success about 15 minutes after the preceding result; a hidden document neither starts attempts nor runs scheduled checks, and becoming visible checks immediately. Use actual `document.visibilityState` transitions, not a page flag. An unselected Television tab page whose browser document remains visible continues checking. Delay one request beyond 10 seconds and observe its abort and failed-attempt throttle; while an attempt runs, no second one starts. In separate delayed-request passes, change only latitude, only longitude and only units: each old request is aborted immediately, and even a late old response is neither shown nor saved. Provider interception forfeits live service behavior to [the opt-in seam](#^templates-weather-live-provider); clock control forfeits real elapsed cadence, not Page Visibility, aborts or request decisions. *(test to be written)* ^templates-weather-ac-request-cycle
- **Acceptance** (real browser → Toolbox → copied Weather page → running server and real JSON store; spawned built `tv` configuration write; captured provider response and provider mock; standard CSS-motion override): Under [live store use, fetch and saving](../../../specs/arch/templates/weather.md#saving-failure-and-access), create Weather from Toolbox, observe the `{}` seed and no page write, then use the documented whole-root command to set only place, coordinates and units. The page makes the exact request, accepts the captured response, displays it without reopening and saves one normalized compatible forecast through a root transaction while preserving place and extra fields. The saved cache has the receipt `updatedAt`, requested coordinates and units, returned zone, mapped current values, at most 24 eligible hours and the returned eligible daily entries. This is the same browser test as [the UI creation and fetch acceptance](../../ui/templates/weather.md#^weather-ui-ac-new); the test cites both anchors. *(test to be written)* ^templates-weather-ac-live
- **Acceptance** (two real browser pages → copied page → running server and real JSON store; captured provider fixtures with controlled response order; provider mock and standard CSS-motion override): Under [saving and selection](../../../specs/arch/templates/weather.md#saving-failure-and-access), two write-access pages may fetch independently; each successful response is shown from memory, and the last transaction to commit supplies the saved forecast without restoring concurrently changed coordinates or units. A save refused for changed access, connection loss or any other reason leaves the in-memory forecast visible and queues no save. When compatible saved and in-memory candidates compete, prefer a non-future candidate over a future one and otherwise the later `updatedAt`. A stale-cache refresh failure leaves both store and shown forecast unchanged; a later success replaces them. The provider mock forfeits live provider behavior to [the opt-in seam](#^templates-weather-live-provider). *(test to be written)* ^templates-weather-ac-cache
- **Acceptance** (owner and read-only real browser pages → copied page → running server, SDK and store; captured provider fixtures delayed or failed; provider mock, connection proxy and standard CSS-motion override): Under [access and failure](../../../specs/arch/templates/weather.md#saving-failure-and-access), a read-only page fetches and displays its own result without writing. An ordinary Television disconnection keeps the last location and forecast and permits a visible page's scripted provider refresh to replace only its in-memory result; reconnecting catches up with stored configuration and restores later saves. Revocation aborts a running provider request, rejects a response released afterward, starts no later request and keeps the forecast already shown; with no forecast it remains loading even if the prior attempt had failed. Provider failure with a compatible candidate keeps it and its unchanged age; without one it reaches unavailable and the next attempt comes only after the failed-attempt interval. The connection proxy forfeits only the severed Television transport; other cases cross the real resource path. Provider interception forfeits the live service to [the opt-in seam](#^templates-weather-live-provider). *(test to be written)* ^templates-weather-ac-access
