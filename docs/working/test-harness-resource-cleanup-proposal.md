## Problem and intended result

In the investigated runs, repeated unbundled application loads consumed several GiB of Chromium response-buffer memory. Persistent Blaxel workers also retain temporary test runtimes across runs, reducing the memory and filesystem capacity available to browsers. The [investigation](chromium-insufficient-resources.md) establishes renderer OOM kills and reproduces `ERR_INSUFFICIENT_RESOURCES`; the exact failing allocation syscall remains unobserved.

The fixes have different effects. The historical theme-reset walk added roughly 3.2 GB of shared memory in a passing run that reached about 0.55 GB available RAM. Built loading removes hundreds of development-module requests per load, but those historical numbers cannot predict its incremental saving after the Vite response correction described below. By comparison, the two leaked runtime prefixes occupied 1.16 GB on the worst worker inspected and 0.079 GB on the other. All of `/tmp` occupied 1.20 GB and 0.16 GB respectively. Cleanup recovers accumulated capacity; it does not guarantee browser headroom. The original worker also retained roughly 1.4 GiB of checkout/dependencies, 0.9 GiB of browser installations, and other intentional caches. Those are outside this cleanup.

This contribution fixes the cached runtime lifetimes, moves five acceptance cases in two files onto the built application, and retains compact resource evidence when an acceptance fails. It also makes the worker reservation cover preparation, execution, process teardown, and result download, with automatic recovery when a coordinator stops renewing its reservation. After taking that lock and confirming the worker is idle, each run removes the two known leaked-runtime prefixes and stale run scratch. This repeatedly reclaims residue from older test revisions as well as newer ones. Cleanup preserves provider services, deliberate caches, and the current run; abandoned runs and reports have the bounded recovery rule below.

PR #9 merged as `f81a2465` on 2026-10-01 and owns the built-application conversion of **“executable theme reset reloads connected Chromium documents under confirmed state.”** Preserve that integrated change; do not duplicate it. Main also includes `982e564d` (PR #32), making registry Vite services answer conditional requests in full. Its runner spec records Chromium 145 retaining about 2 MB per 304 response, roughly 465 MB per application reload. That newer mitigation changes the baseline for future measurements. The investigation numbers above describe the historical runs, not current main's residual memory cost; neither the helper leak nor the lock/download gaps is repaired by the Vite response change.

## Worker exclusion, result retrieval, and safe `/tmp` cleanup

Josh has selected routine cleanup under an exclusive worker lock. There is no pool drain-and-recreate plan or outstanding rollout choice. Before each run, remove only the two known legacy prefixes and stale scratch in the dedicated runner namespace; after execution, remove that attempt's scratch only after its processes stop and its evidence has been finalized outside scratch. Never delete all of `/tmp` or use age alone as proof of disuse.

### What the existing code establishes

The canonical coordinator intends one shard job per sandbox. [`acquireAny()` and `lockCommand()`](../../scripts/run-blaxel-testshards.mjs) acquire `/tmp/tv-testshard.lock`; another coordinator skips an unexpired lock. Within a shard, surface tasks execute sequentially, but a surface can have several test workers and many child processes. This does not prove that a worker never has overlapping jobs:

1. Lock expiry allows reclamation based on time alone. The record identifies the coordinator host/PID, not the remote shard supervisor. Setup is not fully covered by surface owner tokens. The configured TTL is 900/1200 seconds against a 240/480-second worker timeout, but provider timeout is not evidence that every descendant has stopped. Main's spec at `a8e73fbf` explicitly uses TTL as the final availability bound for uncertain cleanup; this contribution replaces that requirement.
2. The shard shell's `EXIT` trap releases the lock before `runShard()` downloads results from `/workspace/television/.testshards/results`. A following checkout clears that fixed tree. This leaves an unprotected interval in which the previous job's evidence can disappear or be replaced. Report identity checks can detect some mismatches but cannot restore deleted files. This source-level race is present at both the branch base and inspected main; no collision was observed during the Chromium investigation.
3. Direct Blaxel process API calls bypass this repository lock. The inventory used that API. `manage-blaxel-testshards.mjs` also provisions and checks workers through `process.exec`, and deletes them through the provider API. The idle snapshots establish neither provider serialization nor a history-wide absence of overlap.

These are demonstrated protocol gaps, not demonstrated causes of the Chromium failures. The download-race follow-up is incorporated here. Replace blind TTL reclamation with a renewable reservation whose expiry requires process cleanup before reuse.

### One lock through process teardown and download

Josh's calibration is that only our runner and pool scripts touch these workers. Correct those code paths using the existing lock; do not add a worker controller, persistent compatibility fence, access-control system, or defenses against hypothetical API callers.

For a participating coordinator, retain the worker lock until both conditions hold: **all execution for the attempt is stopped, and its results are downloaded and validated at the coordinator.** Keep atomic directory acquisition and the existing `lockId` ownership check. Write `expiresAt: 0` for compatibility: the inspected older runner reclaims only a positive timestamp in the past, so it leaves these locks alone. The updated runner uses a separate renewable recovery deadline, described below. That deadline authorizes cleanup of an abandoned attempt, never immediate reuse beneath surviving processes. Normal release removes the directory, as it does today.

The runner's order becomes:

1. Acquire the lock, recovering an abandoned attempt if necessary, then confirm the worker has no prior test/shard work before removing known leftovers. Extend owner-token attribution to the outer shard, including checkout and setup children. Preserve that attempt token alongside surface tokens, which nested supervisors replace today, so detached descendants remain attributable to the attempt. Record the remote process name and PID/start identity so recovery can distinguish the run from PID reuse; the coordinator's host/PID alone is insufficient.
2. Renew the reservation while preparing, executing, cleaning up, and downloading. Keep renewal active while waiting at the existing all-shards-acquired barrier. Keep sequential surfaces and attempt/retry behavior. Record that dispatch was requested before making the API call. If its outcome is unknown, retain ownership while resolving it; a coordinator that exits leaves the bounded recovery path to the next acquirer.
3. On success, failure, timeout, or interruption, stop and audit the run's attributed processes, including descendants of an exited shell. Reuse the existing owner audit and TERM/KILL cleanup. A shell exit or successful kill API response alone is insufficient. The shell finalizes reports but no longer releases the lock in its `EXIT` trap.
4. Download the existing summary, native reports, logs, setup/cleanup evidence, and new diagnostic sidecars to the coordinator's run directory. Validate the existing run/attempt identities and required files. Missing or corrupt evidence remains an infrastructure failure; an early setup failure records which reports were never produced and retrieves what is available.
5. Release the matching lock only after teardown and retrieval complete. Keep the fixed checked results tree: protecting it through download closes the checkout-reset race without a separate artifact archive. Release unused locks after acquisition/upload failures only when execution was never requested and there are no pending writes or produced results to retain.

All runner exit paths must follow that order, including acquisition rollback, architecture rejection, both signal paths, retry, and exception cleanup. An interrupted download retains the lock; retry retrieval without repeating the tests. If the coordinator exits before completing that work, it stops renewing and reports the reservation's recovery deadline. A failed teardown or uncertain dispatch excludes that worker from immediate retries. Keep the default retry budget.

### Automatic recovery with one renewable deadline

**A coordinator keeps its reservation by renewing it; after renewal stops for the recovery interval, the next acquirer stops and audits that run's owned processes, clears its abandoned state, and takes the lock.** The same procedure handles an already quiet worker and a surviving shard supervisor or test descendant. An expired deadline alone never makes the worker available.

Use the coordinator to renew throughout ownership, including result download. Each successful renewal records worker-local time and sets `recoverAfter` to that time plus **20 minutes**, independent of the worker execution timeout. Reuse `--lock-ttl-seconds` to override this recovery interval; do not add another option or carry the worker timeout in the lock record. Renew comfortably within the configured interval, with cadence derived from it so short private-worker checks work too. Renewal requires the same owner and a still-valid deadline; it cannot revive an expired reservation. Only the coordinator renews: a surviving supervisor cannot preserve a crashed coordinator's reservation forever. No daemon, cross-host PID probe, or separate heartbeat service is needed.

The automatic entry point is the canonical runner's `acquireAny()` / lock helper. On finding an expired `recoverAfter`, it performs this bounded worker-local sequence before publishing a new owner:

1. Re-read the matching lock identity and deadline under a short filesystem critical section shared by acquisition, renewal, dispatch registration, and release. Use an OS-released advisory lock (for example `flock` on a fixed guard file outside the disposable lock directory), so a killed recovery process cannot leave a second permanent mutex. Hold it only for worker-local state changes and bounded cleanup, not network downloads. A competing acquirer or late renewal cannot act on a stale read.
2. Stop only the old run's attributed supervisor and descendants, using its owner token and the existing PID/start-identity checks, TERM/KILL escalation, and owner audit. The current stale-owner reaper deliberately leaves live supervisors' children alone; recovery must stop the abandoned run's live supervisors as well, without weakening the ordinary reaper's protection for other owners. Confirm no live or stale owners or remaining attributed processes before deleting their files. A dead supervisor is not enough; detached descendants still count. A late remote dispatch must check the matching, unexpired reservation and register ownership under the same critical section **before** checkout/setup can start. This prevents an API request delayed across recovery from launching the old run into the new checkout. Uploads use attempt-specific scratch paths.
3. Remove the abandoned attempt's scratch and the allowed legacy leftovers, then reset its results as part of the next run's normal preparation. **Discard undownloaded results of this abandoned attempt after the recovery interval.** Do not create a second archive or require an orphan-report download that can itself block reuse. Record the prior worker/run/lock, last renewal and deadline, stopped process identities, cleanup outcome, and whether reports were discarded in a bounded recovery receipt with the incoming attempt's setup sidecars, outside the old results tree being reset. Loss of reports never becomes a passing result for the abandoned run.
4. Publish the incoming reservation only after cleanup succeeds. Recovery is repeatable: if its process dies midway, the old expired identity remains until another acquirer finishes the same work. Normal release and renewal check `lockId`; a returning coordinator that has lost it must stop work and report infrastructure failure, never release or mutate the new owner's attempt.

This defines coordinator loss operationally: it has stopped renewing for the recovery interval. It does not prove that a remote OS process died. A network partition or suspended coordinator beyond that interval has the same consequence as a crash. A healthy coordinator keeps renewing through a long download, so elapsed shard time alone does not end retrieval protection. Once renewal is lost, orphaned reports are the explicit exception to normal download-before-release. Their file timestamps do not extend the deadline; a hung child must not defeat recovery by continuing to write.

The capacity cost is bounded by the remaining recovery interval, the next acquisition attempt, and bounded process cleanup. Quiet crash leftovers wait the same interval as active ones; accept that availability cost to avoid a second liveness test, report-age clock, or special quiet-run recovery procedure. Twenty minutes preserves the existing cold-profile operating allowance while removing its coupling to execution time; it is not a measured provider guarantee. Verify renewal and cleanup timing on private workers before relying on it.

Two correctness limits remain. Failure to identify or stop a process must hold and report the worker rather than run tests over it; an unkillable process or broken provider needs operator repair, not another expiry that ignores the failed audit. Missing or corrupt **lock ownership** is also different from missing scratch metadata: dispatch cannot precede complete ownership registration, and an empty acquisition left before dispatch can be reclaimed after a clean worker audit, but ambiguous live work cannot be killed by a name guess. These limits prevent unsafe reuse; an ordinary crashed coordinator with attributable surviving processes follows automatic recovery and does not need an operator.

### Older branches and pool operations

Older branches matter in two concrete ways. Their helpers still leave the two known directory prefixes, which every updated run removes. Their coordinators also unlock at shell exit and use timestamp expiry. New locks' `expiresAt: 0` stops the inspected old acquisition code from taking an updated run's worker, but cannot correct an old coordinator's own early release. Branches take the correction when they integrate main; updating every active branch or waiting for all old runs is not a prerequisite for this contribution or its final verification.

A legacy lock has no renewable deadline or complete outer-run attribution. Respect its unexpired TTL. After expiry, reclaim it only following a clean worker audit; skip and report one with live or ambiguous work. The inspected old shard's exit trap removes only its own matching `lockId`, so ordinary old work frees itself when it ends. Do not infer an owner token from a process name or build a separate legacy recovery system. An old run that never exits remains an operator case; the pool deletion path below remains available. No permanent old-client exclusion mechanism or pool recreation is proposed.

`manage-blaxel-testshards.mjs` is the other actual API caller to correct. Deletion checks ownership under the same worker-local guard and refuses an unexpired reservation. After expiry, explicit pool deletion may reserve and delete even a worker whose process cleanup failed: destroying the sandbox is the cleanup. Remove that worker from test discovery before calling the delete API, so a failed or delayed deletion cannot admit a test run. Retain and report it as unavailable if deletion fails; do not silently return it to the pool. Unreadable or incomplete records follow one rule for acquisition and deletion: reclaim only after a clean worker audit, otherwise hold and report. A fresh worker never published for test dispatch may be deleted without a lease. Any other worker whose ownership check cannot run is held for operator repair; current discovery ineligibility alone does not prove an earlier run stopped. The manager continues to list such workers for operator repair. `ensure` remains fresh-only, so partial deletion does not refill capacity; the target pool must be deleted and recreated to replace missing workers.

For fresh provisioning, publish the labels used by test-worker discovery only after runtime setup and architecture verification succeed. This closes the interval between sandbox creation and acquiring a lock without relying on a pool-wide dispatch stop. The manager must still identify and report partially provisioned workers, and must not silently reuse them through `createIfNotExists`. Listing/status is read-only. This covers our pool script without a generic API gateway or a new pool-draining protocol.

Preserve the runner's read-only `--audit-stale-owners` mode: it must not recover another run or remove residue before observing it. It may reserve an available worker without recovery, holding that reservation through its existing dependency setup and report collection. A held lock is reported/skipped. This exception preserves the diagnostic's purpose; ordinary test acquisition uses automatic recovery, and pool deletion respects the same reservation deadline with the destruction exception above.

### A directory for each shard attempt

Give every locked shard **attempt** a fresh, short, private directory beneath a runner-owned root, for example `/tmp/tv-testshards/<random-id>/`. Record its run, shard, attempt, lock identity, and remote supervisor identity outside its disposable `tmp/` child for diagnostics. The current attempt's directory is explicitly excluded from pre-run cleanup, including before dispatch. Missing or incomplete metadata in an earlier attempt's scratch does not add a cleanup gate once the lock and worker audit establish disuse. Upload/dispatch failure removes only this attempt's directory when execution is known not to have started and pending requests have settled. An unknown outcome leaves the lock and scratch for recovery. Use a short path because browser and Electron processes can create Unix sockets with limited pathname length.

Export an absolute `TMPDIR` pointing to that child before running preparation and test commands. Keep scripts, plans, askpass, and setup sidecars within the attempt directory as well. Preserve `TMPDIR` through child environments. Continue to keep deliberately persistent npm, Electron, browser-download, and dependency-hash caches at their existing locations outside scratch space. Playwright's transform cache may become attempt-local initially; measure any resulting setup cost before deciding it deserves a separately bounded persistent cache.

The mechanism is supported by both source and installed dependencies:

- On non-Windows systems, [Node's `os.tmpdir()`](https://nodejs.org/api/os.html#ostmpdir) checks `TMPDIR` before `TMP`, `TEMP`, and `/tmp`. Both cached build helpers use `os.tmpdir()`.
- [Chromium 148's `GetShmemTempDir()` and `GetTempDir()`](https://github.com/chromium/chromium/blob/148.0.7778.96/base/files/file_util_posix.cc#L1283-L1302) select the temporary directory when `--disable-dev-shm-usage` is present; `GetTempDir()` reads `TMPDIR`. The investigation observed this flag in the actual browser launch.
- Installed Playwright 1.58.2 uses `os.tmpdir()` for browser profiles and artifact directories in `playwright-core/lib/server/browserType.js`, inherits the parent environment by default, and includes that Chromium flag. Its transform cache also defaults to `os.tmpdir()`.

This establishes the intended wiring; a live Blaxel test must still observe Node-created paths and actual Chromium shared-memory descriptor paths under the attempt directory. We have not run that check at the proposal stage. Setting `TMPDIR` cannot relocate hard-coded `/tmp` paths or X11's global socket directory; the runner's explicit temporary paths must be moved deliberately, and external infrastructure remains untouched. Chromium also unlinks shared-memory files while holding them open, so directory deletion cannot substitute for stopping the owning processes.

### Exact deletion scope and order

Before preparation for **every run**, while holding the worker reservation and after confirming no prior execution or retrieval remains, remove:

- Real directories directly under `/tmp` whose basenames match `television-source-cli-e2e-*` or `television-web-bundle-*`. The helper source and inventories establish these as leaked test builds; Josh has authorized their recurring removal. Missing per-directory metadata on these legacy copies is expected. The whole-worker exclusion and idle check supply the disuse evidence that the prefix alone cannot supply.
- Every attempt directory directly beneath the dedicated `/tmp/tv-testshards/` root except the current one, after the worker owner audit confirms no prior live or stale owners remain. These directories belong to our runner. As with the legacy prefixes, the held lock and clean worker audit establish disuse; missing, half-written, or inconsistent per-directory metadata does not prevent removal. This does not reclaim another run's held lock or decide how dead-coordinator locks are recovered.

Revalidate directory identity immediately before deletion; reject symlink roots, unexpected mount boundaries, or paths escaping the exact allowed parent. Recursive removal must not follow nested links to another tree. Preserve the lock and guard, provider uploads, X11 state, unrelated temporary files, checkouts, and deliberate caches. Reports stay outside scratch; only abandoned-attempt recovery can discard them before download. Do not broaden the legacy patterns to other Television-looking names. Report per-prefix counts, allocated bytes removed, filesystem free space before/after, and skips or errors; those two space measurements need not be equal when files remain open or the filesystem accounts storage differently.

After execution, finalize evidence outside scratch, stop all attributed processes, then remove this attempt's scratch while the reservation remains held through download. Setup failure, acceptance failure, timeout, and interruption use the same ownership rule. If teardown is uncertain, preserve scratch and keep the worker reserved. If deletion fails after confirmed teardown, preserve the original test outcome and add cleanup failure evidence; the worker cannot start another test until pre-run cleanup succeeds. Evidence must still be downloaded. A partial deletion must never be reported as reclaimed capacity for the whole directory.

An inconclusive worker audit or a live consumer means skip deletion **and exclude that worker from test dispatch**, with a recoverable infrastructure failure. Missing scratch metadata alone does not make that audit inconclusive. There is no fallback to deleting unrelated files to obtain headroom. Known residue left by old test revisions is removed on subsequent updated runs without recreating workers or losing their caches. This proposal revision performs no worker cleanup or configuration changes.

## Worker lifetime for cached runtimes

Keep one lazily built source-CLI runtime per test worker and reuse it across launches and test cases. Publish the cached entry only after the build and asset installation succeed. A partial build removes its own directory and leaves the cache retryable. Apply the equivalent ownership rule to the cached versioned web bundles, retaining their per-version reuse.

Test cleanup continues to stop each case's product servers promptly. Worker teardown then stops any remaining servers and removes the shared cached runtime and versioned bundles. Cleanup is idempotent and waits for pending builds before removing their outputs. The worker teardown must cover both the shared Playwright registration helper and the Vitest callers; a per-test deletion would discard reuse and add unnecessary builds. A failed server teardown cannot justify removing files beneath a surviving server. The outer shard's process ownership and scratch cleanup provide the backstop when a worker is killed and cannot execute its own teardown.

The relevant entry points are `test/helpers/playwright.ts`, the two cached build helpers, and the Node/Vitest callers of those helpers. The design should use the runners' existing teardown facilities rather than a general-purpose cleanup registry. Failure during a per-launch runtime copy must also dispose that copy and its newly created home: the current bundle preparation occurs before the launch disposer is registered.

The helper fix matters even with shard scratch: it releases files between test workers within a shard and protects callers on hosts without the Blaxel shard script, including ordinary CI and developer environments. The reviewer independently counted 1,388 source-CLI and 727 versioned-bundle directories on this development host; that is reviewer evidence, not a new inspection by this contributor. Cleaning those existing host files is the host owner's decision and outside this contribution. The helper fix prevents new leakage on updated branches; it does not retrospectively remove unowned files.

When available, the shared browser failure hook can add a snapshot at the failed attempt boundary; this is an enhancement, not the minimum contract. Start/end samples provide context and an OOM delta, not a peak or exact allocation-time measurement. A system OOM-counter increase alone cannot attribute a kill to a browser; readable kernel lines provide process identities.
