# Table template: library assessment

*Research by an agent, October 16, 2026, for the Table template in `docs/working/real-templates-proposal.md`. Versions, licenses and sizes were checked against npm and upstream sources that day.*

**Recommendation: use the former `tv-table` house style with a small amount of template code. Confidence: high for the proposed read-only Table.** The draft has agent-defined columns, string cells and agent-written rows; it does not need a spreadsheet engine. A native `<table>` can use Television’s theme tokens and update only the affected `<tr>` when the resource SDK reports a row change. A sort button can be added if wanted. The [JSON store’s 1 MiB limit](specs/arch/templates/index.md:41) also weakens the case for a grid designed around millions of rows. The [canonical component bundle](packages/canonical/canonical-components.ts:1) contains no table component.

The sizes below are **published file bytes, not download sizes**. Some packages publish minified files and others do not, so the figures indicate the cost of copying files into each artifact rather than a controlled bundle benchmark. Versions and license declarations were checked against current npm releases on October 16, 2026.

### Candidate notes

- **House-style HTML:** The [former skill](packages/skills/skills/tv-table/SKILL.md:1) already specifies the desired layout and token use. Subscribe to `rows` with the SDK’s [child events](specs/product/resources/json-store.md:83), keep a DOM row by store key, and change or move that row when its cells or `order` change. Use text nodes for agent-supplied strings. A sortable header can be a native button with `aria-sort`; cell-by-cell arrow navigation would be a separate product feature.
- **TanStack Table:** Its [headless design](https://tanstack.com/table/latest/docs/overview) makes theme matching easy and offers sorting without accepting another grid’s appearance. It supplies neither markup nor editing or keyboard interaction. We would still write the row reconciliation code, and its module and dependency would need bundling when Television ships the template.
- **Tabulator:** [`updateRow` and `updateData`](https://www.tabulator.info/docs/6.x/update/) fit SDK child events. It has useful [editors and column types](https://www.tabulator.info/docs/6.x/edit/), and text formatters escape cell content. Its [themes use Sass variables](https://www.tabulator.info/docs/6.x/style/), so runtime matching across Television themes means maintaining overrides. Keep [persistence](https://www.tabulator.info/docs/6.x/persist/) off: it otherwise uses local storage or cookies.
- **AG Grid Community:** [`getRowId` with transactions](https://www.ag-grid.com/javascript-data-grid/data-update-transactions/) is the clearest library path for changes from other clients. Its [theme parameters accept CSS variables](https://www.ag-grid.com/javascript-data-grid/theming-parameters/); [editing and typed editors](https://www.ag-grid.com/javascript-data-grid/cell-editing/) and [keyboard and screen-reader support](https://www.ag-grid.com/javascript-data-grid/accessibility/) are documented. It becomes attractive if the Table becomes an editable data grid. Its weight and separate visual language are hard to justify for the current draft. An agent update arriving during an active edit still needs an explicit reconciliation rule.
- **Grid.js:** It is small and offers sorting, search and paging, but its documented update route is [configuration followed by rendering](https://gridjs.io/docs/examples/hello-world). I found no documented keyed, single-row update API or built-in cell editing. Its slow release cadence is another reason not to take on a vendored copy.
- **Jspreadsheet CE:** The [CE repository](https://github.com/jspreadsheet/ce) is MIT and focused on spreadsheet editing. The current npm release has no `license` field, and its formula dependency has neither a license field nor a license file in the published package; those terms would need a release-specific audit before Television could ship the files. Its positional spreadsheet model is also a poor match for stable store row keys. Published entry files for CE, jSuites and formula total roughly **768 KB before bundling**; that is an indicative sum, not a measured working page.
- **RevoGrid:** Its [real-time guide](https://rv-grid.com/guide/realtime-updates) recommends targeted `setDataAt` changes for cells, and its [theme tokens](https://rv-grid.com/guide/types/README) are CSS properties. It has [keyboard](https://rv-grid.com/guide/keyboard) and [accessibility](https://rv-grid.com/guide/wcag) guidance. It is credible if virtualization and in-page editing become requirements, but its chunked component runtime and grid presentation add work to a copied plain-file template.
- **DataTables:** Version 3 [no longer requires jQuery](https://datatables.net/blog/2026/datatables-3). [`row().data()`](https://datatables.net/ref/core/api/row%28%29.data%28%29) followed by [`draw(false)`](https://datatables.net/ref/core/api/draw%28%29) can retain the current page, but a draw is still more disruptive than changing one DOM row; scroll and focus need testing. State saving is [off by default](https://datatables.net/ref/core/option/stateSave), which is essential in the sandbox. [KeyTable](https://datatables.net/manual/extensions/keytable/) adds keyboard cell navigation; [Editor](https://datatables.net/license/) is commercial.
- **SlickGrid:** The maintained [6pac fork](https://github.com/6pac/SlickGrid) has examples of [data-view updates, editing and navigation](https://github.com/6pac/SlickGrid/blob/master/examples/example4-model.html). Its standalone setup uses several scripts and a grid stylesheet. It solves scale and editing problems the draft has not asked for.
- **Handsontable and other checks:** Handsontable’s [license](https://github.com/handsontable/handsontable/blob/develop/LICENSE.txt) permits non-commercial or evaluation use without a commercial key, so it is outside Television’s [license allowlist](specs/product/licensing.md:108). [Simple-DataTables](https://www.npmjs.com/package/simple-datatables) is LGPL, also outside that allowlist. [Glide Data Grid](https://github.com/glideapps/glide-data-grid) is credible and MIT, but requires React, renders cells on canvas, and leaves sorting to the application; it is an especially poor fit for this native HTML template.

**Sandbox and licensing limit on this assessment:** I did not run any candidate inside a Television artifact. Local vendored scripts appear feasible under the [sandbox and artifact-file CORS rules](specs/arch/artifact-frame/isolation.md:57), but browser storage throws and artifact-file workers fail. Disable library persistence and remote-data options, and smoke-test any chosen build in a real sandboxed frame. A vendored library also needs its actual upstream notices recorded under Television’s [vendored-asset rules](specs/arch/licensing.md:200), including notices that travel with a copied template folder.

### Product questions that could change the choice

1. **Will people edit cells in the page?** If yes, define what happens when an agent changes the same cell during an edit, plus validation and failed-save behavior. AG Grid Community or Tabulator then deserves a prototype.
2. **Is sorting the only table control, or are search, filters, paging, selection and keyboard cell navigation expected?** For sorting alone, a small native implementation remains the better fit.
3. **Are cells all strings?** Number and date sorting, status pills and typed editors require column types or clear parsing rules; a library cannot infer those reliably from the draft’s string-only schema.
4. **How many rows and columns should remain comfortable at once, and must sort or layout choices persist across sessions?** Virtualization needs an observed scale target. Persistent preferences need a Television-backed design because browser storage is unavailable in sandboxed artifacts.
