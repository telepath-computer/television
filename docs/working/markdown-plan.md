# Bundled Markdown plan

Markdown is being added as a bundled artifact template. Its page is the existing interactive Markdown editor, with the document stored in the artifact's JSON store instead of a Markdown file. The architecture changes in this branch are draft prose for Rupert to decide.

## Decisions not settled by the existing sources

- Seed every new document with exactly `{"markdown":""}` rather than leaving the store unwritten. This gives agents a stable field immediately, distinguishes a valid blank document from missing data, and avoids a write-on-load race.
- Omit `display` so Markdown uses the shared artifact size and full-screen defaults, as the existing Markdown file editor does within its frame.
- Use `Markdown` as the manifest name and `A Markdown document you and an agent can edit together.` as its Toolbox description.
- Subscribe at the store root to validate the complete `{ markdown: string }` value, but save only the `markdown` child so future extra root fields survive.
- Pass a subscribed Markdown value to the editor only when it is confirmed and differs from the value last passed. This keeps unrelated root-field changes and the SDK's optimistic copy of a page write from replacing an in-progress local draft.
- Reuse the editor's ordinary save pause. The template does not add save-on-blur or a separate save button.
- Keep concurrent behavior deliberately simple: each page or agent save replaces the complete string and the latest store write wins. There is no text merge in this version.
- Keep the existing editor's save-echo suppression. An authoritative value that confirms a save still in progress causes no CodeMirror transaction. A repeat of the most recently completed save is handled the same way when no newer authoritative value has arrived since that save began. This preserves the caret, scroll and undo history. A successful save does not become the rollback baseline when a newer authoritative value arrived while it was pending. A different value is a live remote edit and replaces the open document without being saved back.
- Keep tracking a save already in progress while editing is temporarily disabled. If editing resumes before its confirming value arrives, that confirmation still leaves newer local typing alone. A stored value supplied while editing remains disabled replaces the document, including when it matches the in-progress save.
- Emit one versioned classic script and stylesheet at `/views/markdown/v1/` from the existing `packages/view-markdown` source. The file editor keeps its self-contained inline HTML, file-page layout and start-up code. The v1 script is a separate wrapped build that defines only `window.TelevisionMarkdownEditor`, and its stylesheet contains only rules beneath `#editor`; the copied page owns everything else. The server allows any origin to load both files. Versioning protects copied artifacts from an incompatible mount API. Each shipped version remains available after a later version is added, but Television may freeze the old version rather than continue changing it.
- Keep the copied template page as the artifact document and put the store adapter there. Do not nest `/views/markdown/` in another frame: that would create a second document and bridge lifecycle, and would need new relays for content, navigation, keyboard and pointer behavior. Do not copy CodeMirror into each template: that would duplicate a large dependency and licensing surface in every artifact and let file and store editors drift.
- Expose the typed v1 interface in the architecture spec: mount in the page's `#editor` element with a value, editable state and asynchronous save callback; return only authoritative-value, editable-state, focus and disposal operations. It deliberately exposes no CodeMirror object. Those names and meanings, the one-global script boundary, the editor-only stylesheet scope and compatibility with canonical v2 stay fixed under v1; editor behaviour and appearance can continue to evolve with Television.
- Make the editor read-only until the page is connected, has valid data and has known read-write access. Read shares see the same editor and document without editing. Re-enable editing immediately when those conditions return; the SDK reports any value that changed while disconnected through the ordinary subscription.
- Follow resource guidance rather than inventing offline editing: on disconnection, disable editing and restore the latest confirmed stored document. This discards unsent typing since the last pause in typing long enough to start a save; the pause timer restarts with every keystroke. It also discards saves already sent but not yet confirmed. The SDK still owns rollback and uncertain outcomes for a write already sent.
- Show a quiet `Saving…` message in the existing status area while the SDK reports a page write that has not been confirmed. This leaves the shell code-authoritative while making a slow-to-detect outage visible before the connection state changes.
- On loss of write access, restore the latest stored string and keep it visible read-only. Changing a read share back to read-write resumes from the current stored string; discarded typing is not replayed. Revocation keeps the last delivered string visible but has no live access-return path.
- Use the standard bundled-template unreadable-data copy, adapted to “document”. Missing, invalid or unavailable data hides the editor, produces no repair write, and recovers live after an agent repairs it.
- Keep the template page layout and the loading, status and unreadable-data presentation code-authoritative. The architecture spec owns only its data consequences: when editing is allowed, what is written, what is discarded and that invalid data is not repaired. The editor keeps the existing UI authority: colours and table interactions in `specs/ui/markdown-editor/index.md`, with the rest code-authoritative under the frame-core carve-out. No Markdown-template MDX spec or stories are added because the template introduces no distinct editing UI.
- Use the HTML-artifact link rules because the shared editor runs inside the copied page, which is sandboxed in the browser. A real-stack test proves that relative links resolve against the copy. In the desktop app, the shared editor uses the webview preload bridge: web navigation goes to the host's trusted channel and application links use the preload's privileged handoff. Existing desktop navigation and Markdown file application-link tests cover those parts, but no Electron test composes them in a bundled Markdown template webview. Browser application-link evidence is likewise adjacent rather than exact: existing tests cover the editor's scripted handoff outside a sandbox and native-anchor handoff inside the artifact sandbox, but not a scripted application-link handoff from the v1 editor inside the copied page.
- Use a small first-party Markdown icon, so the template adds no third-party asset, licensing inventory or folder notice. The editor dependencies remain on the existing `view:markdown` licensing surface.
- Keep the file-view build as the one writer of the `view:markdown` licence inventory. Run the same plugin in non-writing verification mode for the v1 build, so the build fails if v1 ever includes a package the surface inventory does not cover.
- Clarify the Television resource skill's state-choice paragraph: a Markdown *file* artifact is file-backed and read-only through a share link, while the bundled Markdown template is store-backed and follows its store access. This prevents the new template from making the old generic wording misleading.
- Add the v1 stylesheet delivery and its canonical-v2 dependency to the Markdown editor UI spec. This is a change to Rupert-owned UI-spec prose and needs Rupert's approval in this pull request.

## Open questions for Rupert

- Should disconnected editors instead retain offline typing and save it after reconnect, as Sticky note does? I recommend keeping the drafted discard behavior for the first version because it avoids adding Sticky note's draft-retention and reconciliation rules. The page restores the latest confirmed string, so it discards all unsent typing since the person's last pause long enough to start a save — the pause timer restarts on every keystroke — as well as saves sent but not yet acknowledged. A dead connection can take seconds or minutes to be reported; typing during that interval is also discarded when the loss is detected. A save the server applied before the loss reappears after reconnection. The code-authoritative `Saving…` notice is the only warning during an unnoticed outage and could be removed without spec review; if accepting this loss depends on that warning, I recommend promising the status area in a UI spec.
- Is the recommended explicit `{"markdown":""}` seed preferable to an unwritten store? I recommend the explicit seed for immediate agent discoverability and an unambiguous blank state.
- After the first version, should simultaneous person and agent edits stay last-save-wins or gain merge/conflict behavior? I recommend shipping the settled last-save-wins behavior first and designing text merging only from observed collaboration needs.
- Should a stored replacement preserve the person's caret? Today an agent write replaces the editor document and moves the caret, as a remote file edit does in the Markdown file editor. I recommend keeping that shared editor behavior in the first version and treating caret mapping across whole-document replacements as a separate editor improvement.
- When read-write access is removed, should unsaved local typing be discarded as drafted, or remain visible locally? I recommend discarding it and showing the latest stored string so a read-only document never implies that unsavable text is shared.
- Is retaining the latest stored document after share revocation the desired privacy behavior? I recommend matching Sticky note and Table: keep what was already delivered visible, make it read-only, and deliver nothing newer.
- Does the loading/error/status shell need a future MDX UI spec? I recommend leaving it code-authoritative for this narrow reuse page unless review identifies a distinctive visual surface; the editor itself already has the intended authority split and no new editing UI is being designed here.
- Is `A Markdown document you and an agent can edit together.` the right Toolbox description? It states the distinguishing behavior without exposing the store mechanism.
- Is `/views/markdown/v1/` the preferred compatibility promise? I recommend it because copied artifacts can outlive the template and installation version; a later incompatible editor mount can add `v2` while retaining `v1`.
- Does Rupert approve the Markdown editor UI-spec addition that names the v1 delivery and its canonical-v2 dependency? I recommend approving it because it records the settled production crossing without specifying new visual behaviour.
