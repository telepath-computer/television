# Bundled Weather plan

Weather is being drafted as a bundled artifact template with a compact, polished forecast card. The architecture and UI specs in this change are drafts for Rupert to decide. Proofs, tests, the template package, and production code follow only after the spec deltas pass review.

## Decisions not settled by the existing sources

- Make the page a reader of agent-written store data. The page subscribes to the whole store, never writes, and makes no weather-service request. An agent fetches the forecast and replaces the stored root.
- Use `{}` as `data.json` and as the valid empty state. A missing value also shows the empty state. Any other value must be one complete forecast, so an interrupted or partial agent write is visibly unreadable rather than mistaken for a forecast.
- Store `place`, an IANA `timeZone`, `units`, `observedAt`, one `current` object, up to 24 `hourly` entries, and up to seven `daily` entries. The time zone lets “Today” remain correct when a retained forecast crosses a daylight-saving transition. Keep the first version narrow: temperatures and the six designed conditions only, with no wind, precipitation amount, humidity, air quality, alerts, coordinates, provider metadata, or interaction.
- Use the closed condition vocabulary `clear`, `partly-cloudy`, `rain`, `snow`, `thunderstorm`, and `fog`. Each current and hourly entry carries `isDay`, so the page does not infer daylight from the viewer clock.
- Require timestamps with `Z` or a numeric UTC offset and require the time zone to be an IANA identifier recognized by the browser. This lets an agent supply unambiguous forecast instants while the page can still determine the current local date without geocoding the place. Require hourly and daily arrays to be strictly chronological, real dates and times, and each high to be at least its low.
- Show how old the weather is from `observedAt`, next to the place and unit. Use “Updated now” below one minute and for future clock skew, then whole minutes, hours, or days. Refresh that label while the page stays open.
- Round temperatures to whole degrees for display without changing stored values. Keep the selected unit explicit as `°C` or `°F` rather than relying on the temperature magnitude to imply it.
- Use a 420-by-420-pixel default and `transparent: true`. The page paints one inset, rounded sky card with its own rim and shadow, so the artifact reads as a floating weather widget rather than a rectangular document filling an ordinary frame.
- Use three layouts based on both artifact width and height. Small applies below 600 pixels wide or 480 pixels high and shows current conditions. Medium begins at 600 by 480 and adds a horizontally scrolling hourly strip. Large begins at 760 by 740 and adds the daily forecast with shared-scale range bars.
- Keep all 24 hourly entries available in the scrolling strip and all seven daily entries in the large panel. Call an hourly entry “Now” only while its stored local hour is current at the place, and call a daily entry “Today” only while its stored date is current there. Other labels come from the stored local timestamps and dates, so a stale forecast never relabels old data as current.
- Let condition and `isDay` choose fixed sky gradients and artwork. Keep snow and fog cool and muted without making their reading areas pale; use navy type at bright sky edges and high-contrast white over darker sky and panels. Do not let the active Television theme recolour the sky, because a theme could make daytime look like night or rain look clear. Continue using foundation typography and spacing so the card belongs with the rest of Television.
- Draw the six weather glyphs as a coherent first-party SVG set owned by the page. Do not add them to the closed foundation icon vocabulary and do not introduce third-party artwork or a licensing delta. Use foundation warning and spinner icons only for the generic unreadable and loading states.
- Make the Toolbox icon a separate first-party square SVG: a rounded blue tile, gold sun, and white cloud. The icon is described now and added with the package after spec approval.
- Use a calm fixed blue sky for empty, loading, and unreadable states in both appearances. The empty copy is “No forecast yet” and “Ask your agent for the weather here.” The unreadable copy follows the established bundled-template alert.
- Keep access loss and disconnection quiet. The page retains the last forecast, catches up after recovery, and remains in loading only if no store value has arrived. Read-only sharing does not remove any forecast browsing behaviour because the page has no write interaction.
- Cover twelve conformance states in the draft stories: clear day in Fahrenheit; partly cloudy night in Celsius; rain; snow; night thunderstorm; fog; an explicit medium layout; a large seven-day layout; loading; empty; unreadable; and clear daylight under dark appearance.
- Keep every story deterministic. The fixtures carry fixed labels and observation ages; the story page makes no network request and does not read the current date, location, or weather.
- Keep shared inventory edits to the bundled row and tuple, the three Weather mentions in the migration map, and the generated spec index. The generic template, installation, product, and licensing specs already cover the new package.

## Open questions for Rupert

- **Where should weather come from?** Recommendation: keep the drafted agent-written model. It matches Calendar, works with whatever weather access the agent already has, keeps API credentials and provider policy out of every copied artifact, remains useful offline with an honest age label, and keeps tests network-free. The concrete self-fetching alternative is Open-Meteo: the free endpoint needs no key but its terms limit it to non-commercial use; a shipped commercial product needs a paid subscription, customer endpoint, and API key. The returned data is CC BY 4.0 and requires attribution. Without a connection, a self-fetching copied page could only show data it had separately cached, and a newly opened copy would have no forecast. Open-Meteo documents these terms at https://open-meteo.com/en/terms and https://open-meteo.com/en/pricing.
- **Is 420 by 420 the right starting footprint?** Recommendation: yes. It leaves enough room for the temperature and condition artwork to breathe while remaining clearly smaller than the 760-by-770 shared default and close to the 360-square Sticky note precedent.
- **Should the widget float on a transparent artifact?** Recommendation: yes. The self-contained rounded sky card is the designed object, and transparency prevents an unrelated document surface from appearing around it.
- **Are the 600-by-480 and 760-by-740 breakpoints right?** Recommendation: yes. Requiring both dimensions prevents an hourly or daily panel from appearing in a wide but too-short resize, while giving each layout a reviewable, stable composition. The seven-day panel needs the 740-pixel height to keep every row legible at the exact boundary.
- **Should app appearance ever recolour a populated card?** Recommendation: no. Day, night, and condition are more meaningful than the app appearance for this object. The dark-appearance story should prove that clear daylight remains clear daylight.
- **Is the six-condition vocabulary enough for version 1?** Recommendation: yes. It covers the requested visual range and keeps the first-party artwork coherent. More conditions can be added in a later schema and design review rather than mapped ambiguously now.
- **Should the first version carry more weather facts?** Recommendation: no. Wind, precipitation, humidity, alerts, and feels-like temperature would compete with the requested hierarchy. Current temperature, short condition, high and low, hourly temperatures, and daily ranges are enough for a polished first version.
- **Should provider attribution be a store field and visible in the card?** Recommendation: not in the agent-written default. The template does not choose or call a provider, so it cannot prescribe one attribution shape. If Rupert chooses a self-fetching provider instead, provider attribution becomes part of that architecture and UI decision.
- **Does the drafted visual direction feel sufficiently Apple-like without copying Apple artwork?** Recommendation: keep the soft atmospheric gradients, oversized temperature, translucent forecast panels, restrained type, and original SVGs. Review the rendered stories before the spec gate and tune spacing, colour, and glyph weight there.
- **Is the twelve-story review surface the right granularity?** Recommendation: yes. Each requested condition needs its own current-condition card because the background changes, while medium and large deserve dedicated stories for responsive composition. The three exceptional store states and the theme-invariance state remain separate.
