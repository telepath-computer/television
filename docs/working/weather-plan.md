# Bundled Weather plan

## Status

Weather remains a proposed bundled artifact template. Rupert changed the data-source decision after the first implementation plan passed review, before implementation began. The Open-Meteo architecture and UI specs, stories and proofs passed independent review before the owner decisions recorded in this revision. The implementation plan below replaces the withdrawn plan for the agent-written design.

## Decisions Rupert made

1. **Open at 340 by 340 reference pixels.** This is now the decided default, with `transparent: true` retained in the draft. It is compact without making the three-character temperature treatment feel pinched.

2. **Fetch forecasts in the page from Open-Meteo.** The store now holds the place name, latitude, longitude, units, and an optional page-owned saved forecast. Agents no longer fetch or write forecast values.
3. **Use Open-Meteo's free API.** Rupert judged Television to qualify because it is free and MIT-licensed, with no subscriptions or advertising, matching Open-Meteo's examples of non-commercial use.
4. **Credit the data visibly when it appears.** Open-Meteo data are under CC BY 4.0, so a card showing forecast data carries the provider and licence credit. Empty, loading, unavailable, and unreadable cards do not carry the credit because they show no provider data.
5. **Treat 10,000 calls per day per IP address as a release constraint.** The provider also lists 5,000 calls per hour and 600 per minute. The release gate below keeps the aggregate effect of many open copies visible.
6. **Keep fetching after revocation.** Revocation stops new store data from reaching the page. It does not stop requests when the last store result the page received contains a configured location; an already-running or later successful response can update the in-memory forecast, but the page cannot save it.
7. **Drop isolated bad list entries.** Current conditions remain strict. An hourly or daily entry with a missing, null, non-finite, invalid, or unmapped value is omitted instead of rejecting an otherwise usable response.
8. **Save at most 24 future hours.** The cache keeps the 23 hourly entries the card can display and one extra to cover an hour boundary before the next refresh.

## Decisions made in this draft

These choices were necessary to turn the direction into one exact contract. Items 7, 14, and 18 now record decisions Rupert made; the remaining choices stay recommendations until Rupert accepts them.

1. **Keep a normalized, page-owned `forecast` cache.** It retains the already reviewed `timeZone`, `updatedAt`, `current`, `hourly`, and `daily` shape, plus the requested coordinates and units. That lets the offline page keep the accepted time-zone, window, label, and display rules without exposing Open-Meteo's parallel response arrays to agents.
2. **Match a cache by coordinates and units, not the display name.** A different coordinate or unit can produce a wrong display and is ignored. A place-name-only change safely reuses any compatible forecast and changes the label. The state-based request check still runs because a whole-root name change can also remove the saved forecast.
3. **Do not add geocoding.** The agent supplies the human-readable name and WGS84 coordinates together. The page calls only the forecast endpoint, so it does not guess which place a name means or add another provider, request, failure mode, or licence.
4. **Make one seven-day request.** The exact request asks for current, hourly, and daily temperature, WMO weather code, and day/night fields, with `timezone=auto`, `timeformat=unixtime`, the selected temperature unit, and `forecast_days=7`. The returned hourly series is ample for the first 23 future entries without a second request.
5. **Use UNIX instants for daylight-saving correctness.** Hourly values become ISO instants and are formatted in the returned IANA time zone. Open-Meteo fixes `utc_offset_seconds` at request time for the whole response and instructs clients to apply it to daily UNIX values. Daily cache entries use the date produced by that offset instead of passing a daily timestamp through the IANA zone. A live New York response spanning the 1 November 2026 clock change confirmed that rule.
6. **Timestamp receipt, not model generation.** `updatedAt` is the instant on the page clock after a complete response has been received and validated. The visible age says how long ago the shown forecast was fetched, whether it came from this page, another open page, or an earlier session.
7. **Keep `current` strict and tolerate bad forecast-list entries.** Rupert accepted this rule. A response needs complete, valid current conditions. Within otherwise present hourly and daily arrays, the page drops an entry with a missing, null, non-finite, invalid, or unmapped value, then requires the normalized candidate to pass the cached-forecast schema and page checks. A malformed page-owned cache remains disposable: the page ignores it, fetches, and replaces it on the next successful save instead of making valid location settings unreadable. This lets an installed copy survive a later provider code or isolated gap without inventing the condition a person sees now.
8. **Map every documented forecast WMO code explicitly.** Codes 0, 1–2, 3, 45/48, the documented liquid-precipitation and frozen-precipitation codes, and 95, 96, 97, and 99 map to `clear`, `partly-cloudy`, `cloudy`, `fog`, `rain`, `snow`, and `thunderstorm`. Current summaries preserve useful distinctions such as mainly clear, drizzle, heavy rain, rime fog, snow grains, slight hail, and heavy hail while the artwork stays within the seven-condition vocabulary.
9. **Use one state-based request check without per-location history.** The page runs the check on every store value, about every minute while visible under the Page Visibility API, and when it becomes visible. An unavailable store behaves like one without a configured location: it starts no request, aborts a running attempt, and clears the failed-attempt record and in-memory forecast. This is a spec change for Rupert from proof review 6, making the unavailable-store transition explicit instead of leaving two valid readings. For the current coordinates and units, the page requests only when no attempt is still running, no failed attempt began in the preceding 15 minutes, and no compatible saved or in-memory forecast was fetched in that period. A successful attempt leaves only its forecast, whose `updatedAt` supplies the freshness check; it does not remain as throttle history. The page tracks at most the running attempt and the latest failure while its coordinates and units stay current. An unanswered attempt is aborted after 10 seconds, attempts never overlap, and failures do not create a faster retry loop. Checking each minute produces refreshes about every 15 minutes and still lets one open page reuse a fresh forecast saved by another.

   In the units-switch example, the Fahrenheit success replaces the Celsius cache and in-memory forecast. Switching back to Celsius finds neither a compatible forecast nor a running or failed Celsius attempt, so it requests at once. A separate failure example starts with a failed Celsius attempt, switches to Fahrenheit, then returns to Celsius within 15 minutes; it also requests at once because a unit change clears failure state for the old values. In the clear-and-reset example, `{}` removes the saved forecast and clears the page's in-memory forecast and attempt state. Setting the same place again therefore also requests at once. Missing, empty, unreadable and unavailable store results all clear the running attempt, failure record and in-memory forecast.

10. **Discard obsolete in-flight results.** A coordinate or unit change aborts an older attempt, so the state check can request for the new configuration at once when it has no fresh compatible forecast. Each started attempt gets a unique page-local identity. One settlement transition installs a successful normalized forecast in memory or records the start time of a failed attempt. It returns no state unless that identity is still the one the page tracks. After A → B → A, a late success from the first A is therefore ignored rather than shown, even though its coordinates and units again match the current configuration. An obsolete result is neither shown nor saved, and its failure does not throttle the current configuration, even when abort delivery races with completion.
11. **Save by a root transaction.** An open page with write access preserves the current place and unknown fields, aborts when the current root is missing, empty or unreadable or when the coordinates or units changed, and replaces any earlier, invalid, or incompatible `forecast`. When two open pages race, the last transaction to commit supplies the saved forecast. This avoids comparing clocks from different devices while still preventing an old response from restoring a location an agent just changed.
12. **Prefer a non-future forecast.** A page may have both a saved forecast and one fetched into memory. It first prefers a candidate whose `updatedAt` is not in the future, then chooses the later candidate, so a clock set ahead cannot permanently displace new results. A successful result remains visible if its attempted save loses access or the Television connection.
13. **Fail softly when a cache exists.** A provider failure keeps the preferred compatible saved or in-memory forecast without an extra error label. Its unchanged age says when the shown forecast was fetched and avoids crowding the small card. With no compatible forecast, the page shows “Forecast unavailable” and says it will try again in about 15 minutes. While the page remains visible with the same coordinates and units, the state check makes the next attempt about 15 minutes after the failed attempt; new coordinates or units can make one sooner.
14. **Distinguish disconnection from revocation.** Rupert decided that both ordinary disconnection and revocation keep in-memory refreshes after the last store result the page received contained a configured location. Revocation stops later store data from reaching the page, but it does not abort a running provider request or stop later requests for the retained coordinates and units. Results can replace the in-memory forecast but cannot be saved. A configured card without a forecast can therefore recover from loading or unavailable after revocation; an empty or unreadable card stays as it was. Losing the connection or access before the first store value leaves the page loading.
15. **Use a compact but complete attribution line.** The UI spec owns `Open-Meteo data · adapted · CC BY 4.0`, its two links, and its placement on cards showing provider data. “adapted” visibly records the condition mapping, selection, labels, and rounding required by CC BY 4.0.
16. **Change only the data-source-dependent placeholders.** Empty becomes “No location yet” because `{}` now means no configuration. Loading also covers a configured first fetch. A new unavailable story covers failure without a cache, and a saved-after-failure story shows the silent cached fallback. Minimum-size stories bind the empty and longest unreadable copy at 230 pixels without adding attribution to states that show no provider data. Those placeholders are centred now that they do not need bottom clearance for attribution. The accepted appearance, condition, time-zone, accessibility, and layout designs remain.
17. **Keep default verification local and add one opt-in live boundary test.** Default browser tests intercept every Open-Meteo request, script its response from captured fixtures, delay it, or abort it, and fail any request without an expected method, URL, query, and disposition. The captured Celsius and Fahrenheit successes, date-pinned Kolkata and New York successes, and out-of-range-latitude error all include their returned status and CORS header; tests for malformed values edit copies while retaining captured headers. Outside CI, one opt-in test sends the exact Celsius and Fahrenheit San Francisco requests from a copied page in Television's sandboxed artifact frame, requires both live responses to pass the page success rule, and may refresh only `current-success.json` and `current-success-fahrenheit.json`. The error and date-pinned fixtures stay fixed. Developers run the live test after any change to the request builder, response normalizer or fetch code and before release. It does not cover the desktop `Origin` and `Referer` path. The provider terms and rate limits, and the future availability of a compatible CORS response, also remain unproven.
18. **Keep only the hourly entries the card can use before its next refresh.** Rupert accepted the 24-entry bound. After filtering, ordering, and deduplicating the provider response, the cache retains the 23 cells the card can display plus one extra for an hour boundary before the next refresh. A compact representative cache measured 15,868 bytes with all 168 provider hours and 2,886 bytes with 24, reducing its hourly-heavy stored form from 15.5 KiB to 2.8 KiB. If the card goes about a day without a successful response, those entries can all become past entries while daily forecasts remain; a large card then shows the current and daily panels without the hourly panel. The `LargeNoHourly` story records that consequence.
19. **Recommend town-level coordinates by default.** The future README asks agents to use only the precision the forecast needs because every configured page discloses the coordinates with the viewer's IP address to Open-Meteo. Finer coordinates remain valid when a person wants a more precise forecast.
20. **Keep the ordinary condition stories fresh.** `Cloudy`, `Rain`, and `Snow` now show ages of 8, 10, and 12 minutes. This is a story change for Rupert: it keeps those condition examples within the 15-minute freshness window, so they remain ordinary successful states rather than implying that a refresh has failed or is still running.
21. **Require a valid configured root when saving a response.** The transaction wording now says it commits only while the store holds a configured location whose coordinates and units match the request. This optional clarification from proof review 8 rules out treating an unreadable root with matching coordinate fields as configured; it does not change the intended transaction contract.
22. **Register live provider seams in one provider-neutral local suite.** Follow the existing PostHog round-trip registration: `test.config.mjs` declares a `live-providers` suite that selects `kind:live-provider`, with one Playwright execution group and surface named `live-providers:browser`. The surface initially owns only the live Weather test through a dedicated config; later provider-backed tests can join without adding another suite or command. A developer runs it with `npm test -- local --suite live-providers`. The suite stays outside `all`, CI, `npm run verify`, Blaxel, and a runner-only Playwright selection. The test harness starts Television with a temporary home and opens the copied page through the application iframe, so the surface declares no unused Vite service. Each provider's relevant spec—not necessarily a product spec—owns its request. This provider-neutral classification and runner wording are decisions for Rupert.

23. **Observe the opaque browser origin through the security origin.** The live seam checks `window.origin === "null"` and the actual request's `Origin: null` header. Chromium's `location.origin` describes the document URL even when the sandbox gives its browsing context an opaque security origin, so it is not the assertion for this boundary.

## Proof design after review

- The shared creation walk installs a controlled browser clock before page code. After the first Celsius forecast appears and is saved, it runs the README place-change example while the card is populated and checks the label, unchanged forecast values and age, unchanged saved forecast, and absence of a provider request. It then holds the Fahrenheit response while making a further place change and adding an unknown field, and checks the newest place on the card and in the saved root after release.
- The latitude, longitude and units abort passes also install a controlled clock before page code. Each starts with a compatible saved forecast whose `updatedAt` is 16 minutes earlier and holds the refresh that this stale forecast triggers. Changing the field under test must abort that request, start one for the new values, discard a late old response, and update the card and store from the new response.
- A read-only page advances through visible minute checks before and after its in-memory forecast becomes stale. This isolates the in-memory freshness rule from the saved cache that a read-only page cannot write.
- A held refresh starts from a stale saved forecast whose sky, artwork, current values, hourly values and daily values all differ from the captured response. The old card remains visible while the request runs, then every visible section changes together.
- The slice 1 README guidance review checked every required field and range, the whole-root and focused commands, `{}` clearing, page ownership of `forecast`, privacy, offline and read-only behavior, attribution, external-network use, transparency, and the named adaptation files. The review also replaced “honest age” with the plainer “shows how long ago it was fetched.”

## What was verified

### Open-Meteo

- The official Forecast API endpoint is `https://api.open-meteo.com/v1/forecast`. Its documentation defines `latitude`, `longitude`, `current`, `hourly`, `daily`, `temperature_unit`, `timeformat`, `timezone`, and `forecast_days`, and documents the requested current, hourly, and daily fields.
- `timezone=auto` returns an IANA `timezone`; `timeformat=unixtime` returns epoch seconds. The documentation says `utc_offset_seconds` is resolved at request time and fixed throughout the response, including across daylight-saving changes. It instructs clients to apply that offset to reproduce provider dates and to convert hourly UNIX instants with the returned IANA zone for daylight-saving-aware local times.
- A live New York response on 27 October 2026 spanned the 1 November clock change. All seven daily timestamps stayed at `04:00Z`, and the returned offset stayed at `−04:00`. Applying that offset produced 27 October through 2 November as the provider dates. Converting the final daily timestamp directly through `America/New_York` produced 1 November at 11:00 p.m., confirming why the daily rule must use the fixed returned offset.
- Four complete live success responses captured on 27 October 2026 now live under `test/fixtures/weather/open-meteo/`: date-pinned New York and Kolkata responses, plus refreshable San Francisco Celsius and Fahrenheit responses. Each records the exact request, `200` status, `Access-Control-Allow-Origin: *`, content type, and unmodified response body. The Fahrenheit response reports `°F` for current, hourly, daily-high and daily-low temperatures. The Kolkata hourly data make the first retained entry at the proof clock the `2 AM` cell, not `2:30 AM`.
- A live out-of-range-latitude request captured on 27 October 2026 is fixed as `error-latitude-out-of-range.json`. Open-Meteo returned status `400`, `Access-Control-Allow-Origin: *`, JSON content type, and the unmodified error body. This lets the browser receive the real HTTP error rather than turning the case into another CORS or network failure.
- The documented response is an object with coordinate and zone metadata, a `current` object, and parallel `hourly` and `daily` arrays. Live seven-day default-model responses for San Francisco and New York on 27 October 2026 matched it, including `current_units`, `hourly_units`, and `daily_units`. Each had 168 equally sized hourly entries, seven equally sized daily entries, and no `null` among the requested values. The contract still requires current conditions to be complete, but drops an isolated bad hourly or daily entry so a copied page can survive a later provider gap it cannot receive a package update to handle. The page then retains at most 24 usable future hourly entries in the saved cache.
- The current official WMO table includes codes 0, 1, 2, 3, 45, 48, 51, 53, 55, 56, 57, 61, 63, 65, 66, 67, 71, 73, 75, 77, 80, 81, 82, 85, 86, 95, 96, 97, and 99. Under [“WMO Weather interpretation codes (WW)”](https://open-meteo.com/en/docs#weather_variable_documentation), code 96 is “Thunderstorm with slight hail”, code 97 is “Heavy thunderstorm”, and code 99 is “Thunderstorm with heavy hail”. The spec maps every documented code.
- The free endpoint needs no key. Open-Meteo's current terms say non-commercial use is limited to fewer than 10,000 calls per day, 5,000 per hour, and 600 per minute, applied by IP address and application. They put returned data under CC BY 4.0 and give private or non-profit apps without subscriptions or advertising as non-commercial examples.
- The terms say request logs can contain IP addresses, coordinates, and other request information and can be retained for up to 90 days. That disclosure belongs in the release decision because every configured page sends its coordinates directly to Open-Meteo.

### Television's frame

- Television's browser artifact iframe and response header use the same sandbox tokens and omit `allow-same-origin`, giving the page an opaque origin. Cross-origin requests therefore send `Origin: null`.
- Television's desktop artifact page is not sandboxed and has the Television server address as its origin. Its Open-Meteo request therefore sends that server address in both `Origin` and `Referer`; the release gate discloses this even though Open-Meteo currently accepts any origin.
- Television's sandbox CSP contains only the `sandbox` directive; it has no `connect-src` restriction. The isolation spec identifies an external service's refusal of `Origin: null` as the relevant limitation.
- A live GET sent with `Origin: null` on 27 October 2026 returned `200`, the documented JSON shape, and `Access-Control-Allow-Origin: *` from Open-Meteo.
- A headless Chromium probe inside an iframe with Television's exact sandbox tokens reported `window.origin === "null"` and successfully fetched the endpoint. Chromium's `location.origin` still described the iframe URL, so the security-origin assertion uses `window.origin`. This verifies the browser path rather than inferring it from headers alone.
- Chromium and Firefox rendered one drawing from the earlier shared condition-artwork file when an `<img>` URL selected its group by fragment and the SVG revealed `.weather-condition:target`. A real Playwright WebKit probe on this development host loaded that file but painted zero non-transparent pixels for clear day, partly cloudy night, and rain. Slice 3 replaced the fragment-and-`:target` technique with inline cloned first-party drawings, and the dedicated artwork acceptance now raster-checks them in Chromium, Firefox and WebKit.
- A Playwright Chromium probe found that automation-created tab activation does not change `document.visibilityState` in this browser build. Installing consistent configurable document-level values changed Chromium to `visibilityState === "hidden"` with `hidden === true`, then back to `"visible"` with `hidden === false`, and dispatched both `visibilitychange` events. The proof therefore declares that visibility helper and forfeits native tab/page-visibility integration rather than pretending tab activation supplies it.
- Node and the repository's Playwright Chromium both formatted the captured Kolkata whole-hour instant as `2 AM` with an ordinary U+0020 before `AM`; adding minutes produced `2:00 AM`. The Node contract now asserts only instants and dates, while the Chromium UI acceptance owns the literal labels.
- With Playwright's clock installed before page code, advancing it by 10,001 milliseconds fired both an ordinary `setTimeout(10_000)` and `AbortSignal.timeout(10_000)` in the repository's Chromium. The timeout proof can therefore advance the installed clock without deciding which timer API production uses.
- Map supplies the repository precedent: its architecture spec names the external host, README obligation, offline limitation, and network-free browser testing rule; its working plan carries the unresolved provider permission, attribution, request disclosure, and release condition. Weather follows that shape, with the release gate below rather than treating CORS or current terms as permanent.

## Release gate

Weather must not be released until Rupert explicitly signs off on all four items together:

- [ ] **Free-API licence judgement:** Television remains within Open-Meteo's non-commercial examples—free, MIT-licensed, and without subscriptions or advertising—and may rely on the keyless free endpoint.
- [ ] **Attribution:** the visible `Open-Meteo data · adapted · CC BY 4.0` line on cards showing provider data, and its provider and licence links, are the approved CC BY 4.0 treatment for the transformed display.
- [ ] **Rate limit and availability:** a page visible under the browser's Page Visibility API makes about 96 scheduled calls a day. This includes Weather cards on unselected Television tab pages while their browser tab remains visible. A fresh compatible forecast avoids a call; a whole-root write that removes the only compatible forecast can add one even when only the name was meant to change. Open-Meteo applies the 10,000/day limit by IP address and application with no free-tier uptime guarantee. Many open pages behind one IP can exhaust the shared allowance.
- [ ] **External request and disclosure:** each configured copy sends latitude, longitude, units, IP address, and ordinary request metadata directly to Open-Meteo. In the desktop app, `Origin` and `Referer` also disclose the Television server address. Current terms allow request logs containing coordinates and IP addresses to be kept for up to 90 days. A provider or CORS change can stop fresh forecasts, leaving only the saved fallback.

As with Map's Esri gate, implementation review cannot substitute for this product and licence sign-off. If the terms, limits, attribution requirement, endpoint, or CORS policy changes before release, the gate must be reviewed again.

## Open questions for Rupert

1. **Should the widget float on a transparent artifact?** Recommendation: yes. The self-contained rounded sky card is the designed object, and transparency prevents an unrelated document surface from appearing around it.
2. **Are the 600-by-480 and 760-by-740 breakpoints right?** Recommendation: yes. Requiring both dimensions prevents an hourly or daily panel from appearing in a wide but too-short resize, while giving each layout a stable composition. The seven-row panel needs the 740-pixel height to keep every row legible at the exact boundary.
3. **Should app appearance ever recolour a populated card?** Recommendation: no. Day, night, and condition are more meaningful than app appearance for this object. The dark-appearance story proves that clear daylight remains clear daylight.
4. **Should Weather typography follow a theme that changes the foundation font?** Recommendation: Reading A—Weather follows the font selected by the active theme through the foundation, while its condition skies and artwork remain fixed. This matches the stories, which use `var(--font-sans)`. Reading B would keep the default foundation font under every theme. Keep the proof link to this question during review. During pre-merge docs prep, replace that link with the decided durable source before merging because `docs/working/` is removed or archived at that stage.
5. **Is the seven-condition vocabulary enough for version 1?** Recommendation: yes. The exact WMO mapping covers every code the selected endpoint documents without multiplying artwork variants.
6. **Should the first version carry more weather facts?** Recommendation: no. Wind, precipitation totals, humidity, alerts, and feels-like temperature would compete with the requested hierarchy. Current temperature, short condition, high and low, hourly temperatures, and daily ranges are enough for a polished first version.
7. **Does the visual direction feel sufficiently Apple-like without copying Apple artwork?** Recommendation: keep the atmospheric gradients, oversized temperature, translucent forecast panels, restrained white type, and original SVGs. The locally darkened header area protects contrast without turning bright skies into dark cards.
8. **Is the 25-story review surface the right granularity?** Recommendation: yes. The original 20 states remain, the two data-source-dependent additions separately bind cached failure and first-fetch failure, minimum-size stories check both the empty and longest unreadable placeholders at 230 pixels, the populated minimum-size story checks the credit, and `LargeNoHourly` shows the offline consequence of retaining 24 future hours. Every condition, responsive stress case, exceptional store state, and appearance promise still has a deterministic story.
9. **Is the attribution line large and legible enough?** At 230 by 230, the populated minimum-size story CSS resolves the credit to 9 pixels; at 340 by 340 it resolves to 10 pixels. On the clear-day sky, the text shadow keeps both readable and the line remains clear of the weather content, but 9 pixels is below the 12-pixel `--text-sm` foundation token. Recommendation: approve the 10-pixel default but raise the 230-pixel minimum to 10 pixels if Rupert finds the minimum-size rendering too fine.
10. **Should “the last store result it received” remain the revocation boundary wording?** Recommendation: yes. It states the observable boundary precisely and settles an unreadable-value-then-revocation case consistently with the request check: only a last received configured result retains a location for refreshes. This clarification appears in both Weather specs and decisions 6 and 14 above, but still needs Rupert's acceptance.

## Observation

A device can wake from sleep before its network connection is ready. If the minute check runs in that interval, the attempt fails and the ordinary 15-minute retry rule applies, so the card may keep showing an older forecast until then. Its unchanged “Updated” age remains honest. This is recorded for implementation and field review; the specs deliberately add no special wake-up retry.
