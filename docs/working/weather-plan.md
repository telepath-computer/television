# Bundled Weather plan

Weather is being drafted as a bundled artifact template with a compact, polished forecast card. The architecture and UI specs in this change are drafts for Rupert to decide. Proofs, tests, the template package, and production code follow only after the spec deltas pass review.

## Decisions not settled by the existing sources

- Make the page a reader of agent-written store data. The page subscribes to the whole store, never writes, and makes no weather-service request. An agent fetches the forecast and replaces the stored root.
- Keep `{}` as the explicit, inspectable starting and reset value in `data.json`. A removed root can also occur and intentionally shows the same empty prompt. Keeping both forms makes a new artifact predictable without treating root removal as an error.
- Store `place`, an IANA `timeZone`, `units`, `updatedAt`, one `current` object, `hourly` entries, and `daily` entries. `updatedAt` is when the agent fetched the complete forecast and matches the page label. Keep the first version narrow: temperatures and seven designed conditions only, with no wind, precipitation amount, humidity, air quality, alerts, coordinates, provider metadata, or interaction.
- Treat `updatedAt` and every hourly timestamp as an instant. Require `Z` or a numeric UTC offset, including optional fractional seconds. A local clock time must use the offset in force at that instant and must not be marked `Z` unless it is UTC. Convert hourly instants to `timeZone` for labels and current-hour selection. Sort hours by instant, which keeps repeated clock labels ordered across a daylight-saving fallback. Define the current hour as the local clock-hour interval containing the current instant, and define the current date as the local calendar date containing it. Sort daily entries by date.
- Let the page tolerate harmless agent output. After stable sorting, keep the first entry for each duplicate instant or date. The hourly display window contains `current` followed by the first 23 stored entries after the current hour, or every one if fewer remain. The daily display window omits dates before the current date and retains the first seven distinct dates, or every one if fewer remain. Either stored array may be empty; array order and extra entries do not invalidate an otherwise valid forecast. Every stored item must still have valid fields. Keep only the page-level checks needed to prevent a wrong display: dates and timestamps must be valid, `timeZone` must be recognized by the browser, and a daily high cannot be lower than its low. Keep these store-reading rules in the architecture spec. The UI spec owns labels, panel presence and placement, and refresh behaviour, and links to each window definition.
- Use the closed condition vocabulary `clear`, `partly-cloudy`, `cloudy`, `rain`, `snow`, `thunderstorm`, and `fog`. `cloudy` has a layered overcast sky and artwork with no sun or moon. README guidance maps common provider terms, including drizzle, freezing rain, sleet, haze, and smoke, onto this vocabulary. Each current and hourly entry carries `isDay`, so the page does not infer daylight from the viewer clock. Only clear and partly cloudy change their sky and artwork between day and night; the other conditions use one design at either time.
- Derive the displayed current high and low from the daily entry for the current date at `timeZone`. Do not duplicate them in `current`. If that entry is absent, omit the high-and-low line instead of showing another day or rejecting otherwise readable data.
- Show how long ago the agent fetched the forecast from `updatedAt`, below the place and beside the unit. Use completed units and the fixed forms “Updated now”, “Updated 1 min ago” or “Updated N min ago”, “Updated 1 hr ago” or “Updated N hrs ago”, and “Updated 1 day ago” or “Updated N days ago”. Future clock skew also shows “Updated now”. Refresh the age while the page stays open.
- Start a shown hourly strip with “Now” from `current`, including `temperature`, `condition`, and `isDay`. Follow it with the retained stored entries after the current hour. Leave out the panel when there are no such stored entries. Convert their instants to clock times at `timeZone`, format them with the `en-US` locale, and include minutes when a local time is not on the hour. Refresh the window and labels while the page stays open.
- Label the entry for the current date at `timeZone` “Today” and refresh the daily window, label, and current high-and-low line while the page stays open. Format other weekdays with the `en-US` locale. The large-panel heading counts the displayed rows, such as “4-day forecast”, instead of assuming seven. Each forecast panel depends only on its corresponding window. A large card with no daily window uses the medium composition rather than reserving empty panel space.
- Round temperatures to whole degrees, with halves away from zero, without changing stored values. Normalize a rounded zero so the page never shows `−0°`. Keep the selected unit explicit as `°C` or `°F` rather than relying on magnitude to imply it.
- Draft a 340-by-340 reference-pixel default and `transparent: true`. The page paints one inset, rounded sky card with its own rim and bounded shadow, so the artifact reads as a floating weather widget rather than a rectangular document. Temperature and artwork scale with both width and height so `104°` and `−12°` fit from the 230-by-230 artifact-frame minimum upward, including wide, short cards.
- Use three layouts based on both artifact width and height. Small applies below 600 pixels wide or 480 pixels high and shows current conditions. Medium begins at 600 by 480 and adds a horizontally scrolling hourly strip. Large begins at 760 by 740 and adds the daily forecast with shared-scale range bars. Keep a wide, short artifact in the current-only layout: width alone would need a fourth side-by-side composition, while the height gate preserves the legibility of the forecast panel.
- Let condition choose fixed sky gradients and artwork; `isDay` selects the day or night design only for clear and partly cloudy conditions. Use white text with subtle shadows on every sky and a local dark gradient behind the upper-left text. Do not let the active Television theme recolour the sky, because a theme could make daytime look like night or rain look clear. Continue using foundation typography and spacing so the card belongs with the rest of Television.
- Draw the seven weather glyphs as a coherent first-party SVG set owned by the page. Do not add them to the closed foundation icon vocabulary or introduce third-party weather artwork. The production package will reuse the Phosphor warning and spinner icons from the foundation, so the later implementation must register those copied assets and include the generated `THIRD-PARTY-NOTICES.txt` required by the licensing spec.
- Make the Toolbox icon a separate first-party square SVG: a rounded blue tile, gold sun, and white cloud. The icon is described now and added with the package after spec approval.
- Use a calm fixed blue sky for empty, loading, and unreadable states in both appearances. The empty copy is “No forecast yet” and “Ask your agent to add a forecast for a place.” The unreadable heading is “This forecast can't be shown”; the rest of the alert follows the established bundled-template pattern. README guidance tells agents to clear a forecast with `{}`, not `null`.
- Keep access loss and disconnection quiet. The page retains the last forecast, catches up after recovery, and remains in loading only if no store value has arrived. Read-only sharing does not remove forecast browsing because the page has no write interaction.
- Cover 20 conformance states in the draft stories: clear day and clear night in Fahrenheit; partly cloudy night in Celsius; cloudy; rain; snow; night thunderstorm at medium and large sizes; fog; a three-digit Fahrenheit reading at the default and 230-pixel minimum sizes; a 590-by-230 wide, short card; a missing current-day range; explicit medium and large layouts; a four-day large forecast; loading; empty; unreadable; and clear daylight under dark appearance. Render the main large story at the exact 760-by-740 breakpoint so seven-row fit is binding.
- Keep every story deterministic. The fixtures carry fixed English labels and fetch ages; the story page makes no network request and does not read the current date, location, or weather. New Orleans has a coherent night-time hourly sequence and its own stormy week. The story renderer builds “Now” directly from `current`; fixture hours begin after the current hour.
- Keep shared inventory edits to the bundled row and tuple, the three Weather mentions in the migration map, and the generated spec index. The generic template, installation, product, and licensing specs already govern the new package.

## Open questions for Rupert

- **Should the default be 280 by 280, 340 by 340, or 420 by 420 reference pixels?** Recommendation: use 340 by 340. It reads as a genuinely small widget while the scaled typography and artwork still fit a three-character temperature. The 280 version is more compact but gives the place and high-and-low line less air; the 420 version occupies 53% more area than 340. These screenshots show the same three-digit state at each proposed opening size.

- **Where should weather come from?** Recommendation: keep the drafted agent-written model. It matches Calendar, works with whatever weather access the agent already has, keeps API credentials and provider policy out of every copied artifact, remains useful offline with an honest age label, and keeps tests network-free. The concrete self-fetching alternative is Open-Meteo: the free endpoint needs no key but its terms limit it to non-commercial use; a shipped commercial product needs a paid subscription, customer endpoint, and API key. The returned data is CC BY 4.0 and requires attribution. Without a connection, a self-fetching copied page could only show data it had separately cached, and a newly opened copy would have no forecast. Open-Meteo documents these terms at https://open-meteo.com/en/terms and https://open-meteo.com/en/pricing.
- **Should the widget float on a transparent artifact?** Recommendation: yes. The self-contained rounded sky card is the designed object, and transparency prevents an unrelated document surface from appearing around it.
- **Are the 600-by-480 and 760-by-740 breakpoints right?** Recommendation: yes. Requiring both dimensions prevents an hourly or daily panel from appearing in a wide but too-short resize, while giving each layout a stable composition. The seven-row panel needs the 740-pixel height to keep every row legible at the exact boundary.
- **Should app appearance ever recolour a populated card?** Recommendation: no. Day, night, and condition are more meaningful than app appearance for this object. The dark-appearance story proves that clear daylight remains clear daylight.
- **Is the seven-condition vocabulary enough for version 1?** Recommendation: yes. The new `cloudy` state covers common overcast forecasts, and the README mapping resolves nearby provider terms without multiplying artwork variants.
- **Should the first version carry more weather facts?** Recommendation: no. Wind, precipitation, humidity, alerts, and feels-like temperature would compete with the requested hierarchy. Current temperature, short condition, high and low, hourly temperatures, and daily ranges are enough for a polished first version.
- **Should provider attribution be a store field and visible in the card?** Recommendation: not in the agent-written default. The template does not choose or call a provider, so it cannot prescribe one attribution shape. If Rupert chooses a self-fetching provider instead, provider attribution becomes part of that architecture and UI decision.
- **Does the visual direction feel sufficiently Apple-like without copying Apple artwork?** Recommendation: keep the atmospheric gradients, oversized temperature, translucent forecast panels, restrained white type, and original SVGs. The locally darkened header area protects contrast without turning bright skies into dark cards.
- **Is the 20-story review surface the right granularity?** Recommendation: yes. Every condition needs a binding current-condition card, clear and partly cloudy need their day-or-night designs approved, the 230-pixel minimum and wide-short composition need stress states, responsive composition, the missing current-day range, and variable day count need dedicated states, and the three exceptional store states plus theme invariance remain separate.
