# Bundled Document plan

Document is being added as a bundled artifact template. Its page is the existing interactive Markdown editor, with the document stored in the artifact's JSON store instead of a Markdown file. The architecture changes in this branch are draft prose for Rupert to decide.

## Decisions not settled by the existing sources

- Seed every new document with exactly `{"markdown":""}` rather than leaving the store unwritten. This gives agents a stable field immediately, distinguishes a valid blank document from missing data, and avoids a write-on-load race.
- Omit `display` so Document uses the shared artifact size and full-screen defaults, as the existing Markdown file view does within its frame.
- Use `document` as the template ID, `Document` as the manifest name, and `A document you and an agent write together, in Markdown.` as its Toolbox description. This separates the template's product identity from the Markdown format and editor it uses.
- Subscribe at the store root to validate the complete `{ markdown: string }` value, but save only the `markdown` child so future extra root fields survive.
- Pass a subscribed Markdown value to the editor only when it is confirmed and differs from the value last passed. This keeps unrelated root-field changes and the SDK's optimistic copy of a page write from replacing an in-progress local draft.
- Reuse the editor's ordinary save pause. The template does not add save-on-blur or a separate save button.
- Keep concurrent behavior deliberately simple: each page or agent save replaces the complete string and the latest store write wins. There is no text merge in this version.
- Keep the existing editor's save-echo suppression. An authoritative value that confirms a save still in progress causes no CodeMirror transaction. A repeat of the most recently completed save is handled the same way when no newer authoritative value has arrived since that save began. This preserves the caret, scroll and undo history. A successful save does not become the rollback baseline when a newer authoritative value arrived while it was pending. A different value is a live remote edit and replaces the open document without being saved back.
- Keep tracking a save already in progress while editing is temporarily disabled. If editing resumes before its confirming value arrives, that confirmation still leaves newer local typing alone. A stored value supplied while editing remains disabled replaces the document, including when it matches the in-progress save.
- Put committed `editor.js` and `editor.css` files in the Document template folder, built from the existing `packages/view-markdown` editor source. The build emits exactly those two files, so a stylesheet import or URL that produced another asset could not escape the check. Each artifact therefore carries the editor it was created with; Television and installed-template updates do not replace those copied files. The page still loads the versioned canonical resources and resource SDK, as normal templates do. The Markdown file view keeps its separate self-contained HTML, file-page layout and start-up path.
- Use one **packaged Markdown editor check** to rebuild the editor into temporary output and compare the JavaScript and stylesheet byte for byte. This follows Map's convention of committed, locally checkable dependencies, but uses a stronger source-to-output comparison because Television owns the editor source and build. Generating the files only during the server or CLI build would leave the source template incomplete and could let the folder reviewed and tested in the repository differ from the one eventually shipped. Recorded hashes alone would prove only that the committed bytes still match their recorded hashes, not that they still match the editor source. The server and CLI builds copy the committed files without rebuilding them.
- Provide `npm run refresh:packaged-markdown-editor` as the supported maintenance command for the committed editor, record and notices. It first builds the Markdown file view to refresh the shared `view:markdown` inventory, then runs the packaged Markdown editor build in a temporary folder, copies only `editor.js`, `editor.css` and the licensing record into place, and asks the notices generator to refresh the template and repository-root files. This keeps the destructive `emptyOutDir` build away from the template folder and leaves the check read-only. The command is code-authoritative maintenance rather than a product promise, so it is recorded here instead of in the architecture spec.
- Commit `packages/view-markdown/packaged-markdown-editor-licenses.json` beside the editor source and build configuration. It records the exact package records from the packaged Markdown editor build and the IDs of vendored-asset records whose `paths` match emitted module paths. The packaged Markdown editor check keeps it current. The license gate and notices generator can therefore reproduce the Document template and repository-root notices without running Vite. The root notices include the editor packages because committed `editor.js` redistributes their code to anyone who clones the repository. Keeping this build-only record outside the template folder avoids copying licensing bookkeeping into every artifact; the user-facing `THIRD-PARTY-NOTICES.txt` remains beside the editor files. The asset IDs ensure that the notice covers the vendored Markdown-table bundle as well as packages from `node_modules`, without giving the asset record a second `noticesFolder` generator.
- Keep the copied template page as the artifact document and put the store adapter there. Do not nest the Markdown file view in another frame: that would create a second document and bridge lifecycle, and would need new relays for content, navigation, keyboard and pointer behavior. Do not serve the editor from a Television route: that would make copied artifacts depend on a later installation and turn an internal template boundary into a compatibility promise.
- Keep a small internal interface inside the template package: mount in the page element whose ID is `editor` with a value, editable state and asynchronous save callback; return only authoritative-value, editable-state, focus and disposal operations. It deliberately exposes no CodeMirror object. The adjacent `page.js` and `editor.js` files may change together in a later template revision, so the architecture spec does not promise an internal global name or TypeScript signature.
- Make the editor read-only until the page is connected, has valid data and has known read-write access. Read shares see the same editor and document without editing. Re-enable editing immediately when those conditions return; the SDK reports any value that changed while disconnected through the ordinary subscription.
- Follow resource guidance rather than inventing offline editing: on disconnection, disable editing and restore the latest confirmed stored document. This discards unsent typing since the last pause in typing long enough to start a save; the pause timer restarts with every keystroke. It also discards saves already sent but not yet confirmed. The SDK still owns rollback and uncertain outcomes for a write already sent.
- Show a quiet `Saving…` message in the existing status area after a page write has remained unconfirmed for a short delay. This leaves the shell code-authoritative, avoids flashing the message for ordinary quick saves, and makes a slow-to-detect outage visible before the connection state changes.
- On loss of write access, restore the latest stored string and keep it visible read-only. Changing a read share back to read-write resumes from the current stored string; discarded typing is not replayed. Revocation keeps the last delivered string visible but has no live access-return path.
- Use the standard bundled-template unreadable-data copy, adapted to “document”. Missing, invalid or unavailable data hides the editor, produces no repair write, and recovers live after an agent repairs it.
- Keep the template page layout and the loading, status and unreadable-data presentation code-authoritative. The architecture spec owns only its data consequences: when editing is allowed, what is written, what is discarded and that invalid data is not repaired. The editor keeps the existing UI authority: colours and table interactions in `specs/ui/markdown-editor/index.md`, with the rest code-authoritative under the frame-core carve-out. No Document-template MDX spec or stories are added because the template introduces no distinct editing UI.
- Use the HTML-artifact link rules because the packaged Markdown editor runs inside the copied page, which is sandboxed in the browser. A real-stack test proves that relative links resolve against the copy. In the desktop app, the editor uses the webview preload bridge: web navigation goes to the host's trusted channel and application links use the preload's privileged handoff. Existing desktop navigation and Markdown file application-link tests cover those parts, but no Electron test composes them in a bundled Document template webview. Browser application-link evidence is likewise adjacent rather than exact: existing tests cover the editor's scripted handoff outside a sandbox and native-anchor handoff inside the artifact sandbox, but not a scripted application-link handoff from the packaged Markdown editor inside the copied page.
- Use a first-party Document icon: a page with a folded corner and a few text lines, drawn at the same stroke weight and scale as the other first-party template icons. It replaces the Markdown mark without adding third-party material. The packaged Markdown editor adds a generator-owned `THIRD-PARTY-NOTICES.txt` to the template folder.
- Keep the Markdown file view build as the one writer of the `view:markdown` license inventory. Run the same plugin in non-writing verification mode for the template build after a current file view build, so the build fails if the template includes a package that the same-tree surface inventory does not cover. This matters because the CLI umbrella attributes the template packages through that inventory. Match emitted repository-local module paths against `scripts/licenses/assets.json`, require every match to cover both `view:markdown` and `source`, and render the template notice from both the exact package set and the matched asset records. The notices generator alone renders notices; the plugin records inputs. This keeps package and license text discovery in the existing inventory, asset manifest and generator.
- Require the bundled README to say that the copied artifact contains `editor.js`, `editor.css`, and `THIRD-PARTY-NOTICES.txt`, and that later Television or template updates do not replace those copied editor files. An adapting agent keeps the `#editor` mount, updates `page.js`, `editor.js`, `editor.css`, and the notices file together, and uses `styles.css` to adapt the look unless it deliberately replaces the editor and licensing material.
- Describe the vendored table runtime's global-side-effect changes in terms of the packaged Markdown editor, not the removed versioned editor route.
- Clarify the Television resource skill's state-choice paragraph: a Markdown *file* artifact is file-backed and read-only through a share link, while the bundled Document template stores Markdown text in its JSON store and follows that store's access. This prevents the new template from making the old generic wording misleading.

## Spec changes for Rupert's review

- Rename the licensing-record interface from `MarkdownTemplateEditorLicensingRecord` to `PackagedMarkdownEditorLicensingRecord`, matching the settled product term without changing its fields or validation.
- Make an absent `view:markdown` inventory a named failure of the packaged Markdown editor check, and make the suite's pre-build refresh that inventory from the current Markdown file view first. This makes “same tree” reproducible instead of leaving it to whoever invokes the check.
- Restore disposal's meaning at the internal editor boundary: disposal ends callbacks and releases the editor. This was lost when the boundary prose was simplified, but the existing implementation and derived proof still rely on it.
- Define an invalid packaged Markdown editor licensing record as the wrong exact shape, unsorted or duplicate package or asset entries, an invalid package record or asset ID, or a named asset that lacks `view:markdown` or `source` coverage. A well-formed ID absent from the asset manifest remains the separate unknown-asset failure. This makes the license gate's rejection deterministic.
- Make it a manifest-loader rule that no asset record may name the Document template folder in `noticesFolder`. The editor licensing record is the only input that owns notices for this folder, so rejecting the second ownership path before generation prevents duplicate or conflicting generators.
- Require the packaged Markdown editor check to name every differing JavaScript file, stylesheet, package record and asset ID. A complete diagnostic makes a stale committed bundle actionable in one run instead of revealing one mismatch at a time.
- Give the packaged Markdown editor build rules their own spec anchor so changes to verification mode, inventory coverage, asset matching, surfaces and output shape remain traceable to the proof assertions.

## Implementation slice

The self-contained-editor implementation reworked the previously passed shared-route implementation in one slice. This follow-up slice renames the template identity from Markdown to Document, then completes the packaged Markdown editor's developer-facing names, updates proofs, changes tests first and records their failures against the old identity, and renames code and assets until the targeted validation is green. The Markdown format, editor, file view and file-artifact identities do not change.

## Open questions for Rupert

- Should disconnected editors instead retain offline typing and save it after reconnect, as Sticky note does? I recommend keeping the drafted discard behavior for the first version because it avoids adding Sticky note's draft-retention and reconciliation rules. The page restores the latest confirmed string, so it discards all unsent typing since the person's last pause long enough to start a save — the pause timer restarts on every keystroke — as well as saves sent but not yet acknowledged. A dead connection can take seconds or minutes to be reported; typing during that interval is also discarded when the loss is detected. A save the server applied before the loss reappears after reconnection. The code-authoritative `Saving…` notice is the only warning during an unnoticed outage and could be removed without spec review; if accepting this loss depends on that warning, I recommend promising the status area in a UI spec.
- Is the recommended explicit `{"markdown":""}` seed preferable to an unwritten store? I recommend the explicit seed for immediate agent discoverability and an unambiguous blank state.
- After the first version, should simultaneous person and agent edits stay last-save-wins or gain merge/conflict behavior? I recommend shipping the settled last-save-wins behavior first and designing text merging only from observed collaboration needs.
- Should a stored replacement preserve the person's caret? Today an agent write replaces the editor document and moves the caret, as a remote file edit does in the Markdown file view. I recommend keeping that editor behavior in the first version and treating caret mapping across whole-document replacements as a separate editor improvement.
- Should a save whose `onSave` promise resolves become the stored baseline before a later `setValue` confirmation arrives? The current editor contract and implementation say yes, so a later refused save restores that successfully saved string. I recommend keeping this behavior: the page's promise resolves only after the store accepts the write, and the page should not have to echo a successful save through `setValue` before refusal rollback is safe.
- Does Rupert approve the clarification that a save does not establish or restore a stored baseline if an earlier overlapping save was refused while it was pending? I recommend approving it because it states the revision ordering the editor already uses and prevents a later result from undoing the earlier refusal rollback.
- When read-write access is removed, should unsaved local typing be discarded as drafted, or remain visible locally? I recommend discarding it and showing the latest stored string so a read-only document never implies that unsavable text is shared.
- Is retaining the latest stored document after share revocation the desired privacy behavior? I recommend matching Sticky note and Table: keep what was already delivered visible, make it read-only, and deliver nothing newer.
- Does the loading/error/status shell need a future MDX UI spec? I recommend leaving it code-authoritative for this narrow reuse page unless review identifies a distinctive visual surface; the editor itself already has the intended authority split and no new editing UI is being designed here.
- The vendored Markdown-table bundle embeds a Font Awesome Free icon at `packages/view-markdown/src/vendor/markdown-tables/index.js:7962`. Font Awesome Free icons appear to use CC BY 4.0, which is not on Television's license allowlist, and this template would copy that icon into every Document artifact. Should a separate change replace it with an icon under an allowed license? I recommend replacement rather than adding CC BY 4.0 to the allowlist for this one icon; that separate change should also correct the existing Markdown file view's asset record and notices.
