# Editable Table spec plan

The architecture and UI changes in this branch are drafts for Rupert to decide. This round changes only specs, independent spec-story markup, and this working document. Proofs, tests, packaged assets, and production code wait until the spec delta passes independent review.

## Draft decisions

- Seed a new Table with `{"columns":{},"rows":{}}`, with no `showHeader`. An explicit value gives an agent the complete root shape, works with starting-data validation, and matches the other bundled templates. An unwritten store would immediately show the unreadable-data state. The four-by-four blank grid remains virtual and makes no write.
- Require `columns` and `rows`; make `showHeader` optional. A missing or false `showHeader` hides the header. Toggling it never changes column names.
- Use string values for cells and column names. Omit an empty cell and an empty name rather than storing an empty string. The human editor edits text, so one representation avoids hidden coercion between JSON types and text.
- Leave extra root, column, and row fields schema-valid and ignore them, following the existing template schema pattern. The named fields still receive full runtime validation because writes after creation do not pass through the manifest schema.
- Treat row and column keys as opaque JSON store keys. Agents can choose valid keys when writing a whole table but must not derive a key from a name. The page uses `push` without a value to generate keys without making a preliminary write.
- Sort rows and columns by numeric `order`, then by key for a deterministic tie. Insert one row or column at a time. Use an order between the neighbouring entries, or one below or above the entry at an outer edge, without renumbering anything else.
- Keep an empty axis useful. When no columns are stored, draw four virtual columns; when no rows are stored, draw four virtual rows. The first edit in a virtual cell materializes the necessary entries through that position in one atomic update.
- Make every page write as narrow as the action permits. A body edit writes one cell path, a header edit writes one name path, and a structural action writes or removes one row or column entry. Multi-selection clearing and deletion use one atomic update containing the affected non-overlapping paths. The page never replaces the root, `rows`, or `columns` for a human action.
- Delete a column by removing only the column entry. Cell values left under that opaque key stay in rows and remain invisible. This keeps deletion independent of the number of rows and follows the requested concurrency contract.
- Remove search and click-to-sort from the editable page. The grid always reflects stored order, so selection, movement, and insertion have stable positions. The inventory description changes with that decision.
- Carry the approved experiment appearance into the UI spec: a quiet ruled grid; position letters and numbers in continuous rounded strips outside it; subtle related markers for a cell; accent treatment only for whole-row or whole-column selection; and plus controls at the strip ends.
- Omit the experiment state inspector, write log, and instruction footer. They explain a prototype rather than belong to the artifact page.
- Use the canonical `<tv-menu>` anchored to the strip button. A range keeps its selection when the context menu opens inside it. Insert adds one entry before or after the range; delete removes the whole range.
- Preserve local text while the active field receives a change from elsewhere. Other paths update immediately. Commit lets normal last-write-wins behavior settle a same-path conflict; cancel reveals the latest stored value. Removing the active row or column ends editing and selects the nearest remaining cell.
- Keep cell selection and keyboard navigation in read-only mode, but remove every write affordance: editing, clearing, plus controls, action menus, and structural shortcuts. Apply the same mode after total access loss while retaining the last table.
- Follow the Checklist save treatment. A disconnected Table becomes read-only and shows “Reconnecting…” in the bottom status strip. A rejected write rolls back and shows “Couldn't save that change.” briefly. An active uncommitted editor closes on access loss or disconnection rather than becoming an offline draft.
- Retain the standard bundled-template loading and unreadable-data states and copy. A repaired value returns to the grid live.
- Use independent story markup, never production or experiment imports. Cover blank, data with the header on, header off, selected cell, selected row, selected column, editing, open menu, read-only, disconnected, save failure, loading, unreadable, and dark states. Story `play` functions focus selections and deterministically create the active editor and open menu.
- Keep the existing Table icon and shared display defaults. This spec round does not change template files, licensing, telemetry, or the bundled ID order.

## Open questions for Rupert

1. **Should “Show header row” and “Hide header row” stay in the row and column menus, or should only an agent set `showHeader`?** The draft keeps the menu item, matching the experiment default. Recommendation: keep it. A person can then name columns without asking an agent to expose the header, and the command changes only one boolean.
2. **Should search and click-to-sort return on an editable Table?** The draft removes both. Recommendation: leave them out. Editing works best when the visible position is the stored position. If either feature remains, inserting a row must still use stored neighbours rather than the temporary view; the new row could then move to another visible position or disappear under the filter as soon as it is committed.
3. **Should cells and column names be strings only?** The requested shape does not state a value type. The draft uses non-empty strings because the approved editor is a plain text field and empty values are absent. Recommendation: accept this narrower contract. Supporting arbitrary JSON would need a display and editing rule for every type, which the experiment did not decide.
4. **What should happen when an agent changes the field a person is actively editing?** The draft protects the local editor until commit or cancel, then relies on last-write-wins for that exact path. Recommendation: keep this behavior. Live replacement would move the caret or discard typing, while merging text would add a new conflict model.
5. **Should a read-only Table retain selection and keyboard navigation?** The draft does, while removing all write affordances. Recommendation: keep selection so the page does not change its basic reading and navigation model merely because access changed.
6. **What should happen to an active edit when access disappears or the connection drops?** The draft closes it, restores the last confirmed value, makes the grid read-only, and uses the same bottom status strip as Checklist. Recommendation: keep this simpler model. Preserving an offline draft would require a new retry and conflict policy for a value that the JSON store refuses while disconnected.
7. **Are the extra read-only, disconnected, and save-failure stories wanted in addition to the requested core state set?** The draft includes them because editability makes access and failed writes visible product states, and the other editable bundled templates specify them. Recommendation: keep them so later conformance covers the complete editing lifecycle.
