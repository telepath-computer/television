# Editable Table spec plan

The first editable design, its proofs, and its three implementation slices passed independent review. Rupert's hands-on review has now produced a Numbers-style design revision. The architecture spec, UI spec, and spec stories contain that draft; the proofs, package, tests, and production page still describe the earlier design and are deliberately untouched until the new spec delta passes independent review.

## Open decisions for Rupert — Numbers-style revision

1. **Should the field be named `headerRow`?** The draft uses this optional root boolean and treats the first displayed row, including a drawn row, as the header when it is `true`. Recommendation: keep the direct name and default it off by leaving it absent.
2. **What should happen to the unreleased `showHeader` and column `name` fields?** The draft ignores them as extra fields and performs no migration. Recommendation: keep this simple rule because no released Table needs its data preserved.
3. **How should the first-row action be named?** Both menus say “Use first row as header” or “Use first row as data”; the row itself is never added or removed by this action. Recommendation: keep these labels because “Show” and “Hide” would now be false.
4. **What units and validity should saved sizes use?** The draft stores positive numbers in CSS pixels, uses the default for an absent or invalid later value, and leaves exact defaults, minimums, and keyboard steps to code. Recommendation: keep one ordinary numeric model rather than add named size modes or constraints to the store.
5. **When should dragging write a size?** The draft previews during the drag and commits once on pointer release. Resizing a drawn position stores the drawn entries needed to reach it. Recommendation: keep this boundary so a drag does not stream store writes.
6. **How should keyboard and assistive-technology resizing work?** The draft uses plus and minus when exactly one whole row or column is selected. Its strip button describes the current size and keys; the visual divider remains pointer-only and adds no Tab stop. Recommendation: keep this small extension of the existing selection model rather than add a focus stop at every divider.
7. **Should the marked first row remain sticky?** The draft keeps the first row with the visible grid while it scrolls, preserving the earlier header's useful behaviour. Recommendation: keep it for long tables.
8. **What exact strip geometry should the stories establish?** The stories use a 26-pixel top-strip height and single-digit side-strip width, an 8-pixel gap to the table, and seven extra pixels for each additional row-number digit. Recommendation: accept these quiet dimensions as the visual baseline Rupert can judge in review.
9. **Should saved sizes get their own story?** The draft adds `Resized`, with unequal column widths, one taller row, and enough rows to show the wider two-digit strip. Recommendation: keep it so conformance covers the new persisted appearance without scripting a drag.
10. **How should add controls use space?** They occupy one item at the end of their strip and reserve no separate outer padding; read-only states omit them and their space. Recommendation: keep this edge-to-edge treatment, replacing the earlier reserved-space decision.
11. **Should static stories simulate sticky scrolling?** The stories render the initial appearance without sticky CSS; the UI prose requires the strips and marked first row to stay visible while the production grid scrolls. Recommendation: keep scrolling as behavioural proof work rather than add compositor machinery to static reference markup.
12. **What interrupts a resize?** The draft ends its preview without writing if the target disappears, a drawn target changes identity, or write access or connection is lost before release. Recommendation: accept the unfinished resize as lost rather than retain another detached draft.
13. **How should a marked first row behave for menus and assistive technology?** Its cells expose column-header roles but otherwise remain ordinary cells: their editor is named by row and column, and the context-menu key selects row 1 and opens its row menu. Recommendation: keep one interaction model while preserving the useful table semantics.

## Earlier open decisions

1. **Should each axis keep at least four displayed positions as the Table fills?** The draft keeps stored entries first and draws blank positions after them until there are four. Recommendation: keep this spreadsheet behaviour so the first edit does not collapse a new Table to one cell.
2. **Should Tab move through cells?** The draft makes Tab move right and Shift-Tab move left whether a cell is selected or being edited. At the outer displayed column they leave the table. Recommendation: keep this behaviour so keyboard entry continues across the blank grid without creating a trap.
3. **May insertion renumber existing entries when no numeric order fits?** The draft uses a transaction that inserts one entry and assigns consecutive integer orders to the displayed stored entries on that axis. Recommendation: accept this one exception to entry-local writes; refusing insertion or relying on equal orders would make the command unpredictable.
4. **Should search and sorting return on an editable Table?** The draft removes both. Recommendation: leave them out. A temporary view order makes structural insertion surprising because the stored result can move or disappear immediately.
5. **Should the page accept number and boolean cells as well as strings?** The draft accepts all three, displays them as text, and writes human edits as strings. Recommendation: keep this tolerant reading because agents commonly fill tables from typed data, while the editor still has one text model.
6. **Should inserting beside a multi-row or multi-column selection add one entry or as many as are selected?** The draft adds one, matching the approved experiment. Recommendation: keep one; adding a batch introduces another ordering and focus rule without serving the basic hand-edited Table.
7. **What should happen when an agent changes the field a person is actively editing?** The draft protects local text until commit or cancel, then uses last-write-wins for a changed commit. Recommendation: keep this behaviour; live replacement would discard typing or move the caret.
8. **Should a read-only Table retain selection and keyboard navigation?** The draft does, while removing write affordances. Recommendation: keep selection so access changes do not also remove the reading and navigation model.
9. **Should typing in a drawn position be discarded when another writer changes the number of stored entries on that axis?** The draft clears the selection and closes the editor, discarding the text being typed. Recommendation: keep this predictable loss rather than risk writing the text into the other writer's new row or column.
10. **Should the experiment's insert and delete shortcuts remain?** The draft drops Cmd/Ctrl-Shift-= and Cmd/Ctrl-minus because they conflict with browser zoom. Recommendation: leave them out; the context-menu key and Shift-F10 provide keyboard access to the same commands.
11. **Should open-menu stories model the canonical panel clip and exterior rim?** Each open-menu story `play` function calls a foundation-owned helper. The helper sets native content scrolling and the private `--_panel-edge-*` properties that the runtime panel controller sets, keeping the edge rim outside that clip. Recommendation: keep this correction and mechanism so later open-panel stories reuse the same foundation treatment.
12. **Should a rollback caused by disconnection show a save-failure message after reconnecting?** The implementation leaves `Reconnecting…` as the only message because the server may have received an unacknowledged write. This narrows the save-failure paragraph in `specs/ui/templates/table.mdx`; the proposed wording is “An insertion whose renumbering transaction aborts shows the same message,” while a write undone by a dropped connection shows only `Reconnecting…`. Recommendation: keep this honest uncertainty instead of reporting a definite save failure.

## Draft decisions

- Seed a new Table with `{"columns":{},"rows":{}}`, with no `headerRow`. No value shows an empty Table; a partial root object shows the readable rows or columns it contains. Neither case makes a repair write.
- Keep `columns` and `rows` required in starting data, and require `cells` in each starting row, while reading later writes tolerantly. Ignore entries without a valid `order`, invalid saved sizes, bad cells, and cells under absent columns. A late descendant write after deletion can be lost without hiding the table.
- Use `headerRow: true` to mark the first displayed row as a header without creating a separate row. Titles are ordinary cells in row 1. Ignore the earlier unreleased `showHeader` and column `name` fields rather than migrating them.
- Store an optional positive pixel `width` on a column and `height` on a row. A drag commits once on release. Resizing a drawn position stores the entries needed to reach it, under the same atomic and renumbering rules as another drawn-position commit.
- Let the header treatment follow whichever row is first after row deletion or reordering. End an unfinished resize without writing if its target disappears or changes identity, or the page becomes unable to write.
- Show the error page for a root or axis container that is not a table, for saved data reported unavailable, or when all access is lost before readable data arrives. Start no write in that state and close an editor without writing.
- Treat row and column keys as opaque IDs. Never derive a key from a name or reuse a deleted key. `push` is the normal way to add one row or column. An agent writing a whole table in one `set` instead generates a fresh random key, such as a UUID, for every row and column. README guidance also tells agents never to write below an entry that does not exist and to give every entry a distinct finite `order`.
- Explain in the README that display letters and numbers map to ordered stored entries followed by drawn positions. B3 in an empty Table requires columns A and B and rows 1 through 3, each with an `order`. An entry without an `order` can be a late write below a deletion and is not repaired.
- Draw blank positions after stored entries until each axis has at least four. A commit stores the positions needed to retain the edited location. The *add control* (“+”) stores the remaining drawn positions and adds one entry after them.
- An insert stores only the drawn positions before the new entry and the new entry. A row or column menu for an entirely drawn selection has no Delete item. These actions use distinct update paths.
- Use the architecture [drawn-position identity rule](../../specs/arch/templates/table.md#^bundled-artifact-template-table-drawn-identity) to decide when the page can still write to a drawn position. Accept that two writers can store the same drawn positions, and that an insert racing a renumber can appear in a different position, rather than adding coordination.
- Keep ordinary writes at the changed cell, row, column, `headerRow`, `columns/<key>/width`, or `rows/<key>/height` path. Storing a drawn column beside a stored row writes only the cell path within that row. Multi-selection actions use one atomic update of distinct paths. Only the renumbering transaction rewrites other entries.
- Near `Number.MAX_VALUE`, an edit in drawn positions can require renumbering. If both axes need it, or if the one-axis transaction aborts, treat the edit as a failed save and show the standard message. Apply any other-axis writes only after the transaction commits.
- Keep stale cell values after column deletion. A column selection clears cells in every selected column, including cells in the marked first row.
- Keep ranges contiguous by displayed position. Incoming reordering that separates the selected keys clears the range. Insert selects the new whole row or column. An add control selects and focuses a cell in the new entry at the previously selected cell's other-axis position, or at the first position. Delete keeps one selection at the first displayed position formerly occupied by the deleted selection; clearing contents keeps the current selection.
- Put “Use first row as header” and “Use first row as data” in both menus. Shift-F10 and the context-menu key open the applicable row or column menu; Shift-Space selects a row and Ctrl-Shift-Space selects a column. Typing with a whole axis selected does nothing except for the plus and minus resize keys, and right-clicking a cell opens no Table menu.
- Keep the strips visible and in the accessibility tree even without a selection. An ordinary press on a strip item selects it; the context-menu key, Shift-F10, or a right-click opens its menu. Inside an editor, right-click and both keyboard commands open no Table menu and do not commit. Add controls remain out of the Tab order.
- Track an open menu's trigger by stored key so an outside reorder does not move the menu to the range anchor.
- Remove search and sorting. Preserve local text when the same stored field changes elsewhere, and write nothing when an edit is unchanged.
- Put the caret at the end of existing text when Return, F2, or a double-click opens an editor. Typing a character on a selected cell replaces its contents.
- Name cells from their contents while the grid conveys position. Keep position names on editors.
- Preserve a selection when focus leaves the editor without a click inside the page, and when Tab moves out of and back into the table control. Escape from an editor cancels and keeps its cell selected; a second Escape clears the selection and moves focus to the grid, where an arrow key selects the first cell. The anchor strip item holds focus for a row or column range.
- Changing `headerRow` elsewhere changes only the first row's treatment; it does not remove that row or close its editor. Close an open menu whenever its selection clears, write access is lost, or the data becomes unreadable.
- While disconnected, keep an existing editor open. A commit gesture has no effect until the connection returns, and Escape cancels while keeping the cell selected. A write already in flight when the connection drops is not recovered; that loss is accepted.
- If focus leaves the document while disconnected, keep the editor and its draft without pulling focus back into the artifact. At an outer Tab edge, let native focus movement leave the artifact and commit from the resulting focus change.
- Do not restore control focus after a connected browser-window blur or any redraw while the page does not have focus. Keep the selection, and let Tab return to it without another focus-restoration mechanism. An agent redraw while the person is elsewhere can therefore leave focus on the artifact body when they return, requiring Tab or a click; this avoids pulling focus away from Television, another artifact, or another application.
- Let a text-composition key open the selected cell's editor before the browser starts the composition, and treat an AltGr-produced printable key as text input.
- Preserve line breaks in the editor while showing them as spaces in the grid. Native text editing and undo work inside the editor. Whole-cell or range clipboard operations and undo after commit remain accepted limitations.
- Treat whitespace-only edited text as empty. Display booleans as `true` and `false`, and tell agents that editing a numeric or boolean cell writes it back as a string. Tell agents that `cells` is an object keyed by column key, never an array, and leaves empty cells out. Use error text that covers unreadable data and unavailable access before data arrives.
- Show the normal save-failure message when renumbering cannot complete. Make a Delete label singular or plural from the number of stored entries the action removes.
- Keep the transient save-failure message visible for six seconds, long enough for a person to notice it and for the conformance capture to settle without making it persistent.
- Keep version `1.0.0` because Table has not been released. A development host with the earlier read-only `1.0.0` copy keeps it until that installed copy is removed.
- Keep the existing icon, shared display defaults, bundled ID order, loading, access, save-failure, and dark treatments.
- Keep the column and row strips visible at all times. Use the muted surface for a marked first row, remove alternating row shading, remove the inset frame gap, and give the grid all four outer borders. Let saved sizes overflow into two-axis scrolling.
