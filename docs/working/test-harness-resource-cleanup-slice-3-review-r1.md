## Is recovery as simple and reliable as Josh asked?

Simple, yes. The whole worker-side protocol is one serialized function with nine operations (`scripts/test/blaxel-worker-lease.mjs:31-219`); recovery is the single `valid && expired` branch of acquisition (`:124-128`) and reuses the same `stop` and `clean` that normal teardown uses, so active and quiet orphans need no separate path (the live quiet receipts show the same procedure finding nothing). The coordinator adds a ten-line renewal loop and a five-step finish order (`blaxel-lease-lifecycle.mjs:5-32`). Every uncertain state holds rather than guesses: an unregistered dispatch denies teardown (`:184`), a surviving or foreign owner denies acquisition and teardown (`:126`, `:129`, `:186`), a cleanup error leaves the old record, a lost renewal stops every further mutation (`run-blaxel-testshards.mjs:328`, `:446`, `:469`), and each of these resolves at the next acquisition after the interval, which is what Josh wanted: a crashed run holds a worker for twenty minutes, never forever. Reliable, with one qualification in refinement 1: the coordinator gives a lease up on the first failed renewal exec, which is safe but turns a transport hiccup into a held worker and a failed shard.

## Blocker

**The committed qualification is bound by name to one person's sandbox and pool.** `scripts/test/cli.mjs:870-873` refuses `experiment:blaxel-harness` unless `TV_BLAXEL_HARNESS_COORDINATOR` equals the literal `tv-cleanup-coordinator-rose`; `harness.test.ts:10-11` fixes the coordinator to the same literal and the pool to `rose-cleanup`, and `:15` and `:109` name the mode file and sentinels after the author. The placement spec (`test-runner.md:149`) and the proofs' shared live declaration say "a dedicated credentialed Blaxel coordinator sandbox outside the worker pool", and the plan keeps this one coordinator only through the integrated gate and then deletes it. Once it is gone, the five acceptance citations this slice adds point at a test that cannot run without editing the canonical runner and the test, and the runner carries a personal resource name. The literal protects nothing: anyone can export that string on a laptop, and the real guards are the ones already present, the sandbox-label check in the driver (`harness.test.ts:97-98`) and the shard-token check in both places. Fix: read the coordinator name and the pool from the environment (the existing variable plus one for the pool), require them non-empty, keep the label and token checks, derive the mode file and sentinel names from the pool, and run the driver once more on a fresh private pool so the citations name the test in its committed form. No lease, recovery, retry or pool-manager change is involved.

## Refinements (none blocking)

1. **Renewal gives up on the first transport error.** `renewLease` marks the lease lost on any rejection (`blaxel-lease-lifecycle.mjs:5-15`), and `leaseOperation` rejects the same way for a worker denial and for a failed or timed-out exec (`run-blaxel-testshards.mjs:328-341`). One Blaxel exec failure during a twenty-minute lease therefore fails the shard as infrastructure and leaves the worker held for the whole interval while the lease is still good. The record's one unexplained lapse, the 60-second lease rejected at entry in `2026-10-27T20-01-14-534Z…`, is the kind of event this sensitivity produces. Treat an explicit `ok: false` as lost at once and retry a transport failure on the next tick while the deadline allows; renewal is idempotent, so the retry is safe, and a real expiry still ends as a denial. One function changes; the ordering contract already covers the loss path.
2. **Pin the coordinator's per-profile default.** The 900-second `normal` value the spec review flagged is now 1200 at `run-blaxel-testshards.mjs:1205-1207`, but the removed `lockTtlSeconds` assertion was not replaced and nothing holds "independent of the timeout profile". One source line beside the forwarding contract.
3. **Optional: remove the checkout reset rather than survive it.** `scripts/test/blaxel-repository.mjs:36,40` still removes `.testshards/results` during checkout, which is why `prepare` copies its evidence into scratch and the shell (`run-blaxel-testshards.mjs:887-889`, after checkout and in the EXIT trap) and teardown (`blaxel-worker-lease.mjs:187-190`) copy it back. Under the lease, `prepare` already resets that tree, so the checkout reset protects nothing and costs three restore points and the failure at `12939310`. Dropping it is the simpler shape, but it touches the repository-selection script and its seam, so it is the owner's call and can wait for the integrated pass.
